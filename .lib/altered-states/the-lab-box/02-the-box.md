## The folder

Everything the team does on the box stays inside `~/doug/altered-states/`:

```
.key/    the repository's deploy key and its known_hosts
main/    the clone — where the team works
```

`main`'s git config already routes GitHub through the deploy key (`core.sshCommand` points at `.key/id`), so `git fetch` there works without any credential of Doug's. The key is the repository's own, not a person's.

A `remote/` worktree with an empty `cmd/` and `out/` — a command channel from an earlier setup — sat beside `main` until Doug ruled it out on 2026-09-26: *"No we don't want that there either. Delete from there when you can. You guys live here,"* and *"You are working in that main clone."* The worktree, its local branch and the `remote` branch on GitHub were deleted the same day.

## The password

Commands that need root take the box user's password from `ALS_REMOTE_PASSWORD` in the Windows user environment on this machine. Doug offered it for exactly this: *"We can put the machine password in there so you can run commands."* It is kept out of every file git or the library carries, because the skill and this book both sync to the identity repository on GitHub. It reaches the box on sudo's stdin inside the SSH channel, never on a command line where the box's process list would show it. The one-line setup is in the [skill](../../../.claude/library/our-skillset/34-als-remote.md#the-password).

## Open

**The GPU is not usable yet.** `nvidia-smi` cannot reach the driver. The driver package is installed, but no NVIDIA kernel module exists for the running kernel (7.0.0-28) — the usual sign that a kernel update landed without the module being rebuilt for it. A newer kernel (7.0.0-31) is also installed and waiting on a reboot. Fixing it needs root and is Doug's to decide: install the module package for the kernel in use, or reboot onto a kernel that has one.

**The environment lives inside the folder.** The account is the lab's, shared, so "installed for the user" would mean installed for everyone on it. Doug, 2026-09-26: *"We need this to be local to the folder. We need to not disrupt other users. How do we refactor into a local python environment where we can control everything? It is terrible practice not to be modular like this."* So uv (0.11.23, the same as here), its Python (3.11.15, the same as here — the stack's floor, [Two Pythons](../the-build/01-two-pythons.md)) and every cache sit in `~/doug/altered-states/.tools/`, the environment is `main/.venv`, and every command the skill runs exports that containment first. Another lab member's uv (0.9.17, with Pythons 3.13 and 3.14) was already in the shared home; it is theirs and untouched, and ours shadows it only inside our commands.

**The packages, and how they got in.** Doug chose the CUDA build of the same torch (2.12.1) over the CPU build this machine runs. The first install, from this machine's actual package list, stopped at resolution with nothing installed: `mei` declares `numpy<=1.26.4`, and this machine runs numpy 2.4.6 only because the lock installs `mei` with `--no-deps` ([requirements.in](../../../requirements.in) says so). A resolver cannot reproduce an environment that was assembled past one; the install has to follow the same two-stage order the lock does.

Doug's direction for the fix: *"use the compiler to generate such things."* So the box's lock is generated by `uv pip compile` from this machine's actual package list, for Linux and Python 3.11.15, and what goes around the resolver is generated too — from this machine's own metadata (a package whose declared dependencies are not all installed here) and from the compiler's conflicts. On 2026-09-26 that was exactly two packages: `mei` (the numpy conflict) and `egg` (declares `wandb` and `blobfile`, neither installed here). With those two installed `--no-deps`, the other 222 of this machine's pins compiled with none changed, and Linux added 21 and nothing else: the CUDA 13.0 stack under torch 2.12.1 (18 packages), `triton`, and `pexpect`/`ptyprocess` for IPython. Resolved normally, `egg` would have brought `wandb`, `blobfile` and their dependencies, which this machine does not have.

Installed and compared the same day, package by package: of this machine's 225, 222 are on the box at the identical version or git commit, `mei` and `egg` among them. The three that differ are the ones chosen — `pywinpty` (Windows-only) and torch and torchvision, `2.12.1+cu130` there against `+cpu` here. The box's only additions are Linux's 21. The stack imports; `torch.cuda.is_available()` is `False` until the driver module above is in.
