## What it is

**A Theme is a Format said of a book that provides eight live properties to everything the book draws, and whose default style is the minimal viewing of a library.** Doug, 2026-09-27: *"one puts their theme in the book. It just occupies the Theme class in the writing folder and should be designed to be extended and made to be dynamic"*; and of what it is for: *"The theme should EXACTLY make use of all the classes in .public. It exists to comprehend them."* It is [Format](11-format-and-theme.md) with `themeProvider = true` and four things of its own: the properties, a contract that hands them down as variables, a sheet that declares them once, and a singular rule. Since [Sprint 94](../projection/99-sprint-94--the-styling-standard.md), 2026-09-29, a book always has one — [Book](../library/05-book.md) stands the framework's in its `$Define` — and [Themes and Formats](20-themes-and-formats.md) is the guide to using it.

### <a id="live"></a>Why the provider is a chemical, and what a write costs

**A property set on a drawn theme must reach everything under it in one paint.** The layer is a chemical whose view reads `this.$theme.values`, so a property changed on the theme is news to the provider alone: it redraws, the sheet's declaration of that property moves, and since every rule beneath reads a variable, no consumer's class regenerates and the browser's cascade does the rest. **Measured 2026-09-29 and pinned in a promise:** the theme's context is one object across the write, every class the same — and every writing beneath the book still redraws once, twenty-four views for twelve words, chemistry's diffusion of a write on an annotation to the writing it annotates. Before the contract, the same write re-rendered twelve of twelve styled elements. The redraw is chemistry's to change and is pitched, never bent around here — it is a second case of [the cascade pitched from Sprint 85](../../../chemistry/.lib/projection/00-planning.md#pitch-cascade), the memo the lift does not have.

### <a id="comprehends"></a>It comprehends every class

**It comprehends the marks' looks, not their structure — since 2026-09-29.** The sheet says how a mark looks: gaps, borders, weights, margins, ink. What an element *is*, a header, a nav, a panel, is its Format's own styled component; what an annotation *means* to the eye, hidden, blank, a page closed, is that annotation's own note. Two structural rules left this sheet for Table's Format that day, the rows' `display: contents` and the spanning of a container child, and came back with the whole grid on 2026-09-30, when Doug ruled that a Table swaps no element and the grid is the sheet's by the mark ([Sprint 95, U4](../projection/100-sprint-95--pages-formats-and-words.md#u4)). The standard, with Doug's questions and their answers, is [Where a look lives](02-theming-and-formatting.md#where-a-look-lives).

**The default sheet carries a rule for every class `.public` puts on an element, and a promise holds it to that:** the promise reads every `pd-` and `pa-` literal out of the source on disk, renders a themed book through styled-components' `ServerStyleSheet`, and diffs the two sets; a class the theme does not know turns it red. The numbered families of the Table, `pa-cols-`, `pa-col-start-`, `pa-col-span-` and `pa-row-start-`, are the grid's mechanism and are read by their roots, `pa-table`, `pa-row` and `pa-col`. The four meanings, Parenthetical's hiding, Self's underline, Paginated's closed page and Blank's box, are the sheet's invariants since [Sprint 95, U5](../projection/100-sprint-95--pages-formats-and-words.md#u5), in its first layer, where until then each was a global style in its annotation's note; the theme's rule for the same mark is the look. **It carries what a reader needs to find their way, on Doug's word that the theme's CSS may target a lot:** a title in ink and without underline, though it links to itself, by the invariant of the Self it stands, as a heading does, and no rule of the sheet's own; the cover's title at twice the size; a table's entries close; a synopsis's italic on its paragraphs and not its catchword; and the Table's grid whole — the automatic grid on `pa-table`, a row and the anchor around a linked cell `display: contents` so a cell is placed by its own marks, a heading and the link around a mention heading spanning the width, and twelve starts and spans — the sheet's by his ruling of 2026-09-30. **Every layer inherits the ink** — the rule for `pd-container` says `color: inherit` — because a self-reference's rule says inherit too, and it inherits from the anchor around it, whose browser default is blue: Libby's headings and its catchword's own name were near-invisible on dark paper in the first photograph, and readable in the second. **And it never sets a level's `display`:** the [pair](03-composition.md) decides the element, and the first sheet's `display: inline` on every sentence made the poem's Lines flow inline in Chrome, since a Line is a sentence by inheritance, until the rule went and Title and Heading stood Block themselves. The ordinary view's one rule, an annotation's own writing hidden, is the default's, and left the test library's theme.

### In use

```tsx
// the-library/.book.tsx
export class $LibraryTheme extends $Theme {
    paper = 'ivory';
    link = 'darkslateblue';
}

// libby/.book.tsx — in front of the library's, which the singular rule takes out of expression
export class $DarkTheme extends $LibraryTheme {
    ink = 'ivory';
    paper = '#1f1f24';
    link = 'lightsteelblue';
}
```

**The library's book class stands its theme in `$Define`, every book of the library inherits it, and Libby stands Dark after its base's, so Dark is in front and wins** — one book of the test library dark, on Doug's word that *"dark is something in the test library to test the ability of theme to be overwritten."* A page switches themes the same way: `book.$is = Dark`, one paint.

## How it is extended

- **A theme of your own** is a class under Theme setting the properties it changes and, when the look differs, its own `style`, declared inside; it is still a Theme wherever one is asked for, since the collection finds by `instanceof`. **To add to the default sheet rather than replace it, extend it in a field, once for the class** — `override style = selection(this.style)\`…\`` — since a subclass's initializer runs after the base's, so `this.style` there is the default, and a field holds one component per class where a define would make one per instance and a book's pages would share no sheet ([Sprint 95, U8](../projection/100-sprint-95--pages-formats-and-words.md#u8)); a subclass inherits the extension. *And a defect, pitched 2026-09-27: Theme's bond passes over Format's on purpose, and chemistry's chain rule reports "$Theme did not call $Format" on every page of every themed book, logging and carrying on — the fix is a template method on Format that Theme overrides; an expected-failure promise stands in the regression, reading Chrome's console, since the check does not fire in the package's build — [Dressing a Library](../writing-a-book/09-dressing-a-library.md).* The test library's theme does exactly this, [Dressing a Library](../writing-a-book/09-dressing-a-library.md).
- **A format that reads the theme** stands on a writing inside the book — a chapter, a word — and reads `props.theme.ink` in its rules; it never needs the theme's class. *A format on the book itself reads the theme only from in front of it:* the front-most annotation draws innermost, so a frame written in front of the theme is inside its provider and a frame behind it is outside. A theme given through `$is` stands innermost of all.
- **Themes nest** as providers nest through the document — [Format and Theme](11-format-and-theme.md#theming) — so a format on a chapter that is also a theme refines the book's.
- **A theme per kind**, Doug's earlier ruling that *"Themes should be single for a type, formats should be individual"* — [The Motif](../the-motif/04-themes-per-type-formats-per-instance.md) — is not built; this Theme is the base it would subclass.
- **What the eight are not, on Doug's three words at the sign-off of 2026-10-01, kept whole because they govern what comes after.** On the sheet: *"If you feel the theme works, great. The more we put in one place, the more has to be changed when someone creates a new library. Writing the theme might be hard. But if that is just the way of things, that is okay."* On the eight: *"You chose those 8 properties. We are creating the most basic theme for the default framework. What's tough is that it's not modular. I wouldn't be surprised if you are evolving it to be overridable based on the needs of Libby's library, and that makes it really badly engineered because Libby's library should be created without the assumption that the base framework will change to accommodate her. So ponder that."* The answer given, and the standing rule: each change to the Theme in Sprint 95 was the framework's own rule named — one global sheet, Table swapping no element, one styled component per class — and the one change her library prompted, `pd-canonical`, was his word for a concept any library's sheet needs; the test at that seam is [the grade](../the-coding-style/07-what-natural-means.md#the-grade), that the next librarian would write it unprompted. The non-modular part is true and left alone: the eight are fixed, a library's own value does not flow down as a variable, and a library that wants to change what the framework draws rather than how it looks meets that wall. Where a component should live, the sheet or its own styled component, is his open question and stays open.
