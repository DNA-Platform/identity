**The design notes Doug asked for on 2026-09-21 — *"We need serious design notes for the annotation system if it is to work that way"* — written, rewritten when he pulled the design back to four pieces, and rewritten again at the review that closed the day.** His name for what this is, and its weight: *"Trait based, if that helps you, but it is an annotation-based writing model! The annotated version of a piece of writing, in this metaphor, can be QUITE different."* And what it asks of an annotation: *"an opinionated form of component framework. You should be able to imagine, from how we did things like formatting in the last one, all the powers an annotation has in specify, in define and by being rendered. You should be able to do a lot there and if there is something you can't do, we should add support for it."* This chapter says what an author writes, what an annotation can do in each of its powers, how the one list is ordered, what the writing may ask of it, what the binder's assert is, which framework facts hold it up, and what support is still missing. The code is `library/.public/package/src/writing/Writing.tsx`, `src/utilities/Collection.ts` and `src/utilities/Specification.ts`; the promises are `.tests/writing.test.tsx`.

## The surface

**An annotation is written into the writing, and that is the default form.** Doug: *"`<Writing> Whatever <Parenthetical /> </Writing>` should be viewed as the default."* And: *"No need to make it dynamic. In fact, we probably should do that most of the time if it makes sense in the constructor."*

```tsx
<Writing>an aside <Parenthetical /></Writing>
<Writing>a paragraph that is drawn <Narrative /></Writing>
```

A class that is always one way stands its annotations in its own bond, after Writing's, several at once if it likes, and defines again — *"that can mostly be what happens in the bond constructor. Don't forget the importance of specify"*:

```tsx
protected override $Define(): void {
    this.annotations.add(this, <Parenthetical />);
}
```

When a writing must be told what it is from outside, `$is` takes one or many — *"Doesn't this form look pretty good? … It's nice to have a genomic consistency"*:

```tsx
<Writing is={Parenthetical}>an aside</Writing>
<Writing is={Narrative}>drawn after all <Parenthetical /></Writing>
```

At runtime, from a button, that same door and no other — an annotation that takes a trait out of expression, given and then taken away again:

```ts
writing.$is = Narrative;
writing.$is = [];
```

There is no third door and no property on Writing for any of it. `expressed` is not a door: it is what a define computes, and a hand outside a define does nothing. *"Let's not have sugar… One can specify the annotation as a child or through `is`. That should be enough."* And on two boolean fields a draft had put on Writing to hold what the annotations meant: *"How could these be there?"* — a type question turned into a flag, and the base carrying its annotations' vocabulary. The writing asks its collection instead.

## The genetics, said once and plainly

**Doug, 2026-09-23, when a first attempt at recomputing expression left thirteen promises red: *"I want you to remember that the annotation system is modeled on genetics… you know networks of genes all work together, flipping each other on and off and augmenting each other — the protein — the trait associated with each one. Generally, you want the cleanest implementation, but it's okay to make a mess as long as what we want is cleanly expressible in the static case — when building classes… But remember that we are creating a system of combinatorial complexity with switching. It is complicated. Let's find it."*** So the mapping is written down once, because every design question in this chapter is answered by it.

| the biology | the writing |
|---|---|
| the genome | the `Annotations` collection — *"our genome (metaphorically)"* |
| a gene | an annotation; its class is the trait it names, Parenthetical for the writing that is parenthetical |
| the genome's code | the collection's `toString`, its members' symbols in order |
| expressed | the collection's `expressed(annotation)` — *"who makes the cut"*, tracked in the collection since 2026-09-24 |
| the protein, the trait it makes | what `defines` does to the writing: a class in `classes`, a layer in `containers`, a value |
| the protein withdrawn | `erase` |
| regulation, genes flipping each other on and off | `defines`, where a gene reaches what stands after it, `writing.annotations.after(this)`, and asks the collection, `express(annotation, false)`, for what it chooses |
| augmentation, a gene changing what another makes | `defines` again, setting any other property on what it finds — E23's *Means modifies Format on render* |
| the membrane a signal crosses | the writing's `$` props: the outside names a value, the annotation carries it, its component draws with it |
| fitness the genome confers | `specifies`, weighing in on the binder's assert — E21 in those words |
| the phenotype | what the writing then IS: its classes, its layers, its level |
| a phenotype one gene confers | *one* property of the writing, which is what its class names — Doug, 2026-09-26: *"each annotation confers a phenotype, it is about some particular property of the writing"* |
| the default phenotype a class specifies | what a class stands in `$Define` — E21 again |
| dominance | order: the front regulates first and its word stands |
| a signal from outside | `$is`, dynamic scoping |

***One annotation, one property — the rule the two phenotype rows yield, from Doug's fuller sentence on 2026-09-26:*** **"Our annotation system is like trait based genome, where each annotation confers a phenotype, it is about some particular property of the writing. The same annotation can be written on many pieces of writing."** *The writing's phenotype is the sum of what expressed; a single annotation's is one property, and that property is what its class is named after.* **So an annotation that confers two unrelated properties is two annotations, and a design is refused on that ground** — a rule to reach for when a class starts collecting duties. And the second clause is why a class carries nothing about any one writing: *the same annotation can be written on many pieces of writing*, so everything an instance knows of where it stands it reads — its writing, `after(this)`, its [`$book`](../library/01-books-in-annotations.md#any-writing-reaches-its-book), the last two already answerable in its `$Define`. What it may not cache is *what its writing carries*: its siblings join the writing after its own bond, so a sibling is a question for `defines` and never for `$Define` — measured in [Sprint 83](../projection/89-sprint-83--memory-management.md).

**And the one thing the biology insists on, which the code did not do until 2026-09-23: expression is COMPUTED, never stored.** A gene is not switched off once and for all; it is repressed for as long as its annotation that takes another out of expression is there, and the moment the annotation that takes another out of expression goes it is expressed again. Before that day `expressed` was written by an annotation that takes another out of expression and the write lasted, so a Narrative given through `$is` and then taken away left the Parenthetical off for good, and a pass settled only when the annotation that takes another out of expression happened to stand nearer the front. Doug: *"the problem is, the whole genetic system needs to be idempotent. But I see the problem. Before a define run, all annotations should be expressed? And it is only in that run that they become unenforced?… Maybe expressed shouldn't be reactive. It's not the way to interact with annotation except with other annotations."*

**So a definition is one act, and it is the whole of the switching** — Doug's specification of 2026-09-24: *"Define is a method that erases all annotation that were run on last define in reverse order, then applies changes, then runs defines on all annotations."* In order: every annotation that ran in the last define is erased, last first, from the record of what ran and never from the membership, since a new `$is` or a removal may have taken it out and it still has to be undone; the edits of `$is` stand in front again, cited to the collection, so `revert(this)` takes back exactly them; the membership is established, and it is what every read sees until the next define; every annotation starts expressed; and they run from the first, each recorded as it runs. *Regulation happens inside `defines`, a gene asking the collection to take what stands behind it out of expression; `inactivates` stood here for a day as a phase of its own and Doug struck it:* ***"I didn't invent inactivates. NO NEW MEMBERS."***

***And the record is what the define did — which is what makes the fixed point.*** **Doug:** *"they need to have fixed point semantics and implementers need to know how to add to that"* — and on 2026-09-24: *"First is most powerful… The annotations added last should be the first on the list. It's like a stack"*; *"Why can't it change whether something is expressed after it is? It should be responsible for knowing where it is. It can know where it is on the list and focus on what comes after… It's just that the list the system decides to keep about what has been expressed has to be based on what it called defines on directly."* **So `express` refuses nothing: it changes the wish, and the run calls `defines` on each annotation whose wish is expressed when its turn comes.** *What the collection says was expressed is what the run did, for everything it has reached, and the wish only for what lies ahead* — so an annotation reaching back to one already reached changes nothing the collection says of it, and can only make trouble for its own intent. **An annotation knows where it stands through `after(this)`**, what stands after it in the order the define established, and every family in the writing folder reaches only there. *An annotation that leaves lets what it took out of expression express again at the next define, and a define is idempotent by construction, since it erases everything that ran before it runs anything again.*

***One generation a define.*** **Doug:** *"this is a metaphor for genetic computing… their phenotype can be to affect other genes. It is powerful and we want to guide it to the right shape while not preventing it from being recursive and powerful."* **While a define runs, the genome is what it established, whole and in order, and every read sees that**; genes express, regulate what stands after them and augment one another within it. **A gene whose phenotype changes the genome itself — adding a gene, removing one — changes the next generation**: the change is recorded at once, the run goes on over the genome it established, and the next define establishes the change. *So recursion unfolds one generation a define — a gene added by a gene adds another — and nothing in one generation can see itself half-changed. Drawn, the passes of an ordinary mount carry the generations: two generations of additions settle in the three draws of any mount, React's development double being one of them. Whether what a gene adds converges is the gene's to be idempotent about — adding what is absent, as a promise does.*

**Two things follow, both measured.** Expression is the collection's and not the annotation's: an annotation holds no flag and nothing in a define changes an annotation, which is what Doug's *"enforcement is moved to the collection not on the annotation"* asked. And the genome's code is membership alone — the collection's `toString` is its live membership, so a method that adds or removes an annotation wakes the writing and the define that establishes the change is quiet; while the code carried each member's expression, the string changed inside the very pass that computed it and the rendered promises measured a render loop.

**What an author's switch is, then.** Not `expressed`, which is the network's. An author writes the annotation or does not; a class stands one in `$Define`; a page gives an annotation that takes another out of expression through `$is` and takes it away. That is the door, and it round-trips.

## <a id="two-guides"></a>Two guides, and the overlap is the test

***Doug, 2026-09-23, when the props path settled:*** **"That is how the writing can be like a membrane for its genome. It expresses a dynamic trait that is part of the phenotype of its genotype. Annotating writing as a way of specifying what it is, using genetics as a metaphorical guide for a programming model."** · **"How we use genetics as a structural guide, writing as a semantic one, and it's important to find the overlap to understand that we are making something sensible."**

**Genetics is the STRUCTURAL guide.** *It says what parts there are and how they act on each other: a genome of genes, expression computed rather than stored, families that suppress and augment one another, dominance by order, a phenotype that is the sum of what expressed.* **It is where the mechanism comes from, and it answers every question about how the pass runs.**

**Writing is the SEMANTIC guide.** *It says what the parts MEAN and what they are called: an annotation points out a trait the writing has, its contents are what someone wrote in it, its note is what it says on the page, its container is the element it draws as.* **It is where every name comes from, and it answers every question about what a thing IS.**

***And the overlap is the test that the thing is sensible.*** **A part earns its place when BOTH guides hold for it.**

| the part | genetics says | writing says | holds |
|---|---|---|---|
| **an annotation** | a gene, making one trait | a note pointing out a trait the writing has | **both** |
| **`expressed`** | expressed right now, recomputed each pass | whether the writing has that trait as it stands | **both** |
| **a family** | a network of genes flipping and augmenting each other | a pair like Narrative and Parenthetical, written together | **both** |
| **the `$` membrane** | a signal crossing into the cell | a prop written on the element, carried by the annotation to its component | **both** |
| **`inactivates`** | regulation, exactly | ***nothing*** — no document has an inactivation | **struck 2026-09-23** |
| **`review`** | ***nothing*** | a wrapper, and not a word a reader of books holds either | **struck 2026-09-23** |

***The last two rows are the test catching its own faults.*** **Both were members that made sense in the metaphor and meant nothing in a document**, and both were struck the day they were written. *That is what the overlap is for: genetics alone produces jargon with a mechanism and no meaning, writing alone produces a word with meaning and no mechanism, and only where they meet is there something to build.*

**And the membrane row is the newest, and worth saying whole.** *An author writes `<Quoted rule="red" />`. The `$` membrane carries `rule` across into the annotation as `$rule`, the annotation hands it to its styled component, and the writing draws differently.* **A signal from outside crossing into the genome, expressed as a trait of the phenotype** — *and on the writing side, simply: you said what this writing is, and it is drawn that way.*

## The powers of an annotation

**FOUR, and two that stood here on 2026-09-23 were struck the same day.** `inactivates` was a member invented out of a word Doug used to explain the idea — *"can't they cancel each other out, like certain genes, by inactivating the others?"* — and he struck it: ***"I didn't invent inactivates. NO NEW MEMBERS. You set expressed to false."*** Suppression is a gene reaching its family in `defines` and setting a property, which is the same act by which it reads or augments them, so it never needed a door of its own. `review` went with it: ***"No more review."***

**An annotation supplies its own machinery, in the places it already stands.** Doug: *"The annotation itself should supply the machinery to do something. What can it do in defines. What can it do when rendered? Look at where defines is called and where it lives in view — it is hidden in the annotation part of the markdown. But it is there. Do you get it? Genetics. We add features."*

1. **In `specifies(writing)`** — the annotation weighs in on the binder's assert: it checks the writing it stands in, and a failed `$check` is one of the failures the writing answers. A cover only on a chapter; a Summarized demanding a summary; a Demanding wanting something written. E65's `specifically`, renamed by him.
2. **In `defines(writing)`** — *"a method that takes the thing and actually performs an action"*: when the writing defines itself, at its bond and at every draw, each expressed annotation acts on the writing. The pass runs over a copy: *"you can't remove annotations from writing, but you can interact with them."* And it must be idempotent: *"the onus is on implementers to be idempotent."*
3. **In `erase(writing)`** — the undo of `defines`, which a define calls on every annotation that ran in the last one, last first, before anything runs again — *"erase is on an annotation. It shouldn't be on the collection. Erasing is a part of define() on the collection"* — so each annotation takes back what it did and no other annotation needs to know how. Parenthetical erases its class; an annotation that adds a layer takes back its own, `revert(this)`.
4. **By being rendered as a note on the page** — every annotation is rendered by `annotate()` inside the writing it annotates, after the contents, as its own writing with `pd-annotation` on it, hidden in the ordinary view and shown in an annotated one, and then its `note()`, null by default, at the level of the writing; one with something to say at that level overrides `note`, as Parenthetical renders there the global style that hides its class. Doug, 2026-09-22: *"Having the annotations annotate their writing with the pd-annotation, which we can easily make invisible, yet to a note function which renders at the level of their annotated writing... is semantically what an annotation is!"*

***Why the note is INSIDE the container and not beside it, ruled 2026-09-23.*** **Doug, when the alternative was drawn for him:** *"No, it is inside the writing, beside it would be weird. It is not inside… an annotation isn't quite beside the writing."* **An annotation stands in the writing's own collection, so it is part of that writing rather than a sibling of it, and the markup should say so.** *Rendering it beside the element would claim it stands next to the writing, which is false; the alternative was built and measured on 2026-09-23 — 84 of 86, with only the two promises that name the placement going red — and it was not taken for that reason and no other.*

**And the writing asks.** *"In writing, we can check for the presence of the Formal attribute… is an annotation of this type expressed in the collection — that should be a well-formed question at any time."* So `contains(Class)` answers whether an expressed one of the class is there, `containsOne` whether there is exactly one, and `view` puts the class on when `contains($Parenthetical)`. That is a type question answered by the type, never by a flag.

**The containers, the first power added.** *"The annotated version of a piece of writing, in this metaphor, can be QUITE different"* — so the powers an annotation lacks are the model's point, not its edges. It began on 2026-09-22 as one `container`, a single element a class or an annotation set; on 2026-09-24 it became `containers`, on Doug's design: *"make container an… ordered set of elements and have view compose them and everyone can add and remove from that somehow — and then no one needs to cache anything."* So a writing draws through an ordered collection of layers, every one cited to whoever added it — since C5 the core [Collection](../utilities/01-collection.md) — its own element a span by default: a class replaces its own, `this.containers.replace(this, 'span', 'section')`, and an annotation adds a layer after it with `add`, cited to itself, and takes it back with `revert(this)`. `view` draws them inner to outer: the first is the writing's own element, wearing its classes and its id, and each after it is drawn around the one before — Doug, 2026-09-25: *"The parent's container should be first. And if so, it looks like we should render inner to outer and that should be documented. It's important that we can have multiple formats targeting the inner part based on the classes it has on it"* — so a format targets the classes inside with a descendant selector, however many layers out it stands. Every layer around the writing wears `pd-container`, *"Yes, put a framework class: pd-container"*, and its own element never does, so a rule reaches a writing's layers without reaching the writing that holds it — which is how a Parenthetical hides the whole. That is how an annotation changes the element its writing draws as, which is the whole of what [Format](11-format-and-theme.md) does, and how a Reference makes its writing a link without being a Format. A theming format composes its style with a provider in its bond, so the element it hands over carries the provider as its own parent — *there is no second power that wraps, and the one that stood here for an afternoon was struck.*

**How the annotations are hidden.** Annotation puts `pd-annotation` on its own container, added in Annotation's bond after Writing's, and a parenthetical writing has `pa-parenthetical` on its container; what a class does to its element is a stylesheet's rule and never a component type in the code. Doug, refusing a styled span: *"No! Never code to component types. Put a class on there… and that can be hidden right?… But annotations aren't themselves parenthetical."* The span that held them all, with `pd-annotations` on it, stood from the morning of 2026-09-22 to the afternoon, when an annotation became a note on the page and each container carried the class itself. The rule that hides `pd-annotation` is placed when the page or a Theme is written, and an annotated view leaves it off to show what was written in the annotations; until then they stand visible.

**The draw as designed on 2026-09-22, built and green.** Doug: *"What if we make a set called classes, render those. pd-annotations is fixed on the annotation container. Have the annotations contained move to view, annotations renders the inside. Classes are rendered on the container, and write the parenthetical annotation to put the class in define and maybe some sort of styled component that targets .pa-parenthetical?"* And, striking a style mounted at the page: *"It can put the class in classes in defines, and then render the styled component as its view? That is the programming model."* So `classes` is a collection each writing owns — a set until 2026-09-24, cited to each annotation since — which its annotations fill at every define, and `view` draws on the writing's own element, the first container, since 2026-09-25; `annotate` renders the annotations it is given after the contents, each as its own writing with `pd-annotation` on it and then its note, null by default, and `view` gives them back to front, so that the front, first to act in the pass, is last on the page and wins a stylesheet's cascade — *"the one on top doesn't mean first in the DOM, it means last — which is to mean most powerful"* — an afternoon's ruling replacing the morning's span; Parenthetical adds `pa-parenthetical` when it acts and renders, as its note, the styled-components global style that hides the class, so the style enters the document by the annotation being rendered inside its writing. The set is declared with the definite-assignment mark and no initializer, and the bond's first line makes it empty, because a per-mount derivative inherits its template's fields and a Set made by a field initializer would be one Set for every writing of the class; Doug: *"This can't be getting and setting from a static set. If it needs to be reset at bond construction, they do it."* A define never clears it: every annotation that ran erases what it added before anything runs again, and each adds when it runs.

**The undo, and the idempotent define.** Doug, 2026-09-22: *"You are calling defines in both places right? We need this to be idempotent. First in bond constructor, then the one in view effectively leaves this the same."* `$Define`, empty on Writing and called after the contents are sorted and before the written annotations enter, is where a class stands its own annotations, so the first define sees the final list. `erase(writing)` on Annotation is the undo of `defines` — *"an annotation method which has the thing undo what it is supposed to do"* — and since 2026-09-24 a define erases everything that ran before it runs anything again, so an annotation's `defines` need not guard against running twice; what it must be is exact in its undo — *"it is entirely up to the annotation to be idempotent"* — its `erase` taking back what its `defines` put, and nothing else.

**Annotations.** *"Annotations, in writing, should be a type of Collection, but we are going to override its methods to accomplish this."* So `Annotations`, in Writing's file directly under `$Annotation`, is a [Collection](../utilities/01-collection.md) of annotations with every change cited to its author: `add(author, ...givens)` makes annotations from any givens, parented to the writing, and stands them at the front in the order written, so the last added is first — E26, and Doug's *"It's like a stack"*; a change is read at the next define, which establishes what iteration, `find`, `expressed`, `contains` and `containsOne` answer until the one after; and its `toString`, the genome's code, is the live membership. **Iteration answers what was established and the core holds the live membership, on purpose** — the define reads the live one past its own override to establish it, and a later tidying that made them one would put the writing back into the loop. The two questions count only what is expressed — *"is an annotation of this type expressed in the collection — that should be a well-formed question at any time"* — so the generic collection in utilities knows no writing word.

**What a power cannot do yet.** An annotation cannot reach the framework's own hiding, `$hide`, which is a render filter and means not drawn rather than hidden. It cannot draw as an ancestor of its writing either, and that was tried twice on 2026-09-23 as a power of its own and struck both times; what it can do instead is hand the writing a component that already wraps, which is what a theming [Format](11-format-and-theme.md) is, and which serves *"we can use styled components directly to the extent that we are able"* — with one limit measured rather than guessed: two independently authored styled components cannot both style one element at render time, so composing a look happens at definition, and two Formats on one writing resolve by order, the front unexpressing the rest.

## `expressed` — who makes the cut

**Expression is the collection's, since 2026-09-24.** Doug: *"define can access the annotations collection. So during the define run, it needs to be in a valid state. I think it should have an express(annotation) and expressed(annotation): boolean, so one can know and react to them, and those all start as true, and tracking is kept in the collection"* — and, of one member answering both: *"Have it work with instance or type."* So `expressed(given)` answers the expressed annotation or nothing, asked of an annotation, which names itself, or of a class, which names its instances — from what the run did for those it has reached and from the wish for those ahead; and `express(annotation, expressed = true)` is how an annotation, while it runs, says which of those after it are expressed. Every define starts them all expressed. It decides whether an annotation runs, whether its `specifies` weighs in, whether its note renders, and what `contains` counts. *"It's not the way to interact with annotation except with other annotations."*

## `$is` — dynamic scoping

**`$is` is the prop that says what a writing is from outside: one or many, in any form the framework can build, and it is the changes, not the set.** Doug, 2026-09-22, on a draft whose setter stood the annotations at once and whose getter answered what it stood: *"I think you are confusing levels. $is should just be the changes. annotations should be the full set. If you need an annotationEdits. The getter for $is is the simple prop. The annotationChanges are evaluating them. And then define might need to take the edits and apply them to the annotations, get a new copy and walk it… That way the annotations have access to all available ones when defines is called."* So the given lives on the collection as `is`, and Writing's `$is` is a getter and setter over it, typed exactly and reading as what was given; a given is a class, a component, an element with its content, or a chemical. **The collection carries the given, possesses the edits and applies them.** Setting it makes the edits at once, and every define — at the bond and at the start of every view — stands them at the front, in front of what was written and of what the class stood: *"they do get integrated in before define… they need to be registered to… the piece of writing and can be undone."* They are cited to the collection, so `revert(this)` takes back exactly the edits, whatever was prepended since, and what they did is erased from the record of what ran; the same given again is nothing. A change from a button is counted and redraws: it was not, for a night, because the framework wrapped a field and never an accessor, and Doug ruled it a bug — *"A get / set property better be reactive… These things should always have been reactive"* — and chemistry's 2ffbe4c wraps a declared accessor as it activates a field, the two promises that stood red going green with nothing changed here. Two earlier shapes of the day, a setter that made the edits at once and a bare `edits` field on Writing made in the bond, went the same evening when Doug named the collection the one place: *"That's our genome (metaphorically) the Annotations collection, and it should be able to do all the things we need. Writing can wrap some of them for convenience, but make Annotations the source of almost all complexity to storing, enumerating, editing annotations and it knows what they are so it can be specific."* Doug, on a draft that had kept a reference to notice a change in `define` instead: *"Looks like one too many things on this list… Why isn't $is just a collection that has the annotations, annotationEdits (rename to just edits, the typing clarifies because we see it next to it) has what they became and it was set on $is setter set, and then before define, the annotations and edits are joined, processed and then rendered."* Identity does not survive a render — *"I think that's okay"*.

## <a id="precedence"></a>Precedence — class, then subclass, then children, then props

**Doug, 2026-09-23:** *"The class > subclass > what is passed in children > props should be the precedence order and I am pretty sure it was."* **It was, and this is where it is made in the code, read off `$Writing`'s bond and the collection's pass rather than recalled.**

| laid down | where | ends up |
|---|---|---|
| **the class** | `$Define()`, called after the contents are made and before the written annotations are added, adding with the collection's `add`, which means the front | furthest back |
| **the subclass** | its own `$Define()` calling `super.$Define()` first, so what it adds is prepended in front of the base's | in front of the class |
| **the children** | the bond adds each written annotation after `$Define`, prepended in turn, so the last written stands nearest the front | in front of the subclass |
| **the props** | the `$is` setter makes the `edits`, and the pass drops and re-prepends them before it walks | in front of everything |

***What changed on 2026-09-24 is WHEN `$Define` runs, not the order it produces.*** **It used to run first, before anything was sorted, so a class could not read its own contents; it now runs after the contents and before the written annotations**, which Doug ruled a bug fix. *The order is untouched because the written annotations still enter after the class's. Measured on the way: moving `$Define` to the very end, after the written annotations, reddened five promises, every one a written annotation losing to a class default — which is why the written annotations are added after it. [The seam, and a shape that was reversed](06-how-writing-is-extended.md#define).*

***So the list runs, front to back: props, children with the last written first, subclass, class.*** **And the pass walks it front to back, so the more specific acts first.** *That is the whole of the ordering, and the four rows are the four places a piece of writing can be said something about.*

**Which way the ordering points depends on the surface, and this is the part that bites.** On an **additive** surface it does not matter at all: `classes` is a collection each annotation adds to under its own name, drawn once each, so none of them meet. On a **single-valued** surface it inverts: the `id` holds one value, so the LAST to act writes over everything before it, and the last to act is the one furthest back — the class. *Doug wants that competition — "We want competition… last set is winning" — and a [Compilation](../utilities/01-collection.md) answers the last value set; the layers of `containers` are not single-valued, so two annotations that each add one both draw.*

***A family that wants the front to win on a single-valued surface says so, by unexpressing its own kind.*** **Doug, 2026-09-23:** *"Support uniqueness in the Format family if you need it. Have each one just check the whole list and set expressed false for everything that is an instance of it but itself."* [Format](11-format-and-theme.md) is three lines of exactly that, and it is what makes the front win where plain overwriting would have let the back win.

**And the second half of the same ruling is why nothing has to be undone:** *"try not to do anything other than render, so that nothing needs to be erased."* *An annotation whose effect is what the writing draws has no mark to take back, and `erase` stays empty.*

## The one list, and its order

**Every writing owns one collection of annotations. An annotation enters at the front, so the last to enter has the last word.** E26, and Doug: *"Add to front seems to make the most sense from an overriding perspective and the dynamic ones are all add to front. So let's build on those semantics."* The pass runs front to back, so the front acts first and its word stands. **The bond adds the contents, then lets the class stand its own annotations in [`$Define`](06-how-writing-is-extended.md#define), then adds each annotation the caller wrote, prepended in turn — so the written stand in front of the class's, the later written nearer the front; then `$is` gives what it gives in front of everything.** *Since `$Define` runs after the contents, a class whose annotations depend on what was written in it can read them there — which is what a [Mention](10-developing-an-annotation.md) does — and since it runs before the written annotations, it cannot see what a caller gave, which is the point.* From the front: what `$is` gives; what was written, the later nearer the front; what a class stands in `$Define`. Doug, 2026-09-22: *"dynamic form should win — I thought is strictly goes in front of the normal annotations"*; *"base > subclass > caller — this is how annotations should override each other."* The class's defaults stood in front of the written until Composition's first promises, when a class's Permissive inactivated a written Strict. Nothing is made unique: *"we don't validate uniqueness and for ones that are unique, we find the first."* The collection is a plain list and a `find` is a filter by `instanceof`, so a subclass of an annotation is found where its base would be; the class-keyed index of 2026-09-21 was removed on 2026-09-23 — *"I don't want to be caching the classOf anything"* — and the one word of what it holds that the collection reads is `expressed`, for the question above.

## `specify` — the binder's assert

**`specify` is written and called by nothing in the library; the binder's tests call it, and it cascades.** Doug: *".public, the compiler and the binder work together. The specification exists so that one can have performance and check specification. Rarely does one read what 'up to code' means, but we are glad that it can be specified that the place is safe to eat."* And: *"really think of the tests in the binder as part of the framework. We are building a form of assert library, and all the annotations weigh in on it, and we can call it whenever… and it should be called recursively down — so specify calls specify on anything in reach — contents and annotations — that is writing. Causing a downward cascade that can cause a lot of errors to appear."* So `specify` answers a list of failures: its own specification's, then each expressed annotation's `specifies`, then everything in reach that is writing, contents and annotations alike. The detached Specification checks when asked and answers its failures; its `expressed` flag went with `formal`, since nothing echoed into it. *"Oh true, we don't need formal at all! specify is just called in the test. Good. Drop it."* Formal and Informal are gone from the file; *"I'm glad it gave us an example but we will have plenty more annotations."*

## The cost, measured

**Doug, 2026-09-22: *"From an optimization standpoint, is there anything we need to do in Collection that might help optimize it? … We want to walk away making sure this works."*** Measured the same day with a probe built and removed in one turn, a tree three deep with a fan of twenty-five, 16,276 writings, built through the framework's eval form inside the suite's environment:

| tree | build | specify, cascading | view, every writing | find, every writing | per writing |
|---|---|---|---|---|---|
| bare | 593 ms | 93 ms | 212 ms | 4.6 ms | 8.1 KB |
| with Parenthetical and Narrative on each | 1,012 ms | 113 ms | 379 ms | 6.9 ms | 21.1 KB |

And one writing with four thousand children bonds in 218 ms after the bond stopped prepending them.

**What the numbers say.** The collection is not on the critical path: a find is a third of a microsecond, the two collections of a writing are under a kilobyte of its eight, and filing an entry under its chain is a few map operations against the tens of microseconds the framework spends making the chemical. **The cost that matters is that an annotation is a chemical**: each one adds about 6.5 KB and 13 µs, four fifths of a bare writing, so a book at the first library's scale of eighty-five thousand writings would carry 690 MB bare and 1.8 GB with two annotations on each. That is the framework's per-chemical footprint, and it is where any real optimization lives — either in chemistry, or in a lighter form for an annotation, which Doug has already gestured at: *"Annotations aren't visible anyways. Maybe that's the reason they will tend to rely on their parent for storage."* Nothing in the collection was changed on these numbers; what could be, if ever needed, is a lazy index that is built on a collection's first find, which would spare the map on the many contents collections never asked by class, and is worth perhaps a twentieth of the memory.

## The specification, at the heart

**Writing, Annotation and Specification are the heart of the abstraction, and this is where the specification is read, by Doug's ruling of 2026-09-23: *"document specification in a central place to Writing, Annotation and Specification make the heart of the abstraction so put it there."*** A specification is a class of rules about a writing, and every class of writing checks with its own through the `specification` property, `new WritingSpecification()` on Writing and reassigned by a class that has more to say: `CompositionSpecification` extends Writing's, `SectionSpecification` extends Composition's, and so on down the classes, so the rules inherit as the classes do. A rule is a method of the specification whose name begins with `$`, marked `@specify('what it says')` for its description, and it says its rule with `$check(holds, 'the sentence a failure reads')`, which throws when the rule does not hold. **A subclass replaces a rule by naming it again**, since the rules are gathered by name from the base's prototype up to the class's, the nearer winning, and it lifts a rule by naming it with an empty body. The cost of that is the cost of a name: a `$`-named method on a specification that is not meant as a rule runs as one, and a rule misspelt in a subclass adds a rule rather than replacing it, so a rule's name is written once in the base and copied, never retyped.

**The check is `specify`, on every writing, and it is the binder's.** It asks the writing's own specification for its failures; then every expressed annotation weighs in through `specifies(writing)`, **which runs the annotation's own `specification` against the writing it annotates**; then every piece of writing among the contents is asked in turn, so one call at a book answers every failure in it. Nothing in the library calls it: the bond does not, and a writing that breaks its rules is built and rendered and refused only when asked, which is what *assert mode* meant at E21. Every failure names its place — `Writing / Writing 1 / Writing 0: …` — since the parent hands each child its code.

***ONE SPECIFICATION PER WRITING, and the annotations are traits that participate in it — ruled 2026-09-24.*** **Doug:** *"I think we want to use specifications in the specifies of Annotation. Can we just repurpose them, but not to specify the annotation, to specify the writing? And then, can we make sure that all of the specifies are being called when specify is called in writing? This makes one spec and the annotations are like traits that participate in it."* **So an annotation's `specification` holds rules about the writing it stands in, written like any other specification** — `$`-methods, `@specify` descriptions, `$check` — and never rules about the annotation itself. *And then:* ***"So then we won't call specify on the annotations"*** — **the cascade goes into contents and never into annotations**, since an annotation weighs in on what it annotates rather than being checked in its own right; *an annotation that one day needs more than one specification can have more than one.*

**Every rule runs, and that was a defect before it was a design.** *Until that day each annotation's `specifies` ran inside one try-and-catch, so the first `$check` that threw ended it and any rule after it was never asked — `$Referent` carried two and reported whichever fired first.* **A specification's `check` asks every rule and collects every failure**, and a promise now holds it: a Level on a writing that is not a composition, written as something other than a number, reports both.

**A rule that depends on a precondition keeps the guard and the check together.** *An annotation that applies only to some writing checks that first, by the policy of 2026-09-23 — "Do we want annotations to fail silently or throw? Throw I think." — and since the rule after it could not run on another kind, the two stay in one rule rather than two, or the second would report a crash as a failure.* **Two faults that are independent are two rules**, as a Level's are. Writing itself has no rule; a letter may hold anything.

**Measured 2026-09-24**, on a tree of 16,276 writings: a cascade in 23.6 ms bare and 120 ms with two annotations on each, against 93 ms and 113 ms two days before — on par, with every annotation now running every rule it carries. *The cost is about 3 µs an annotation, and most of it is `Specification.rules` walking the prototype chain on every call; nothing caches it, by the standing rule that a cache waits for a measurement that asks for one.*
