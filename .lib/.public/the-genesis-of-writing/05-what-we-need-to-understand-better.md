## The rulings Doug gave while the documents were being read

**Each is his own sentence, and each settles something the documents left open.**

1. *"Specification should happen whenever we can provide safety in something that will be compiled out at runtime."* This confirms what E20, E21 and E65 say and extends it into a rule for writing the core: any guarantee that can be a `specify` test is one, and nothing is checked in production. It answers the notes' ninth open item — a Section without its Heading in production is not handled, because production has no checks by design — and it frames the seventeenth: the walk that runs every writing's `specify` is test-mode machinery, ours to build.
2. *"We aren't going to have the TypeOfTypes. No more type. We have a type as an annotation, but not every instance of writing has a type like it does now. We are doing direct inheritance between the parts."* The first library gave every word a companion type class and bonded each element with its type; none of that returns. `Type` exists only as the annotation E35 declares, named from its source, and a writing carries one only when one is written on it. Section extends Composition, Heading extends Sentence, Cover extends Chapter, and a subclass is its parent by inheritance alone. This leans the notes' twelfth open item toward names rather than a class hierarchy, unless a Type is subclassed to weigh on a specification as E35 allows.
3. The documents are written down verbatim and commented on beside, never inside, and Claude Desktop's newer versions replace them whole. This book is that ruling carried out.
4. Asked which is the authoring surface for references, the stream's tags or the first library's bracket notation: *"We will write the components to take what the compiler provides. The compiler should be generating ()[] as its result and not anything else."* The compiler's one output is the link, `[words](address)`, and a component such as Of or Means is written to take that link and nothing else; what an author writes upstream of the compiler is not what the components are built against. This is E52 made a rule for the whole core.
5. Asked where the specification runs first: *"We should have a test mode, and we should have a unit test suite setup for every library that is scaffolded by the call to specify."* So there is a test mode, and `specify` is not only the writing's own tests but the scaffold of a suite: every library built on the core gets a unit test suite generated from the calls to `specify` over its writing. That is the runner the notes' seventeenth item asked about, and it is a library's, not a browser's.
6. On reading the first library's source beside the Genesis: *"the existing code is being rewritten so you have to make sure that what is in the source was not intended to change by me. Maybe you found a problem I did not foresee but it needs to change in the direction of the Genesis as the source of truth."* The Genesis wins; every divergence in the source is a change he intended or a gap the source solved, carried in the Genesis's shape. [Answering Claude Desktop from the Source](06-answering-claude-desktop-from-the-source.md) sorts them.
7. Four more, given the same evening and recorded in that chapter's last section: Heading, Title and Summary are classes as the Genesis has them and E30's order is tested; *the parse is gone*; the pair is **parenthetical** and **narrative** with `print` dropped, parenthetical leaning toward hidden, annotations still printed, and styled-components serving directly through Format; and the Genesis's Quote is the basic, a block quotation perhaps a prop on it, as the first example of spanning semantic and visual structure.

## Answered by reading, before the core is written

**These are ours, and none of them is a question for Doug.** The reading is the first work of the sprint, and each item names who reads.

1. **The $Chemistry surface the model declares as imported.** The model assumes a `$Chemical` whose children are constructor arguments, a `parent`, a bond constructor taking the children, a catalytic constructor, and `$Block`, `$Html` and `$Func` for React content. The framework has its own names and shapes for each of these, and the first library's conventions are known from the catchup: a bond written as `$X(block: $Block)`, the computed `$Html` type rather than a class, formulas that a class files as a specimen and that swap in during the walk before the parent's bond. Cathy reads `library/chemistry/package/src` and its branch library and writes the mapping as a chapter of this book, so the core is written in the framework's words and the model's are translated once.
2. **The formulator.** E11, E53 and E54 describe a constructor that takes TSX and returns TSX before bonding, recursively; Doug has said the team was *missing how formulas work in $Chemistry* and that today's types are similar. Whether the framework's formula mechanism is the formulator, or a seam beside it, is settled by reading the framework, and the answer decides how `<Author>Doug</Author>` becomes a Type with an Of.
3. **Where the specification runs.** The first library carried a specification utility and a `specify` on its classes; how it ran, how it was compiled out, and whether its runner walks a tree is read before the new `specify` is written, so a feature that already exists is translated rather than reinvented. Queenie reads it with Cathy; the tests are hers.
4. **The compiler's input.** The first library's binder reads files and names — a chapter's file, a mention's brackets — and refuses a library that breaks the specification of a library. Over the new core its reading phase meets the stream's annotations instead of the first library's elements. What must change in the binder, and what stands, is read from its phases; Arthur reads it. This item stops at the point where the authoring surface is Doug's to rule, below.

## Studying the Genesis again, 2026-09-21

**Doug: *"You may carefully study The Genesis of Writing… for places where you think you might not understand yet either. Ask me questions."*** Nine places, each a thing the stream says that we cannot build from without one more word. None is answered from the first library; where the first library did something, that is noted as the bias to watch, not as an answer.

1. **The levels after E12.** E6 numbers Letter 0, Word 1, Sentence 2, Paragraph 3, Section 4. E12 says *"if Letter is level 1"* so that text is 0, and E15 calls Letter *"the canonical level 1"*. Claude Desktop's model keeps Word at 1 beside Letter and leaves the rest. Is that the numbering — text 0, Letter and Word both 1, Sentence 2, Paragraph 3, Section 4 — or does everything above Letter shift? Strict admission at every level depends on it.
2. **What a Format holds.** E23: *a place for themes and styled components; no constraints, like Letter.* E24: a Theme takes only Formats and often contains a styled-components theme provider. With styled-components serving directly through Format, is a Format the styled component a writing is drawn as, a set of style values, or the annotation that says which of a theme's components this writing wears? The first library made it a styled element with a selector, which is the bias to watch.
3. **Whether the core ships a Cover class.** E51: *"an implementer subclasses Chapter for the book, then a subclass inserting the Cover type, then uses components that work for types of covers."* Read with the ruling that Cover is an annotation applied to a chapter: does the core ship only the Cover annotation, and an implementer's subclass of Chapter inserts it in its bond, or does the core also ship a Cover chapter of its own?
4. **What an author writes for a reference.** The stream writes `<Mentioned as=quote/>`, `<Means>quote</Means>`, `<Ref for=quote>`; the compiler produces the link and nothing else. Does an author also write the first library's `$[ ]`, `[[ ]]` and `[[[ ]]]` in prose, expanded by the compiler, or is that notation gone with the first library and the tags are the surface?
5. **The Canonical, the nameless Letter.** E33: *a type of nameless Letter that serves as a suffix for a piece of writing; a symbol that reappears; signifies writing with a canonical referent goes there.* Does an author write it, or does a class that has a canonical referent supply it — a synopsis always suffixed with the mark that leads to its book, an entry in a table with the mark that leads to its chapter? The first library had the author write it and the specification demand it, which is the bias to watch.
6. **How a section or a chapter is addressed.** E30 calls Heading, Title and Cover *referents that mean each*. Is a section's key its heading's words, and a chapter's its title's, without a Mentioned being written, so that a Means to a section resolves to its heading; or is a writing addressable only when a Mentioned is written on it (E21), and the canonical merely the place a link lands?
7. **The margin.** E9: commentary belongs in the margin, and annotations are where types, references and meaning lie. The margin is never specified. Is it a thing in the model — where asides, notes and footnotes live — or a name for what the model does not hold?
8. **Where the back matter prints.** E10: the tail is *the back about the book and not a part of it, not visible in the writing.* The ruling of 2026-09-20: annotations are still printed, mostly parenthetical, and *parenthetical means hidden more than not rendered.* Does the tail print in place, hidden, or at the back — of the chapter, of the book — as end matter a reader can turn to?
9. **The formulator against the framework's formula.** E53: `<Author>Doug</Author>` becomes `[Author, <Of>[Doug](/my-autobiography)</Of>]`, a string then an annotation. The framework's formula swaps a tag's type by the name written inside it and rewrites nothing else. Is the formulator that swap — Author resolving to the Autobiography type with "Doug" as its content — or a rewrite of the children that the framework does not have and would be pitched to it? And with the ruling that the compiler writes only links, the link inside the Of is the compiler's and the shape is the formulator's; is that the division?

**Answered on 2026-09-21, the first four.** The levels: *text 0, Letter and Word 1, then 2, 3, 4.* A Format: *"Need to design around styled components"* — not ruled, a design still to make. The Cover question was not understood as asked — *"Not sure what this is"* — and is asked again below in plainer words. References: *"Refer to the documents"* — the stream's tags are what an author writes.

**And a note given with them that governs every answer here:** *"I want the same minimal, thoughtful, structural coding style to remain, and that we are going to deprecate and rewrite old books so that this new version of public becomes the current one. But… it was just a sketch and reality has to come in, and many of our decisions did not make it to that sketch yet."* The Genesis is canon where it speaks and a sketch where it is silent. A decision Doug made in the room that never reached the sketch still stands; the bias to watch is toward the first library's implementation, never toward his decisions; and the framework, the compiler and what was measured are the reality that has to come in.

**Answered the same day, the next four.** The cover: an author writes `<Type>Cover</Type>` *"near the bottom on the annotations list"* of the chapter. The Canonical: *the author writes it.* Addresses: *"Not mentioned. Not Headings. Titles should have ids as part of both the book and chapter system. They are mentioned by default in the classes"* — a book and a chapter are addressed by their titles, whose classes carry the mention; a heading is not an address. The tail: *"There is no tail. I was referring to the annotations"* — there is no back matter to print; what E10 called the tail is the annotations, hidden where they stand.

**And from the discussion with Claude Desktop the same day**, recorded verbatim in [the sixth chapter's corrections](06-answering-claude-desktop-from-the-source.md) and the [reply itself](07-what-to-tell-claude-desktop--reply-one.txt): every composition has a canonical, its first element, which each level names — a heading for a section, a title for a chapter, the cover for a book — and a subclass overrides by returning another value; the cover is first *and* carries the Cover annotation, found by searching the annotations by type name; parts are compositional and are never searched by class; the Title need not be a section; the Summary is optional and constructed from the first writing that is not the title; the Canonical is a Letter that means something; there is no Referent, and Mention and Reference are not Types; `specify` is turned on in test, of three modes; the `$` is on the property and the class and disappears on the component and the JSX prop. Still open and his: the Title's superclass and level; whether Mention extends Reference; copy or mention for the constructed summary. Still owed to us: the stream from E66, since his E68 numbers the levels differently from the answer given to us. *Answered 2026-09-25, that there is none — Doug: "There is no newer stream afaik so if you see the topic, it was in the old conversation anyways."*

And one about the ruling of the day before rather than the stream: **the scaffolded suite.** A unit test suite set up for every library, scaffolded by the call to `specify` — generated test files the library keeps beside its books, so an author adds to them, or a suite generated at test time from the library's writing and kept nowhere?

**Answered the same day, the last three.** The margin: *"I don't know what that means, but I think it was abstract. It wasn't about classes. You can ignore."* Set aside. The formulator: *"For now, let's try to build an abstraction that accomplishes what the formulator would do. The ensure function gets a lot of the way there. We should be able to dynamically change annotations and those should be able to change things like style and other properties of the cell. The annotations are like its genome."* So no rewrite of children is asked of the framework; the writing API is the abstraction, annotations change at runtime, and a change to them changes how the writing draws. The suite: *"Just have the suite in the app that the binder creates, and have it be runnable by a command that in the app that the binder installs, and the person building a library can add their own test files. I think that accomplishes both having specification AND encouraging them to use it."* And, amending the test mode of the day before: *"Instead of test mode, it might be easier to create a flag called formal on writing, and it starts as false, and if flipped to true, the setter also recursively changes all its source writing. And when formal is true, specifications run and if false they don't. Then, even at runtime, specification can be enforced."* `formal` is his word. And on it, the same day: *"Yes good on formal. We can then flip it, and maybe, much of the scaffolded test suite is just running that for all books in the library and the implementer is encouraged to write unit tests in the specification, and less outside in regular tests (though both should be used obviously)."*

**Four more the same day, answering what Claude Desktop had left open.** *Title extends Heading.* On the Summary and, with it, the tail: *"Why can't the summary be a summary anywhere in the children of the chapter. If there is one, we append a parenthetical one to the end. Also, since we have a firm type distinction between annotations and compositions, we don't need the annotations to be at the end do we. We can have them wherever and they are ignored in scans — this is what content is — a scan that ignores annotations. So then we can right append."* So E5's rule that annotations come at the end is withdrawn; `contents` is the scan that ignores them wherever they stand; and a constructed summary is appended, parenthetical, at the end. On the mention: *"Parent can be parent in render, not just parent in class so be careful interpreting me. A Mention is a sibling annotation. But I thought I renamed this Referent. Let's call it a referent instead of a mention, but export it as Mentioned as a component?"* On when a formal writing specifies: *"At the end of the Writing bond constructor. We might want to write functions on writing like: $Reorganize. It runs after writing bond constructor setup but before specify, so subclasses can adjust the source as needed in there. In this case, the writing bond constructor can be called at the start of every other class's bond constructor, and organize can do the heavy lifting. $Reorganize looks kind of like a bond constructor."* Asked what the appended summary holds: *"The parenthetical appended summary holds something like the first paragraph of the chapter. It's a proxy. Something to put in the table if it wants to surface a summary. Maybe we should make annotations that help us with organization. Summarized could be an annotation for a chapter, and it checks that there is a summary. Then, if we want chapters to have a summary, the writer can be Summarized in there."* So a constructed summary is a proxy holding something like the first paragraph, for the table to surface; and whether a chapter must have a summary at all is a demand an author places with an annotation, `Summarized`, whose `specifically` checks for one — the first annotation that organizes, which is the genome of E20 carrying a demand rather than a meaning.
