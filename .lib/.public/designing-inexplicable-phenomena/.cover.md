The design record of the Inexplicable Phenomena repository — how `@dna-platform/lib` is used to build ways of *viewing* the repo's content. Where [The Semantics of Books](../the-semantics-of-books/.cover.md) derives the object model from its source conversation, this book tracks the **design decisions of the repo itself**: what gets built on the classes, which prior work is extended rather than reinvented, and what each surface must do. Notes first, designs when settled — a chapter here is allowed to be a working notebook, kept honest by citing where each idea came from.

5. [The Live Library](05-the-live-library.md) — Doug's aside of 2026-08-22, written down as an aside and not as a plan, because a constraint that arrives after a decision costs more than one written down before it. Yes to both facts: this is a GitHub repository and the application is served by GitHub Pages, at a repository path today and at a domain root the day one is pointed here. What he described is a DYNAMIC CONTENT SYSTEM — very limited GitHub API access to one branch, holding people's comments and a person's journal, fetched by the site at runtime, with readers editing their own section of the library — and the observation that follows it: THAT WOULD NEED LIVE VALIDATION, WHERE STATIC CONTENT CAN BE VALIDATED AT BUILD TIME. THE ONE THING THIS CHANGES NOW, and it is why the aside earns a chapter rather than a note: the branch is currently deciding where the model's cross-book validation runs, and Doug's own answer was that it might only run when the library checks itself as part of the build. This aside says BUILD-TIME IS WHERE IT RUNS AND MUST NOT BE WHERE IT LIVES — a rule living in the compiler is a rule the browser cannot ask, since the compiler is node-side and renders nothing, while a rule living in valid() on the class can be asked from either side, the build calling it over the whole corpus and a page calling it over one arriving comment. That is already the framework's shape and the validating phase says so in its own words: it invents no rules, the bond constructors require what they require and valid() answers the softer questions. So the constraint is one sentence — THE RULES ARE THE MODEL'S AND THE BUILD IS ONE CALLER — which costs nothing to keep true and a rewrite to lose. Then what a live library would need that does not exist, named so the size is visible and none of it proposed: a write path, since a public site cannot hold a token that can write, so it is a function or an app or a form that opens a pull request and it is UNANSWERED; a fetch path that is not a module import, since the books map is dynamic imports the compiler wrote while a comment arrives as data and has to become writing at runtime; live validation, which is the same valid() and a different caller; and a section that belongs to a reader, which the model has no notion of, since the library's own summit is a SINGLE autobiographical subject and a library of many journals is a shape the derivation has not been asked about. Ends on the part that is already true: A COMMENT IS A CHAPTER AND A JOURNAL IS A BOOK, so the metaphor does not need extending to hold either — what would be new is who writes them and when they arrive, not what they are. It is not a feature request against the model; it is a caller the model has not met.
6. [The Back of the Page](06-the-back-of-the-page.md) — Doug's, 2026-08-22: THERE IS A BACK TO EVERY PAGE — count the sections, the paragraphs, the words, the subject spine, the attributes, and that is a COMPLETELY DIFFERENT VIEW OF THE SAME PAGE OR BOOK. A view the framework does not have and needs nothing new to build, which is the fact worth writing down because it is the test of whether a thing is really a view. THE BACK IS A PERSPECTIVE, and measured across package/src the framework uses NEITHER of chemistry's two axes — zero occurrences of perspective, reveal or look — so the back would be lib's first thing on the horizontal axis, and The Canonical Echo already predicted the shape when it called Cover, Synopsis, Reading and Links named lenses. WHAT IT SHOWS IS ALREADY A MEMBER, EVERY LINE OF IT, which is the whole argument: how much writing is five getters that already exist, the subject spine is the card climb Doug ruled and it opens no book, the attributes are the author, the subject and the canonical which the cover already finds, the links are a filter over words once a link is phrasal, and what is present but not read is the mentioned syntax. So the back is a view() and nothing else — no member is added to any class to support it, which is exactly the property that makes it a view rather than a report. WHAT AN ATTRIBUTE IS, now that Doug has said it plainly: a phrase that is ABOUT its page rather than PART of its reading — word grade, parenthetical, and enumerable, all three of which the code already does. WHICH MEANS THE ANSWER TO 'HOW DOES AN ATTRIBUTE REVEAL ITS METADATA' IS THAT THE BACK REVEALS IT: an attribute does not need to draw itself into the reading or become an element attribute or announce anything, it needs to be FINDABLE, and it already is — the back is the view that goes looking. And it is the same specification as the mentioned syntax one step on, present and unread and reachable, so once syntax is composed rather than swallowed and attributes are phrases rather than props, everything a back would want to show is a PART of the thing it is the back of, and the back stops being a report about a page and becomes a reading of it. The name is Doug's and used; VERSO is raised as the trade's word for the back of a leaf, beside the Leaf the framework already has. Closes on what is not answered: whose back, since a page and a chapter and a book and a subject and the library could each have one; how a reader turns to it, which is the book's affordance rather than the model's; and whether the counts are the same counts the build reports, because a back that disagreed with the build would be the card and the contents disagreeing a second time.

[The Unit of Code](07-the-unit-of-code.md) — Three programs, three answers to what one piece of code is — and one rule that decides all three: THE UNIT OF CODE IS WHATEVER THAT PROGRAM STATES ITS INVARIANTS OVER. A program's file boundaries should fall where its promises fall, because a promise that spans two files is a promise neither file can keep, and the way that failure arrives is always the same — a cycle, a stale copy, or a rule with two homes that disagree. lib's unit is a WORD, chemistry's is a concern because its invariants are stated BETWEEN classes, and the compiler's is a phase because its invariants are stated over a SEAM. AMENDED 2026-08-30: the lib row said a CLASS and it is a WORD. In v1 the two coincided — 51 files, 51 classes, one each — and the first draft named the class because they were never apart. They came apart in v2, where a word takes THREE classes: the data, the law, and the meaning. Letter.tsx is $Letter, $LetterSpecification and $TypeOfLetter, and Doug ruled the file stays whole, then did it again by hand the same day, folding TypedSpecification.ts into Type.tsx so the word type holds its own three. The rule at the top is why, unchanged: lib's invariants are stated about a letter, a word, a sentence — not about a specification and not about a type — so splitting the three would put a word's own invariant across an import boundary, which is exactly the failure this chapter records happening three times. The 51-classes measurement was a v1 count of a v1 coincidence; the WORD is what it was always measuring. Closes on what the rule FORBIDS, which is why it is a rule rather than a description: splitting chemistry one class per file, gathering lib into concern-sized files, giving the compiler classes, and a rule with two homes.
8. [The Order of a Class](08-the-order-of-a-class.md) — The member order inside a class, given by Doug four times in one sitting and quoted rather than paraphrased because paraphrase is what kept getting it wrong. AMENDED 2026-08-30, when he gave it again and it had changed. THE ORDER IS NOW SEVEN GROUPS: fields, then properties, then the bond constructor, then the constructor, then methods, then protected methods, then private methods. AND INSIDE THE FIELDS THE VISIBILITY RUNS THE OTHER WAY — private first, then public, then protected — which is deliberately opposite to the method block, and the reason is worth having rather than only the fact: a private field is the thing nothing outside may touch, so it is met before anything is built on it; a private method is the thing nothing outside may call, so it is met last, after everything that calls it. Both put the reader where they need to be, and they are opposite because a field is read before its uses and a method is read after them. WHAT MOVED is load-bearing and not a restatement: the 2026-08-27 order had ONE property group covering fields, getters and argumentless data-returning members, with a second group beneath for those that could not fit on one line. The new order splits that first group in two. Under the old one, $Word's protected patterns (a multiline field) and parts() (a multiline property) competed for the same slot and the code answered it two ways in two files; under the new one there is no contest, because graphemes and patterns are FIELDS at the tail of group one while canonical and parts() are PROPERTIES in group two. THE PROPERTY TEST SURVIVED UNCHANGED and is the only way a method reaches the top of a class: a member is a property only if it takes NO ARGUMENTS AND HANDS BACK DATA, both halves required, and writing something on one line does not make it one. canonical() and parts() qualify; specify() does not, because it validates and throws; where, select, selectMany and single do not, because they take arguments — so the monadic operator set does not sit in the property stack however short each line is. ONE-LINE FORM IS FOR PROPERTIES, methods are never written that way and every pair of methods is separated by an empty line, with one standing exception Doug wrote himself: a run of boilerplate methods that are each a single delegation may be flattened as a block, and a method with a real body stays multiline even sitting directly beneath three flattened siblings. AN EXCEPTION MESSAGE MAY NEVER ENUMERATE A ROSTER — say the shape, never the roster — because a thrown message is code no test reads, so nothing fails when the world moves out from under it. Carries one READING flagged as a reading and not a ruling: a field or property that cannot fit on one line sits at the END of its own group. And it says where it STOPS — it orders the MEMBERS of a class and says nothing about what is written inside one, which is The Closeness Rule, the law this chapter is one expression of.

12. [The Closeness Rule](12-the-closeness-rule.md) — The law that the other three style chapters are expressions of, said out loud by Doug for the first time on 2026-08-30: THINGS ARE CLOSER WHEN MORE RELATED AND SMALLER WHEN LESS RELEVANT. Two dials, independent — PROXIMITY encodes how related two things are and runs same line, stacked with no gap, one blank line apart, different methods, different classes, different files; SIZE encodes how relevant a thing is, INVERTED, and runs one line, several lines, its own method, its own class. So the layout of a file is a drawing of the semantic graph and the reader reads the drawing whether or not it was drawn on purpose, which is why a blank line the author did not mean is a distance the reader will try to account for. AND IT SETTLES WHAT ARTFULNESS MEANS, which is the opposite of what a first reading assumes: art is what you do where the convention is SILENT, never a licence to bend one for a better-looking result — the conventions ARE the closeness rule already applied to the cases that recur, and where one speaks it decides. Ruled directly the same day when the two were put in conflict: when the ORDER and the ASSOCIATION disagree, THE ORDER ALWAYS WINS, because the fixed order is the scale bar and a scale bar that flexes measures nothing. So a member is never moved out of its group to sit beside a relative, and if the urge to move it is strong that is diagnostic rather than decorative — the member is probably on the wrong object. Art therefore operates in exactly two places the order says nothing about: INSIDE a group, which is what stacks with what and where the blank lines fall, and ABOVE the class, which is which classes share a file. THE FOUR INSTRUMENTS are Doug's own list — ordering, stacking, brevity through line count, and paragraphs in code. Ordering is position as meaning. Stacking is members that are one idea drawn as one block with no blank lines even where the default would separate them, and $Sentence is the canonical drawing: three flat delegations and one tall single, where the block says these four are one idea and the height says this one does something the others do not, both facts true and both drawn. BREVITY IS THE COMPACTNESS RULES, three of them: a one-line if or for drops its brackets, which the package already does; a guard at the top of a method is written entirely on one line, which nothing does yet and which single's four-line branch violates eight times over, the reason being not the lines saved but that a guard drawn as a branch promises the reader a second path through the method and there is not one; and a for doing technical housekeeping goes on one line as a filter call might have been, which is Parser.tokens almost word for word — fourteen lines of loop with two continues doing what a filter and a map would have done. PARAGRAPHS IN CODE AMENDS A STANDING RULE and the amendment belongs to the Grammar's author to make: the Grammar said flatly no blank lines inside methods, a method is one thought, and the amendment is that a method is one thought and A THOUGHT MAY BE WRITTEN IN MORE THAN ONE PARAGRAPH — what the Grammar was guarding against, a method doing several unrelated jobs, is still forbidden and is now told apart from a method doing one job in stages. The test offered as a reading: phases are phases if naming them would produce names, and separate methods if extracting them would. Closes on what the law forbids — a blank line spent for readability, because spending one without meaning it makes every other one weaker; a DOUBLE blank line, because there is no second rung; moving a member out of its group; a guard drawn as a branch; and a comment. Every name in the chapter is Doug's own, and the title is flagged as a proxy taken from his sentence rather than a name he gave.
