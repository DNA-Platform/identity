The design record of the Inexplicable Phenomena repository — how `@dna-platform/lib` is used to build ways of *viewing* the repo's content. Where [The Semantics of Books](../the-semantics-of-books/.cover.md) derives the object model from its source conversation, this book tracks the **design decisions of the repo itself**: what gets built on the classes, which prior work is extended rather than reinvented, and what each surface must do. Notes first, designs when settled — a chapter here is allowed to be a working notebook, kept honest by citing where each idea came from.

4. [Ways of Reading](04-ways-of-reading.md) — The view catalogue: the book as the fundamental website, view patterns decomposed into three shipped moves — lens, reading, arrangement; a book is an evolvable authored structure, and views multiply claims. THREE LAWS FOR EVERY VIEW now: identity through change, views multiply claims, and — added out of The Parse — A VIEW READS, IT DOES NOT RE-DERIVE. The manifold flattened a chapter into ~55 lines of strings before drawing it, which is a SECOND POPULATION OF THE MODEL wearing a data structure, and it failed three ways in one sprint: it SNIFFED what the model knows (asking a string whether it started with an angle, so every quotation silently became prose the moment the model carried that angle as a mark on the paragraph rather than in the copy), it INVENTED ADDRESSES by arithmetic over array positions while a reference resolved by walking the model, so links followed to nothing when the numbering changed, and it BORROWED A MODEL MEMBER for its own state, storing a ribbon's slot in the writing's number because a number happened to be there. So: ask the model rather than testing its output; an address is a POSITION and not a formula, so the anchor rendered is the string a reference resolves and the two cannot drift; and a view's own state lives on the view. The corroboration that proves a view is really reading is one writing read at four altitudes with each altitude walking its own count — and the failure mode of building that the lazy way is a number compared to itself.
5. [The Live Library](05-the-live-library.md) — Doug's aside of 2026-08-22, written down as an aside and not as a plan, because a constraint that arrives after a decision costs more than one written down before it. Yes to both facts: this is a GitHub repository and the application is served by GitHub Pages, at a repository path today and at a domain root the day one is pointed here. What he described is a DYNAMIC CONTENT SYSTEM — very limited GitHub API access to one branch, holding people's comments and a person's journal, fetched by the site at runtime, with readers editing their own section of the library — and the observation that follows it: THAT WOULD NEED LIVE VALIDATION, WHERE STATIC CONTENT CAN BE VALIDATED AT BUILD TIME. THE ONE THING THIS CHANGES NOW, and it is why the aside earns a chapter rather than a note: the branch is currently deciding where the model's cross-book validation runs, and Doug's own answer was that it might only run when the library checks itself as part of the build. This aside says BUILD-TIME IS WHERE IT RUNS AND MUST NOT BE WHERE IT LIVES — a rule living in the compiler is a rule the browser cannot ask, since the compiler is node-side and renders nothing, while a rule living in valid() on the class can be asked from either side, the build calling it over the whole corpus and a page calling it over one arriving comment. That is already the framework's shape and the validating phase says so in its own words: it invents no rules, the bond constructors require what they require and valid() answers the softer questions. So the constraint is one sentence — THE RULES ARE THE MODEL'S AND THE BUILD IS ONE CALLER — which costs nothing to keep true and a rewrite to lose. Then what a live library would need that does not exist, named so the size is visible and none of it proposed: a write path, since a public site cannot hold a token that can write, so it is a function or an app or a form that opens a pull request and it is UNANSWERED; a fetch path that is not a module import, since the books map is dynamic imports the compiler wrote while a comment arrives as data and has to become writing at runtime; live validation, which is the same valid() and a different caller; and a section that belongs to a reader, which the model has no notion of, since the library's own summit is a SINGLE autobiographical subject and a library of many journals is a shape the derivation has not been asked about. Ends on the part that is already true: A COMMENT IS A CHAPTER AND A JOURNAL IS A BOOK, so the metaphor does not need extending to hold either — what would be new is who writes them and when they arrive, not what they are. It is not a feature request against the model; it is a caller the model has not met.
6. [The Back of the Page](06-the-back-of-the-page.md) — Doug's, 2026-08-22: THERE IS A BACK TO EVERY PAGE — count the sections, the paragraphs, the words, the subject spine, the attributes, and that is a COMPLETELY DIFFERENT VIEW OF THE SAME PAGE OR BOOK. A view the framework does not have and needs nothing new to build, which is the fact worth writing down because it is the test of whether a thing is really a view. THE BACK IS A PERSPECTIVE, and measured across package/src the framework uses NEITHER of chemistry's two axes — zero occurrences of perspective, reveal or look — so the back would be lib's first thing on the horizontal axis, and The Canonical Echo already predicted the shape when it called Cover, Synopsis, Reading and Links named lenses. WHAT IT SHOWS IS ALREADY A MEMBER, EVERY LINE OF IT, which is the whole argument: how much writing is five getters that already exist, the subject spine is the card climb Doug ruled and it opens no book, the attributes are the author, the subject and the canonical which the cover already finds, the links are a filter over words once a link is phrasal, and what is present but not read is the mentioned syntax. So the back is a view() and nothing else — no member is added to any class to support it, which is exactly the property that makes it a view rather than a report. WHAT AN ATTRIBUTE IS, now that Doug has said it plainly: a phrase that is ABOUT its page rather than PART of its reading — word grade, parenthetical, and enumerable, all three of which the code already does. WHICH MEANS THE ANSWER TO 'HOW DOES AN ATTRIBUTE REVEAL ITS METADATA' IS THAT THE BACK REVEALS IT: an attribute does not need to draw itself into the reading or become an element attribute or announce anything, it needs to be FINDABLE, and it already is — the back is the view that goes looking. And it is the same law as the mentioned syntax one step on, present and unread and reachable, so once syntax is composed rather than swallowed and attributes are phrases rather than props, everything a back would want to show is a PART of the thing it is the back of, and the back stops being a report about a page and becomes a reading of it. The name is Doug's and used; VERSO is raised as the trade's word for the back of a leaf, beside the Leaf the framework already has. Closes on what is not answered: whose back, since a page and a chapter and a book and a subject and the library could each have one; how a reader turns to it, which is the book's affordance rather than the model's; and whether the counts are the same counts the build reports, because a back that disagreed with the build would be the card and the contents disagreeing a second time.
