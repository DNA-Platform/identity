The design record of the Inexplicable Phenomena repository — how `@dna-platform/lib` is used to build ways of *viewing* the repo's content. Where [The Semantics of Books](../the-semantics-of-books/.cover.md) derives the object model from its source conversation, this book tracks the **design decisions of the repo itself**: what gets built on the classes, which prior work is extended rather than reinvented, and what each surface must do. Notes first, designs when settled — a chapter here is allowed to be a working notebook, kept honest by citing where each idea came from.

## Chapters

2. [Markdown with LaTeX on the Composition Classes](02-markdown-with-latex.md) — Markdown-with-LaTeX built into the object model — `$Latex` inline, `$Markdown` an authoring adapter that renders composition objects through eval.

4. [Ways of Reading](04-ways-of-reading.md) — The view catalogue: the book as the fundamental website, view patterns decomposed into three shipped moves — lens, reading, arrangement; a book is an evolvable authored structure, and views multiply claims. THREE SPECIFICATIONS FOR EVERY VIEW now: identity through change, views multiply claims, and — added out of The Parse — A VIEW READS, IT DOES NOT RE-DERIVE.
5. [The Live Library](05-the-live-library.md) — Doug's aside of 2026-08-22, written down as an aside and not as a plan, because a constraint that arrives after a decision costs more than one written down before it. Yes to both facts: this is a GitHub repository and the application is served by GitHub Pages, at a repository path today and at a domain root the day one is pointed here.
6. [The Back of the Page](06-the-back-of-the-page.md) — Doug's, 2026-08-22: THERE IS A BACK TO EVERY PAGE — count the sections, the paragraphs, the words, the subject spine, the attributes, and that is a COMPLETELY DIFFERENT VIEW OF THE SAME PAGE OR BOOK. A view the framework does not have and needs nothing new to build, which is the fact worth writing down because it is the test of whether a thing is really a view.
7. [The Unit of Code](07-the-unit-of-code.md) — Three programs, three answers to what one piece of code is — and one rule that decides all three: THE UNIT OF CODE IS WHATEVER THAT PROGRAM STATES ITS INVARIANTS OVER. A program's file boundaries should fall where its promises fall, because a promise that spans two files is a promise neither file can keep, and the way that failure arrives is always the same.
8. [The Order of a Class](08-the-order-of-a-class.md) — The member order inside a class, given by Doug four times in one sitting and quoted rather than paraphrased because paraphrase is what kept getting it wrong. AMENDED 2026-08-30, when he gave it again and it had changed. THE ORDER IS NOW SEVEN GROUPS: fields, then properties, then the bond constructor, then the constructor, then methods, then protected methods, then private methods.
9. [What Carries Over](09-what-carries-over.md) — Doug asked the team what changes between the versions and what stays, so it was measured rather than remembered: v1 is 51 files, 3,498 lines, 46 classes and 54 published exports; v2 is 16 files, 491 lines, 23 classes of which eleven are $TypeOfX — twelve substantive — and it publishes NOTHING. Eleven words appear in both and thirty-five v1 classes have no counterpart.
10. [The Type and the Instance](10-the-type-and-the-instance.md) — The type holds the meaning and the instance holds the data, so meaning moves without subclassing — the type is a factory for its class, freeing the single inheritance slot. One question decides where a member goes; the corollaries were learned expensively — a rule is a method not a property, rules run base-first deduped, there is one specification and it is the type's.
11. [The Coding Style](11-the-coding-style.md) — The single index of every style rule in force, so a refactor can find the ruling before it undoes one — each row saying what a document rules and the day the ruling was given. OPENS ON THE TWO ANCHORS, given 2026-09-05 as the reason behind the language law rather than another rule: THIS IS THE PUBLIC LIBRARY, and IT IS CLOSED UNDER BOOKS.
12. [The Closeness Rule](12-the-closeness-rule.md) — The law the other style chapters are expressions of: PROXIMITY encodes relatedness, SIZE encodes relevance inverted, the order always wins, art operates only where the convention is silent. The four instruments — ordering, stacking, compactness (bracketless one-liners, guards on one line, housekeeping fors small), paragraphs in code with extraction earned by polymorphism alone. What the law forbids: readability blank lines, doubles, moved members, guards drawn as branches, comments.
13. [The Default Dress](13-the-default-dress.md) — The Wikipedia default, ripped off intentionally — and SINCE 2026-09-04 EVERY DRESS IS A STYLED CHEMICAL. The mechanism is $Chemistry's own (particle 11); what this chapter owns is how the library uses it, in three rules: a dress is a CLASS declaring selector = styled.h2 with its CSS as fields and a view that writes that element, which is what makes it DI-able where a raw styled component answers null.
14. [Shells Over Types](14-shells-over-types.md) — RULED 2026-09-02 and obeyed: everything derives from Writing, base classes stay free for the end user, kinds are TYPES and the type grants the powers, so a canonical class is a SHELL — visibly one. The test for any new class: name what it does that its type could not confer.

16. [The Shape of TSX](16-the-shape-of-tsx.md) — HOW TSX IS LAID OUT, HOW A COMPONENT IS NAMED, AND WHAT $ IS FOR — written 2026-09-04 because the branch had rules for the layout of a class and none for TSX, which is most of the code.
17. [The Interface Type System](17-the-interface-type-system.md) — The design of the second $Writing, written while it was being built with Doug: the four purposes in his words (any part replaceable, $Writing easy to subclass by FOLDING IN types, specifications so types can be CAUSAL, and the check run statically at build — 'we're making a little compiled language'), and the sentence the whole thing turns on.
