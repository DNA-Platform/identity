The demos are its worked examples and this is where their conventions are ruled.

## Chapters

1. [Using the Public Library](01-using-the-public-library.md) — What a CONSUMER of the public library writes, as distinct from what the library is written as — five of Doug's rulings from the Wikipedia demo, 2026-09-06: a consumer subclasses plainly with no interfaces, types or specifications (the four-declaration file is the library's shape, so that an end user COULD subclass); the convention that .chapter subclasses the book's NORMAL CHAPTER and default-exports it, imported as Chapter, with the book subclass in .book; a web page is written in web design language, not clever names; no comments in the demo any more than in src; and the five questions asked before any class — do you need it, can a styled component tag it, can the DOM keep its structure, what is the minimum, what stops a flat list organized — applied to every bit of code, with the Wikipedia book as the worked example.
2. [Reading the Source](02-reading-the-source.md) — Why the figures and equations took a day: not difficulty — SUBSTITUTION. The PDF sat on disk for hours, sampled pixel by pixel for the page geometry and then used as a picture and nothing else, while the demo carried sixty-five sections of invented prose. A demo is EVIDENCE and a plausible substitute is what it must not be. Carries what a PDF does not contain and what stands in for it — no spaces (a gap wider than a fifth of the line height), no paragraph marks (parindent, so a paragraph ends at the next indented line), heading levels by size and then by number pattern — the split between reading text in node and rasterising in Chrome, and the rule that an equation is transcribed and CHECKED against its crop, never parsed.
3. [The Address, and Where It Was Never Wired](03-the-address-and-its-wiring.md) — THE ADDRESS SCHEME, gathered from the three places it was already ruled so nobody derives it a third time — Sprint 30's R10 (a NUMBER works down the parts by position and ends in an anchor in the query string; a STRING appends to the path), Sprint 46's grammar (a mention is named for what it represents and found by its copy; by position, by kind, by name; steps split on slash), and $Catalogue.follow() and parts() which already walk and read through — and WHERE IT WAS NEVER WIRED, measured: mentions are made for words, sentences, paragraphs and a section's paragraphs and for nothing on the library ladder, so book.catalogue() is undefined and the scheme is dormant above a section; there is no $$Chapter; heading ids are made from text; adstyle is address mangled by the dress sweep; and nothing leverages a writing's document reference. Carries Doug's chapter rulings of 2026-09-10 verbatim, the anchor convention in his words (a chapter's index, its document at 0, the address as the fragment and the id), and the one open timing question with its three framework answers.
4. [The Book's Little Framework](04-the-book-s-little-framework.md) — THE THREE FILES A BOOK WRITES, in Doug's words from the 2026-09-11 brainstorm: .book carries the book subclass and its registrations, .chapter the document kinds and themes the book's chapters share, .document the normal document in one line; a chapter file is a class extending the book's own chapter and writes its document in print(), passed into the book as a component; one page per book with chapters as anchors the router owns; the library level stands apart and a chapter never holds its document but means it; a chapter mention converts into a path and whatever takes a title consumes it; the mention classes inherit from Reference with no type shells; composition is the ladder and types stay in the block. CITATIONS, designed the same day as an experiment that holds: keyed entries in an ordered list, citations by key, the number the entry's place; a printed document has its chapter as parent so book and chapter are walks; a chapter's document reference is made at its bond and filled by the document at its own, read as a promise; Writing.read() reads what a writing means. AND THREE FACTS MEASURED THE SAME MORNING: the suite reads dist (Solutions 5); a mention is made by its holder in its own body or the parent chain cycles; print the children is the block read without its annotations, theming untouched.
5. [The Book Is the Layout](05-the-book-is-the-layout.md) — HOW TO WRITE A BOOK AGAINST THIS FRAMEWORK, written 2026-09-13 at Doug's instruction by the session that had just been corrected three times in an afternoon. The anchor: book is layout, chapters are logical parts — the book answers WHERE, a chapter answers WHAT. Every file but .book is content and content is chapters, so a logical part of the page is a FILE; and .book itself has an ORDER — the class inheriting from the book kind FIRST, then every component the book is written with, because the file is named for the book and the book is the layout. The book finds a chapter by its TYPE, never its position or its name, and the type is the only answer available because a chapter writes its document in print() which runs after the book draws. The book draws by a TEMPLATE METHOD PER PART, like header() and footer() — inlining a part's drawing is the fault, because it is the one thing a consumer cannot override. Four rules: nothing cached, what is wanted is a get-only property; one list walked once; a group is NAMED and never a remainder, because a remainder is one misreading from dissolving the apparatus, which is what the previous team was fired for; and print={false} declares without drawing and already works. The look stays the format's. RULED 2026-09-13: header() and footer() are a book kind's, not Book's - Book assumes nothing, the article has them and the encyclopedia is a type of article; books are for layout, and this is exactly the kind of thing one does when implementing a book.
6. [Publishing a Library](06-publishing-a-library.md) — HOW A LIBRARY BECOMES A SITE — the settled account of the geometry Doug ruled 2026-09-15: a library holds the books, its face is .public and is what GitHub Pages serves, the binding lives in the face, and everything the binder generates compiles inward, never into a book's folder. The first copy from any binding (npm run copy makes .public in the library pointed to, viral by design), install by hand, the sync from the origin .pubconfig names, the build that leaves one prerendered page per book. What a consumer does, in five steps.
7. [Specifying a Library](07-specifying-a-library.md) — Where a claim about a library belongs, and how it is raised — written 2026-09-15 after Doug named an abuse: the framework's Specification is for a piece of writing specifying ITSELF, and borrowing it for a library meant joining every failure into one string and splitting the message back apart to recover which book each belonged to. THE LINE: everything one book can check about itself is a rule on its kind, owed to the framework — every book has a subject, the table of contents catalogues all chapters; only what needs MORE THAN ONE book lives at the library level, and the test to apply is whether one book could answer it alone. The library's rules are vitest tests in .binding/specification that the build runs in-process, so npm test and the build run the same file; a test says which book it is about in typed metadata and the build lands its failure on that book's cover as a compiler line the VS Code problem matcher already reads. The metadata a build knows is .graph.json, written once per read and keyed by digest, with one member per fact in reading.ts reaching by TYPE so a library's own cover and title still answer. Carries the thousand-book analysis with its measurements: the wall is memory at ~140MB a heavy book retained for the process's life, the render's 52 minutes of boot, the serial spawn, the six O(N-squared) loops fixed, and what stays linear.
