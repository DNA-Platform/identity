Defects diagnosed in this branch, one chapter each, indexed by **what was observed** rather than by what it turned out to be. [Projection](../projection/.cover.md) indexes the same work by time; this book indexes it by problem, and neither answers the other's question. Specified in [Solutions](../../../../.claude/library/library-tree/06-solutions.md).

Every entry below opens with the **symptom** — the error text, the wrong value, the visible behaviour — because a reader arrives holding one of those and not a diagnosis. Each chapter carries a keyword line for grep, drawn from the vocabulary below.

## The keyword vocabulary

Grow this list only when a genuinely new class appears, and grow it here so the next writer sees it.

**Surfaces:** `framework` (chemistry itself) · `model` (`@dna-platform/lib`) · `demo` (the app) · `tooling` (compilers, validators, sync) · `library` (books and covers) · `sync` (identity and branches)

**Mechanism classes:** `stale-artifact` (a compiled or derived thing that outlived its source) · `missing-parent` (a chemical built outside chemistry) · `render-loop` (mutation during render) · `wrong-altitude` (a decision made at the wrong level) · `unproven-deletion` (a member removed without proving it dead) · `silent-default` (a guard or flag that did nothing) · `lifted-class` (code reasoning about the class as written, where the object was built from a class the framework made) · `rebind` (prop binding re-running over an already-built instance's held state) · `absent-case` (a gate ran correctly over content or timing that could not exercise the defect) · `narrowed-declaration` (a subclass narrowed what its base widened, and the narrowing travelled the wrong way)

[The link I built three times](03-the-link-i-built-three-times.md) — Doug asked for a book's TITLE to be the interaction and pointed at prior art; it took THREE corrections because I iterated on guesses instead of opening the file. Round one added separate buttons and a running head; round two kept the name but bolted an 'entry N' label beside it; round three dressed the title in a dotted underline — each satisfying the letter of the last correction and breaking the same law again. NO TEST FAILED AT ANY POINT: green, typed and rendering the whole way, with Doug's patience as the only detector. The mechanism was two files away — $RibbonMark and $Return are subclass-plus-view(), references that RENDER THEMSELVES, and a table of contents row prints itself with nothing applied to say it is one. The model's answer to 'how do I make this followable' is NOTHING: a cover IS a $Reference$<$Book>, so reference-hood is what a thing already is and every round added signal to announce a property it already had. Worst part: Sprint 47's retro states this in one line and I READ IT at the top of the same session — reading is not consulting. The lesson is about research, not links: when someone points at prior art, open it before writing a line, and never use the reviewer as your search process — three corrections spent on what one file would have answered is outsourcing research to the person least able to afford it.
4. [The sprint that planned what it had not designed](04-the-sprint-that-planned-what-it-had-not-designed.md) — A long sprint produced 4 of 38 requirements, all framework floor, and a demo built entirely from classes that predated it — a regression check presented as a demonstration. EVERY GATE PASSED: requirements approved, every requirement traced to a unit, work verified with fresh numbers, altitudes obeyed. The mechanism: ORIGIN TRACING RUNS ONE WAY ONLY. It asks whether every requirement has a unit, never whether every unit has a MECHANISM — so $Type and its resolution were written as units, with files and dependencies and scenarios, for a thing whose central mechanism had never been designed. Two things follow and both did: the implementer starts where the mechanism is clear, so the bond-constructor work consumed the session and the undesigned unit was deferred by being unbuildable rather than by anyone deciding; and FEASIBILITY GETS MISTAKEN FOR DESIGN — a deferral of the BUILD was treated as a deferral of the DESIGN, and a five-point feasibility case was written where a mechanism was owed. Compounding: the chapter itself said 'the design session first' and 'the cost is in the design conversation, not the code', and no gate checks whether a declared design session happened. THE FIX: a unit with no mechanism is not a unit — mark it DESIGN OWED and give it no files and scenarios so it cannot pass as buildable, and run the self-check both directions. THE LESSON: ceremony passes gates. The question that catches it before work starts is 'for each unit, what runs and when?' — where there is no answer, that unit is a design session, and starting anywhere else is choosing the tractable over the necessary.
5. [The suite that passed against a stale build](05-the-suite-that-passed-against-a-stale-build.md) — A framework change that SHOULD have broken four lib classes landed, and the lib suite reported 108/108 passing — a false green reported in the room as a result before anyone asked what the suite was testing against. Reading the number could not catch it, and 'deps: { inline: [/chemistry/] }' reads like it means 'use the source' but controls bundling, not resolution. The mechanism: the lib resolves its dependency through node_modules and package.json points at dist/, so the suite was exercising the LAST BUILD of chemistry rather than the working tree. One probe settles it and should be run first — node -e "console.log(require.resolve('@dna-platform/chemistry'))". Rebuilding turned 108/108 into 105/108, with three failures naming exactly the four classes an audit had predicted. THE CHANGE WAS CORRECT THE WHOLE TIME; THE VERIFICATION WAS NOT. Fix: when a change crosses a package boundary, rebuild the dependency before running the dependant's suite — without it the run is not a weaker check but a check of DIFFERENT CODE. The lesson: an unexplained pass is exactly as suspicious as an unexplained failure and far more dangerous, because nobody investigates good news; it happened twice in one session. The habit that catches it — before reporting a green number, say what it exercised: not 'the suite passed' but 'the suite passed against this build of that dependency'. If that sentence cannot be completed, the number is not yet evidence.
6. [The class that was not the class](06-the-class-that-was-not-the-class.md) — A chemical asked to enumerate its own properties answered with the FRAMEWORK'S instead — the class declared name and synopsis, and walking its prototype chain returned inline, viewLevel, perspectives, children and parent with nothing to tell them apart; and the same shape again wearing different clothes, a static assigned inside a bond constructor reading back as undefined through the imported class, with nothing thrown. FOUR INSTRUMENTS, EACH WRONG DIFFERENTLY, three corrected by Doug rather than by a failing test: stopping the prototype walk at the base class BY IDENTITY never terminates, because the instance's chain does not contain it; Object.keys misses everything because many chemicals are made by Object.create, so the fields live on the object the instance was made FROM; a framework-name exclusion list built from the source is incomplete by construction, because the runtime surface carries members the plain classes never declared; and feature-detecting the base level stops immediately, because the very first prototype owns everything. The chain, READ rather than guessed by printing it: $Chemistry inserts EXACTLY ONE LIFTED COMPOSITE prototype at the top, carrying every backing and every method as a getter, with the authored classes intact below it. So all four failed for one reason — they reasoned about the class as written, and the object was built from a class that was made. What works: skip the lifted level, identifiable because it is the only prototype carrying $-prefixed getters, exposing the backings the membrane keeps private everywhere else; and a static is not a place to keep anything, since one assigned during a bond constructor lands on the lifted class and the imported class never sees it. THE LESSON IS NOT ABOUT PROTOTYPES: a twelve-line probe that printed the chain answered in one run what four corrections could not, so when three attempts at one problem fail DIFFERENTLY, stop attempting and instrument — each failure was informative and none was evidence, because none made the actual shape visible.

[The contents that failed before adoption](07-the-contents-that-failed-before-adoption.md) — **a book with an AUTHORED table of contents rendered a bond failure in that chapter's place — 'Cannot read properties of undefined (reading summary)' — while every model-level test on the same book passed** — children bind before their parent adopts them, and the contents' summary derives from the book, so the getter reached through a parent it did not have yet; the spliced contents never hit this because the splice ran inside the book's bond; the failure PREDATES the sprint that found it, since nobody had ever rendered an authored one. The fix is the shipped $Cover pattern plus its validity half: catch the ancestor's demand that cannot apply yet, state your own valid(), and let derived getters answer undefined before adoption. The probe rule held again — three theories each fit some evidence, one printed run settled it.

[The field that buried a method](08-the-field-that-buried-a-method.md) — **opening The Team threw 'this.book.at is not a function' from the contents' row-building, though the book passed instanceof $Book a line earlier** — a state field named at on the $Book subclass (its open-page number) buried $Book.at(), the location method; a field and a method share one name space and the field wins, and nothing complained until something finally asked the contents for rows. Renamed to page. [The parent that changed on screen](09-the-parent-that-changed-on-screen.md) — **the shelf page failed to load with 'this.book.at is not a function' from the contents' row-building, after the same code passed the whole suite** — an element's parent is the chemical that interprets it, and on screen that is whatever RENDERED it, so a contents drawn inside a page-switching chemical answered this.parent with the page switcher; one hop of parent is a bind-time fact, not a render-time one. The fix ships in the model: $TableOfContents.book climbs to the nearest $Book, the canonical's guarded walk, and parts() names the wrong parent plainly when it finds one. Hold with chapter 07: the same reach failing BEFORE adoption there, ON SCREEN here — derived members climb or answer undefined, never trust the single hop.
10. [The prop that emptied the shelf](10-the-prop-that-emptied-the-shelf.md) — **the shelf rendered with no member spines and no written entries — furniture drawn, books gone, no error — after one prop was added to the singleton it renders through** — passing a prop to an already-built instance appears to re-run binding over it, and members assigned from outside after construction did not survive; proven as a sequence (prop absent: present · prop present: empty · prop removed: back), with the in-framework path FLAGGED rather than asserted. The fix: never pass props to a bound singleton that accumulates state — wire callbacks by assignment (module slots set once), render the instance bare. Two ways into a chemical, construction and assignment, and props belong to construction.
11. [The constructor that captured the wrong instance](11-the-constructor-that-captured-the-wrong-instance.md) — **clicking a book entry did nothing — handler ran, screen stayed, no error — where the handler reached the page switcher through a module variable assigned in the constructor** — React development mode constructs a component twice and keeps one, so a constructor that registers *this* outward holds whichever construction ran last, not necessarily the kept one, and every click mutated an instance no view would re-render. The fix: register in view() — only a rendered instance runs its view, so the variable always names the one on screen. A constructor knows it ran; it cannot know it was kept.
12. [The writing that looped its page](12-the-writing-that-looped-its-page.md) — **a page written with a specialized inline element threw 'Too many re-renders' during render, and the element never appeared — the host rendered 41 times and the child zero, but only when it stood inside another chemical's writing; standing alone it was fine** — the law carried for two sprints ('a subclass that declares its own props and overrides a method its view() calls will not render') was FALSE, and four filed routes had each failed for a different wrong reason. Five one-variable cases found the true rule — inline, PASSED A PROP, inside a block — and a probe printing identities showed the instance, block and component all stable while the children churned forever. Props are construction and were being recorded as mutation: a chemical written inside another's writing is BUILT during that render and handed its props there, the empty lastProps guard makes every prop a change, the reactive setter records it into the running scope, the scope finalizes dirty, and the host renders again. The framework already said 'this write is not news' with its rendering flag; it was never raised for the one write that never is. Fixed in the bond, NOT in the setter — guarding there on 'has not mounted' drops real mutations of a lensed instance and chemistry's own perspectives suite catches it. The lesson: a filed law is a claim and claims decay, and a theory that reads as true but is irrelevant is a signal to keep instrumenting rather than start fixing.
13. [The chapter that wrote its sections twice](13-the-chapter-that-wrote-its-sections-twice.md) — **nothing failed — no error, no warning, green suites and correct pages for two sprints — while every chapter in the demo BUILT ITS SECTIONS TWICE, the model holding one set and the reader seeing another** — four sections built where two were written, proven by counting construction. view() carried two contracts, declare and draw: the bond evaluated the chapter's writing into its parts, then React called view() again and evaluated the same writing into different objects. The base told the contracts apart with a self-check asking whether it had been overridden, which is the real defect — a subclass overriding view() purely to RESTYLE would have had its sections harvested out of its styling. Fixed by reading the declaration once and drawing what is held, through the shipped frame seam; the self-check deleted with nothing in its place, because a document that writes no sections falls through on its own. IT EXPLAINS TWO EARLIER FILINGS — the parent that changed on screen and the constructor that captured the wrong instance are both TWO POPULATIONS OF ONE OBJECT, each fixed where it hurt rather than where it came from, so a symptom filed twice is a signal the cause was never found. The lesson: a method with two contracts gets told apart by a check, and the check is the smell — and this defect COULD NOT FAIL, since both populations came from the same writing and looked identical; the only way to see it was to ask the model what it held and compare it to what was drawn.
14. [The green that exercised nothing](14-the-green-that-exercised-nothing.md) — Five sprints reported 'app tsc 0' and 'driven, zero page errors' while a demo page crashed on open — because TWO GATES WERE NOT CHECKING and neither said so. The typecheck PASSED BY NOT RUNNING: 'cd app && tsc --noEmit' exits 0 having compiled ZERO files where the project form compiles 46 and finds 5, one of them the live crash, named by the compiler the whole time. The driver PASSED BY NOT BEING RUN: it threw at its own step three on a renamed selector, exited non-zero, printed a bare stack trace with no indication of how far it got. Both numbers were TRUE and both scopes were SILENT, and the scope was the whole content of the claim. The fix is that the artifact states its own scope — files typechecked, debt named BY IDENTITY so a fifth error cannot hide among four, unexpected counted, never a bare PASS — and the driver reports checkpoint accounting. The habit that catches it: WATCH THE GATE GO RED BEFORE TRUSTING ITS GREEN. Third appearance of the stale-build law — and a symptom filed three times is a cause nobody fixed: the cause is reporting a number without its scope. TWO MORE FROM THE PARSE, and one is a FALSE RED. The relative -p does it too: 'tsc -p tsconfig.json' from inside app/ prints nothing and exits 0 while the same config by ABSOLUTE path finds four real errors — the shortcut was believed and THE GATE CONTRADICTED IT, winning because it states its scope. And inverted: a driver reported four failures that did not exist, because the dev server had outlived three deleted modules and was walking a module graph that was gone; restarted at the same commit, zero. A FALSE RED COSTS WHAT A FALSE GREEN DOES and costs it faster, since it sends you diagnosing correct code — the tell is that when a driver and the unit suite disagree about the same objects, suspect the PROCESS before the code. So the scope rule extends to what a gate RUNS AGAINST: a suite states which build, a typecheck which files, A DRIVER WHICH SERVER.
15. [The requirement I invented, and then failed](15-the-requirement-i-invented-and-then-failed.md) — A probe checked that a hand-written part was SEEN BY THE MODEL, found it was not, and the sprint was reported BLOCKED — with a proposed fix that would have rewritten the parse at every level, reaching back into the previous sprint's design. Doug dissolved it in one sentence he had already written down: the parse is post-hoc, the standard view renders the BLOCK, and a written part already draws itself. The probe was correct and the thing it measured was wrong. THE MECHANISM: a requirement was INVENTED and then treated as given — inserting something into prose means it DRAWS where it was written, which the block already does; 'the model must also see it' was added silently as the way to measure the real requirement, and once a made-up criterion is the measurement, failing it looks exactly like failing the requirement. Checked properly, all three drawings pass and nothing needed changing; the parse not surfacing an inline written part is a gap in METADATA, not a failure of insertion. Reading a law is not consulting it — already filed about research, now filed about requirements, and costlier: the first wasted three corrections, this nearly bought a rewrite of the parse. THE TELL, worth memorising: a blocker that appears at the exact moment your own measurement fails is a closed loop with nobody outside it. The check before reporting anything blocked — WHOSE WORDS IS THIS CRITERION IN? If the answer is mine, it is a proposal, not a blocker.
16. [The parse that woke its own parents](16-the-parse-that-woke-its-own-parents.md) — **both demo drivers went red with 'Maximum update depth exceeded', verify-book stalling at check 0 — while every unit suite stayed green, lib 203/203 and chemistry 674/674, tsc clean in both** — the parse had been given a parent so a scope could reach through it, and parts() writes part.index onto everything it composes, so the write diffused up the new chain, re-rendered the ancestors, and their views asked for parts again; before the parenting a composed part was its own parent and the write had nowhere to go. Three reverts eliminated the framework, the third informatively: reverting all of chemistry gave a DIFFERENT error, which proved the cause was in the model. THE LAW: a parse may not be given a parent while it mutates what it makes — so region-scoped substitution through the parse is unavailable until a reading stops writing to what it composes, which is a design question rather than a patch. It surfaced turns after the change because nothing drove the demo in between, and no test renders a book — the fourth filing of a green that exercised nothing. DISCHARGED 2026-08-12 in The Parse: the law still holds and its CONDITION no longer does, because Doug's answer was to remove the writing rather than work around it — nothing carries a number (position answers, and a number is what a REFERENCE holds) and mentioning propagates BY LINEAGE rather than by assignment, which makes this defect's fix and mention-propagation one mechanism instead of two. With nothing written the parse threads lineage and both drivers stay green at 51 and 25 checkpoints. AND THE SECOND WRITE WAS NEARLY MISSED: the repair's plan counted only the number, and rereading THIS CHAPTER while planning surfaced part.$role = 'mention', which fires for the same reason — caught before it could take the drivers red a second time, which is the whole return on filing a defect.
17. [The regex that remembered where it stopped](17-the-regex-that-remembered-where-it-stopped.md) — **the page's word count moved 475 to 578 with no change that should add words; a word typed inside an unclosed fence was counted as writing and took the driver red; and the facing-page comparison DISAGREED WITH ITSELF ON SCREEN, 21 words against 30, while the unit suite comparing THE SAME TWO OBJECTS reported them equal** — three theories fit some of the evidence and none of it, and the row that should have redirected the search immediately was the last one, since a test and a screen disagreeing about the same objects is not a disagreement about the objects. A MODULE-LEVEL /…/g REGEX CARRIES lastIndex BETWEEN CALLS, so the first section parsed left the cursor wherever its match ended and every section after it was divided from the middle — one fact producing all three symptoms at once. The code it replaced did NOT have the bug: the demo built the expression inside the function with new RegExp, and hoisting it to module level read as tidying while it was hoisting STATE. Fixed by building it per call with the reason in the source so nobody tidies it back. THE RULE IS NARROW ENOUGH TO APPLY WITHOUT THINKING: if a regex is used with .exec in a loop or with .test, build it where it is used — const says nothing, since the binding is constant and the cursor is not. AND THE TELL IS WORTH MORE THAN THE RULE: a defect whose symptom depends on HOW MUCH WAS PROCESSED BEFORE is state that outlived a call, and a suite misses it because a test builds one object and asks one question while a page builds many and asks in order.
18. [The checkpoint that compared a number to itself](18-the-checkpoint-that-compared-a-number-to-itself.md) — **a driver checkpoint passed on its first run and every run after, and was reported to Doug as evidence — 'the model reads at every altitude and the count cannot move, 260 words as paragraphs, 260 as words' — and there was nothing that could have failed it.** Doug read the sentence and asked what it meant, which is how it was caught. WATCHING THE GATE GO RED WOULD NOT HAVE HELPED, and that is the point: breaking the parse would have moved both numbers together, so no breakage reachable from the code could turn it red. The view rendered ONE GETTER beside four different lists — switching altitude changed the ROWS and never re-derived the COUNT — so the driver compared the result of one expression to the result of the same expression. The claim it appeared to make was real and worth making; the claim it ACTUALLY made was that a getter is stable, and the sentence in the report was accurate about the numbers and false about what they showed. Fixed by having each altitude WALK ITS OWN COUNT four different ways down the model, plus two checkpoints that CAN fail — the rows must differ at every altitude, and the word altitude must print one row per word — driven as 260 words through 4 sections, 11 paragraphs, 17 sentences, 260 words. THE LESSON: a checkpoint that cannot fail is not a checkpoint, and the question the runner cannot ask is WHAT WOULD HAVE TO BREAK FOR THIS TO GO RED. The shape to look for is an identity dressed as an agreement — two things corroborate only when computed by DIFFERENT PATHS, and a corroboration test must be able to name TWO WALKS.

[The rule that was typeset as mathematics](19-the-rule-that-was-typeset-as-mathematics.md) — **a horizontal rule in prose was being typeset as display mathematics, and a turned page opened nine pixels down — both live, both deterministic, and both shipped green because no gate that ran could fire on them** — filed together as one mechanism wearing two faces: a gate's scope includes WHAT IT RAN AGAINST, and content and timing are both part of that. The framework was cut back so $Figure is the thing added at paragraph grade, with drawn() returning nothing and a subclass overriding only that; the demo had been drawing every figure through katex, so once no kinds shipped beneath $Figure every figure the notation produced landed in the mathematics path — a picture, a rule, anything. BOTH DRIVERS WERE GREEN AND BOTH WERE RIGHT: 51 checkpoints and 25, and not one driven page contained a '---'. It was found by writing the fix for something else, because rendering a rule for the first time is what made it appear. The second, caught in the same run: head() reset the scroll in a setTimeout(0) that could land before the turn had PAINTED, while light() leaves a smooth scrollIntoView still animating that carries the fresh page down after the reset — latent for as long as the guess about ordering happened to win, and this sprint's extra render work is what made it lose; it waits two frames and JUMPS now, confirmed by running both drivers twice, because a race that stops reproducing is not a race that was fixed. This is chapter 14 one turn further out — there the gates were not checking and said nothing about it, here they were checking correctly over material that could not exercise the defect. THE CHEAP FIX IS CORPUS, NOT ASSERTION: one rule and one formula on a driven page would have caught it the day it landed, and neither costs a checkpoint. And a timing guess is a defect that has not fired yet — setTimeout(0) against a render is a claim about ordering that nothing enforces.
20. [The narrowed prop that disowned its base](20-the-narrowed-prop-that-disowned-its-base.md) — **adding one property to one class produced thirty type errors, none of them in that class and none of them about that property** — they named canonical, parts, where, select, single and at, six members apiece across five classes nobody had touched. The property was $role, declared to say a reference MENTIONS its referent. AS CONST WAS A RED HERRING and believing it would have filed the wrong rule: the first reading was that as const narrows the property out of reach of the $ machinery, which is plausible, makes the errors go away, and is wrong — tested by predicting the general case and checking it, since $role?: 'mention' = 'mention' gives the same thirty at the same sites. ANY narrowing does it. The mechanism, read off the compiler rather than inferred, is the indented chain that tsc --pretty false prints: a $-prefixed member feeds the COMPUTED PROPS TYPE, every chemical answers a component, and a component is a function OF ITS PROPS — so props are CONTRAVARIANT, a narrower props type makes the component less assignable, the class stops being assignable to its own base, and every member whose type mentions the chain fails at once. Thirty errors are ONE relationship broken and reported everywhere it is mentioned. So a widening declaration is load-bearing: $role?: Role is not ceremony around a value that is always 'mention', it is what keeps the subclass a subclass — declare a $ prop at the BASE'S type, never at the value's, because the narrow fact belongs in the initializer, which is not part of the type. This is chapter 06 at compile time rather than runtime. The diagnostic habit is worth more than the rule: read the indented chain, not the top line — the top line named canonical, and canonical had nothing to do with it.
