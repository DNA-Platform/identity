The standing register of every questionable part of this branch's code — **organization, names, semantics, implementation**, which are [Doug's own four axes](../projection/20-the-audit.md) — each entry carrying the line that shows it and a verdict that can be argued with. Commissioned 2026-08-21 out of one sentence: *"I am worried that I lost track of the code in this repository… we have lost the high level design goals and things have gotten muddy."* **This book is the muddiness, itemized.**

It exists because **`lib` is an application development framework built on a first-order theory of semantics, identity, cognition and consciousness**, and *code that exemplifies a formalism has to be flawless in a way that most code does not* — **every place the code says something the theory does not is a place a reader learns the theory wrong.** That is the standard every entry is judged against and the only one.

**It is not [Solutions](../solutions/.cover.md) and it is not [Projection](../projection/.cover.md).** A thing that is simply wrong and can be fixed is a **defect** and goes to Solutions, indexed by its symptom — *Doug drew that line himself: "it's a bug. And a good one. But it's not a wart in the framework."* Projection indexes the work by **time**. This book indexes it by **kind**, and none of the three answers another's question.

**Entries carry stable identifiers — `O1`, `N7`, `S2`, `I13` — that never move and never get reused**, so the sprint record can cite into them without breaking. And it is written to be **edited, never appended to**: a resolved entry gains its resolution in place, so a reader always meets the current state rather than an archaeology of one.

*The name is a proxy standing for Doug's correction. A **condition report** is what a conservator writes about a volume before it is worked on — an itemized record of every defect and questionable area, made so the work can be planned. His own incumbent word is **wart**; a third candidate is **collation**.*

## Chapters

1. [How to Read This](01-how-to-read-this.md) — The frame that makes the rest legible, and the most useful chapter for anyone picking the code up cold. Doug's four axes and what each kind of fault costs. THE FRAMEWORK HAS FIVE STRATA AND THEY ARE DATABLE, read off git: the founding on 2026-07-27, THE WRITING SPINE ON 07-31 WHICH IS THE BEST CODE IN THE PACKAGE, the apparatus on 08-02/03 at eight classes in one day, the filling-in…
2. [Organization](02-organization.md) — Where a thing sits and whether it is alive at all, which is the axis no test can reach. NINE ENTRIES. Three files imported by nothing, swept properly across all four programs — a zero-byte Literature.tsx that is a name the derivation uses and a promise the package has not kept, a 198-line teaser written and abandoned in one day, and a 152-line case-shell.
3. [Names](03-names.md) — Roughly two hundred and fifty member names extracted and judged one by one against the semantics of libraries and books. THIRTY-ONE DO NOT FIT AND SIX COLLIDE, against a large majority that do — and that ratio is the argument for striking the exceptions rather than tolerating them, because a near-consistent vocabulary is damaged more by one wrong word than an inconsistent one is by twenty.
4. [Semantics](04-semantics.md) — Where the code says something the theory does not, which is the axis that matters most and the one nothing can test, because a class hierarchy that contradicts its own derivation compiles perfectly. FIFTEEN ENTRIES, each citing the passage it disagrees with. THE THEORY'S TWO CENTRAL CLASSES DO NOT EXIST.
5. [Implementation](05-implementation.md) — Mechanisms that are not obvious, not precise, or not swappable, judged by Doug's own test: could an implementer swap one kind of functionality for another without fighting the framework, and does the mechanism read as inevitable to somebody who has not been told. TWENTY-ONE ENTRIES, and almost every one was written between 2026-08-19 and 08-21.

[The Cleaning](06-the-cleaning.md) — The work, ordered, out of Doug's ruling: clean the new stuff — and the chapter now carries FOUR THINGS, which is what a register owes a sprint that has to start from it. [The Three Codebases](07-the-three-codebases.md) — Doug's ask to compare the chemistry code, the early framework code and the compiler code, answered by measuring rather than by impression — and the only chapter here that registers DIFFERENCES rather than faults, because the finding is that three codebases written by the same team answer the same question three incompatible ways.
