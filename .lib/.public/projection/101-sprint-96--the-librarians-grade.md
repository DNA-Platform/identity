### <a id="the-standard"></a>The standard, read — styled-components' own words, fetched 2026-10-01 from its documentation

- **The unit of style is the component.** Motivation: *"every bit of styling is tied to a specific component."* A look is extended by wrapping — *"To easily make a new component that inherits the styling of another, just wrap it in the `styled()` constructor"* — and composed by reference: *"Whenever a component is created or wrapped by the `styled()` factory function, it is also assigned a stable CSS class for use in targeting… without having to fuss around with naming and avoiding selector collisions."*
- **A global sheet is for resets and base typography.** `createGlobalStyle`: *"a special StyledComponent that handles global styles… things like CSS resets or base stylesheets can be applied."* Nothing more is said for it; the rest of the library is about components.
- **A theme is values, provided by context, read in interpolations.** *"Injects the theme into all styled components anywhere beneath it in the component tree, via the context API"*; `color: ${props => props.theme.main}`; a nested theme is a function of its parent's; a `theme` prop overrides.
- **`attrs` is for a prop every instance has**; *"pass props directly when every instance needs a different one."*
- **A styled component is declared once.** *"By declaring a styled component inside the render method… you are dynamically creating a new component on every render"* — the per-definition cost that [Solutions 99](../solutions/99-the-sheet-that-was-one-file-per-page.md) met per bond.

### <a id="where-we-stand"></a>Where `.public` stands against it

| the standard | `.public` today | the cost paid |
|---|---|---|
| a look is a component | **a Format is one** — a styled component in a field, its mark through `attrs`, Bold, Emphasis, Underline and the Reference's anchor the same; **a kind of writing is not** — Paragraph, Section, Title draw a plain element with marks and have no component of their own | a kind cannot be dressed by wrapping it; it is dressed by a selector against its mark, from a sheet |
| a global sheet is a base | **the Theme's sheet is the dress of every kind**, a hundred rules on the framework's side and a hundred more on the library's, with three cascade layers invented to order them against the Formats' | the layers exist because style is not componentized; [Solutions 80](../solutions/80-the-rules-that-won-by-counting-classes.md) and [68](../solutions/68-the-value-that-was-said-twice.md) are its collisions; a library's look is one long sheet, which is his fear |
| a theme is values | **the Theme is two things in one class** — the eight values, handed down as custom properties so a write moves one declaration and regenerates no class, which is better than the standard's re-render; *and* the base sheet | "is it valuable to have a theme?" — yes, as the first thing; the muddle is the second thing living in the same class |
| extend by wrapping | a library extends the sheet with `selection(this.style as …)` and reads values through `at()` because the type says they may be absent | the cast and the helper in every library's theme — the fight the first row found |
| never declared where it is made again | kept, since U8 | — |

### <a id="the-design"></a>The design, 2026-10-01 — his, said in the standard's terms, a trial struck on the way

**His rulings, in order, the same afternoon:** *"We ARE using styled components, so let's use them right."* · *"Can't we have both? Format adds classes and styles, and overriding can happen at either layer?"* · *"The classes don't have to be removed for the styled component to target locally with them."* · *"It shouldn't be so hard to write styled components to override the format of components. Just subclass an annotation and rewrite its style."* · *"No you don't need DI!"* · *"Just rewrite the annotation and use yours!"* · *"Style the semantic compositions in the theme, but for the annotations, shouldn't we make them self-contained?"* · *"The right way ISN'T one per page."*

**The standard, as people develop with it:** one styled component per kind of element rendered, declared once at the module's top, never per page and never per instance; one `ThemeProvider` at the root holding tokens, a second only to change tokens for a subtree; one global style at the root for the reset and the base typography, which in a content application is treated as part of the theme; a component with a box of its own carries its own rules and a parent styles a child only by referring to the child's component inside its own template; overriding by wrapping, or by writing your own and using it in place.

**Read onto a book, which is his design:**

- <a id="the-design-theme"></a>**The Theme is the provider and the base typography.** Its sheet keeps the rules for the levels and the kinds — what a paragraph, a title, a heading, a line look like in this book — since that is the document's typography and the standard's own place for it. It stops carrying any annotation's layout. A library overrides it as it overrides any Format: a subclass that rewrites or extends its `style`, which is how Libby's two themes already stand.
- <a id="the-design-annotations"></a>**Every annotation is self-contained.** A Format's rules are its styled component, as now. An annotation that lays out or dresses what it marks — Table's grid, List's items, Cover's card, Paginated's hidden pages, the Reference's anchor — carries its own rules for its own marks, and the book's theme expresses them, since the book is what expresses global style. The Theme's sheet no longer comprehends every `pa-` mark; each annotation does. *The one mechanism to decide with the code open: how an annotation with no layer of its own declares its rules and the book's theme gathers them, once per class, so that a rewritten annotation brings its own.*
- <a id="the-design-override"></a>**Overriding happens at either layer, and needs no registry.** A library restyles a kind in context by a Format whose styled component targets the kind's mark locally, under its own class — the marks stay on every element for exactly this. A library restyles an annotation by subclassing it, rewriting its `style`, and writing its own into the chapter in place of the original. The layers keep the order: a Format's rules beat the theme's.
- <a id="the-design-type"></a>**The theme's type says what is true.** The eight are present beneath a Theme, which every book has; the index signature that typed everything as `unknown` goes; `at()` and the cast go with it. The augmentation stays in the theme's own file, where a library's declarations are bundled from.

**The trial struck.** U7 componentized Paragraph — a seam on Writing, a styled component per kind, `styles` on the Theme — and was built to 342 of 342 with every page at 0 pixels before his rulings arrived; it was the standard read wrongly, moving the document's typography out of the theme where the standard keeps it, and adding a mechanism, `styles`, that subclassing already is. Taken out of `src` whole the same hour, `git checkout`, the tree clean at `23cae31`. What it taught is kept: a kind's component rules must open with the layer order statement or the layers invert by injection order; the pair must replace a kind's own element as it replaces a span; and a promise that draws a writing bare draws it under no theme.

### <a id="the-recommendation"></a>What I had recommended before his rulings — kept as the trail, superseded by the design above

**Componentize the kinds, and let the sheet be a base.** Every kind of writing declares its styled component once per class, as the three basics do today — `selection.p.attrs({ className: 'pd-paragraph' })` with its look read from the theme's values — so a kind's look is its own, extended by wrapping and replaced by a subclass registered for a book, which the `$` registry already does per book. The Theme's sheet reduces to what the standard says a global sheet is for: the reset, the base typography, the four invariants. The marks stay — on every element, for the DOM's legibility and for the exotic case a sheet must reach — but dressing a kind by selector becomes the exception rather than the way. A Format is unchanged. The eight are typed present beneath a Theme and the sheet's extension needs no cast, since a kind's component is typed by the kind.

**What it answers of the rows:** the figures' elements become the figures' components, `pre`, `img`, `svg` each a styled tag with its mark; the cast and the helper go; the first paragraph of a section and a paragraph of lines are marks a class adds in its own semantics, on his ruling, and then rules in the Section's and the Paragraph's components rather than a library's sheet; the explorer's layout keeps its grid, as a Format, and the open and opened marks come from a Book and a Chapter subclass that work together, on his ruling, with nothing written across in `defines`.

**What it costs:** a styled component per kind, 103 fields; the change of Sprint 95's D2, which put a kind's look in the sheet, ruled 2026-09-30 and now read against the standard; a brainstorm of its own, since it is the shape of every library written after.

**And what it would not be:** a wart over the most important classes to remove minor warts elsewhere — the test is [the grade](../the-coding-style/07-what-natural-means.md#the-grade) read again in Libby's library once a kind is componentized: does her theme get shorter and say less, or does she write a subclass per kind where one rule stood? *That is measured before it is adopted, on one kind, Paragraph, in a trial.*
