## What the room held — the finding

**The two passes that read the notation read different text.** The scanner ran the language's one regex over a file's **whole source**, with a line helper of its own; the transform parsed the same file with TypeScript and scanned only the tree's text nodes — JSX text by the JSX rule, strings as written — splicing by offset. **Probed 2026-09-28, over five spellings in one file:** `// [[ A Ghost Title ]]` in a comment, `import x from './[[ A Path ]]'`, `title="[[ In A Prop ]]"`, `{'$[ In A String ]'}` and `[[[ In Prose ]]]`. The scanner catalogued the comment and the import path as titles; the transform never saw the comment. Since a chapter is named by the first title form in its file, a comment above a chapter's title would have named the chapter, silently.

**And the transform read a literal.** The `references` plugin dropped a module's query before asking whether it was a `.tsx`, so the raw module the assembly imports for an Append — one string literal holding a whole file — was scanned like a chapter and a `$[ X ]` in it compiled. *Read from the code when this was written, and shown on a real page by the build: [Solutions 96](../solutions/96-the-literal-the-transform-modified.md).*

**Measured before the research, the test library's 46 files:** the parser 28.1 ms cold and 7.7 ms warm; the regex over the same source 0.3 ms, 128 forms. TypeScript 5.9.3. *A first count said 60, a shell-quoting artefact.* What TypeScript gives, and what the transform's parse already cost, are in [the research](../the-catalogue-and-the-specification/10-reading-tsx-with-the-compiler-api.md). The rules that bound the sprint: the compiler reads files and the notation, never a tag; it enforces as much as it can from what it gives; its register is the binder's — [The Binder, As Built](../the-catalogue-and-the-specification/07-the-binder.md).

## <a id="plan"></a>The plan — the register

*Three approaches stood at mechanism altitude: the parser locates and the language reads, which was taken and which Doug described himself as "a step after the parse that goes through the valid places"; a scanner of our own over TypeScript's, measured and not built; the regex over raw source with comments masked, rejected. The plan was sized before it was divided — the scanner 56 lines, the transform's walk 25, the line helper 12 — and ran in one session. Decisions and units are kept one line each; the test scenarios became the suite and the risks are stubbed below.*

### Decisions

**D1** one reading module in the catalogue, `catalogue/source.ts`, parsing a file as TSX and yielding its text runs — kind, absolute `from` and `to`, the raw slice — and the line of any offset; the scanner and the transform both take the runs. **D2** what is read is JSX text, string literals and templates with nothing substituted, nothing else, a form anywhere else silent — *settled by Doug's approval of R1 as written.* **D3** the parse held with the structure's reading, keyed on modified time and size, invalidated by the watcher; the transform taking the held reading when the text Vite hands it is the text held; incremental parse measured, not assumed. **D4** lines the parser's. **D5** two performance rows, `parse` and `regex over raw source`, and a count of parses cold and warm. **D6** no fork; within a run the forms found by the regex or by TypeScript's scanner as the research measured, an edit a splice by position unless the printer round-tripped — *decided by the research: the regex, the splice.* **D7** the design of record edited in the same sprint. **D8** a raw module is a literal and the transform leaves it alone; the structure still reads the file for the references it spends.
