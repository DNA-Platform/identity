**What the catchup found standing.** Every book of his already ends its table of contents in a section said to be the appendix, headed *How this book is built*, listing its machinery; the base book reads those sections for the chapters it keeps out of its pages, and the layout puts a built class on the book when the open chapter is one of them. ## His rulings, verbatim and in order

1. **The view.** *"It would be a view for a collection of chapters. Presumably the book would have to support this mode, but for those chapters, we might imagine that they can declare themselves in some reference manual, by name, and then the table of contents knows how to surface the reference manuals, and then in each reference manual, only a fraction of the table of contents tree is showing for the chapters in the manual… We need to plan it, and ideally, it would be very annotative, and the same table of contents is present for the reference manuals, it just knows how to adapt to a context. Can we imagine this? I don't know if it is different views but it sure could be."*
2. **The part.** *"A section in the table of contents, and perhaps all chapters be annotated with a `<Part>` annotation specifying parts of the book, with a name that says what part they are in. And the table of contents knows how to organize itself into parts. For manual chapters or reference chapters or whatever elegant name you come up with, the part with give cohesion to the manual."*
3. **The trait.** *"On the chapter. It is a trait that specifies a type of chapter. And then, if convenient, one can wrap that trait in a chapter type, but that is harder to adapt. I would say keep it at the trait level. In fact, a Manual can be a type of Part! So it is a specialization of an annotation but it can be done with inheritance."*
4. **The look.** *"Yes a format the trait brings, though we want the manual and this to be the same code. We duplicate nothing. Perhaps the reference manual is just a book where everything is in one reference manual, with maybe some special classes to help with the case where everything is one. Does that make sense? This shouldn't be two things."*

**Two earlier rulings fix where the drawing lives, and were cited before any approach was offered:** *"The purpose of a book is layout"* and *"Why would the annotations a chapter has affect what a book decides to do with it in its view?"* — [How a Book Is Built](../writing-a-book/00-02-how-a-book-is-built.md). So the base book reads the trait and draws; a part never draws.

- <a id="d2"></a>**D2. - <a id="d3"></a>**D3. The reference manual has no parts: every chapter says it is a manual, and the book is its body.** *Struck and rewritten 2026-10-09 on his word after the probe — "A chapter shouldn't require a part. The implementer should be able to add the Part name to every chapter, or to put headings in their table. And then yes, they have trouble with name collisions. But it is not mandatory. It is not that a part HAS none. It is that it requires none. And I am worried that your notes are too myopic. The point is that the implementer is FREE to integrate parts as desired, and the way we are doing parts for Reference Manual is a whole different view."* **So the notes say freedom, not prohibition: a heading that names a part is allowed and wears an id as any heading does, the collision the implementer's; the part's name on every chapter is allowed; a tree, a list, a hand-written table are allowed; and the reference manual's view is one view among any.** *And of that view, his:* *"But in the reference manual, clicking the thing in the table that represents the manual itself would probably take you to the first chapter in the manual right? The parts place would be the UI context of the reference manual, but the literal place it takes you is the first chapter of the part."* **So in the manual's tree, the row that stands for a part is a press that turns the book to the part's first chapter; the part's place is the context the tree gives it, the folder open with its rows; and the literal place is the chapter. - <a id="d11"></a>**D11. The package assumes nothing about which chapters are in parts: a chapter surfaces its part or none, the table groups, and whatever reads parts filters by checking.** *His design, 2026-10-09, when the catalogue's entries were found outside the all-or-none rule by an accident of the table's `chapters` set and a truer set was put to him:* *"You still don't understand that we WANT the special chapters as chapters. ## <a id="the-probe"></a>The probe, 2026-10-09 — his words, and what the code answered

**His rulings while the probe ran, verbatim, all part of the reference manual's design story.** *"I don't know what a leaf is.
