## Where this sprint comes from

**Doug, 2026-09-28, verbatim:** *"I also want you to migrate your code comments out of figures and .public in general, and into the documentation, as you document how .public is supposed to be used to implement libraries. Your classes are simple but very powerful so you can document them. Make sure how to have a clear back and forth between the code and docs so you have an easy time documenting. And of course, in Libby's library, put the documentation in the library to prevent such issues."*

**The issue he means was shown on a page the same day:** the manual's Code figures print a file exactly as written — [Solutions 96](../solutions/96-the-literal-the-transform-modified.md) — so a tool file that carries a comment explaining itself prints that explanation beside Libby's chapter explaining the same thing. The documentation belongs in the library; the file prints bare.

## What the room holds — measured 2026-09-28

**`src` carries 23 comment lines in 47 files, all of them in `figures`:** `Figure.tsx` 7, `Append.tsx` 7, `Code.tsx` 4, `Svg.tsx` 3, `Image.tsx` 2 — each the class's purpose and Doug's words, written with Sprint 89; the other 42 files are bare already. The [Figures](../figures/.cover.md) book's three chapters hold what the comments say, written the same day, except one stale line: `Image.tsx` says the binder imports a picture as the bundler emits it, and since [Solutions 95](../solutions/95-the-picture-that-came-from-the-dev-server.md) the binder copies the picture beside the pages and the Append's text is its address there.

**The test library carries about 120 comment lines in 26 files:** the manual's five tool files (36 lines, each tool's account of itself — the book, the theme's `at()` and sheet, the running head and byline, the catchword, the four faces), the manual's own chapters and door (16), and every other book's apparatus and chapters (the library's cover, table and Of Libby; Libby's book, cover and two chapters; the persona's book, cover and poem; the paper's book and argument; Some Projects' book, table and The Work). Each says what the file shows of `.public` and quotes the ruling behind it — the content of Libby's chapters, standing in the code.

**One wart beside them:** `projects/.table.tsx.tsx`, the drawn table's `$Entries` section from Sprint 84, imported by Some Projects' table. Since Sprint 89 a file named a chapter's name, one character and more is a file accompanying that chapter, so the inventory reads it as an Append on the table with the identifier `tsx` and the type `.tsx`. It binds, and it is wrong.

**The rule already in force:** [How a Class Is Documented](../the-coding-style/08-how-a-class-is-documented.md) — one book per folder, one chapter per class, four parts; *"The chapter links to the code and the code never links to the chapter"* — Doug's own ruling, *"You are supposed to use reference documents in the branch that LINK to the code"*; a class is done when its code carries no comment. And the register of a library's own code, [the cleanup skill](../../../../.claude/library/our-skillset/35-cleanup.md): *"The code carries no comments. Everything a comment would have said belongs in the chapter standing beside it."* Measured 2026-09-28: **six class files in `src` have no chapter whose name carries theirs** — `writing/Means.tsx`, `Mention.tsx`, `Reference.tsx`, `Referent.tsx`, and `utilities/Binder.tsx`, `Html.tsx` — and the writing and utilities covers name none of the six; the other 41 correspond by name. The correspondence exists for most of the tree, nothing checks it, and where it fails a class is documented nowhere but its sprint record.

**And the wart, run rather than read:** the account of Some Projects returns `.table.tsx <- .table.tsx.tsx id="tsx" type=.tsx`, and nothing unaccounted.

### Decisions

| | decision | why, and what it was chosen over |
|---|---|---|
| **D1** | **The way back from code to docs is the correspondence by name, checked by a tool we maintain, designed for how we get around.** From a file, its chapter is the book named for its folder and the chapter whose cover entry names its class; from a chapter, its header links the file; grep for the class's name across the branch library finds every mention. The tool proves every class has a chapter and every chapter a class, and prints what fails. No line enters the code; the ruling of 2026-09-22 that the code never links to the chapter stands. | Doug, 2026-09-28, handing it to us: *"Whatever it is, be prepared to maintain it. And it should be designed for you to navigate. You have the cover. You have grep. How do you like to get around? How do you know to move back and forth between the right part of this and the code? Hopefully you see that the library itself is the view for the documentation, so it is clear where all code is documented. A library can be used to lend identity to a codebase, but notice that the documentation is the primary source and the code are documents to be considered."* **That last sentence is the principle, and the later sprint's seed:** the code files are documents the library considers, the way a chapter's accompanying file is — [chapter zero](00-planning.md#the-code-library). And for now, his word on the direction: *"For the regular code, we have the documentation library sadly detached, so we have the branch point to the code."* |
| **D2** | **Each figures comment is routed to its chapter's part before it leaves:** the class's purpose to *What it is*, a quotation to the citation column, a rule of use to *How it is extended*; the stale line in `Image.tsx` corrected in the chapter to the copy beside the pages. | Move first, then remove — [the cleanup skill](../../../../.claude/library/our-skillset/35-cleanup.md) on comments; a comment deleted with nowhere to go is reasoning lost. |
| **D3** | **The checker is a tool beside How a Class Is Documented,** `08-how-a-class-is-documented--check.ts` — a PROXY — in the team's convention of a tool beside its chapter; it reads `src` for exported `$`-classes and the branch library's per-folder books for chapters and the files their headers cite, and prints the failures as diagnostics in the binder's form. | The compilation catalogue's convention; a check that lives with the rule it checks. |
| **D4** | **Libby routes the test library's comments herself,** each to the chapter that documents the thing: a tool's account into the manual chapter that prints it, a book's into the chapter that says what the book is — The Books I Keep already says what each book shows — the persona's and the paper's into their own covers' chapters, the ghost-title comment in The Work kept as the one fixture the structure's promise reads. | Her library, her first person; [Autonomy](../../../../.claude/library/teamspeak/05-autonomy.md). |
| **D5** | **STRUCK by Doug. `projects/.table.tsx.tsx` stays as it is: a file accompanying the table with the identifier `tsx` and the type `.tsx`, which is what the rules say and what he meant.** Its comment moves into Libby's prose with the rest; a resource on a table of contents is supported, not corrected. | Doug, 2026-09-28: *"Hmm, you gave a resource to the table of contents. Bold... Not sure it's right but interesting and should be supported… in our world .tsx.tsx is just something that has identifier and type as tsx independently. No need for a hack!"* The plan had called the account's reading a wart; the account was right and the plan was wrong. |
| **D6** | **Code highlights its syntax, HTML included, by an annotation and an outside library — designed here, built on Doug's yes to the mechanism.** *The sketch:* a `Highlighted` annotation said of a Code figure, a Format whose layer tokenises the letter's text with highlight.js — already among the package's dependencies — into spans wearing token marks, the language an attribute or read from the append's type, `.tsx` highlighting its markup as part of the code; the default sheet gives the token marks colours from the theme's ink, and a library's theme overrides them. The figure stays a literal; the annotation expresses the highlighting, which is the annotated version's own power. | Doug, 2026-09-28: *"We should support syntax highlighting in code, we should support html as part of code."* An annotation rather than a member of Code, because a Code figure without it prints plain, and because *"adding annotations, and integrating with outside libraries"* is the shape he named for the brainstorm. **His yes owed on the mechanism before a line of `src` moves.** |
