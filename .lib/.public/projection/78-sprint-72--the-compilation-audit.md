## <a id="plan"></a>The plan — ***guardrails, 2026-09-15***

### <a id="decisions"></a>Decisions, each with what it was chosen over

- <a id="d1"></a>**D1 — Resolve follows specify; no task is added.** The order becomes `configure · inventory · assemble · specify · resolve · bundle · render · record` — `assemble` ahead so the modules exist to load, `resolve` after because a name read from the running book cannot exist before the book is loaded, and the specify child is the one place every book already is loaded. *Chosen over a new load task (a third construction of every book — Doug: "It's expensive") and over keeping names from folders (his word: "reading the book names from the running app").* This is the field's one lifecycle — load content once, derive routes and pages from what was loaded — said in the binder's words.
- <a id="d2"></a>**D2 — The graph is what the load answered, written once beside the manifest.** The specify task writes one record per book — its folder (the key), and what the live book answered: `title`, `name`, author, subject, the files vite loaded to construct it, a digest over them, and the writings the specification reached — into a JSON file beside `.manifest.json`, in the manifest's own at/read/write shape, on the sync's kept list, committed as the manifest is. Every later task, and the next build, reads it. *Chosen over a module under `application/` (no page reads it), a vite virtual module (the binder writes files a person and `tsc` can read), and a third loading of the books (the render still constructs each book once per route, in production, as a reader's browser will).* The folder is the key — module, scope, record — and the title is the name — route, page, uniqueness. **The binder reads `book.name` and `book.title`; it never derives a name of its own** — the old dot-stripping `nameOf` is deleted with nothing left that strips dots.
- <a id="d3"></a>**D3 — The library's specification is the framework's `Specification` over the dataset, in `.binding/specification`, with two runners — [his ruling](#r-rules).** `LibrarySpecification extends Specification<Graph>` in `specification/library.ts`: `@specify` methods and `$check`, the code that already enforces every rule in the package, now over the graph — which is the dataset, the list of every book's name, title, author and subject. A new rule about *what it means to be a library* costs one method. Two things run it, separate on his word: **vitest** — `library.test.ts` reads the graph and makes one promise per rule from `rules()`, so `npm test` in any binding lists every rule of the library by its description, and a library adds its own by adding a method (the viral binding); and **the build** — the specify task runs the same rules in a development child once every record exists. A rule's message opens with the book's folder and `›`, the convention Sprint 71's descent set for a failure's place, and the runner lands it on that book's first file in the compiler's line shape. Two rules this sprint: a book's name is not empty; no two books share a name — the second quoting both titles and both folders. *Chosen over plain functions at resolve (not the framework's word for a rule, and a person cannot extend them from a test file) and over U6's `$Library` kind in the package (a package change; `$Library` already means a book's reference to its subject's library in [The Subject](09-the-subject.md)).* No `src` line. The environment hazard — `Specification.check` answers nothing under a production shell — is closed by where it runs: every runner under `specification/` runs in development, as Sprint 71's children do.
- <a id="d4"></a>**D4 — Author and subject relationships are readings this sprint, not rules.** Every demo cover writes its author and subject as text — *Wikipedians*, *Scott Aaronson*, *Knowledge* — and none names a book. So the graph records the text, and resolve reports the edges it can read — a record whose author or subject equals another's title — as counts on its line, without inventing what an author or subject must name. *Chosen over a rule both demos would fail on day one, and over a reference convention between books, which is `$$Synopsis`'s ruling (Sprint 71: "This will be the sense in which the book is catalogued").*
- <a id="d5"></a>**D5 — The walk descends everywhere, excludes by name, and a book beneath a book is a book.** A folder whose *name* is in the never-set or in `inventory.excludes` is skipped at any depth — "specify exclusions, one of which is .public" with no new field; a folder holding `.book.tsx` is a book, its key the path from the library with forward slashes; the walk continues beneath it; a nested `.book.tsx` is its own book with its own flat route, never a chapter of the outer one (Sprint 37: cataloguing, not nesting — "the inner book keeps its own route"); the library root's `.book.tsx` is the base and never a book. *Chosen over excludes as paths (a second shape for one idea) and nested URLs (names come from titles, not paths).*
- <a id="d6"></a>**D6 — The cache is a digest per record, decided in the parent, printed every build.** Before any child is spawned, each book in scope whose record's files still hash to its digest is carried unchanged; the rest are loaded. The digest covers the files vite loaded for that book — its own, the base `.book.tsx`, any other book's `.book.tsx` it extends, its assembled module — and the binding's fixed inputs: the two packages' resolved entries and the child's own code. `.pubconfig` is out (root and excludes are recomputed every build; no record's answer depends on it). The task line prints *N loaded · M unchanged · W writings specified* every build, because a check that stopped running is indistinguishable from one that started passing. Deleting the graph file is the reset. *Chosen over a graph-level version (a `design/` edit would reload every book) and over a mtime (bytes are what changed).*
- <a id="d7"></a>**D7 — One child, one spawner; per-book children stay.** The two identical vite bootstraps (`specify.mjs`, `render.mjs`) become one child that loads a named module; the two spawn loops become one function. A child per book stays the default for specify, because each book's `.book.tsx` registers its theme on the shared `Book` class at module load and the render is isolated per route for exactly that reason; one process for all books is a later, measured unit. *Chosen over a long-lived server holding every book (unmeasured against the registration hazard and chemistry's process-wide chemical map).*
- <a id="d8"></a>**D8 — One generated index.** `application/books.ts` is deleted; `routes.ts`, written at resolve from the graph, carries each route's loader inline; `main.tsx` already reads only `routes` and `root`. The assembled module exports the ordered list of files it was built from, so a failure's first index maps to a chapter file by reading, not by rebuilding the order. *Chosen over keeping two indexes keyed two ways.*
- <a id="d9"></a>**D9 — `inventory.root` names the folder as written — pending [ruling 2](#rulings-owed).** `.encyclopedia`, `aaronson`: stable, filesystem, known before any load. *Chosen over the title's slug (a title in the inventory slice, known only after the load).*
- <a id="d10"></a>**D10 — The audit is a register in this chapter and fixes in the refactor.** What the reading found wrong or doubled in Sprint 70–71's work is listed once, each with its line and its disposition — fixed in a unit here, or recorded for Doug. A defect with a symptom goes to Solutions.

- <a id="d11"></a>**D11 — What is read off a book is a set of members, not a hard-coded list — [his ruling](#r-scale).** *"The code needs to scale to more rules and more information that we can pull off the objects, like we are doing with book names."* So the child does not spell `title, author, subject`: a class in `specification/` holds one member per fact, each answering data from a live book, and the record is what its members answered — collected the way `Specification.rules()` already collects rules, through the prototype chain, so a library that copied the binding adds its own by subclassing. **A new fact about every book costs one member; it costs no new pass, because the book is already loaded.** *Chosen over a fixed record shape (every new fact would edit the child, the type and the graph).*
- <a id="d12"></a>**D12 — Expensive per book and cached; cheap over the set and always.** The split Doug predicted — *"It might need to be two separate things"* — falls out of what each thing reads:

  | | the gathering (D11) | the specification (D3) |
  |---|---|---|
  | reads | one live book | every record at once |
  | costs | a book load — seconds | data — microseconds |
  | runs | once per changed book, kept by digest | every build, and in vitest |
  | grows by | one member per fact | one method per rule |

  **So more rules are free at any library size, and more facts are free after the load that was already being paid.** A rule can only ask what a reading gathered, which is the price, and the right one: a rule that needs a new fact names the reading it needs.
- <a id="d13"></a>**D13 — Books are read in batches, one process each; drawing stays one process per page.** *Measured 2026-09-15:* a child costs **2.0–3.1s before it reads anything** (vite 0.7s, `createServer` 0.3s, happy-dom 2.2s), then the first book pays the package load — **turing 6.7s, then `.article` 1.5s, then `.encyclopedia` 0.5s in the same process**. So the wiki's three books are **10.7s in one process against 16.9s in three**, and the marginal book after the first falls by an order of magnitude. The rule that makes sharing safe is what already forced the isolation: **a book registers its theme on the shared `Book` class at module load, so a pass that DRAWS must stay one process per page — and a pass that only READS draws nothing and may share one.** The bound on sharing is chemistry's, cited not assumed: [`$Reaction._chemicals`](../../../chemistry/package/src/abstraction/reaction.ts) is a strong `Map` written in every reaction's constructor and cleared only by `destroy()`, which nothing calls here — so a process retains every chemical of every book it has loaded, and a library of hundreds cannot be one process. **Hence a batch size, one knob, defaulting to the whole library and lowered when a library is large.** *Chosen over one process for everything (unbounded memory) and over today's one-per-book (the 3.1s constant paid N times).* **The gate:** the per-book counts under batching are identical to the per-book children's — 1,016 · 277 · 2,995 — or the batch is wrong.
- <a id="d14"></a>**D14 — One place shapes a token, and the two readings are told apart.** Three callers made a URL token out of text through `reflection.kebab`, which opens out capitals because it was written for class names — so every acronym split (`NP-completeness` → `n-p-completeness`). `reflection.slug` is the copy reading; `kebab` is now that reading over a class name with its capitals opened out, byte-identical for every class name. Everything a reader can see takes `slug`: a book's name, a heading's id, a catalogue's anchor — the last two moving together, so a contents entry still reaches the heading it names. **Built, `756d312`.** *Left where they are and flagged: `folded(key)` in `Fold.tsx` colliding by name with `reflection.folded(writing)`; `$Ref.url()`'s bare-key rule; the binder's `nameOf` and `placeOf`, which this sprint rewrites anyway.*
