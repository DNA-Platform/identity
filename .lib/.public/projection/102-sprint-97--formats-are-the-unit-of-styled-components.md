### <a id="research"></a>What the research says, 2026-10-01

- **styled-components, its own documentation.** A component is extended by wrapping — *"To easily make a new component that inherits the styling of another, just wrap it in the `styled()` constructor"* — and defined once, outside render: *"otherwise it will be recreated on every single render pass… will thwart caching and drastically slow down rendering speed."* Reusable pieces are `css` fragments interpolated into a template; `attrs` is for a prop every instance has; a theme is values provided by context and read in interpolations, and `createTheme()` turns them into CSS variables so a switch regenerates no class and, under server components, the provider is a pass-through. `createGlobalStyle` is for page-level resets and nothing more is said for it. Sources: [basics](https://styled-components.com/docs/basics), [advanced](https://styled-components.com/docs/advanced).
- **A theme designed for extension is extended by parts.** MUI's theme holds `components[Name].styleOverrides` keyed by *slot* — *"a slot name as a key (use `root` to target the outer-most element)"* — with `defaultProps` and `variants`, and its guidance: theme overrides for application-wide consistency, *"prefer creating new components for heavy customizations"* ([theme components](https://mui.com/material-ui/customization/theme-components/)). Chakra v3's recipe is `base`, `variants`, `compoundVariants`, `defaultVariants`, reading semantic tokens by name, moved into `theme.recipes` to be shared ([recipes](https://chakra-ui.com/docs/theming/recipes)). Both are the same shape: a skeleton with named pieces a consumer fills.
- **Design tokens are three tiers:** global primitives, semantic aliases, component-scoped — *"token authors manage global tokens… theme authors manage alias tokens… component authors manage component tokens"*; a brand change edits one tier ([token architecture](https://cdn.jsdelivr.net/npm/@memi-design/cli@2.6.2/notes/token-architecture/token-architecture.md), [nearform](https://nearform.com/blog/implementing-design-tokens-in-workflows)). Our eight were one tier, chosen by the framework; a library's tokens are the library's.
- **The OO literature on designing for extension.** The template method *"defines the skeleton of an algorithm in a superclass operation, deferring the implementation of some of its steps to subclasses"* — hooks, static, chosen at the class; strategy varies the whole by delegation at runtime ([sourcemaking](https://sourcemaking.com/design_patterns/template_method), [Horstmann](https://horstmann.com/oodp3/slides/ch06/index.html)). Effective Java's Item 19: design and document for inheritance — every overridable method named with what it does — or prohibit it. React's own doctrine is composition over inheritance ([react docs](https://17.reactjs.org/docs/composition-vs-inheritance.html)), kept where it fits: a Format's styled component is composed of fragments, and what a subclass overrides is a named part.
- **Chemistry's `$` for injection** — [The Representative](../../../chemistry/.lib/composition/11-the-representative.md): `$(A,B)(C)` registers *for A, a B is a C*, reaching what the scope *binds*; `<X/>` written in TSX is React's own path and is not resolved; a field initializer runs before any scope exists. A chapter's annotations are made at the chapter's bond, before the compiler hands the chapters to the book's bond, so a registration on a book class cannot reach a chapter's `<Table />` as the compiler stands.

**And measured, on the galley before the draft:** the writing of annotations, drawn and hidden by `.pd-annotation { display: none }`, is **27% of the paper's page bytes, 32% of Libby's, 21% of the manual's — 42,722 bytes — and 115 of the paper's 339 nodes, 167 of Libby's 335, 346 of the manual's 2,718.** Every Reference's url, every Level's number, every Append's whole file, in every page, for nobody.

### <a id="the-policy"></a>The policy — styling in an OO component framework, with styled-components and `$`

*What every OO component framework with pluggable appearance settled — Swing's look-and-feel with a UI delegate per component and a defaults table, WPF's implicit styles keyed by type and resolved up the element tree, Flutter's `ThemeData` with a slot per widget, Android's theme attributes — is three sentences, and chemistry already has the third:* **a component owns its structure and reads its appearance from a theme; a theme is a typed value object with a slot per component; a component is replaced by registering a subclass for its type in a scope.** *Here is each as `.public` states it. Identifiers `P1` on, stable; S1 to S4 above stand as ruled.*

- <a id="p1"></a>**P1 — A Format is a styled component with a class around it, and a library writes as many as it has looks.** `class $Card extends $Format { style = selection.div\`…\` }` is the whole of one; the class is the shell that lets it be subclassed, stood by a kind, registered for a scope and found by type. Styled-components' own rule holds unchanged — defined once, in a field, never per instance — and a library that defines thirty is a page that defines thirty styled components. *Observed:* the base's Formats and Libby's read as one field each; nothing in `src` or the test library makes a styled component anywhere but a class field.
- <a id="p2"></a>**P2 — The base ships structure and no appearance.** Every Format of `src` carries what its marks *mean* and nothing a library would choose: Table the grid, `display: contents` rows and the twelve starts and spans; List the item and its marker; Paginated its closed pages hidden, S4; Cover a `header` and TableOfContents a `nav` with empty templates; Bold, Emphasis, Underline their tags; Reference's anchor the browser's own link and Self's the same, its two declarations struck — *a library dresses anchors and self-references in its theme, his word*; Content's span its class alone; Synopsis a Format for its power over the text with no layer; Biography and Autobiography annotations that mark. Code wraps its lines when `numbered` and carries each number as data, `data-line`, drawing none; Equation, Math and Date mark. Every mark stays worn, A8, so anything can be reached from above. *Observed:* a grep of every `src` template for a size, colour, weight, margin, padding, border, background or glyph at zero; the marks' promise green.
- <a id="p3"></a>**P3 — The Theme is a typed value object and one styled component, with no values and no style of its own in the base.** `$Theme extends $Format`: `themeProvider = true`, the singular rule, said of a book, and one hook, `values`, returning `{}`, that a library's theme overrides to name its own reactive fields. A library's theme declares its tokens as fields, names them in `values`, types them for styled-components in its door as every application does, and writes its `style` — the one component that dresses the kinds, `pd-`, and every mark whose Format it does not replace, links and self-references among them. The provider hands the values down as custom properties, declared inline once on the theme's element, so a write moves one declaration and regenerates no class; a bare book is the browser's defaults. *Observed:* `Theme.tsx` under thirty lines with no `font`, no eight, no `Values`, no augmentation, no sheet; Libby's theme a class of fields, `values` and `style`.
- <a id="p4"></a>**P4 — A component designed for change is composed of named parts.** A theme's or a Format's `style` is made of `css` fragments returned by protected methods — `style = selection.div\`${this.typography()} ${this.frame()} ${this.links()}\`` — the slots of the design systems, the template method of the OO literature, in styled-components' own `css`; a subclass overrides one part or the whole, and the composition is made once per class at the template's field initializer, since a method stands on the prototype before any field runs. The base's Formats are each one part and need none; a library's theme and its larger Formats use it, and the manual's theme overrides a part where it now rewrites fifteen rules. *Observed:* the pattern in Libby's theme and Cover; the manual's theme as one overridden method.
- <a id="p5"></a>**P5 — Replace by registration; add by import.** A library's door registers its components on its book class, once, in configuration — `$(TheLibrary, Theme)(LibraryTheme)`, `$(TheLibrary, Self)(LibrarySelf)`, `$(TheLibrary, Table)(LibraryTable)` — and every book of the library, a subclass built by the compiler as `$($SomeProjects)`, resolves them, since a registration on a class is inherited by its subclasses and `$($Class)` is one component per class. That reaches what the framework stands for itself, which already asks — `Book.$Define`'s `$(theme)`, `Title.$Define`'s `$(self)` — **and what a chapter writes, once the framework asks where it takes a written annotation:** `reflection.chemical` resolves the element's type in the scope it is written in, the one place `.public` takes a written word, so a chapter writing the framework's `<Table />` gets the library's — WPF's implicit style. A look the framework has no word for — Framed, Literary, a Card — is the library's own Format, imported from its door and written. By-name export under the framework's name is then a choice, not a need, and the twenty-five import lines go. *Observed:* Libby's door with its registrations and no re-export; her chapters importing from `@dna-platform/public` and from her door only for her own words; a chapter's `<Table />` served as her Table; `$(` with two arguments only in doors.
- <a id="p6"></a>**P6 — Where a rule lives, one law and no machinery.** Structure in the Format that is the element; the look of a library's own box in that library's Format; the look of a kind, and of any mark whose Format the library does not replace, in the library's theme by mark; a state is a mark the class toggles; a quantity is a theme value read through the provider, never a literal. No `!important`, no cascade layer, no `:has` chain — the base has no sheet to order against. Where a library's theme and one of its Formats address one property of one element, the library has written the same thing twice; styled-components injects in definition order, so a door that declares its theme before its Formats lets a Format's own rule win, and the guidance says so.
- <a id="p7"></a>**P7 — The base's components are catalogued: each, its styled field, what a subclass overrides, how it is registered.** Written the same night on his task — *"Go through all the classes. Which of the annotations do you feel are essential?… document the classes, what annotations control them, what they mark, and leave them to be styled in the base sheet. - <a id="p8"></a>**P8 — Performant by construction and by number.** S1's bytes and nodes; no base sheet, so a book's sheet file holds the library's rules alone; one styled component per class, never per instance; a theme write moving inline declarations; resolution a lookup at the bond and nothing at draw; no `:has`, no `!important`, no layers; a page turn one class toggle.
