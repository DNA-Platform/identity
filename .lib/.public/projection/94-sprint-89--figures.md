## Where this sprint comes from

**Doug, 2026-09-28:** *"We are going to start my library from scratch, and reuse what is there for scrap. I don't think I need it looking like Wikipedia… The concept of resources is important, and we need to think through it and make it work. The vision here is that one writes code for one's library in one's library, and it is in one's library as resource documents associated with chapters. This allows a library to be a sort of convenient documentation system for a code library, and more specifically, the code library that is used to build itself… We need this very early on, since we need a place to put the types and annotations that we will need to build our library. So let's spend some time on that, and let's use the binder (which I also call the compiler) to enforce as much of this as we can. The payoff is a library whose inside contains its own outside, at least in printed form, which is a good step for a library that's closed under books."*

**And on what a resource is:** *"The usage of the code is informal and for the documentation. It need not be used. But it can be used. We likely need a `<Resource/>` component which controls where it goes, and it should be powerful and select the right control. But there can be a lot of resources — any file who sits between it and the next chapter is one of its resources along with those who share a name — so we will have to have ways of specifying different things here. Obviously ts and tsx are the file types most important, but md, png, jpg, are very important. Maybe svg, css… So we need a scalable system where the compiler can find a way to surface them to the rest of the application. The problem is that if you just make it Resource, then how can we subclass it? We need a serious design session here to get this right and flexible."*

## What the room already held — the review of v1, v2 and v3

**v2, which Doug's library runs on** ([`.archive/.public`](../../../../.archive/.public/), [Sprint 74's record](../../../../.archive/.public/.lib/projection/80-sprint-74--conversation-as-a-folder.md)): `Resource` was an annotation a chapter placed in its own text, `<Resource>.tsx</Resource>`, naming its file by suffix *as content and never as a prop*. The binder's `binding:resources` plugin found the placement in the chapter's source at build, matched a file beside the chapter by the chapter's own name, read it raw and swapped in a code navigator printing it. A missing file failed the build. Three rulings stand from that sprint: **resolved by the binder, never at draw** — resolved at draw, the placement re-entered the parse and one book took the whole library down at 291 seconds on a 4GB heap; **imported by its whole filename, always**, since a chapter and its paint share a name; **the documentation is the primary artefact and the code carries no prose**. The code viewer as *a place a reader goes* was designed and not built; the word for a program shown from a file was proxied as *Listing*. Doug's reference book has seven chapters, each printing its code at its foot, and its book file re-exports them.

**v3, this code:** the inventory read every file of a book once and said what it was — apparatus, a chapter, a resource accompanying a chapter by name, or unaccounted, which the bind refuses; the file rules held a closed list of extensions; the structure read a resource for what it refers to and refused one that names, `RESOURCE-NAMES`. **And the v2 plugin was still registered in the binder and dead:** it imported a code navigator and a Resource that v3's `.public` did not have.

**v1, where code was integrated with the project** ([the Build book](../../../../.archive/.archive/app/src/sections/book/library/the-build/)): one file beside the chapters, `figures.tsx`, imported twice — as a module, so its figures run on the page, and raw, so a chapter prints the exact slice of source it is discussing through a Listing figure with a caption: *"the diagrams below do not draw a picture of this rule — they run it, so a wrong rule draws a wrong tree."* That is the integration kept: a resource is a module and a text at once, and the chapter chooses what part of it to show.

**Two rulings of the brainstorm, verbatim, 2026-09-28.** On legibility: *"We are writing this repo in .public. It will be a library. It is important that the chapters of the library are not parenthetical. We work so hard on annotation so that the text, itself, can remain legible. I want to be clear that so much of .public exists to protect the integrity of the semantic structure of the text that we write in this repo, because it will serve as a form of publication."* On closure: *"Resources allow the system to be closed under chapters, with the accompanying files being where the coding complexity lives, and then forcing them to be surfaced inside the structure."*

**His answers to the first four questions, verbatim.** On the shape: *"We don't have kinds in .public. If you put them there, then we need to talk about where and why. The resource is a file whose contents are copied… Resource should help you put the contents of your resource in the page. That makes it a view-like component like Next. The question is, how did the component get to the page, and how do we specify default resource viewers (subject to discussion) and how do we override them? Presumably they might specify a class in the resource control. How does the code get there? Perhaps it adds it to the chapter as an annotation so the Resource can display it using some control."* On association: *"Any file that has the extension-free name of the chapter as its prefix. The rest of the name is its filename, skipping one character as a separator, so it might be .ts or version1.tsx, and that is how it can be interacted with. We also need to support self in some way, which would be a chapter's own code, but that can be implemented in a second version."* On surfacing: *"by annotation that has the filename appended to chapter by the binder."* On use: *"it should be used if there. I meant one need not give a chapter a resource. I'm not sure how to enforce the usage. The hard part will be to specify when the chapter's own code should be in its page."*

## How the naming was found

*Three approaches stood here at mechanism altitude — a resource as an annotation with kinds under it, a resource as a composition of its own, and no placement at all with the compiler printing an appendix — the first recommended. Doug's answers below superseded them, and the list is spent.*

**His answers to the second four, verbatim.** On viewers: *"I'm not even sure we need the control. Maybe we just have Resource be the base and we make classes like CodeResource, MarkdownResource, and they subclass Resource, and they know how to interact with the resource annotation on the page."* On defaults: *"It doesn't look like we need a default anymore. We just need great extension documentation to understand what controls exist."* On level: *"It should be able to be placed and used anywhere, no limitations."* On use: *"We can't. But it will be there as an annotation."*

**And his answers to the first draft of the requirements, verbatim, which renamed the thing.** *"The attribute should have contents equal to the file, we make a Resource annotation, rather than using it for the view, and the contents of the annotation are the file contents, whatever base class interacts with a resource throws if it's not found, and that thing can be subclassed to provide different ways of viewing and interacting with resources."* *"It should append the Resource annotation which has the contents of the file and takes the identifier (part after chapter name then separator before extension) and type (extension like .tsx), that can be passed as props to the annotation."* Then, on what it is: *"What is this like in a book? It's not an appendix. It is like buying ikea furniture — the instruction manual has the actual furniture as a resource, and while we can't interact with that in a library closed under books, we can do something like put a photo / diagram / or some sort of representation of the thing outside. But this thing can be ANYTHING!… It's something like a Representation — not the thing but the representation of the thing. Not the chapter but the code for the chapter… a string literal is a representation of the string, quoted… Inside the string there is not code. It syntax highlights to one color. It is uninterpreted. That is what this is like. So Literal!… What if the Literal was the thing the binder puts in the chapter, and the Symbol was the Letter that interacts with it, or takes React and can be its own literal. Like assigning a literal to a variable. And one can invent ways of viewing by subclassing symbol?… This is a user interface symbol that allows the user to interface with the literal visually."* And on the end: *"The test for this is to create a reference manual for Libby's library, and move a lot of the code used in the framework into the manual, and have Libby document how she uses those tools in the context of being the Librarian of a Library… And then the other test is to have one image and one SVG and to prove that both can work, and all the symbols — `<SVG />`, `<Image />`, `<Code />` maybe should all work with direct input or when configured for a resource so that the same tool can be used to express a literal in the code. And now we have the beginnings of the semantics of the representation of things that are not quite writing in the sense of .public."*

**The naming, settled, verbatim.** Asked to confirm three words at three layers: *"Literal is the annotation and the binder's (compiler's) word for it. I changed Resource and you need to update your notes."* On the symbols: *"Code, Image and SVG in .public, with appropriate configuration. `<Svg/>` — that is more elegant than all caps. I think this deserves a new folder called symbol, and Symbol, Literal and the various forms of Symbol can live there. And that can grow as we invent more."* On the bare name: *"It is empty, identify it by its extension. This will probably only be the norm for single resource chapters."* Then a walk through other words — *"It's like an Attachment… Can these be called Figures?… Symbolic and figurative are similar… What if we be neutral and just call the annotation Append… Okay how does that feel? We are doing Figures"* — and the settling: *"Okay so I guess we can switch this from Resources to Literals… No, I don't think we have Resource anymore. The annotation is a literal and the type of Letter is a symbol. Letters can still have annotations right? So we still have a lot of power, and we want annotations to work in Symbols too."* And on the manual: *"It is a book in the library that is the library reference manual. It can store anything — base classes for books and chapters, annotations, and whatever else. The chapters document them. We might even try to make a code viewer like in the .demo, and give the whole book a code navigator feel?… But you literally use the code in the reference manual as the tools in the library."*

**And his answer to the approval, which settled it the other way, verbatim:** *"No we switched now to Figure and Append and the folder is called figures. The library folder is changed to libraries. And this feature is Figures, not resources, though we can think of the files as the resources appended to the chapters required to create the figures."* On the manual: *"the folder names are not causal, but I like the idea of subjects having a reference manual. But no, ..reference is the book representing the subject, not the reference manual. This is the manual that accompanies the reference. It could be .manual, if you want to create a convention. Otherwise just give it a name and put it in a folder that is anywhere. Libby, what do you prefer?"* — and Libby's preference, in the room: **The Manual**, in a folder `manual`, filed under Libraries, by her, since a dot in front of a folder is a catalogue in the dot type system and a manual is a book.

**Approved 2026-09-28, verbatim:** *"Approve. The reference manual. `.manual` can be the folder, but the elegance is that we have the catalogue — the book that is the catalogue that represents the subject — as the reference (like reference desk) — and then this is the accompanying reference manual that gives technical information about the subject. Kind of elegant right? But yes, approve. And capture these things in the documentation and implementation and extension notes. And that, as we build, it is worth writing a very general version of figures to go in the .public library package so that it grows over time, as long as we step back and design it to be up to spec. We want to support many types of figures in our writing."*

## Requirements — the register

*Redrafted 2026-09-28 to his settled naming and **approved** the same day. Two standing instructions bound the plan: **Figure is designed generally**, a base many kinds of figure can grow from in `.public`, stepped back to the spec before any kind is written; and **the reference and its manual** are a pair — a subject's catalogue is its reference, the manual the technical information accompanying it. Two words in `.public`, and the file is only the file: an **Append** is the annotation the binder appends to a chapter for each file accompanying it, the file's contents uninterpreted, *"like an appendix, but by action"*; a **Figure** is the kind of Letter an author writes to interface an append visually. The files are *"the resources appended to the chapters required to create the figures"*, and the feature is Figures. The observed column each requirement carried became the promises; they are read where they run.*

**A. The accompanying file, and whose it is.** **R1** a file accompanies a chapter when its name is the chapter's extension-free name, one separator character, and the rest — `5-the-plate.ts` with an empty identifier and the type `.ts`, `5-the-plate.version1.tsx` with `version1`; the chapter's own file and the apparatus accompany nothing; a file naming no chapter is unaccounted and refused. **R2** the closed list of extensions grows to `ts`, `tsx`, `md`, `png`, `jpg`, `jpeg`, `svg`, `css`, `json`, `txt`, `csv`. **R3** a chapter need not have one; an empty identifier is the norm for a chapter with a single file; *self*, the chapter's own source, is a second version.

**B. The binder appends each accompanying file to its chapter as an Append.** **R4** at build, for each accompanying file, the binder appends to its chapter an `Append` whose contents are the file's contents, uninterpreted — the text of a text file, an image as its address — with `identifier` and `type` as props, written into the chapter's module and never read at draw; *"it's just text that has been appended to the chapter."* **R5** `Append` is a class of `.public`'s in a folder of its own, `figures`, said of a chapter; *"they are there in the annotations and anyone can check"*; the structure keeps reading an accompanying file for what it refers to and refusing one that names. **R6** nothing enforces that an append is used — *"We can't. But it will be there as an annotation."*

**C. Figure, the letter that interfaces an append.** **R7** `Figure` is a Letter, placed anywhere, that names an append of its chapter by identifier, or by type alone where the identifier is empty, and whose text is that append's contents; given React instead it is its own appended text, *"like assigning a literal to a variable"*; given both, the append's contents come after its own; annotations work on it as on any letter — *"we want annotations to work in Symbols too."* **R8** the ways of viewing are subclasses of Figure, three shipping beside it: `Code`, `Image`, `Svg`, each working with direct input or configured for an append, *"so that the same tool can be used to express a literal in the code"*; `src/library` becomes `src/libraries` — *"IF it's figures, then library needs to be libraries."* **R9** a figure naming an append its chapter lacks throws, at bind, through the writing's own specification — *"whatever base class interacts with a resource throws if it's not found."*

**D. The manual, and the visible end.** **R10** **The Manual**, a book of the test library in a folder `manual`, by Libby, filed under Libraries: its chapters each hold, as accompanying files, the code the library is built with, *literally used* as the library's tools, re-exported through the manual's book file; Libby documents in each chapter how she uses that tool. **R11** one image and one SVG, proven from an append and from direct input, a Code figure the same; the dead v2 plugin gone. **R12** the legibility rule: a chapter's prose holds one figure per representation, the appends are hidden, the composition untouched. **R13** a chapter of the developer story says what an append and a figure are, how a file is named, how the binder appends it, which figures exist and how to write one.

**Out of scope:** *self*, the chapter's own source; markdown parsed as writing; a viewer beside the page and the code-navigator feel for the manual; enforcement of use.

**Names.** Doug's: `Figure`, `Append`, `Code`, `Image`, `Svg`, `identifier`, `type`, the `figures` folder, `libraries` for the library folder, *the manual*. Struck by him: `Resource`, `Literal`, `Symbol`. Ours, flagged: *accompanying file* as the prose word for the file, and **The Library Reference Manual** as its title, Libby's choice.

## <a id="plan"></a>The plan — the register

*Planned 2026-09-28 with the inventory, the file rules, the assembly, Letter, Space and Next open; guardrails, not choreography. ### Decisions

**D1** Any single character separates and the dot is the convention; the account decides the chapters first, so a `.tsx` accompanying a chapter always carries an identifier; identifiers are unique per type, so `chapter-name.id.tsx` beside `chapter-name-id.tsx` is refused. **D2** The binder appends in the book's module: the assembly imports each text file raw and hands the chapter's element its Appends as added children through `cloneElement`; the `binding:resources` plugin removed. *As built, a picture is never imported — [Solutions 95](../solutions/95-the-picture-that-came-from-the-dev-server.md).* **D3** `Append` is an annotation in `src/figures/Append.tsx`, `$identifier` and `$type` as attributes, its text the contents, marking `pa-append`, said of a chapter, drawing no note. **D4** `Figure` is a Letter in `src/figures/Figure.tsx`, marking `pd-figure`, naming its append by the same two attributes, drawing the append's contents after whatever the author wrote; its specification throws when the chapter holds no append so named. **D5** `Code`, `Image` and `Svg` are Figures in `src/figures/`, `pd-code`, `pd-image`, `pd-svg`, the default sheet gaining their rules. **D6** `src/library` becomes `src/libraries`. **D7** The Manual is a book of the test library, its chapters holding as accompanying files the code the library is built with, re-exported through its `.book.tsx`. **D8** Documentation is a book of its own, `figures/`, and a chapter of the developer story.

**Doug's answers to the plan's four, 2026-09-28, verbatim.** D1: *"A dot,"* and then: *"The dot is nice, but why don't you just skip a character, let them use what they want, and we make the dot a convention and recommendation."* And: *"the compiler would error on: chapter-name.id.tsx, chapter-name-id.tsx. Because ids must be unique per type."* D2: *"The file isn't in the bundle. It gets written onto the chapter… or can we not do that? Tell me the best thing, but the idea as I was thinking it is that `<Append>Here's what is in the file</Append>` and that is effectively appended to the chapter's code."* D6: *"This sprint, as U5."* D7: *"Sure do as Libby wants. And name it whatever you like. The Library Reference Manual is a boring but easy to comprehend choice for the one at the top, and then do what you want in other subject catalogues. One way something can become a subject is when a book is complex and needs a lot of code, it splits into a catalogue that catalogues what it is about, the original book, and the reference manual for it. And that is a very normal reason to move from book to subject. Do note that in the implementation documents that as one builds their library, the subject catalogue grows because books become a poor container for their contents."* And, when the binder's refusals were being written: *"Make sure to have the binder/compiler deliver errors in a consistent way. It should be like a tool that compiles the code by binding the books of the library."*
