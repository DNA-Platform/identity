## Where this sprint comes from

**Doug, 2026-09-28:** *"We are going to start my library from scratch, and reuse what is there for scrap. I don't think I need it looking like Wikipedia… The concept of resources is important, and we need to think through it and make it work. The vision here is that one writes code for one's library in one's library, and it is in one's library as resource documents associated with chapters. This allows a library to be a sort of convenient documentation system for a code library, and more specifically, the code library that is used to build itself… We need this very early on, since we need a place to put the types and annotations that we will need to build our library. So let's spend some time on that, and let's use the binder (which I also call the compiler) to enforce as much of this as we can. The payoff is a library whose inside contains its own outside, at least in printed form, which is a good step for a library that's closed under books."*

**And on what a resource is:** *"The usage of the code is informal and for the documentation. It need not be used. But it can be used. We likely need a `<Resource/>` component which controls where it goes, and it should be powerful and select the right control. But there can be a lot of resources — any file who sits between it and the next chapter is one of its resources along with those who share a name — so we will have to have ways of specifying different things here. Obviously ts and tsx are the file types most important, but md, png, jpg, are very important. Maybe svg, css… So we need a scalable system where the compiler can find a way to surface them to the rest of the application. The problem is that if you just make it Resource, then how can we subclass it? We need a serious design session here to get this right and flexible."*

## What the room already holds — the review of v2 and v3

**v2, which Doug's library runs on** ([`.archive/.public`](../../../../.archive/.public/), [Sprint 74's record](../../../../.archive/.public/.lib/projection/80-sprint-74--conversation-as-a-folder.md)): `Resource` was an annotation a chapter placed in its own text, `<Resource>.tsx</Resource>`, naming its file by suffix *as content and never as a prop*. The binder's `binding:resources` plugin found the placement in the chapter's source at build, matched a file beside the chapter by the chapter's own name, read it raw and swapped in a code navigator printing it. A missing file failed the build. Three rulings stand from that sprint: **resolved by the binder, never at draw** — resolved at draw, the placement re-entered the parse and one book took the whole library down at 291 seconds on a 4GB heap; **imported by its whole filename, always**, since a chapter and its paint share a name; **the documentation is the primary artefact and the code carries no prose**. The code viewer as *a place a reader goes* was designed and not built; the word for a program shown from a file was proxied as *Listing*, the printing trade's own. Doug's reference book has seven chapters, each printing its code at its foot — the sheet, the masthead, the chapter mark, the plate, the ledger, the switchboard, the domain — and its book file is a door re-exporting them.

**v3, this code:** [the inventory](../../package/.binding/inventory/chapters.ts) reads every file of a book once and says what it is — apparatus, a chapter, a resource accompanying a chapter by name (`1-the-plate.tsx.tsx` leaves `1-the-plate.tsx`, `2-the-source.ts` leaves `2-the-source`), or unaccounted, which the bind refuses; [the file rules](../../package/.binding/inventory/filenames.ts) hold a closed list of extensions a resource may carry. [The structure](../../package/.binding/catalogue/structure.ts) reads a resource for what it refers to, its references spent from every page that draws it, and refuses one that names anything, `RESOURCE-NAMES`. The test library's masthead is a resource used as a module only. **And the v2 plugin is still registered in the binder and dead:** it imports a code navigator and a Resource that v3's `.public` does not have, so the first placement would break the build.

**v1, where code was integrated with the project** ([the Build book](../../../../.archive/.archive/app/src/sections/book/library/the-build/)): one file beside the chapters, `figures.tsx`, imported twice — as a module, so its figures run on the page, and raw, `import figures from './figures.tsx?raw'`, so a chapter prints the exact slice of source it is discussing through a Listing figure with a caption: *"the diagrams below do not draw a picture of this rule — they run it, so a wrong rule draws a wrong tree."* That is the integration to keep: a resource is a module and a text at once, and the chapter chooses what part of it to show.

**Two rulings of the brainstorm, verbatim, 2026-09-28.** On legibility: *"We are writing this repo in .public. It will be a library. It is important that the chapters of the library are not parenthetical. We work so hard on annotation so that the text, itself, can remain legible. I want to be clear that so much of .public exists to protect the integrity of the semantic structure of the text that we write in this repo, because it will serve as a form of publication."* On closure: *"Resources allow the system to be closed under chapters, with the accompanying files being where the coding complexity lives, and then forcing them to be surfaced inside the structure."*

**His answers to the first four questions, verbatim.** On the shape: *"We don't have kinds in .public. If you put them there, then we need to talk about where and why. The resource is a file whose contents are copied… Resource should help you put the contents of your resource in the page. That makes it a view-like component like Next. The question is, how did the component get to the page, and how do we specify default resource viewers (subject to discussion) and how do we override them? Presumably they might specify a class in the resource control. How does the code get there? Perhaps it adds it to the chapter as an annotation so the Resource can display it using some control."* On association: *"Any file that has the extension-free name of the chapter as its prefix. The rest of the name is its filename, skipping one character as a separator, so it might be .ts or version1.tsx, and that is how it can be interacted with. We also need to support self in some way, which would be a chapter's own code, but that can be implemented in a second version."* On surfacing: *"by annotation that has the filename appended to chapter by the binder."* On use: *"it should be used if there. I meant one need not give a chapter a resource. I'm not sure how to enforce the usage. The hard part will be to specify when the chapter's own code should be in its page."*

**Reusable as they stand:** the accounting by name, the refusal of the unaccounted, the closed list of kinds, build-time resolution, the door pattern, the reading of a resource's references. **To reimagine:** the placement, since a regex over source for an element is what v3 forbids its compiler; the printing, since nothing in v3 prints code or shows an image; the association by position; the kinds; and how the compiler surfaces resources to the application.

## Approaches, at mechanism altitude

1. **A resource is an annotation on a host writing, kinds as classes under it, chosen through a registry.** `<Resource>` names its file as content, as Synopsis names a chapter; the compiler resolves the name at build into a compiled form carrying what the page needs — a module specifier and the kind — exactly as it turns `$[ ]` into an address, so nothing reads disk at draw. The base annotation's `defines` stands the control for the kind: `Listing` for code as text, `Figure` for an image, `Passage` for markdown. A library subclasses a kind, or registers a class for an extension, or writes the kind directly, `<Figure>`. *Trade-off:* the host's level must admit what is added — a paragraph a listing, a section a passage.
2. **A resource is a composition of its own** — `<Listing>`, `<Figure>`, `<Passage>` are writings whose text is the file, standing where a paragraph or a section would, `Resource` a base that picks the kind at `$Define`. *Trade-off:* a base switching on kind is the kind-conditional the coding style forbids unless the switch is a registry, and a composition cannot be put on an existing writing.
3. **No placement: the compiler prints every resource as an appendix of its chapter**, `<Resource>` only relocating one. *Trade-off:* the strongest closure and the least control; Doug: *"it need not be used."*

**Recommended:** 1, with the compiler also writing each chapter's resources into its module as a gettable property on the graph, `chapter.resources`, so a placement resolves against it at build and any writing may enumerate them; 3 kept as an option of the bind that lists what a chapter never placed.

**His answers to the second four, verbatim.** On viewers: *"I'm not even sure we need the control. Maybe we just have Resource be the base and we make classes like CodeResource, MarkdownResource, and they subclass Resource, and they know how to interact with the resource annotation on the page."* On defaults: *"It doesn't look like we need a default anymore. We just need great extension documentation to understand what controls exist."* On level: *"It should be able to be placed and used anywhere, no limitations."* On use: *"We can't. But it will be there as an annotation."*

**And his answers to the first draft of the requirements, verbatim, which renamed the thing.** *"The attribute should have contents equal to the file, we make a Resource annotation, rather than using it for the view, and the contents of the annotation are the file contents, whatever base class interacts with a resource throws if it's not found, and that thing can be subclassed to provide different ways of viewing and interacting with resources."* *"It should append the Resource annotation which has the contents of the file and takes the identifier (part after chapter name then separator before extension) and type (extension like .tsx), that can be passed as props to the annotation."* Then, on what it is: *"What is this like in a book? It's not an appendix. It is like buying ikea furniture — the instruction manual has the actual furniture as a resource, and while we can't interact with that in a library closed under books, we can do something like put a photo / diagram / or some sort of representation of the thing outside. But this thing can be ANYTHING!… It's something like a Representation — not the thing but the representation of the thing. Not the chapter but the code for the chapter… a string literal is a representation of the string, quoted… Inside the string there is not code. It syntax highlights to one color. It is uninterpreted. That is what this is like. So Literal!… What if the Literal was the thing the binder puts in the chapter, and the Symbol was the Letter that interacts with it, or takes React and can be its own literal. Like assigning a literal to a variable. And one can invent ways of viewing by subclassing symbol?… This is a user interface symbol that allows the user to interface with the literal visually."* And on the end: *"The test for this is to create a reference manual for Libby's library, and move a lot of the code used in the framework into the manual, and have Libby document how she uses those tools in the context of being the Librarian of a Library… And then the other test is to have one image and one SVG and to prove that both can work, and all the symbols — `<SVG />`, `<Image />`, `<Code />` maybe should all work with direct input or when configured for a resource so that the same tool can be used to express a literal in the code. And now we have the beginnings of the semantics of the representation of things that are not quite writing in the sense of .public."*

**The naming, settled, verbatim.** Asked to confirm three words at three layers: *"Literal is the annotation and the binder's (compiler's) word for it. I changed Resource and you need to update your notes."* On the symbols: *"Code, Image and SVG in .public, with appropriate configuration. `<Svg/>` — that is more elegant than all caps. I think this deserves a new folder called symbol, and Symbol, Literal and the various forms of Symbol can live there. And that can grow as we invent more."* On the bare name: *"It is empty, identify it by its extension. This will probably only be the norm for single resource chapters."* Then a walk through other words — *"It's like an Attachment… Can these be called Figures?… Symbolic and figurative are similar… What if we be neutral and just call the annotation Append… Okay how does that feel? The annotation is a literal and the type of Letter is a symbol. Letters can still have annotations right? It can store anything — base classes for books and chapters, annotations, and whatever else. The chapters document them. We might even try to make a code viewer like in the .demo, and give the whole book a code navigator feel?… But you literally use the code in the reference manual as the tools in the library."*

**And his answer to the approval, which settled it the other way, verbatim:** *"No we switched now to Figure and Append and the folder is called figures. The library folder is changed to libraries. ## Requirements

*Redrafted 2026-09-28 to his settled naming and **approved** the same day; each names what would be observed if it held. Two standing instructions for the plan: **Figure is designed generally**, a base many kinds of figure can grow from in `.public`, stepped back to the spec before any kind is written; and **the reference and its manual** are a pair — a subject's catalogue is its reference, the manual the technical information accompanying it — which the plan may adopt as a convention, `.manual`, or leave as Libby's plain name. Two words in `.public`, and the file is only the file: an **Append** is the annotation the binder appends to a chapter for each file accompanying it, the file's contents uninterpreted, *"like an appendix, but by action"*; a **Figure** is the kind of Letter an author writes to interface an append visually. The files are *"the resources appended to the chapters required to create the figures"*, and the feature is Figures.*

### A. The accompanying file, and whose it is

| | requirement | observed |
|---|---|---|
| **R1** | a file accompanies a chapter when its name is the chapter's extension-free name, one separator character, and the rest: `5-the-plate.ts` accompanies the plate with an empty identifier and the type `.ts`; `5-the-plate.version1.tsx` with the identifier `version1` and the type `.tsx`; `5-the-plate-figures.tsx` with `figures`; the chapter's own file and the apparatus accompany nothing; a file naming no chapter is unaccounted and refused, as today | the inventory's account lists each chapter's accompanying files with identifier and type; a bind of a folder holding `5-the-plate.version1.tsx` binds and one holding `plate.tsx` is refused |
| **R2** | the closed list of extensions an accompanying file may carry grows to what a library needs: `ts`, `tsx`, `md`, `png`, `jpg`, `jpeg`, `svg`, `css`, `json`, `txt`, `csv` | a `png` beside a chapter is accounted; a `bak` is refused |
| **R3** | a chapter need not have one; an empty identifier is the norm for a chapter with a single file; the chapter's own source, *self*, is a second version | the test library binds with chapters that have none |

### B. The binder appends each accompanying file to its chapter as an Append

| | requirement | observed |
|---|---|---|
| **R4** | at build, for each accompanying file, the binder appends to its chapter an `Append` annotation whose contents are the file's contents, uninterpreted — the text of a text file, an image as its address — with two props, `identifier` and `type`; written into the chapter's module the way references are compiled, never read at draw; *"it's just text that has been appended to the chapter"* | the compiled chapter module holds one Append per file; the bound page holds it hidden, as every annotation's writing is |
| **R5** | `Append` is a class of `.public`'s in a folder of its own, `figures`, an annotation said of a chapter; the chapter's annotations hold them and anyone may check — *"they are there in the annotations and anyone can check"* — and the structure keeps reading an accompanying file for what it refers to and refusing one that names, as today, under the binder's renamed words | `chapter.annotations.find($Append)` answers them; an appended file that names is refused |
| **R6** | nothing enforces that an append is used — *"We can't. But it will be there as an annotation"* | a file no figure shows binds, and its append is on the page |

### C. Figure, the letter that interfaces an append

| | requirement | observed |
|---|---|---|
| **R7** | `Figure` is a Letter — placed anywhere, no limitation — that names an append of its chapter by identifier, or by type alone where the identifier is empty, and whose text is that append's contents; given React instead, it is its own appended text, *"like assigning a literal to a variable"*; given both, the append's contents come after its own; and it is a Letter, so annotations work on it as on any letter — *"we want annotations to work in Symbols too"* | in a paragraph or a section it draws the append; with contents of its own it draws those; a Format on it dresses it; the composition admits it everywhere |
