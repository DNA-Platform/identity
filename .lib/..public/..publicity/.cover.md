***WHAT `.public` IS FOR, in one sentence, so that nothing in this catalogue is read as being about a web framework:*** **library semantics establish the soundness of a knowledge graph — a knowledge graph is an abstraction of a library, and the canonical semantics are chosen because they are suggestive.** *The statement is [The Soundness of a Knowledge Graph](../the-semantics-of-books/18-the-soundness-of-a-knowledge-graph.md), and it is the first thing to read in this branch.*

This is the cataloguing book for the `.public` branch library. `.public` is the subject of *publicity* — the public view onto the whole repository, the library made public so that it can be read, lent, and built upon. It is where the library metaphor takes renderable form: [`@dna-platform/lib`](../../package/), the canonical code library for creating libraries, lives beside this branch in `package/`, and the [public view application](../../app/) that renders the repository to the world lives in `app/`. Publicity is not their API reference — it records the team's applied knowledge of building that public face: why a code library is a pale reflection of what a library means here, why depending on `lib` is what makes a repository a branch, and why in this library publicity means lending — an `npm install` is a book checked out. Publicity catalogues that knowledge as it accumulates — and now the branch's own verbs alongside its records: the procedures this code can be asked to perform, which belong to this repository and would be meaningless anywhere else.

### [The Semantics of Books](../the-semantics-of-books/.cover.md)

***THE BRANCH'S THESIS LIVES HERE, in [The Soundness of a Knowledge Graph](../the-semantics-of-books/18-the-soundness-of-a-knowledge-graph.md) — read it before anything else in this catalogue.*** **Library semantics establish the soundness of a knowledge graph; a knowledge graph is an abstraction of a library; the canonical semantics are chosen because they are suggestive.** *That chapter is the design purpose of `.public` stated rather than derived, and it is what makes the object model's exactness a requirement instead of a preference — every name in it is a node kind in a graph whose correctness is defined in terms of those names. It also carries the division the architecture rests on: global reference to the catalogue, local well-formedness to the specification, and the compile as the only moment the library exists as one object.*

The rest of the book is the derivation of the object model that [`@dna-platform/lib`](../../package/) realizes — `$Composition`, `$Book`, `$Chapter`, `$Title`, `$Author` — worked out from Doug's 2026-07-18 *Semantics of Books* conversation, with every claim cited to where in that conversation it came from. Two levels of closure (composition, then book), built from the bottom. Not the finished spec: the record of how the understanding evolved, kept honest by pointing at its source.

### [The Condition Report](../the-condition-report/.cover.md)

The standing register of every questionable part of this branch's code, along Doug's own four axes — organization, names, semantics, implementation — each entry carrying the line that shows it, a stable identifier that never moves, and a verdict that can be argued with. Commissioned out of one sentence: *"we have lost the high level design goals and things have gotten muddy."* Where [Solutions](../solutions/.cover.md) records **defects** by their symptom and [Projection](../projection/.cover.md) records the work by **time**, this book records the code by **kind of fault** — and it is written to be edited rather than appended to, so a resolved entry gains its resolution in place. Its first chapter dates every file in the framework and names the strata, because knowing which code is the standard and which was written in a hurry is what makes the rest legible.

### [Debugging a Page](../debugging-a-page/.cover.md)

How the look of a page is debugged through the layers that draw it, as fast as it can be — written from the day the Wikipedia look was restored and every address became the compiler's. The loop as it stands with every step measured, the probes and the rule they obey, the browser that should be kept open, prototyping on the compiled output and carrying it back, and the traps that each cost an hour. A tutorial for the team; the name is a proxy.

### [Designing Inexplicable Phenomena](../.designing-inexplicable-phenomena/.cover.md) — Design

The design record of the repository itself, **a subject since 2026-09-11**: how `@dna-platform/lib` is used to build ways of viewing the repo's content, and how the code that does it is written, typed, dressed and consumed. One book of twenty-six chapters until Doug asked whether anyone could read it whole; now a catalogue of five books that sit beside it as peers — [Ways of Reading](../ways-of-reading/.cover.md), the earliest notes on how content is viewed; [The Coding Style](../the-coding-style/.cover.md), how the code is written as ruled; [The Type System](../the-type-system/.cover.md), what the framework is beneath the style; [The Motif](../the-motif/.cover.md), how a book looks; and [Writing a Book](../writing-a-book/.cover.md), what a consumer writes, the demos' conventions and the little framework every book builds for itself. Each readable in a sitting, every chapter's entry carried over as it was.

### [The Public Skillset](../the-public-skillset/.cover.md)

A skillset — a book whose chapters compile to slash commands — and the first one that lives in a branch rather than in the team's own [Our Skillset](../../../../.claude/library/our-skillset/.cover.md). Every other book here is a record, each indexing the same work along a different axis: [Projection](../projection/.cover.md) by **time**, [Solutions](../solutions/.cover.md) by **symptom**, [The Condition Report](../the-condition-report/.cover.md) by **kind of fault**. This one is not a record at all — it holds **procedure**, the verbs the branch can be asked to perform. A record remembers what happened; a skill is the instrument for doing it again, correctly. Its three chapters — `public-audit`, `public-audit-performance`, `public-audit-parse` — are routines first run by hand against a real browser and then written down, each carrying the numbers the branch had when it was written so a later run has something to beat, and the traps that cost that session an hour. A branch earns skills of its own when its verbs name files that exist only here: these reach into `.public/package` and `chemistry/package` and would break the moment either moved, which is exactly why they belong to this branch and not to the team's repo-agnostic set.
