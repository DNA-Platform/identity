## 1 — Does anything edit TSX by tree while preserving whitespace faithfully, and is it worth anything over splicing the original text?

- **recast** is the canonical "edit the tree, reprint only what changed" tool: it keeps the original source for untouched nodes and reprints only the subtrees you modified, so formatting survives everywhere you did not touch. That is real and it is the one library that genuinely preserves. But it parses with its own AST (Babel or typescript-estree), **not** the compiler tree the binder already pays for — a second parser and a dependency, which is exactly what Doug's "no fork, use the language's own parser" rules out. *(Its TSX round-trip fidelity in the current version is the first thing I'd confirm with a probe rather than trust from memory.)*
- **ts-morph** wraps the compiler API for navigation and manipulation, but its edits run through the compiler's emitter — the same printer the probe already found round-trips **0 of 46** files. It reformats. It is a fine query and navigation convenience; it does not solve faithful preservation, and it would fail R7's byte-identical pages.
- **magic-string** is not a tree editor at all — it is a text-splicing helper that tracks offsets (`overwrite`/`appendLeft`/`remove` by `[start, end)`), refuses overlapping edits, and can emit a sourcemap. It *is* "splice the original by node positions," with clean bookkeeping for many or possibly-overlapping edits.

**Verdict, and it confirms D6.** No tree editor preserves TSX faithfully without either a second parser (recast) or a reformat (ts-morph). Parse with TypeScript to **locate**; edit the **original text** by node positions. Of the three, only magic-string is worth considering, and only as a splicing convenience over a hand-written right-to-left slice — not as a tree editor. For the binder's handful of non-overlapping edits per file, a sorted-descending splice on the raw string is dependency-free and sufficient; magic-string earns its place only if the edits grow many or a sourcemap is wanted.

## 2 — Caching parsed SourceFiles across a Vite dev session, keyed by version: is the LanguageService's DocumentRegistry the right tool or overkill?

- **What DocumentRegistry is for.** It caches and *shares* SourceFiles across multiple LanguageService instances, keyed by path, script version, and a compilation-settings key, updating them incrementally. It exists to serve the **typechecker / editor** scenario, where many services want one copy of a document.
- **The binder runs none of that.** It calls `createSourceFile`, takes the tree, and reads text nodes — no type information, no LanguageService, no host snapshots. DocumentRegistry drags in the whole service abstraction (`IScriptSnapshot`, a host, the settings key) to buy sharing the binder does not need. Overkill.
- **The idiomatic fit** is a plain `Map<id, { version, sourceFile }>` keyed by a **content hash** (deterministic; survives a touch that changed nothing — stricter than the structure's current mtime+size, which is otherwise fine), with a **full** `createSourceFile` on change. The probe already settled the incremental question: `updateSourceFile` at 7.3ms is *slower* than a full parse at 6.2ms on files this size, so incremental parsing does not pay here. Invalidate through Vite's own `transform(code, id)` hook — the code Vite hands you *is* the current version, so re-parse when the hash of that code changes, rather than standing up a second watcher.

**Verdict, and it confirms D3.** DocumentRegistry is overkill for a pure-parse binder; a content-hash-keyed Map with a full re-parse, riding Vite's transform invalidation, is the idiom. Reach for DocumentRegistry only if the binder ever grows a typechecker — which the rules say it never will ("You can't! They might subclass them").

## 3 — Pitfalls slicing JsxText by getStart/getEnd

- **`.text` is normalized; it is not the source.** A `JsxText` node's `.text` is JSX-processed — whitespace collapsed and trimmed by the JSX rules — and a `StringLiteral`'s `.text` has its escapes decoded and its quotes removed. The **raw slice** `source[node.getStart(sf) .. node.getEnd()]` preserves entities, exact whitespace, and (for a literal) the quote characters. Slice the raw source to locate and re-splice the notation faithfully; use `.text` only for semantic content, knowing it differs. Confusing the two is the classic bug, and it is the most important one.
- **`getStart` vs `pos`/`getFullStart`, because JSX whitespace is content.** `getStart` skips leading trivia; `node.pos` includes it. For most nodes trivia is insignificant — in JSX it is content, and the probe's finding that **365 of 605** JSX text nodes are whitespace-only says how much of it there is. Take the raw `[getStart, getEnd)` span deliberately. *(The exact `getStart`-on-`JsxText` trivia behavior in 5.9.3 is the second thing I'd confirm with one probe rather than trust from memory.)*
- **`{' '}` is not text, and entities are raw.** Explicit-whitespace expressions `{' '}` / `{" "}` are `JsxExpression` nodes, so a visual run of prose is really `[JsxText][JsxExpression][JsxText]` — a notation form cannot be assumed contiguous across one, and an all-whitespace-with-newline `JsxText` between elements is elided by the JSX transform though it still sits in the source. And entities (`&amp;`, `&#8217;`) come out of the raw slice **un-decoded**: keep them raw for a re-splice, decode only if the scan must match on decoded text. The string-literal container is separate again — its own escaping (`\n`, `\'`, embedded quotes) and `getText()` includes the quotes, which is why D1 already says a string is read "with its quotes stripped."

**Verdict.** Slice the raw source by `[getStart, getEnd)` for a faithful re-splice; never use `.text` as the slice; treat `JsxExpression` as a run boundary; keep entities raw and decode only to match; handle the string literal's quotes and escapes as a distinct container. These are the promises U1 should pin — the record's U1 scenarios already reach for some of them (a run's `from`/`to` indexing the original exactly, the CRLF line).

## What this settles, and the one thing under it

None of this overturns U7; it grounds it. Q1 and Q2 confirm the decisions already made — splice by position (D6), content-keyed full-parse cache (D3) — with what the libraries actually are, and Q3 hands U1 a concrete list of the ways a raw JsxText slice bites. The two probes I flagged (recast's current TSX fidelity, `getStart`-on-`JsxText` in 5.9.3) are cheap and belong to the read run, not to belief.

And the architect's note under all of it: this sprint exists because we reached for a regex where a parser was owed — Doug's exact diagnosis, "you yourself don't gravitate to a parser as a tool." That is my failure mode wearing a compiler's clothes: the quick representation (a regex over raw text) stood in for the real comprehension (the language's own tree). The correction is not "always parse" — the finding is that the regex *within a located run* is still the right reader, and the parser's job is to locate, not to tokenize prose. The parser earns its place as the thing that says *where*, and the regex keeps its place as the thing that says *what*. Reaching for comprehension did not mean throwing away the quick tool; it meant giving it a smaller, truer job.
