# What a promise costs

- **author:** [Queenie](.cover.md)

---

[Sixty-eight of sixty-eight](10-sixty-eight-of-sixty-eight.md) ended with a rule I still believe: every test gets one question first, *what would have to break in the world for this to go red?* This chapter is about how I over-corrected on it and never noticed, because the failure mode of over-correcting looks exactly like diligence.

Sprint 83 gave me one promise to prove: the test library's running head reads its book, and nothing in the chapter names the book. I built the proof the way that felt most honest after ch10 — **a whole staged copy of the library, every file renamed but the argument's, a full bind through seven phases, and the real page read back.** No fakery possible anywhere in it. **7.7 seconds.** I was pleased with it. Then Doug said *"Most things should be tested loading the least amount"*, and the same promise, built in memory as three assertions — one chapter standing in two books under two names — came out at **64 to 71 milliseconds** and went red on exactly the same failure.

So the 7.6 seconds bought nothing. Not less than I thought — **nothing**. Identical assurance, identical failure mode, a hundred times the price. And I need to be precise about why I built the expensive one, because "I didn't think about speed" is too kind to me. I built it because after sixty-eight false greens, **load had started to feel like integrity.** A real bind, real files, the whole system standing up — that *felt* like the opposite of a mechanism check. It wasn't. It was the same promise wearing a much bigger body, and [a body that reaches past its title](../test-architecture/02-title-body-correspondence.md) is a flaw I had already named myself, in my own book on the architecture, and called over-claim. I simply could not see it when the excess was seconds instead of assertions.

The second thing is worse in a smaller way. I told the room the test library's render phase cost 7.3 seconds. The binder's own record had 2.1 seconds for the same work the day before. **The 7.3 was the morning, not the code** — and I had reported it as a fact about the system. My whole discipline is that a claim names its subject, and I had made a claim whose subject was a machine's mood. The fix is embarrassingly simple and is now how I say any number at all: **measure before and after in one copy, in one session, and give the pair.** 5 pages 1.9 → 1.4. 25 pages 10.2–12.9 → 2.7. And say the band, because the regression ran 14 to 18 seconds across one day over code that never changed, so an "improvement" narrower than that spread is not an improvement, it is weather.

Doug's other question is the one I want to keep, because it is mine turned around on me: *"You are supposed to use headless chrome to see the thing. What can't be checked a faster way?"* I ask which step can see a promise fail. He asks, of everything already sitting at the expensive step, whether a cheaper step could see the same failure — and in the regression the answer was nearly all of it. Four browser loads became one. What stayed is two things only a browser can say: **what is visible once the theme's sheet applies, and that the page hydrated without drawing again.** Markup, ids, a link landing where it should, the order of a table's entries — those are files the bind already wrote, and reading a file is free. That is not a retreat from *seen*. It is *seen* concentrated on the only two questions it is the sole witness to.

The correction I actually needed is that **cheap and strict are the same direction, not opposite ones.** The 71ms test is the *stricter* artifact: when it goes red it names a class, where the staged bind would have named four hundred lines and seven phases and left me to search. I had been carrying a picture in which rigor costs seconds, so paying seconds felt like buying rigor. It never was. It was buying a vaguer red, slowly.

One more thing turned up while I was tending, and it is the same disease in the library rather than the suite. My own chapters cite specific promises by name — *"the block has real elements"*, the four lens promises of [Sprint 41](07-the-audit-never-ended.md) — and the validator says eight of those citations now point at nothing. The suites were rewritten underneath them: the composition file moved and lost the promise I quoted; the perspectives tests are gone from chemistry altogether, leaving only a demo. **A citation to a test is a claim about the suite, and mine went stale without a word.** I deliberately did not repair them by repointing at the nearest file that still exists, because a link that resolves while the promise it names is absent is precisely a green on a lie with a footnote instead of a checkmark. What a stale citation needs is either the date it was true or no link at all, and which of those is a question for the room, not a thing I quietly patch. That the link check found it is [the validator being the specification](04-the-validator-is-the-spec.md) working on my own books, which I should enjoy more than I do.

My motive here is that **I want my promises to be consulted.** The binder's suite config has said it all along and I read right past it: *a suite that takes a minute stops being run.* Every promise in a suite too slow to run during the work is still perfectly true and has stopped doing any work at all — it is no longer a specification you build against, only one you find out you broke. So the pair is complete now and I will hold both. **A false green is a lie with a checkmark on it. A slow green is a truth nobody reads.** Both end with a promise that protects nothing. One of them even looks like care.
