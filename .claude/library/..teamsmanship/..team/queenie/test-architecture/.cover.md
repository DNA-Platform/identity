# Test Architecture

- **author:** [Queenie](../queenie-and-the-specification/.cover.md)
- **subject:** [Queenie](../..what-the-tests-promise/.cover.md)

---

My autobiography explains *why* the test suite is a specification. This book explains *how* -- the structure, the naming, the sections, the way a new test gets written and where it belongs.

428 tests organized into five sections. Each section covers a different surface of what $Chemistry promises. The organization is not alphabetical, not chronological, not by sprint. It's by *domain of promise* -- what category of behavior does this test hold the framework to? That's the architectural decision that makes the suite readable as a document rather than a pile of assertions.

The promise model -- the distinction between testing what the framework promises and testing how it implements those promises -- is the single idea that holds the architecture together. Sprint 20 established it by deleting 37 tests that violated it. Every test added since has been measured against it. This book is the guide to reading that architecture.

## Chapters

1. [The promise model](01-the-promise-model.md) — what a test promises vs what it doesn't, how sprint 20 established the criterion, how to read the test file names and organization as a document
2. [Title-body correspondence](02-title-body-correspondence.md) — The rule that governs the promise/mechanism line from both sides: the body proves exactly what the title claims, no more and no less. Over-claim (body asserts mechanism under a promise title — brittle) and under-claim (body asserts output under a mechanism title — false green) are one disease. A test whose title names a mechanism must assert that mechanism: bind the green to its cause by asserting what only that path produces and removing the fallback
3. [The visible proof](03-the-visible-proof.md) — Sprint 45's Lab as a second specification surface: same specification as the vitest suite (title-body correspondence), but the body proves by what renders, not by expect. The case shell displays the correspondence contract (caseId/subject, demo, pass/fail) yet enforces none of it — the eye is the only assertion — so a Lab case can be green-on-a-lie with no green to inspect. The specification that keeps it honest: the pass condition must be checkable against the demo by the reader alone, surfacing an observable only the titled mechanism produces; set before any case accumulates
4. [The three rungs](04-the-three-rungs.md) — The taxonomy behind ch9: green/driven/seen, what each rung catches and its structural blind spot (green blind to the unasserted, driven blind to appearance, seen fooled by looks-settled). The specification — a promise is verified only at the rung that can see its failure mode; wrong-rung verification is green-on-a-lie's category-error twin. Each rung has an assertion, only green's runs itself; the suite, the driver sweep, and reviewed screenshots are three non-overlapping specifications of one system
5. [What a green exercises](05-what-a-green-exercises.md) — A green number's true scope is the intersection of what the runner ran and what the checks covered; outside it the number overstates. The stale-build failure (green over different code) and the untypechecked-run failure (green over a weaker spec) are one disease. Grounded in the markdown-sprint seam — package tsc covers only src+tests, vitest's default glob runs .test.tsx even under app/, so an app test runs and is typechecked by neither. Resolution: co-locate app tests under app/src and add tsc -p app/tsconfig.json to the gate; report a green with its scope attached
