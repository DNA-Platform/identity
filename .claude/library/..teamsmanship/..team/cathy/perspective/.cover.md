- [A function prop made per draw defeats the diff](a-function-prop-made-per-draw-defeats-the-diff.md) — Found 2026-10-15 under a reactive loop in Doug's library. A particle redraws itself after every commit and updates React **only if the drawing differs** — which silently requires the drawing to be a pure function of the state *down to identity*, because `diff` compares a function by identity. So a handler built inside the draw is a prop that is never equal to itself, and the guard inverts into an engine: the whole drawing was byte-identical between draws except two freshly-made mouse handlers. It hides because the skip path normally quiets it, and surfaces only where something else keeps the chemical dirty — **two cheap faults, each survivable alone, multiplying**, which is why a dozen bisections never dropped out a cause. The rule generalized: "never a component made per pass" and "hover is CSS" are one rule about identity, and I had only ever written down its instances. With the diagnostic: sign each drawing with every function tagged by identity, and ask which chemical's drawing is not a function of its state. **Second round:** the invariant that makes the field fix *correct* rather than lucky — `augment` must wrap every handler afresh because the wrapper carries the scope, and the one line `wrapper[$original$] = handler` plus `equivalent`'s unwrapping is what keeps that layer transparent, so the contract is stable *source* identity, not "no functions in a draw". The better gate: patch React's `useState` and count setStates reaching the post-commit effect's diff branch — a healthy page is exactly **zero**, and a warning count hides thousands because React dedupes. And the mistake worth keeping: the dev server re-bundled its dependencies mid-session, two cuts "confirmed" a cause inside that window, and both confirmations were worthless — **a fault that disappears is not evidence until you put it back and watch it return.**

- [The theme was a responsibility question](the-theme-was-a-responsibility-question.md) — I designed the theme FOUR TIMES in one conversation and Doug overturned the first three; every wrong version put the answer in whichever object was easiest to reach — a vocabulary of roles, then a property per class, then colours and families, which is a stylesheet in an object called the top-level semantics of display. The fourth correction taught me something: a theme that selects and arranges is Strategy's oldest failure mode, where the strategy returns the finished product and has become the implementation. What fixed it was asking WHO OWNS WHAT and holding four axes, the theme owning only what would be incoherent if each view decided it alone. The suite rejected every wrong design before Doug had to, and the library predicted the worst moment — heap exhaustion was the parse that woke its own parents, returning under a condition its discharge never covered. Warts written down rather than waited for: the application never renders the book, a compiled book cannot be a subclass, page is declared twice. And the measurement that reframed everything — the framework's ENTIRE drawing was 108 lines while one demo book spends 503 that nothing else can reach, so a framework whose classes cannot be usefully overridden does not look brittle from inside, it looks SMALL.
