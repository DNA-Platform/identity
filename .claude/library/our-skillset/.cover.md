Skills are the verbs the team can invoke from the terminal. Each one lives as a `SKILL.md` file in `.claude/skills/{name}/`, and the platform loads it when someone types `/{name}`. They are the interface between Doug's intent and the system's capabilities. [On Skills](../..environmentalism/04-on-skills.md) specifies what a SKILL.md must contain and how it's compiled.

The active skills fall into clusters. Sprint and workspace management (`/sprint`, `/workspace`). Team structure (`/role`, `/responsible`, `/teammate`). Knowledge and review (`/library`, `/review`, `/skill`). Communication (`/listen`, `/discuss`). Tending and structure (`/retro`, `/branch`, `/audit`, `/reflect`, `/organize`). Navigation and research (`/think`, `/explore`, `/remember`, `/explain`). Environment and setup (`/identity` — bring the team into a repo).

## Chapters

1. [sprint](01-sprint.md) — begin or resume a sprint: name it, define its purpose, assemble the team, and write it as a chapter in Projection
2. [library](02-library.md) — browse teammate libraries: list books with summaries, or show the chapter list of a specific book
4. [responsible](04-responsible.md) — query who owns a file or path: lookup against the agent registry
5. [role](05-role.md) — create or update a role definition: a context-loading strategy that shapes attention and priorities
6. [skill](06-skill.md) — create new skills: analyze the request, decide the right form, and build it
7. [review](07-review.md) — review code through a teammate's lens: scoped by path, concern, or agent
8. [organize](08-organize.md) — tend the shared library: verify territory, connect isolated content, compact redundancy
9. [workspace](09-workspace.md) — create a new code workspace: initialize package.json, register in root config, set up structure
12. [listen](12-listen.md) — start or stop a collaborator listener: polls Claude Desktop for new responses
14. [teammate](14-teammate.md) — onboard a new teammate: the teammate sets up their own library with help
15. [discuss](15-discuss.md) — start a team discussion: multiple voices talking to each other, following the discussion protocol
16. [retro](16-retro.md) — run a sprint retrospective: tend libraries, reflect, discuss what changed
17. [branch](17-branch.md) — set up or navigate a library branch: the team's record of working on a project
18. [audit](18-audit.md) — run a comprehensive library health check: validates everything the Compilation catalogue inventories
19. [reflect](19-reflect.md) — tend the personal library: update recency, tend the catalogue, restructure as needed
20. [think](20-think.md) — think outside the context window: Claude dispatches a question to Claude Desktop, evaluates the response, stores the result
21. [explore](21-explore.md) — walk the library: start at a catalogue, follow links, take notes at every room, fix small things, produce a perspective entry mapping the walk
22. [remember](22-remember.md) — store knowledge in the library: explore to find the right room, place the knowledge in context with links, update the catalogue
23. [explain](23-explain.md) — the public interface to identity: the responsible teammate explores the relevant room and describes it in their own voice
24. [identity](24-identity.md) — set up the team identity in the current repo: pull, branch, gitignore, and sync back
25. [pull](25-pull.md) — pull the org's changes down, staged through the project branch so the working copy is never updated from an unverified state
26. [push](26-push.md) — push changes to the right places: identity to the org branch, branch library to the project branch, code to the project repo
27. [think-async](27-think-async.md) — think at length: a teammate keeps thinking in their own persistent context while the voice keeps talking, and you can follow the thinking as it forms
28. [ce-brainstorm](28-ce-brainstorm.md) — STEP 1 OF 4, then /ce-plan — work out what something needs to BE before anyone decides how to build it — step one of the feature workflow, with the gate that no code is written until requirements are approved, and the altitude rule that keeps approaches at mechanism and product shape rather than architecture
29. [ce-plan](29-ce-plan.md) — STEP 2 OF 4, then /ce-work — turn approved requirements into guardrails — decisions, units, files, test scenarios, risks — capturing the WHAT and never the HOW, enriching the same chapter in place with stable unit identifiers and origin tracing so nothing silently drops. A unit with no mechanism is not a unit: it is marked design owed and refused files and scenarios, out of the sprint that shipped 4 of 64 requirements because an undesigned unit looked exactly like the buildable ones beside it. AND A CONTRACT IS CORRECTED BY IMPLEMENTATION, NEVER BY REREADING — added out of The Build, where a card contract written from the design and reread across a whole session carried TWO faults, both found within hours of two sessions building against it and neither by anyone looking again: a field the base class already owned, and one word meaning a folder to one side and a route to the other, invisible because each side was internally consistent. So the practice is to dispatch against an imperfect contract rather than polish one, since a seam two people are building against is being tested while a seam nobody has built against is only being admired; and when a builder reports the contract cannot be met, BELIEVE THE BUILDER, because both faults were reported as impossible-as-specified and both times the specification was what was wrong. Flag rather than route around: the session that found the shadowed field wrote it down instead of renaming, which is the only reason it reached the contract at all.
30. [ce-work](30-ce-work.md) — STEP 3 OF 4, then /ce-compound — execute an implementation-ready plan, deciding the how with the code in front of you — refuses a requirements-only chapter, routes large work back, verifies with evidence stated in numbers, and keeps a ledger because conversation memory does not survive compaction
31. [ce-compound](31-ce-compound.md) — STEP 4 OF 4, then /ce-brainstorm again to close the loop, or /ce-handoff to end the session — distribute what a sprint learned while the context is fresh, AND COMPACT WHAT IT LEAVES BEHIND. A DEFECT becomes a chapter in the branch's Solutions book, indexed by the symptom as it was observed with a keyword line for grep; everything else goes to the room whose subject it already owns, because a second copy of a practice drifts. One lesson per run, overlap edits rather than duplicates, reread before editing, claims grounded by reading the defining line, the neighbourhood checked within bounds and never on a guess, and the cover updated in the same act with the TOC tool. COMPOUNDING SUBTRACTS AS WELL AS ADDS, which is the one place their plugin has nothing to say: a docs folder has no cover to keep true and no reading cost to protect, and 'the knowledge store only compounds value when it's findable' cuts both ways — an unread eighteen-thousand-word sprint chapter is exactly as unfindable as a missing one. A lesson that left for its own room has been COPIED, not moved, until the sprint chapter stops carrying it. A sprint chapter is written at full working weight while the sprint runs and that is correct; at compounding it stops being a plan and becomes the INDEX this library already says it is. What is provably spent once a sprint closes: the test scenarios became the suite, the order happened, a risk that fired is in the record with what it cost, the self-check passed before work started — each replaced by a STUB saying what stood there, never a silent deletion, which would leave a later reader thinking the sprint never planned; units and requirements survive as a REGISTER, one line each, because the record cites them by identifier. Three rules keep it honest: MEASURE before and after and state both, since '122,595 words to 105,982' is a finding and 'compacted the library' is not; CHECK EVERY ANCHOR before and after, a gate that earns its keep even where nothing is cut because it finds links that never resolved; and a cover is re-edited only if the cut made it FALSE, since the requirement is that a synopsis stays true, not that it is rewritten. Across chapters as well as within them — settled accounts are the destination and sprint records are the trail, so where they say the same thing twice the sprint record yields and keeps the finding plus a link.
32. [ce-handoff](32-ce-handoff.md) — NOT A STEP — run at a session boundary from whichever step you were on, and the next session runs nothing, it opens by reading Where things stand — close a session by writing WHERE THINGS STAND into the current sprint chapter — rulings verbatim, honest state, blockers, verification with numbers, the wrong turns already tried; one plan per session, opening orients but never acts because the working copy is the truth. EIGHT fixes carved from the two sessions that failed: it ends with a push or it did not happen; the first line is the next action as a command; written for the person reading it, in plain words; three to five things to read, claimed sufficient; ONE STATE, NO LAYERS — the old state is deleted in the same act; the reading list is shaped for the step it hands INTO (a brainstorm needs sources, not code); A STOPPED PUSH IS A SESSION BOUNDARY — secure the branch library before obeying any reconcile advice; and a sprint with a demo hands over the command, the route, and what to see first. TWO MORE, out of the handoff that MOSTLY WORKED — its machinery held, the first line said /ce-brainstorm and that is what Doug ran, and his second message was already inside the framework's semantics so orientation cost almost nothing; the two things that slipped are one mistake, THE HANDOFF CLAIMED WHAT ITS WRITER COULD NOT KNOW. 'Sufficient' is a claim and it was wrong: the list said 'read these four and they are sufficient' and Doug's opening instruction was to read at least thirty, because the correction for having no list at all overshot into a promise nobody could keep — the reader's need depends on the conversation the reader is about to have, which has not happened yet, so name three to five with what each is load-bearing for and STOP THERE, a starting point rather than a boundary. And NAME THE STEP, NEVER THE SPRINT'S SUBJECT: the handoff pointed the brainstorm at the build and the sprint became cataloguing on Doug's redirect inside the session — a handoff can know which command comes next because that follows from where work stopped, and it cannot know what the next sprint is ABOUT, because that is Doug's to set and he sets it in the room.
33. [ce-review](33-ce-review.md) — STEP 4 OF 5, then /ce-compound — show the work and COLLECT WHAT SHOWING IT PRODUCES; the one step of the loop that is OURS rather than Compound Engineering's. THE IMPLEMENTER OWNS BEING DONE (Doug: 'you own being done and the review is where I weigh in') — this is not a permission gate and nobody asks whether they may proceed; the implementer decides whether a requirement is satisfied and says so with evidence, and CHECKING that judgement is what happens here. Its likeness to brainstorm is not the batching but the PRODUCT: a review round produces NEW REQUIREMENTS, numbered on from the last identifier into the sprint chapter, and the work loops back to ce-work against them unofficially. It is the loop's second intake of requirements — from SEEING rather than from describing. It exists because only brainstorm's gate was human, so the workflow had a person at the front door and nobody at the back, and the failure was exactly what that predicts: a session reporting green with a red suite beside it and no demo. A round carries the requirement walk stated AS A NUMBER, the epiphenomenal decisions nobody ruled, the demo run through our own extremely-well-designed filter FIRST, and questions cheap enough that reviewing actually happens. It refuses a green number without the red one beside it, 'it renders' from a test container, and a demo described rather than shown. A round that turns up nothing new is how the step ends. It also makes work stricter: a demo is a stop condition, not a closing flourish. A proposal until it has run twice unchanged.

## Archived

Five skills moved to `.claude/.archive/skills/`: agent, dna, hear, speak, issue. They may return when the collaborator relay, the system management patterns, and issue tracking evolve.

`issue` was the most recent to go. It tracked open work first as a folder of `issues/*.md` files, then through the GitHub Issues API — and neither stuck: Doug removed the tracker and the approach with it. What to reach for instead is genuinely undecided, so the skill waits in the archive rather than standing as the answer. The seed is in [future work](../.projection/future-work.md#issue-tracking-is-unsettled).
