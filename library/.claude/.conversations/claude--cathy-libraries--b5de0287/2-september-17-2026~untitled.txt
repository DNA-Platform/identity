# PART 1 · WHAT THIS IS FOR

## The claim underneath everything

**A library is a knowledge graph with library semantics, and the semantics are what make it sound.**
A knowledge graph is an abstraction of a library; we are choosing *canonical library semantics* —
a catalogue, a call number, an author, a subject, a citation — because they carry integrity
properties an ad-hoc graph does not have.

Three that drive the whole compiler:

1. **A reference names a THING, never a PLACE.** `[Doug](My Library Log)` points at a book by its
   *title*, not a path. Addresses are derived late, from the catalogue, and can change without any
   reference changing.
2. **The catalogue refuses by NON-MEMBERSHIP ALONE.** If a title is not in the catalogue, the
   citation is refused. No filesystem probe, no fuzzy match, no fallback. You cannot cite what the
   library does not hold. That is the entire integrity story.
3. **The compile is the only moment the library exists as one object.** At runtime there is no
   server and no index — just prerendered HTML. Every cross-document truth is established at build
   time or it does not exist.

## What it physically is

Books written as TSX, where the prose is **JSX text**, inline in the markup. No markdown, no MDX.

```tsx
export default class OnBooks extends BookkeepingChapter {
    print() {
        return <Chapter>
            <Title>On Books</Title>
            <Paragraph>A book is the unit of authorship, and it sits beside its
            *$[subject]( Bookkeeping )* as a flat peer.</Paragraph>
        </Chapter>;
    }
}
```

Output: **prerendered static HTML, one page per book, on GitHub Pages under a base path.** No
runtime server. A reader moves between books by loading another page.

## The scale — this should drive "minimum components"

| | |
|---|---|
| books | **6** |
| chapters | **51** |
| prose objects parsed out of those chapters | **2,702** |
| rendered pages | **6** |
| framework source files | **107** |
| compiler source files | **54** (1,953 lines) |
| `.tsx` files in scope for the reference transform | 112 of 132 |
| a full TS-compiler-API scan of the corpus | low hundreds of ms |

**Six books.** Not six thousand. It should grow to a few hundred. Design for *instant while
editing prose* and for *not rotting*, not for scale.

## What is being added, and why the compiler must change

A reference notation in the prose, resolved statically against a **card catalogue**. Prefix
allocates, postfix returns:

```
 *[ X ]( Y )        allocate here                        -> nothing
 *$[ X ]( Y )*      allocate a stand-in, this writing    -> an address
**$[ X ]( Y )*      allocate a stand-in, the book        -> an address
**$[ X ]( Y )**     allocate a stand-in, the collection  -> an address to a reference
  $[ X ]( Y )*      no allocation, just stand in         -> an address
```

Plain `[ text ]( target )` too, and **it is already in use** in our covers:

```tsx
<Author>[Author: Doug](My Library Log)</Author>
<Subject>[Doug](Doug&rsquo;s Library)</Subject>
```

`(My Library Log)` is a **book title**, not a URL. Every book's author points at an autobiography;
"authorship lives in an autobiography" is already implemented, not proposed.

## The constraint that forces this into the static layer

The runtime substrate is an in-house reactive framework (components are classes; each has an
initialiser that runs once per construction). We established this month, over sixteen agents and
three candidate designs, that the initialiser **cannot be made to re-run** — and the decisive
reason is that **a miss is unrecordable**: the substrate cannot write down *"I asked for key K and
it was not there."* That negative dependency is exactly what an incremental system needs to be
sound. The runtime structurally cannot supply it. **A static parse can.**

So the catalogue is static, or the system is unsound. Settled.

# PART 2 · WHAT A LIBRARY LOOKS LIKE ON DISK

A library is a folder. Inside it are **book folders**; a book folder is any folder carrying a
`.book.tsx`. Beside them sits `..public/`, which is where everything generated goes.

```
.me/                                     THE LIBRARY (this is the live one, Doug's)
  my-library-log/                          A BOOK. Its .book.tsx is the book's own class.
    .book.tsx
    0-lead.tsx  1-the-books.tsx  2-the-sheet.tsx  ...      CHAPTERS, ordered by filename
    2-the-sheet.tsx.tsx                    A CHAPTER THAT DOCUMENTS A RESOURCE. The double
                                           extension means "the chapter about 2-the-sheet.tsx".
                                           The chapter places its own source with
                                           <Resource>2-the-sheet.tsx</Resource>.
  ..reference/                             ANOTHER BOOK (12 chapters). The `..` prefix is a
                                           library-catalogue book in our naming system.
  .claude-and-our-projects/                A SUBJECT FOLDER holding three more books:
    ..reference/  .claudes-importer/  semantic-reference-theory/.reference/

  ..public/                              EVERYTHING GENERATED, and the compiler itself
    .binding/                              THE COMPILER, COPIED IN. See Part 4.
      .graph.json                          THE PERSISTED CATALOGUE. See below.
      .manifest.json                       every file the last build wrote
      .pubconfig                           this library's configuration
      .shell.html  index.html  code.css    the page shell
      application/                         GENERATED MODULES (books.ts, routes.ts, stylesheets.ts)
      node_modules/                        this library's own install — the compiler is not shared
    assets/                                THE BUNDLE. One entry chunk per build, hashed.
    <book>/index.html                      THE PRERENDERED PAGES, one per book
```

Two things about that layout that matter to the design:

- **`node_modules` lives inside `.binding`.** The library is not a workspace member. It installs
  its own copy of everything, which is why the Vite config does the deduping described in 4.3.
- **`assets/` accumulates.** There are 27 `.book-*.js` and 13 `claudes-importer-*.js` chunks in
  there right now from past builds. `manifest/removal.ts` deletes what the *source* no longer
  writes, but hashed bundle output from old builds survives. Minor, but it is the kind of thing a
  clean design should just not have.

## The catalogue as it exists today

`.graph.json` — six entries, one per book. This is a real entry, verbatim:

```json
{
  "folder": "..reference",
  "book": {
    "name":    "Doug's Library",
    "title":   "Doug's Library",
    "author":  "My Library Log",
    "subject": "Doug's Library",
    "chapters":   ["Doug's Library", "The Librarian", "Table of Contents", "Lead",
                   "The books", "The Sheet", "The Masthead", "The Chapter Mark",
                   "The Plate", "The Ledger", "The Switchboard", "The Domain"],
    "catalogued": ["The books", "The Sheet", "The Masthead", ... ],
    "shelves":    ["Doug's Library", "Doug's Library", "My Library Log", "Claude & Our Projects"],
    "types":      ["Catalogue", "Cover", "Document", "Document"]
  },
  "digest": "eb6431b095e1fe70",
  "walked": 452
}
```

The six `walked` counts sum to exactly 2,702 — that is where the prose-object number comes from.
A book whose `digest` is unchanged is skipped on the next build.

**So the catalogue already exists and already has content-digest skipping.** The gap between this
and the design is exactly two things:

- **(a)** nothing below chapter level — no declaration sites, no anchors inside a chapter;
- **(b)** it is produced by **evaluating** the books (loading and running them) rather than
  **parsing** them.

# PART 3 · THE FRAMEWORK PACKAGE — `src/`, 107 files

This is the published npm package the books import. It is not the compiler, but the compiler's job
is to feed it, so you need to know what the vocabulary is. **One word per file**; a file is named
for the word it defines, and each file holds that word's class, its type and its registration.

finds a reference among a writing's own elements. Giving a `$Title` a reference means putting a
`$Reference` in its block. Nothing new is needed in the framework for that.

# PART 4 · THE COMPILER — `.binding/`, 54 files, 1,953 lines

Run as `tsx binding.ts`. It runs nine phases and exits.

**It is a TEMPLATE, not a dependency.** `manifest/copy.ts` copies this entire folder into each
library as that library's own compiler; `manifest/synced.ts` keeps a copy current with the package
it came from. **The library it compiles is its own parent folder.** No monorepo, no workspace.

## 4.2 `binding.ts` — the nine phases, real source

```ts
// THE BINDER IS A COMPILER: a sequence of named tasks, each run in order, each saying what it
// did, the sequence stopping at the first that fails.
//
// RESOLVE FOLLOWS SPECIFY, because a book is named by its own title and a title is a thing a
// running book answers. So the books are assembled, then read once — which is the expensive step,
// and the one that is kept — and only then are they named, ruled on, and given their addresses.

export const tasks: Task[] = [
    { name: 'configure', run: state => { state.chosen = configure(state.binding); ... } },

    { name: 'inventory', run: state => {
        state.found = walk(state.library, chosen);
        if (state.found.books.length === 0) throw new Error(`${state.library} holds no book`);
        const wrong = misaccounted(state.found, chosen);
        if (wrong !== undefined) throw new Error(wrong);
    } },

    { name: 'assemble', run: state => {
        state.previous  = manifest.read(state.binding);
        state.assembled = found.books.map(book => assemble(state.face, book));   // TO DISK
        state.written   = [books(state.binding, found), stylesheets(state.binding, chosen)];
    } },

    { name: 'specify', run: async state => {
        // LOADS AND RUNS EVERY BOOK, walks its object tree, writes the graph.
        const verdict = specifying(state.binding, found, scope, graph.read(state.binding), chosen);
        state.graph = graph.write(state.binding, verdict.held);
        const wrong = verdict.failures.length ? verdict.failures
                    : await running(state.binding, found, 'specification/library');
        if (wrong.length) throw new Error(`the library does not specify — ...`);
    } },

    { name: 'resolve', run: state => {
        state.table = resolution(found, graph, chosen);        // PURE. Never loads a book.
        state.written.push(routes(state.binding, state.table));
    } },

    { name: 'bundle', run: async state => {
        const built = await build({ ...configuration({ isPreview: false }), configFile: false });
        state.bundled = emitted(built);
    } },

    { name: 'render', run: state => { state.rendered = rendering(state.binding, names); } },

    { name: 'proof', run: state => {
        // RUNNABLE ON ITS OWN, reading the pages the last binding wrote, so a person checking one
        // page does not pay for a bundle to find out.
        const wrong = proof(state.face, pages);
        if (wrong.length) throw new Error(`the pages are not readable — ...`);
    } },

    { name: 'record', run: state => {
        const current = manifest.write(state.binding, {assembled, written, rendered, bundled});
        removal(state.face, state.previous, current);
    } },
];
```

**That top comment is what the new design kills.** "A title is a thing a running book answers" is
the only reason `resolve` follows `specify`. Parse the titles out of the source instead and the
expensive load-and-run-every-book step leaves the critical path entirely.

## 4.3 `vite.config.ts` — what is already there

Four plugins: `@vitejs/plugin-react` (with `decorators-legacy`), a `transformIndexHtml` template
plugin, `resources()`, and a preview middleware that 301s `/turing` to `/turing/` to match GitHub
Pages. Plus these, each one a bug already paid for:

- **`resolve.dedupe` = every dependency in package.json**, not a hand-written list. A book reaching
  for `chroma-js` failed the bundle with "Rollup failed to resolve import" because the hand list
  had never heard of it. *What a library installs is exactly what its books may reach for.*
- **`ssr.noExternal` = every `file:` dependency.** SSR externalisation made Node walk up from the
  package's own folder and load a **second copy of React**; every prerendered page came out an
  854-byte error shell **while the build reported success**.
- **`resolve.extensions` puts `.tsx` before `.ts`**, because a chapter and the resource it
  documents share a name, and Vite loaded the code in the chapter's place and ran it.
- **one chunk on purpose** — the pages are prerendered and a reader moves by loading another page,
  so splitting buys nothing; the warning limit is set above what we ship rather than at it.
- `build.outDir` is the library folder with `emptyOutDir: false`.

## 4.4 `assembly/book.ts` — the artifact that must go virtual

```ts
export const assemble = (face: string, book: Book): string => {
    const lines = [
        `import { $ } from '@dna-platform/chemistry';`,
        `import $Book from '${from}/.book';`,
        ...book.files.map(file => `import $${classed(file)} from '${from}/${named(file)}';`),
        `const Book = $($Book);`,
        ...book.files.map(file => `const ${classed(file)} = $($${classed(file)});`),
        `export const book = $<$Book>(`,
        `    <Book>`,
        ...book.files.map(file => `        <${classed(file)} />`),
        `    </Book>`,
        `);`,
    ];
    // WRITTEN ONLY WHEN IT CHANGED. A thousand books rewritten identically every build is a
    // thousand writes vite must then decide are new, and the digest that keeps a book from being
    // read again has the book's module among its inputs.
    if (!existsSync(book.module) || readFileSync(book.module,'utf8') !== written) writeFileSync(...);
    return relative(face, book.module);
};
```

Note it **already composes by reference** — it imports chapters, it does not inline them. So your
answer costs nothing to adopt; this file just needs to stop being a file. Its input is a
**directory**, so adding a thirteenth chapter invalidates nothing.

## 4.5 `assembly/resources.ts` — the plugin shape we would copy

```ts
export const resources = (): Plugin => ({
    name: 'binding:resources',
    enforce: 'pre',
    transform(code, id) {
        const file = id.split('?')[0];
        if (!file.endsWith('.tsx') || !code.includes('<Resource>')) return null;
        const standing = accountOfFiles(dirname(file)).resources.get(basename(file)) ?? [];
        const imports = [];
        const drawn = code.replace(placement, (_, asked) => {
            const named = standing.find(one => one.endsWith(asked));
            if (named === undefined) throw new Error(missing(basename(file), asked, standing));
            imports.push(`import resource${imports.length} from './${named}?raw';`);
            return `<CodeNavigatorForResource file="${named}">{resource${n}}</CodeNavigatorForResource>`;
        });
        return imports.length ? [importLine, ...imports, drawn].join('\n') : null;
    },
});
```

Its own comments carry two rulings:

- *"A resource is a BUILD-TIME fact. There is no disk at draw time and nothing to walk for."*
  Resolved at draw time instead, this once cost 291 seconds on one book and died on a 4GB heap,
  and because every book extends the library's own, one book took the whole library with it.
- *"It runs `pre`, so what the React plugin compiles is ordinary markup and nothing downstream
  needs to know a resource was ever written."*

## 4.6 THE BOOTSTRAP PROBLEM, stated exactly

```json
"bind": "tsx binding.ts",   "dev": "vite",   "build": "tsx binding.ts"
```

**`npm run dev` is literally `vite`.** It serves artifacts a *previous* `bind` wrote to disk —
`application/books.ts`, `application/routes.ts`, and the per-book modules.

**The dev server depends on the batch and cannot produce what it serves.** Right now the package's
own copy is stale — `books.ts` is absent, `routes.ts` is an older generated shape — so `npm run
dev` there fails outright. The live library works only because someone ran `bind` in it recently.

**This is the thing to fix. Everything else is detail.**

### Q2 · Where does the catalogue live, and when is it built? — **THE CRUX**

- **(b)** Lazy, with early transforms emitting proxies that resolve on a later pass.
- **(c)** Persisted and loaded from disk, rescanning only what changed by digest (what we do now).
