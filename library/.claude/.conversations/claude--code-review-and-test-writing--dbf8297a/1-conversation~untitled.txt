How are purity and idempotency related?


Delineated purity and idempotency as distinct functional programming concepts.




Great question! Purity and idempotency are related but distinct concepts:

Purity
A pure function:

Same input → Same output (deterministic)
No side effects (doesn't mutate external state)
typescript
// Pure
const pure = (x: number) => x * 2;
pure(5) === pure(5) === pure(5);  // Always 10

// Impure
let counter = 0;
const impure = (x: number) => x + counter++;
impure(5);  // 5
impure(5);  // 6 (different output!)
Idempotency
An idempotent operation:

Repeated application has same effect as single application
f(f(x)) = f(x)
typescript
// Idempotent
const setToTen = (obj: any) => { obj.value = 10; return obj; };
setToTen(setToTen(obj)) === setToTen(obj);  // Both leave obj.value at 10

// Not idempotent
const increment = (obj: any) => { obj.value++; return obj; };
increment(increment(obj)) !== increment(obj);  // Different effects!
The Relationship
Purity implies idempotency for repeated calls with same input:

typescript
// Pure function
const double = (x: number) => x * 2;
double(5) === double(5);  // Idempotent with respect to output

// But NOT idempotent in the mathematical sense:
double(double(5)) !== double(5);  // 20 !== 10
Idempotency doesn't imply purity:

typescript
// Idempotent but impure (has side effects)
const ensureConnected = () => {
    if (!connected) {
        connectToDatabase();  // Side effect!
        connected = true;
    }
};

Your view() methods should be:

Pure: Same chemical state → same tree (no randomness, no external reads)
Idempotent in effect: Calling twice in succession produces identical trees
typescript

firstTree === secondTree;  // Idempotent: no changes between calls

Understanding $Particle: A Deep Analysis
The Identity Paradox $Particle creates a fascinating identity system where each particle has a unique symbol that serves as its persistent identifier across all transformations. The [$symbol] is assigned once during construction and becomes the particle's immutable fingerprint in the React reconciliation tree. What's remarkable is how this symbol can be temporarily borrowed - when the wrapped view function executes, it swaps symbols with its $this target, performs the render, then restores the original symbol. This creates a brief quantum superposition where the particle assumes another's identity for rendering purposes while maintaining its own identity for React's tracking.

The Template Singleton Pattern Every $Particle class maintains a static template instance through [$$template]. This singleton serves as the canonical instance for that particle type - the first instance created becomes the template, stored on the constructor itself. This pattern ensures that particle types can have a default, reusable instance without explicitly managing singletons. The [$isTemplate] getter provides a clean way to check if any given instance is the blessed template. This becomes crucial for Chemistry's component system where templates serve as the default rendering targets when no specific instance is provided.

The View Wrapper Architecture The most ingenious aspect is how the constructor hijacks the prototype's view method and replaces it with a wrapped function. This wrapper isn't just a simple proxy - it's a self-contained execution environment that carries both the instance ($view.$this) and the original implementation ($view.$view). When called, it applies props to the target instance, calls the bond lifecycle method, and then executes the original view bound to potentially a different this. This creates a method that's simultaneously an instance method and a portable function component.

The Mutable Function Properties JavaScript functions are objects, and $Particle exploits this by attaching $this and $view as mutable properties on the wrapped view function. This means any code holding a reference to particle.view can dynamically change what instance it operates on or what implementation it executes. This is neither pure OOP nor pure functional programming - it's a hybrid that uses functions as mutable containers for behavior and state references. The function becomes a configurable pipeline rather than a fixed operation.

The Props Application System The [$apply] method provides a systematic way to map React props to particle properties. It takes the incoming props object and applies each property prefixed with '$' to the instance, except for React's reserved props (children, key, ref). This creates a seamless bridge between React's props-based component model and Chemistry's property-based object model. The children prop gets special handling, stored in the [$children] symbol rather than as $children, maintaining clear separation between content and configuration.

The Frame Method Duality The frame method introduces another layer of flexibility by accepting a $this parameter that shadows the instance's own this. This allows one particle to provide the framing (the Fragment wrapper with its key) while another provides the content (the view). The key always comes from the frame owner (the real this), maintaining stable identity in React's reconciliation even as the content changes. This separation of container identity from content identity enables sophisticated composition patterns.

Symbol-Based Encapsulation The extensive use of symbols for private properties creates true encapsulation in JavaScript. These symbols aren't just for privacy - they create a parallel property space that won't collide with user-defined properties. A particle can have both a public symbol property and a private [$symbol] without conflict. This dual namespace allows the framework to maintain its internal state while giving developers full freedom with the public property space.

The Universal Render Capability Every particle can render every other particle through view swapping. Since the wrapped view function just calls $view.$this[$apply] and $view.$view.bind($view.$this)(), any particle can serve as a rendering vessel for any other particle's data and behavior. This universality means particles aren't locked to their original types - they can shapeshift at runtime, assuming different identities for different purposes while maintaining their React tree position.

The Lifecycle Integration Points The [$bond] method provides a hook point that runs after props are applied but before rendering. This creates a predictable lifecycle where particles can establish relationships, validate state, or perform other setup based on their current configuration. The fact that this is called on the swapped $this rather than the original instance means the lifecycle follows the effective instance, not the vessel instance.

The Self-Contained Component Export The module exports new $Particle().view, creating a default particle instance and immediately extracting its wrapped view function. This exported Particle is simultaneously a React function component and a method with swappable internals. It carries its own default instance but can be reconfigured to render any other particle. This creates a universal component that can become anything while maintaining a stable module export.

The Type System Integration The [$type] property stores the constructor function, creating a runtime type system. This allows particles to know their class even after prototype chain manipulation. Combined with the template system, this creates a two-level type identity: the class (shared by all instances) and the template (the canonical instance of that class). This runtime type information enables dynamic behavior based on particle types without instanceof checks.

The Children Handling Strategy Children are handled specially through the [$children] symbol rather than being treated as a regular prop. This separation allows particles to distinguish between configuration (props that become $ properties) and content (children to be rendered). The view can access children through this[$children] while props can still include children for pass-through to nested components, creating flexibility in how content flows through the component tree.

The Identity Preservation Through Swapping The symbol swapping mechanism in the wrapped view is subtle but crucial. Before rendering, it temporarily assigns the vessel's symbol to the target instance, renders, then restores the original symbol. This ensures that any code within the view that references this[$symbol] gets the correct identity for React keys, while the instance's original symbol remains unchanged after rendering. This temporary identity loan maintains React's reconciliation stability.

The Constructor as Factory The constructor doesn't just initialize - it performs a complex transformation of the instance into a hybrid object-component. It extracts the view method from the prototype, wraps it with the execution environment, and replaces the instance method with this wrapper. This happens for every instance, meaning each particle gets its own wrapped view with its own $this and $view references. The constructor is really a factory for creating these portable component functions.

Testing Strategy Philosophy Testing $Particle requires validating both the static structure (template relationships, symbol presence, type references) and the dynamic behavior (view swapping, prop application, identity preservation). Tests should verify the contracts that enable the framework's flexibility without being brittle to implementation details. The focus should be on the observable behaviors that developers will depend on: Can views be swapped? Do props apply correctly? Does identity persist through transformations? These behavioral contracts matter more than specific implementation mechanics.

class $Catalogue {
    private dependencies = new Map<symbol, Map<any, any>>();
    private references = new Set<Symbol>();
    private canonical = Symbol("$Catalogue.canonical");

    $get<T extends $ParameterType>(type: T, reference?: symbol): $Parameter<T> | undefined {
        reference = reference || this.canonical;
        let dependencies = this.dependencies.get(reference)!;
        if (!dependencies) return undefined;
        const $type = $symbolize(type);
        return dependencies.get($type);
    }

    $set<T extends $ParameterType>(type: T, dependency: $Parameter<T>, reference?: symbol) {
        reference = reference || this.canonical;
        const $type = this.symbolize(type);
        if (!this.check(type, dependency))
            throw new Error(`${$type} is not a valid type reference for ${dependency}`);

        let dependencies = this.dependencies.get(reference)!;
        if (!dependencies) {
            dependencies = new Map();
            this.references.add(reference);
            this.dependencies.set(reference, dependencies);
        }

        dependencies.set($type, dependency);
    }

    protected symbolize(type: $ParameterType): any {
        if (typeof type === 'string') return type;
        if (typeof type === 'function')
            return type.name ? type.name : type.toString();
        return $symbolize(type);
    }

    protected check(type: $ParameterType, dependency: any): boolean {
        if (typeof type === 'string') return true;
        if (typeof type === 'function') return true;
        return $ParamValidation.validateArgument(dependency, type);
    }
}

For the Dynamic Loading Pattern in the Bundle:
Since Rollup bundles everything together, the circular dependency is already resolved at build time. But your require('./chemical') won't work in the bundle. Here's the solution:

typescript
// particle.tsx
export class $Particle {
    private static $$Chemical: any;
    private static get $Chemical() {
        if (!this.$$Chemical) {
            // In bundled environment, $Chemical is already available
            // through module resolution
            if (typeof require !== 'undefined') {
                // Development/Node environment
                const { $Chemical } = require('./chemical');
                this.$$Chemical = $Chemical;
            } else {
                // Bundled environment - use a different strategy
                // The bundle will have already resolved this
                // You could use a registration pattern:
                this.$$Chemical = (globalThis as any).__CHEMISTRY_CHEMICAL__;
            }
        }
        return this.$$Chemical;
    }
}

// chemical.ts  
export class $Chemical extends $Particle {
    static {
        // Register itself for runtime lookup
        if (typeof globalThis !== 'undefined') {
            (globalThis as any).__CHEMISTRY_CHEMICAL__ = $Chemical;
        }
    }
}
Or even simpler - since Rollup resolves circular dependencies at bundle time, you might not need the dynamic loading at all in production. You could:

typescript
// particle.tsx
let $ChemicalClass: any;

export class $Particle {
    private static get $Chemical() {
        return $ChemicalClass;
    }
}

// Export a setter for $Chemical to call
export function set$Chemical(chemical: any) {
    $ChemicalClass = chemical;
}

// chemical.ts
import { set$Chemical } from './particle';

export class $Chemical extends $Particle {
    // ...
}

// Register itself
set$Chemical($Chemical);
This way the circular dependency is resolved through a setter pattern that works in both environments.

Testing Philosophy: Building Durable Unit Tests
The Purpose of Unit Testing Unit tests exist to verify that a piece of code fulfills its contract - the promises it makes about its behavior. A unit test should document what the code is supposed to do, not how it does it. When a developer reads a test, they should understand the intended behavior of the system without needing to examine the implementation. Tests serve as living documentation that executes, providing both specification and verification. The best unit tests outlive multiple refactorings of the underlying code because they test the stable contract, not the volatile implementation.

Testing Features vs Implementation Details The cardinal sin of unit testing is coupling tests to implementation details. An implementation detail is anything that could change without breaking the public contract. Testing that a private method was called, that a specific internal data structure was used, or that operations happened in a specific order (when order doesn't matter to the outcome) creates brittle tests that break during valid refactoring. Feature testing focuses on observable behavior: given this input, expect this output; given this state change, expect this new state. When you test features, you can completely rewrite the internals and the tests still pass if the behavior remains correct.

The Relationship Principle Good tests verify relationships and invariants, not absolute values. Testing that "ID equals 1" is brittle; testing that "ID1 differs from ID2" is durable. Testing that "the first instance has template status" is fragile; testing that "exactly one instance has template status" is robust. This principle extends to all aspects of testing: verify that sorting produces correct ordering, not specific positions; verify that transformations maintain properties, not specific outputs; verify that relationships hold, not that specific values appear.

Isolation Without Mocking Madness Unit tests should isolate the unit under test, but excessive mocking creates tests that verify mocking configuration rather than actual behavior. The best tests use real objects where possible, creating minimal test doubles only for external dependencies, expensive resources, or non-deterministic behavior. When you mock everything, you're testing that your mocks work, not that your code works. When a test requires extensive setup and mocking, it often signals that the code has poor separation of concerns.

State Independence Each test should start from a known state and leave no traces that affect other tests. Global state, static variables, and singletons are the enemies of test independence. When tests can run in any order and still pass, you have achieved true test isolation. This means resetting counters, clearing caches, and ensuring each test constructs its own test subjects. The temptation to share setup between tests for performance should be resisted unless the setup is truly immutable.

Semantic Test Structure Tests should follow the Arrange-Act-Assert pattern with clear semantic boundaries. Arrange sets up the test context, Act performs the operation being tested, and Assert verifies the outcome. When a test has multiple acts and asserts interleaved, it's really multiple tests masquerading as one. Each test should verify one logical concept, even if that concept requires multiple assertions. The test name should complete the sentence "It should..." with a clear, specific behavior.

Testing Error Paths Good tests verify both success and failure modes. Testing only the happy path leaves half the code unverified. Error conditions, edge cases, and boundary values often harbor the most bugs. When code can fail in multiple ways, each failure mode deserves its own test. This includes not just exceptions, but also graceful degradation, fallback behaviors, and error recovery. The error path tests often reveal missing error handling or unclear error contracts.

Performance Characteristics as Features While unit tests shouldn't be performance tests, algorithmic complexity is a feature. If a function promises O(1) lookup or O(n log n) sorting, tests can verify this contract without measuring exact timings. This might mean testing that doubling input size doesn't quadruple execution iterations, or that accessing any element takes constant operations. These tests document performance contracts without being sensitive to hardware or environmental variations.

Refactoring Confidence The ultimate measure of test quality is refactoring confidence. Good tests let you refactor fearlessly because they verify behavior, not structure. If changing an implementation detail breaks tests, those tests are too coupled. If changing behavior doesn't break tests, those tests are too loose. The sweet spot is tests that break only when actual behavior changes, providing a safety net that catches real regressions while allowing implementation evolution.

Test as Design Tool Writing tests first, or at least thinking about testability during design, produces better architecture. Code that's hard to test is often hard to use. If setting up a test requires extensive boilerplate, the API is probably too complex. If testing requires accessing private members, the abstraction is probably wrong. If tests are deeply nested with complex conditions, the code probably has too many responsibilities. Tests are the first client of your code - if they struggle, so will human clients.

import { $lib, $rep } from '@/catalogue';

            const user = $rep('user');

            const found = $lib.$find(user);
            expect(found).toEqual({ name: 'Alice', id: 1 });
        });

        it('should return undefined for missing representations', () => {
            const ghost = $rep('ghost');
            expect($lib.$find(ghost)).toBeUndefined();
        });

        it('should overwrite on re-index', () => {
            const config = $rep('app.config');
            
            $lib.$index(config, { version: 1 });
            expect($lib.$find(config)).toEqual({ version: 1 });
            
            $lib.$index(config, { version: 2 });
            expect($lib.$find(config)).toEqual({ version: 2 });
        });

        it('should handle complex types', () => {
            const fn = $rep('handler');
            const handler = () => console.log('handling');
            
            $lib.$index(fn, handler);
            expect($lib.$find(fn)).toBe(handler);
        });
    });

    describe('$next() - Inheritance Chain', () => {
        it('should create child that inherits from parent', () => {
            const setting = $rep('setting');
            $lib.$index(setting, 'parent-value');
            
            const child = $lib.$next();
            expect(child.$find(setting)).toBe('parent-value');
        });

        it('should allow child to override parent values', () => {
            const theme = $rep('theme');
            $lib.$index(theme, 'light');
            
            const child = $lib.$next();
            child.$index(theme, 'dark');
            
            expect(child.$find(theme)).toBe('dark');
            expect($lib.$find(theme)).toBe('light'); // Parent unchanged
        });

        it('should create deep inheritance chains', () => {
            const root = $rep('root');
            const mid = $rep('mid');
            const leaf = $rep('leaf');
            
            $lib.$index(root, 'from-root');
            
            const middle = $lib.$next();
            middle.$index(mid, 'from-middle');
            
            const bottom = middle.$next();
            bottom.$index(leaf, 'from-bottom');
            
            // Bottom sees entire chain
            expect(bottom.$find(root)).toBe('from-root');
            expect(bottom.$find(mid)).toBe('from-middle');
            expect(bottom.$find(leaf)).toBe('from-bottom');
            
            // Middle doesn't see bottom's values
            expect(middle.$find(leaf)).toBeUndefined();
            
            // Root only sees its own
            expect($lib.$find(mid)).toBeUndefined();
            expect($lib.$find(leaf)).toBeUndefined();
        });
    });

    describe('$new() - Fresh Catalogues', () => {
        it('should create isolated catalogue', () => {
            const data = $rep('data');
            $lib.$index(data, 'root-data');
            
            const fresh = $lib.$new();
            expect(fresh.$find(data)).toBeUndefined();
        });

        it('should not affect root when writing to fresh', () => {
            const fresh = $lib.$new();
            const key = $rep('key');
            
            fresh.$index(key, 'fresh-value');

        });

            cat3.$index(rare, 'found-in-third');
