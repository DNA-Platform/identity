Monorepos & The Pattern You're Describing
Standard monorepos (Nx, Turborepo, pnpm workspaces) keep everything in one repo — multiple packages, shared tooling, a single Git history. The coordination layer is the build system itself. There's no illusion of separation; it really does all live together.
What you're describing — one place where everything is visible but the real source of truth is distributed across multiple repos — has a few real implementations:
1. Git Submodules
The oldest approach. A parent repo contains .gitmodules entries pointing at other repos at specific commits. The parent references child repos but doesn't contain their history. git clone --recursive pulls everything. The coordination layer is manual — you update submodule pointers explicitly. Very fragile in practice; most teams hate it.
2. Git Subtree
Merges foreign repo history into a subdirectory of your repo. You can push/pull changes back to the origin repo. Less annoying than submodules but history gets messy fast.
3. The meta Tool (npm)
This is the closest match to what you're imagining. You have a "meta repo" that is itself just a .meta JSON file listing child repos and where they clone to. Running meta git status runs across all of them simultaneously. Each child repo is independently versioned, has its own remote, and can be worked on standalone — but the meta repo is the coordination layer that lets you operate across all of them as a unit. Genuinely elegant for this use case.
4. Changesets / Nx Affected + Separate Remotes
Some teams use a monorepo internally but publish each package from its own auto-generated repo via CI (GitHub's actions/checkout + push to separate repos). The source of truth is the monorepo; the individual repos are derived outputs.
5. What GitHub itself Does
GitHub uses a combination: a "universe" repo as the coordination layer with submodules pointing at individual service repos. The universe repo is what their deploy system reads. Engineers work in individual repos but the deploy state lives in the coordinator.

This is actually a well-solved pattern, and the right answer is pnpm workspaces as your monorepo layer, with each package structured to be independently publishable and independently clonable.
The key architectural insight is: every package should be valid on its own, and the monorepo is just a convenience wrapper — not something any package depends on.
How It Works
text
$chemistry/                     ← the monorepo coordination layer
  pnpm-workspace.yaml
  package.json                  ← just scripts, no real code
  packages/
    catalogue/                  ← could be github.com/doug/$chemistry-catalogue
      package.json              ← name: "@chemistry/catalogue"
      src/
      tsconfig.json
    reflection/                 ← could be github.com/doug/$chemistry-reflection
      package.json              ← name: "@chemistry/reflection"
      src/
      tsconfig.json
    particle/
    ...
Each package.json declares its dependencies on other packages using the same name it would have on npm:
json
{
  "name": "@chemistry/reflection",
  "dependencies": {
    "@chemistry/catalogue": "workspace:*"
  }
}
The workspace:* protocol is the magic — pnpm resolves it to the local package during development, and strips it to a real semver range when you publish. The package itself never knows or cares whether it's living in a monorepo or not.
Extraction Path
When a package outgrows the monorepo, you:
Create github.com/doug/$chemistry-reflection and push the packages/reflection/ directory there as the root
In the monorepo, replace that directory with either a git submodule pointing at the new repo, or just remove it and let consumers depend on the published npm package
Contributors who want to work across all packages still clone the monorepo and get the submodule alongside the other packages — it just happens to have its own remote now
The meta tool makes option 3 even smoother: the monorepo becomes a .meta file listing all the child repos, and meta git clone reconstitutes the whole workspace in one command, each package with its own origin.
The Practical Tension
The one thing to decide up front: is the monorepo the source of truth, or is it a view over independent repos?
Source of truth in monorepo (Turborepo style): packages don't have their own repos until you explicitly extract them. Simpler while the project is young.
Source of truth in individual repos (meta style): the monorepo is just a manifest. Each package always has its own remote. More overhead early, but zero migration cost later.
For $Chemistry, given that the packages have clear semantic boundaries (catalogue, reflection, particle) and you're already thinking about this, I'd start with the monorepo as source of truth — but structure each package as if it already lives alone. When reflection gets big enough to warrant its own repo, the extraction is just a git subtree split and a pointer swap.
