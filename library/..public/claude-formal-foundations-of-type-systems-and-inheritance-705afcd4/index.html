The Formal Foundations of Type Systems
The Starting Point: Typed Lambda Calculus
The minimum formalism is surprisingly small. Everything starts with the simply-typed lambda calculus (STLC, or λ→), which you can write on an index card:
Syntax (terms):
text
e ::= x            -- variable
    | λx:τ. e      -- abstraction (function)
    | e₁ e₂        -- application (call)
Syntax (types):
text
τ ::= B            -- base type (Int, Bool, etc.)
    | τ₁ → τ₂      -- function type
Typing judgments take the form Γ ⊢ e : τ, read as "under context Γ, expression e has type τ." The context Γ is just a list of variable-type bindings like x:Int, y:Bool.
Typing rules (the entire system is just three rules):
text
  x:τ ∈ Γ
────────────── (Var)
  Γ ⊢ x : τ


  Γ, x:τ₁ ⊢ e : τ₂
─────────────────────── (Abs)
  Γ ⊢ (λx:τ₁. e) : τ₁ → τ₂


  Γ ⊢ e₁ : τ₁ → τ₂    Γ ⊢ e₂ : τ₁
──────────────────────────────────────── (App)
  Γ ⊢ e₁ e₂ : τ₂
That's it. That's the kernel from which Haskell's and TypeScript's type systems are both grown. Each rule reads top-to-bottom as "if the stuff above the line holds, then the stuff below the line holds."
Soundness: Progress and Preservation
The standard technique for proving a type system is sound (i.e., "well-typed programs don't go wrong") is the Wright-Felleisen method (1994). You prove exactly two theorems:
Preservation (aka Subject Reduction): If Γ ⊢ e : τ and e → e' (e steps to e'), then Γ ⊢ e' : τ. Types are preserved through evaluation.
Progress: If ∅ ⊢ e : τ (e is well-typed in the empty context), then either e is a value, or there exists some e' such thate → e'. Well-typed closed terms don't get stuck.
Together these give you: a well-typed program either produces a value or runs forever — it never reaches a nonsensical stuck state. This is what "sound" means.
Adding Subtyping (Inheritance): System F-sub
To model inheritance/subtyping, you add a subtyping relation τ₁ <: τ₂ ("τ₁ is a subtype of τ₂") and one critical new typing rule:
text
  Γ ⊢ e : τ₁    τ₁ <: τ₂
────────────────────────────── (Sub)
  Γ ⊢ e : τ₂
This is the subsumption rule: if something has type τ₁ and τ₁ is a subtype of τ₂, then it also has type τ₂. This single rule is the formal heart of all inheritance.
The subtyping rules for function types give you the famous variance rule:
text
  τ₃ <: τ₁    τ₂ <: τ₄
────────────────────────── (S-Arrow)
  τ₁ → τ₂  <:  τ₃ → τ₄
Functions are contravariant in their input and covariant in their output. This is the formal reason why, for instance, Animal → Cat is a subtype of Cat → Animal.
For record types (which model objects/classes), you add:
text
{x:Int, y:Int, z:Int} <: {x:Int, y:Int}
A record with more fields is a subtype of one with fewer — this is width subtyping, the formal basis of structural inheritance (which is exactly TypeScript's model).
What Haskell Actually Uses: System FC
Haskell's compiler (GHC) uses System FC — System F (polymorphic lambda calculus) extended with coercions. The key additions over the basic system:
Type variables and ∀-quantification: ∀α. τ (this is System F, enabling parametric polymorphism)
Type equality coercions: a term-level witness γ : τ₁ ~ τ₂ that proves two types are equal
Coercion application: e ▷ γ — cast expression e using coercion γ
This is how GHC compiles GADTs, type families, and newtypes — all complex type equalities get reduced to explicit coercion terms in the intermediate language. The key paper is Sulzmann, Chakravarty, Peyton Jones, and Donnelly (2007), "System F with Type Equality Coercions."
The soundness proof for System FC still uses progress + preservation, just with a more elaborate set of rules.
What TypeScript Deals With: Structural Subtyping + Row Types
TypeScript's situation is formally messier because its type system is intentionally unsound in several places (e.g., bivariant function parameter checking was a deliberate choice). But the formal model closest to what it does is:
Structural subtyping on record/object types (width + depth subtyping)
Union and intersection types: τ₁ | τ₂ and τ₁ & τ₂
Bounded polymorphism: <T extends U> is formally ∀(T <: U). τ
This is essentially System F-sub with unions and intersections, sometimes called System F∧∨<:. The TypeScript team has published on this — notably the work on narrowing and control flow analysis sits outside classical type theory and is more ad hoc.
The Minimum You Need to Hold in Your Head
ConceptFormalism
Functions + typesSimply-typed λ-calculus (λ→)
Generics/polymorphismSystem F (λ2)
Inheritance/subtypingSystem F-sub (F<:)
Haskell's actual coreSystem FC (F with coercions)
Soundness proof techniqueProgress + Preservation
The canonical textbook is Benjamin Pierce's Types and Programming Languages (TaPL). Chapters 1–15 cover everything above, and it's genuinely well-written. If you want to go deep on System FC specifically, the GHC wiki and the Sulzmann et al. paper are the primary sources.
The beautiful thing is that the whole edifice really does rest on those three typing rules I started with — every extension is just adding new syntax, new types, and new rules in that same judgmental format.

Notation Reference
Judgment Form
text
Γ ⊢ e : τ
Γ — typing context: a finite map from variable names to types. Example: {x: Int, y: Bool}
⊢ — "entails" / "proves"
e — a term (expression)
τ — a type
Full reading: "context Γ proves that term e has type τ"
∅ ⊢ e : τ — e has type τ with no assumptions (closed term)
Inference Rules
text
  premise₁    premise₂
────────────────────────── (RuleName)
  conclusion
Above the line: conditions that must hold
Below the line: what follows if they do
This is a sequent: conclusion holds iff all premises hold
Rules compose: a premise of one rule can be the conclusion of another — this is how you build derivation trees
Meta-variables (naming conventions)
text
e, e₁, e₂    — terms (expressions)
τ, τ₁, τ₂    — types
x, y, z       — variable names
Γ, Δ          — contexts
B             — base types (Int, Bool, ...)
γ             — coercions (System FC)
α, β          — type variables (System F)
Key Operators
text
λx:τ. e       — function taking x of type τ, returning e
                 (λ is the binding operator; x is bound in e)

e₁ e₂         — apply function e₁ to argument e₂
                 (left-associative: f a b = (f a) b)

τ₁ → τ₂       — function type: takes τ₁, returns τ₂
                 (right-associative: A → B → C = A → (B → C))

∀α. τ          — universal type: τ holds for all types α
                 (α is bound in τ)

τ₁ <: τ₂      — τ₁ is a subtype of τ₂
                 (every value of τ₁ is also a value of τ₂)

τ₁ ~ τ₂       — type equality (System FC)

e ▷ γ          — cast e by coercion γ (System FC)

Γ, x:τ         — context Γ extended with binding x:τ

x:τ ∈ Γ        — binding x:τ exists in context Γ

e → e'         — e reduces (evaluates) to e' in one step
BNF Grammar Notation
text
e ::= x | λx:τ. e | e₁ e₂
::= means "is defined as." | means "or." This defines e as one of three forms — a variable, an abstraction, or an application. This is the complete syntax. There are no other term forms in the base calculus.
Derivation Example
Prove {f: Int→Bool, x: Int} ⊢ f x : Bool:
text
  f:Int→Bool ∈ {f:Int→Bool, x:Int}       x:Int ∈ {f:Int→Bool, x:Int}
  ─────────────────────────────────(Var)   ───────────────────────────(Var)
  {f:Int→Bool, x:Int} ⊢ f : Int→Bool      {f:Int→Bool, x:Int} ⊢ x : Int
  ──────────────────────────────────────────────────────────────────────────(App)
  {f:Int→Bool, x:Int} ⊢ f x : Bool
Two applications of (Var) feed into (App). The tree terminates when every leaf is an axiom (a rule with no premises, or a context lookup). This is a typing derivation — a proof that the term is well-typed. If no such tree exists, the term is ill-typed.

System F (λ2) — Polymorphic Lambda Calculus
Extend STLC with two new term forms and one new type form:
New Syntax
text
e ::= ... | Λα. e | e [τ]
τ ::= ... | α | ∀α. τ
Λα. e — type abstraction: a term parameterized over a type variable α
e [τ] — type application: instantiate a polymorphic term with concrete type τ
α — a type variable (stands for an unknown type)
∀α. τ — universal type: τ for all possible α
New Typing Rules
text
  Γ ⊢ e : τ    α ∉ FV(Γ)
────────────────────────────── (TAbs)
  Γ ⊢ (Λα. e) : ∀α. τ
FV(Γ) — free type variables in context Γ
The side condition α ∉ FV(Γ) ensures α is genuinely abstract — Γ doesn't already mention it
text
  Γ ⊢ e : ∀α. τ₁
──────────────────────── (TApp)
  Γ ⊢ e [τ₂] : τ₁[α := τ₂]
τ₁[α := τ₂] — substitute τ₂ for every free occurrence of α in τ₁
New Reduction Rule
text
(Λα. e) [τ]  →  e[α := τ]
Type application reduces by substituting the type argument into the body. This is the type-level analog of(λx. e) v → e[x := v].
Derivation Example
The polymorphic identity function:
text
  α:Type, x:α ⊢ x : α
  ──────────────────────────(Abs)
  α:Type ⊢ (λx:α. x) : α → α
  ────────────────────────────────(TAbs)
  ∅ ⊢ (Λα. λx:α. x) : ∀α. α → α
Instantiate it at Int:
text
  ∅ ⊢ (Λα. λx:α. x) : ∀α. α → α
  ──────────────────────────────────────(TApp)
  ∅ ⊢ (Λα. λx:α. x) [Int] : Int → Int
Then by reduction:
text
(Λα. λx:α. x) [Int]  →  λx:Int. x
Relationship to Haskell/TypeScript
text
-- Haskell
id :: forall a. a -> a        ≡  id : ∀α. α → α
id x = x                      ≡  Λα. λx:α. x
text
// TypeScript
function id<T>(x: T): T       ≡  id : ∀α. α → α
Both languages infer the Λ and [τ] — you never write type abstractions or type applications explicitly. The compiler inserts them. System F is the formal object they're elaborating into.
Bounded Quantification (F<:)
TypeScript's <T extends U> requires one further extension — combine System F with subtyping:
text
τ ::= ... | ∀(α <: τ). τ
text
  Γ, α <: τ₁ ⊢ e : τ₂
──────────────────────────────── (TAbsSub)
  Γ ⊢ (Λ(α <: τ₁). e) : ∀(α <: τ₁). τ₂


  Γ ⊢ e : ∀(α <: τ₁). τ₂    Γ ⊢ τ₃ <: τ₁
─────────────────────────────────────────────── (TAppSub)
  Γ ⊢ e [τ₃] : τ₂[α := τ₃]
The only change: α is no longer unconstrained — it must be a subtype of a bound. This is System F<: (F-sub), described formally in Cardelli & Wegner (1985) and chapters 26–28 of TaPL.

SRT — Notes on the Formalism
What is specified
Domain: Referents. A referent is that which a variable might stand for in any consistent first-order logic. This is the domain of discourse — not objects, not sets, not types. Referents.
Signature: One ternary relation, no functions, no constants.
text
R(x, y, t)
Alternate notation via "transpiration":
srt
x =t> y
x — subject position (that which refers)
y — object position (that which is referred to)
t — transpiration (the manner/mode/context of the referring)
Logical framework: First-order logic. Axioms are hypothetical only (no assertoric axioms in base SRT).
Referent roles: Referents can play two semantic roles:
Subjective / symbolic: arbitrary representation, no required literal form. Symbols.
Objective / literal: that which is represented. Literals.
This is not a type distinction in the formal sense yet — it's a role distinction within the semantics of R.
Extension mechanism
SRT can only be extended by:
Adding one constant at a time
Accompanied by axioms that describe it — these constitute a definition (in SRT's own sense of "definition")
The extended theory must remain consistent
Once extended with referents and definitions that constitute a consistent theory, it ceases to be SRT and becomes a named Semantic Theory — an ontology rather than an epistemology.
Semantic conjugation
Defined as the propositional equivalent of homoiconicity. SRT can host its own canonical representation: it can describe the relationship between a representation and what that representation refers to, using the same R(x,y,t) relation. SRT's canonical representation is natural language, expressed existentially.
Perspective and consciousness (the speculative layer)
A perspective is a consistent semantic theory (a consistent extension of SRT). Adding new literals not in its representation makes the perspective incoherent (inconsistent). Coherence can be restored (non-uniquely) by adding symbolic referents that incorporate the new literals — this is subjective qualification.
text
perspective P (consistent)
    + new literal l ∉ representation(P)
    → P' (inconsistent)
    + symbolic referent s such that l ∈ representation(P'')
    → P'' (consistent, P'' ≠ P)
A change in perspective = objective disqualification → subjective qualification. A conscious experience = a representation of this change, possessed by the qualifier, in the context of identity semantics. Consciousness = the narrative preservation of qualifier identity through this process (semantic homeostasis).
What is NOT yet specified (flagged in our earlier assessment)
Axiom schemas for R(x,y,t): What are the structural axioms? Reflexivity? Transitivity? Symmetry? What holds of R in general before any extension?
Formal definition of transpiration (t): What sort of thing is t? Is it a referent? A relation? Does it range over the same domain as x and y?
Precise rules for definitional extension: What exactly counts as a valid definition? What is the formal criterion for "axioms that describe a constant"?
Consistency proof (or relative consistency): No proof yet that SRT-as-described is consistent, or consistent relative to some known system.
The literal/symbol role distinction has no formal typing yet — it's described semantically but not captured in the syntax or inference rules.
Where this sits relative to what we just covered
The type-theoretic formalism (λ-calculus, System F, etc.) gives you typing judgments: Γ ⊢ e : τ. SRT doesn't have that yet. It has a single relation and an extension discipline. The question you're now asking — building a type system — is essentially: how do you layer typing judgments onto the R(x,y,t) substrate? How does the subject/object role distinction become a formal type distinction? How does definitional extension interact with typing?
That's the gap between where SRT is and where the formalism in this conversation can take it.
