Press one of the three channel buttons to select a channel — pick an empty one (the LED above that number will be solid/dim if unpaired, or blink slowly if currently bonded)
Press and hold that same channel button for ~3 seconds until the LED above it starts blinking rapidly (about 2x per second). That's pairing mode.

Channel 1 is often pre-paired to the included dongle out of the box, so use channel 2 or 3 for Bluetooth to keep the dongle option available.
If holding the button doesn't trigger the rapid blink, try a quick triple-press of the channel button instead — a few models use that gesture.

Choose Administrator → OK

16:43 UTC, 8 May 2026
Important distinction to confirm first: in netplwiz Properties there are two fields — User name and Full name. Make sure which one you're editing, because the risks are very different:
Full name = display name only. Safe to change to "Ana." This is what shows on the lock screen and Start menu. No downside.
User name = the actual SAM account identifier Windows uses internally. Changing this for a Microsoft-account-linked user is where things get risky.
If you change User name on a Microsoft-linked account, potential issues:
Link to the Microsoft account may break or behave weirdly. Windows internally references the account via this identifier for OneDrive sync, Microsoft Store license bindings, app authorizations, and (importantly) BitLocker recovery key escrow. The mapping can desync.
The profile folder doesn't change. C:\Users\<whatever-it-is-now> stays as-is. You'd just have a username/folder mismatch.
Login behavior is unchanged. She'd still sign in with her email — the email is what authenticates against Microsoft's servers. The local username is just a label.
It may silently revert. Microsoft account sync can overwrite local changes on next handshake. People report this both happening and not happening; it's inconsistent.
Edge cases: some apps that registered themselves against the old username (rare but it happens — VPN clients, certain license systems) may need re-auth.
The honest call: if all you want is "Ana" to display on the lock screen and in Start menu, change Full name, not User name. That's what Full name is for, and it's risk-free. User name is the kind of field you change when you have a specific reason and accept the chance of something downstream breaking.
If netplwiz is letting you change User name freely, that's because Windows doesn't gate it — but "Windows lets you do it" and "Windows handles it gracefully" aren't the same thing here.
Want to do Full name only, or do you have a reason you specifically want the internal identifier changed too?

How do I create an SSH key for ana@atlas.love - I know it uses the web interface and bash
Claude
13:36 UTC, 9 May 2026
Open Git Bash (or PowerShell — both work, but Git Bash is closer to the Linux flow):
1. Generate the key:
bash
ssh-keygen -t ed25519 -C "ana@atlas.love"
When prompted:
File path: press Enter for default (C:\Users\<her-username>\.ssh\id_ed25519), or specify a custom name like id_ed25519_ana if she'll have multiple keys
Passphrase: optional but recommended — adds a second factor in case the key file is compromised
2. Start the SSH agent and add the key:
bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
(If you used a custom filename, point at that instead.)
3. Copy the public key:
bash
cat ~/.ssh/id_ed25519.pub | clip
The | clip pipes it straight to the Windows clipboard. (Or just cat it and copy manually — make sure you grab the entire line, starting with ssh-ed25519 and ending with ana@atlas.love.)
4. Add to GitHub via web:
Sign in to GitHub as Ana
Top-right avatar → Settings
Left sidebar → SSH and GPG keys
New SSH key
Title: something descriptive like "Windows desktop" or "Ana's main PC"
Key type: Authentication Key
Paste into the Key field → Add SSH key
May prompt for password / 2FA confirmation
5. Test:
bash
ssh -T git@github.com
You should see Hi ana-username! You've successfully authenticated...
One thing worth setting up while you're at it — tell git who Ana is for commit attribution:
bash
git config --global user.name "Ana"
git config --global user.email "ana@atlas.love"
Otherwise commits will be attributed to whatever default git picked up.
If this machine is going to have both your account and Ana's at different times, ping me — there's a slightly different setup using ~/.ssh/config to keep multiple keys cleanly separated.

They're two independent agents that share filesystem, git, auth, and account, but not context. Think of them like two engineers pair-programming on the same repo from different keyboards — they can both see the code, both edit it, but neither knows what the other is currently thinking about.
What they share:
Auth & account — same OAuth token, same usage budget. Both consume from your Pro/Max allocation.
Filesystem — both can read and write any file in the workspace. They see each other's edits the next time they read a file.
Git state — same repo, same branch, same staged/unstaged changes. If one commits, the other sees the new state on its next read.
Configuration — CLAUDE.md, .claude/settings.json, MCP servers, custom slash commands, skills, allowlist. Anything in ~/.claude/ or .claude/ is read by both.
Session storage — both write transcripts to ~/.claude/projects/<workspace-hash>/. You can resume either session from either interface.
What they don't share:
Conversation context — completely separate. Terminal Claude has no idea what panel Claude has been told.
Plans & working memory — if you told the panel "we're refactoring auth," the terminal doesn't know.
Permission state — toggling YOLO mode or Shift+Tab cycles only affect that session.
In-flight tool calls — separate processes.
The big gotcha: file-system race conditions.
If both sessions edit the same file roughly simultaneously, last-write-wins. Worse: each one reads, then writes, based on what it read — so even sequential edits can lose data if their windows overlap. Two scenarios that bite people:
Panel Claude refactors userService.ts while terminal Claude is also writing to it → one of their changes silently disappears.
Terminal Claude does git checkout . to undo something while panel Claude has uncommitted changes in its working memory → panel Claude's "I just edited this" model is now stale.
Patterns that work well:
Different files, same repo. Panel works on frontend, terminal works on backend. No collision risk.
One plans, one executes. Use the panel in Plan mode to design something complex; once you've got a plan you like, paste it into terminal Claude with --dangerously-skip-permissions and let it grind. Or vice versa.
One explores, one writes. Terminal Claude does codebase archaeology (grep heavy, "how does X work?") while panel Claude implements based on what you've learned. The exploration session stays out of the implementation context.
Background long task in terminal, interactive in panel. Run claude -p "fix all eslint errors" --dangerously-skip-permissions > out.log in PowerShell as a one-shot, work normally in the panel meanwhile.
Patterns that cause pain:
Both editing the same files concurrently.
Both running npm install or modifying package.json at once.
Both holding "current state of X" in working memory and acting on stale assumptions.
Practical hygiene if you're going to run two:
Commit before splitting them. Clean git status is your safety net.
Mentally assign domains. "Panel owns src/components/, terminal owns src/api/." Even just for an hour.
Tell each one what the other is doing. "There's another Claude session refactoring the auth module right now, don't touch auth/." It'll respect that as context.
Don't run both in YOLO mode at the same time unless you really know what you're doing. The collision potential goes up sharply when neither pauses for confirmation.
Resuming either from either:
claude --resume in PowerShell shows a list including sessions started in the panel.
/resume in the panel shows sessions started in the terminal.
So if you start something in the terminal, get pulled away, and want to continue in the panel later, you can. They're the same data, just different chrome.

A few less obvious settings:
Sign-in screen background — by default it inherits the lock screen. To use a solid color or different image: Settings → Accounts → Sign-in options → scroll down → check/uncheck "Show lock screen background picture on the sign-in screen."
For multiple monitors — the lock screen image is the same across all displays; Windows scales it. If you want different images per monitor on the lock screen, you can't out of the box (third-party tools like DisplayFusion can).
For a Windows-spotlight-style rotating image but with your own photos — use Slideshow with a folder; that's the closest. Spotlight specifically pulls from Microsoft's CDN and you can't substitute your own.
If you want the lock screen to actually appear (and not get skipped by auto-login): Settings → Accounts → Sign-in options → "If you've been away, when should Windows require you to sign in again?" → set to "When PC wakes up from sleep" or set a time. Otherwise the lock screen never shows.
