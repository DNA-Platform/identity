What approaches exist for maintaining bidirectional links between documentation and source code at scale? I'm interested in systems where the documentation references the code AND the code references the documentation — like Doxygen, Rustdoc, literate programming, doc-as-code. What survives maintenance at scale and what tends to rot? Specifically: how do teams keep the links from breaking when either side changes?

The useful way to organize this space isn't by tool but by what forces a link to be revisited when one endpoint changes. Every linking scheme is really a bet about that forcing function, and durability tracks it almost perfectly. There are four forcing functions, in ascending order of strength:
Proximity — you see the doc because it's physically next to the code you're editing.
Shared lifecycle — doc and code are co-versioned and reviewed in the same change.
Mechanical verification — CI fails if the link is broken.
Single source of truth — the link can't exist in a broken state because both endpoints are derived from one artifact.
Before mapping tools onto that, the distinction that matters most at scale: there are two kinds of rot, and almost all tooling only addresses the first.
Referential rot — the target no longer exists (dead link, renamed symbol, stale line number). Mechanically detectable.
Semantic rot — the link still resolves, but the prose no longer describes what the code does. The link checker passes and the documentation lies.
Semantic rot is the real killer, and only two things catch it: making the doc executable, or generating both sides from one source. Everything else is hygiene for referential rot.
Mapping the approaches
The co-location/extraction family (Doxygen, Javadoc, Rustdoc, JSDoc, Sphinx autodoc) wins on proximity. Code→doc is free because they're the same file; doc→code is generated. This is genuinely rot-resistantfor API-level docs, because a developer editing the function stares at the docstring. But it only covers "what this symbol is." It does nothing for narrative ("how auth works across these twelve files"), and that narrative is where rot concentrates.
Literate programming (WEB/CWEB, noweb, Org-babel) collapses the link by making one source — maximally coherent, which is why it never escapes its niches. The narrative order and the compiler's required order diverge, diffs get ugly, and most engineers won't write prose to write code. It's a single-source-of-truth win that loses on every social axis at team scale.
Doc-as-code (Markdown in-repo, MkDocs, Docusaurus, Antora) buys you shared lifecycle: same repo, same PR, CODEOWNERS on the docs directory. That's a real improvement, but the actual cross-references inside the prose are still just hyperlinks and descriptions that rot silently. Shared lifecycle protects existence better than content.
Then the mechanically-verified tier, which is where things actually hold:
Doctests — Python doctest, Rust's compiled-and-run doc examples, Elixir doctests, Go's ExampleFoo functions in godoc. The doc is a test. Change the behavior and CI breaks. This is the single most robust bidirectional mechanism in common use, because it ties doc content to code behavior, not just to an anchor's existence — so it catches semantic rot.
Transclusion — instead of pasting code into docs (which drifts immediately), the doc includes real source lines by reference: Sphinx literalinclude, mdBook {{#include}}, embedme, Docusaurus snippet plugins. The doc shows current code because it pulls from the file. This kills the "example diverged from reality" problem without requiring the example to be executable.
Link checking in CI (lychee, Sphinx nitpicky mode) — catches referential rot only. Necessary, not sufficient.
And the strongest tier, single source of truth:
Schema-first generation — OpenAPI, Protobuf, GraphQL SDL, JSON Schema. Both the docs and the client/server code are generated from one spec, so the link can't rot. This is the biggest practical win in the whole field, and it works precisely by dissolving the bidirectional problem into two unidirectional generations from a shared root.
Derived cross-reference graphs — Kythe (Google), Glean (Meta), Sourcegraph, LSP-based indexers. These are the actual scale answer for true bidirectional navigation. Rather than authoring links, language indexers emit a graph of relationships from the source on every index run. Derived links can't rot because they're regenerated; if the symbol moves, the next index reflects it.
That last point is the meta-lesson, and the one I'd press hardest: at real scale, the winning move is to stop maintaining links and start deriving them. Authored links rot proportional to change velocity times distance. Derived links regenerate. Teams that win either generate both endpoints from one spec, or generate the link graph from static analysis of the endpoints. Hand-maintained traceability survives only where it's mandated and heavily tooled — DOORS-style requirement IDs in DO-178C/ISO 26262 safety-critical work — and there it survives by being expensive, not by being clever.
So, concretely, how teams keep links from breaking
The patterns that survive maintenance, roughly in order of leverage: generate API reference from source, never hand-write it; put anything that can be an example into a doctest so the test runner enforces it; transclude real code rather than pasting; for APIs, go schema-first so both sides derive from the spec; run a link checker in CI for referential rot; co-version docs with code and gate doc directories with CODEOWNERS so changes are at leastseen; and for genuine cross-references, lean on a derived index (Sourcegraph/Kythe-style) rather than authored hyperlinks.
What rots no matter what you do: conceptual and architectural narrative — "how the system works as a whole." It can't be doctested and can't be generated, because it describes an emergent property of many parts. The honest mitigations are to keep it deliberately high-level and slow-changing, date it, and treat it as append-only history (ADRs) rather than pretending it's live truth — plus generating what can be generated from it, like dependency or call-graph diagrams, so at least the structural skeleton stays current even as the prose ages.
The clean way to state the whole thing: a link's half-life is set by its forcing function, and content-level forcing (executable or generated) is the only kind that survives both rename and rewrite. Everything weaker buys you detection of broken pointers while letting the prose quietly go false.
If you want, I can go deeper on any one branch — the Kythe/Glean graph model is interesting if you're thinking about scale, and the doctest-vs-transclusion tradeoff has some subtlety worth unpacking depending on whether your priority is "examples are correct" or "examples are real."
