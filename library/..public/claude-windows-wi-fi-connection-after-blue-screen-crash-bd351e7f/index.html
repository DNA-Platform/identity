This is a classic post-BSOD network stack corruption pattern. The Telegram clue is actually very revealing—Telegram uses its own MTProto protocol and can bypass certain Windows networking components that other apps depend on.
Most likely culprit: Corrupted DNS settings
Telegram maintains its own DNS resolution and hardcoded server IPs, so it works even when Windows DNS is broken. Chrome and WhatsApp rely entirely on Windows system DNS.
Quick diagnostic: Open Command Prompt and run:
text
ping 8.8.8.8
If that works but ping google.com fails, DNS is definitely your problem.
Fixes to try in order:
Flush DNS and reset (Command Prompt as Administrator):
text
ipconfig /flushdns
ipconfig /release
ipconfig /renew
If that doesn't work, manually set DNS:
Settings → Network & Internet → Wi-Fi → your network → Edit DNS
Set to Manual, IPv4: 8.8.8.8 and 8.8.4.4 (Google's DNS)
Nuclear option if still broken (Admin Command Prompt):
text
netsh winsock reset
netsh int ip reset
Then restart.
The BSOD likely corrupted something in the Winsock catalog or DNS client service. The manual DNS fix should get you working immediately, and the netsh reset will clean up the underlying corruption.
Try the ping test first—that'll confirm the diagnosis.

Glad that worked. Here's what likely happened:
The BSOD interrupted Windows mid-write to some network state file or registry entry. When Windows crashed, the DNS Client service was probably in the middle of caching something or updating its resolver state. On reboot, Windows restored the network adapter connection (so Wi-Fi "connected" fine), but the DNS Client service loaded corrupted cached data.
Result: Your machine could reach the internet at the IP level (packets flowed fine to 8.8.8.8), but it couldn't translate "google.com" → IP address. Every app that asked Windows "where is google.com?" got garbage or timeouts.
Why Telegram worked: Telegram is built for adversarial network environments (it was designed to resist Russian government blocking). It hardcodes backup server IPs, uses its own DNS resolution, and can bootstrap connectivity without relying on the OS DNS stack. Once it connected, Windows saw actual traffic flowing and updated the network status icon from globe → signal bars—but that was cosmetic. The underlying DNS was still broken.
The fix: ipconfig /flushdns cleared the corrupted cache, and release/renew forced a fresh DHCP handshake that repopulated DNS settings cleanly from your router.
BSODs are rare these days—usually a driver issue, hardware problem, or (occasionally) a bad Windows update. If you see another one soon, might be worth checking the crash dump to see what triggered it.
