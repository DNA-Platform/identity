Yes, several good options exist:
Dedicated SVG optimizers
SVGO (SVG Optimizer) — the gold standard. Node.js-based CLI/library that applies dozens of optimization passes including merging paths, removing redundant attributes, collapsing groups, and shortening coordinate precision. Has a web UI at svgomg.net
Scour — Python-based alternative to SVGO, similar approach
What they actually do to paths
Merge adjacent/overlapping paths with the same fill/stroke into combined <path> elements using boolean union
Convert absolute coordinates to relative (shorter strings)
Round decimal precision (e.g. 12.3456789 → 12.35)
Remove invisible/duplicate nodes
Collapse <g> groups with identical styles into the child elements directly
Path-specific merging tools
For the more sophisticated geometric merging you're describing (actually unioning path shapes), that's more of an Illustrator/Inkscape operation than a pure compression tool:
Inkscape's Path > Union (or via command line: inkscape --actions="select-all;path-union")
Illustrator's Pathfinder > Unite
These reduce separate overlapping shapes into single paths, which can dramatically shrink file size for complex illustrations.
For Ana's workflow specifically, SVGOMG (the web UI for SVGO) is probably the most practical — drag and drop, visual preview, adjustable settings. For batch processing microstock submissions, SVGO's CLI can be scripted to process entire folders at once.
The biggest wins typically come from coordinate precision reduction and group collapsing rather than path merging, unless the illustration has a lot of overlapping shapes.

What SVGO/SVGOMG won't do

What you'd actually need
The pixel-merging problem is essentially rectangle packing / run-length encoding in 2D — finding the minimum set of rectangles that covers all same-colored regions. This is a well-studied but non-trivial algorithm. Tools that actually do this:
Potrace — converts bitmaps to smooth vector paths by tracing region boundaries. This is the closest to what you're imagining, but it produces curves, not rectangles
Primitive (by Michael Fogleman) — represents images as overlapping geometric primitives, SVG output available
png2svg type tools — some do naive per-pixel rects, others do basic run-length merging
The core problem
A 100×100 bitmap naively produces 10,000 <rect> elements. Even after perfect rectangle merging, a photographic image might still need thousands of shapes to represent color gradients. SVG is genuinely bad at photographic content — the resulting file would be larger than the original PNG.
Where this approach actually works well is for pixel art, icons, or images with large flat color regions — where the rectangle merging produces dramatic reduction.

This is a genuinely profound point and I want to make sure I have it right.
The line detector ambiguity
When you convolve and find a line, you've detected a discontinuity. But there are two fundamentally different causes:
Occlusion boundary — two different objects, one partially hidden. The line "belongs to" the nearer object's silhouette
Surface boundary — one continuous scene, like a tile grout line or a painted stripe. Both sides belong to the same depth layer
Why collapsing this is catastrophic
A compression system that greedily resolves this becomes wrong in ways that propagate. If you misclassify an occlusion as a surface boundary, you'll try to fit one gradient across what are actually two independent objects at different depths — and fail expensively.
Your proposed solution
Don't resolve it. Encode the line as a detected feature with the ambiguity intact — essentially a node in a semantic graph with an unresolved type flag. Later passes, with more context, can resolve it. Or leave it unresolved and let reconstruction handle both interpretations.
This maps to something real in neuroscience
V2 and V4 are thought to do exactly this disambiguation — they receive V1's edge detections and add the occlusion/surface label using surrounding context. It's a later, more expensive computation.
For Samantha this means
Your encoding pipeline has explicit uncertainty states. Lines carry a boundary_type: [occlusion | surface | unknown] tag, and downstream shape matching uses this to constrain which library shapes are even candidates.
The unknown state isn't a failure — it's compressed ambiguity, resolved lazily.
