How do graph databases model recursive hierarchies where nodes define rules for their own organization?
Claude
10:14 UTC, 17 June 2026
Recursive hierarchies are the case graph databases are built for, so it's worth separating the easy half of your question from the interesting half.
The easy half: a hierarchy is just nodes joined by directed edges of one relationship type — (child)-[:CHILD_OF]->(parent). What makes it recursive is that the same edge type chains to arbitrary depth and the engine traverses that chain without you specifying how deep. MATCH (n)-[:CHILD_OF*]->(ancestor) walks the entire ancestor path regardless of length — the thing SQL does awkwardly with recursive CTEs and graph engines do natively. A node with several parents turns the tree into a DAG; if edges can cycle you've left "hierarchy" behind and need bounded depth (*..n) or explicit cycle detection to keep traversal well-defined.
The interesting half is "nodes define rules for their own organization" — reflexive structure, where part of the graph describes how the rest is arranged. There's a ladder here, increasing in power and in how much thedatabase itself understands the rules rather than your application code.
Rules as properties. The crude version: a node carries orderingRule: "date_desc" or inheritancePolicy: "override". Cheap, but the rule is opaque to the engine — only your code interprets it, and traversal can't reason about it.
Rules as nodes (reification). Promote the rule to a first-class node and point at it: (Category)-[:GOVERNED_BY]->(Rule). Now rules are queryable, shareable across many nodes, and versionable — and a rule node can itself sit in a hierarchy, giving you a meta-hierarchy traversable by the same queries as the data. This is the move that makes the reflexivity real rather than cosmetic.
Inheritance / resolution. Once a node can define a rule, the question is whether descendants inherit it, and that's resolved at query time by walking up the ancestor chain to the nearest node that defines the relevant rule — most-specific-wins, the same pattern as the CSS cascade, prototypal inheritance, or lexical scope:
cypher
MATCH path = (n)-[:CHILD_OF*0..]->(a)
WHERE a.orderingRule IS NOT NULL
RETURN a.orderingRule ORDER BY length(path) LIMIT 1
The hard part isn't the walk; it's the conflict policy when two ancestors disagree. You need a deterministic rule — nearest wins, explicit precedence, or monotonic union — and you have to pick, because the graph won't pick for you.
Metacircularity. The deepest version is where the rules and the data they govern are the same kind of thing — same node space, same relationship types — so the graph describes itself:

RDF/OWL is the canonical realization. rdfs:subClassOf and rdf:type are themselves resources, the ontology — the rules — lives in the same triple store as the instances, and SPARQL queries both levels uniformly. An OWL reasoner gives you actual inheritance: define a property on a class and it's entailed for every subclass and instance below it. SHACL pushes further, making the "shapes" that constrain a graph into graphs themselves. TypeDB builds a type system with inheritance directly into the data model and runs inference rules as part of the schema — about as literal a realization of "nodes defining the rules for their own organization" as exists in a shipping product.
Three conceptual hazards become unavoidable once rules can reference rules:
Levels stop being structural. Data versus metadata is no longer about how anything is stored — it's just which relationship you're following. Powerful, but without discipline (named graphs, explicit typing) you lose track of which level you're on.
Termination and well-definedness. A rule that governs its own organization can land you evaluating the rule in a context that contains the rule. That's a fixpoint problem, and it's why Datalog uses least-fixpoint semantics with stratified negation — to keep the meaning well-defined. Without something equivalent, self-reference gives you the database version of "this sentence is false."
Materialize or evaluate. Forward-chain (run the rules and store the derived edges) or backward-chain (resolve at query time)? Storage and staleness against query cost. OWL reasoners tend to materialize; Datalog and Datomic can do either.
So the real spectrum runs from "rules are inert strings the application reads" to "rules are nodes the engine reasons over" to "the graph is its own schema." The further right you go, the more the database does the organizing instead of your code — and the more you inherit the obligations of any self-describing system: a deterministic resolution order when rules conflict, and a guarantee that self-reference terminates.
