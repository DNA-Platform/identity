Context, so the answer fits our situation: a React component library built on styled-components v6 that prerenders every page to static HTML and hydrates it with the same components. Pieces of writing carry semantic classes put there by annotation objects: pd-for what a piece of writing is (pd-paragraph, pd-code), pa- for an annotation's mark (pa-table, pa-reference). A Format is an annotation that is itself a styled component and may replace the element it annotates (a Table replaces a section's element with its grid, whose column rules are generated inside it). One Theme component renders a single global sheet keyed on those classes and provides eight token values (font, size, leading, measure, space, ink, paper, link) through ThemeProvider. We are drawing the line between a component's own styles and that global sheet, and want to draw correctness from how the community already does it. Please answer with sources, the three main considerations for each part: (1) How do mature design systems in 2026 (for example Radix Themes, Chakra and Panda, MUI with Pigment CSS, shadcn on Tailwind, and a BEM-style system such as GOV.UK Frontend) divide component-local rules from global semantic-class rules, structure against skin and tokens against rules, and what fails when the line is drawn wrong (specificity wars, two authors of one property on one element, a theme coupled to every class)? (2) Should token values flow through ThemeProvider interpolations or through CSS custom properties written once by the theme, given server rendering and hydration parity, theme switching without regenerating classes, and where styled-components v6 and the broader ecosystem are heading? (3) Is there a recognised home for the rules a component's meaning requires regardless of theme, such as a parenthetical hidden, a blank invisible, or a closed page unseen: with the component that means it, or in the theme's sheet? (4) How do a semantic-class stylesheet and CSS-in-JS component styles coexist without collisions: cascade layers (@layer), injection order, naming convention, or something else, and what do design systems that mix the two actually do?

The ecosystem has largely converged, and your architecture maps onto that convergence with few changes. Tokens become CSS custom properties written once. Component rules own structure. The global class sheet becomes a lower-precedence layer. The rules that carry meaning (hidden, invisible, unseen) sit outside the theme as enforced invariants.
1. How mature systems divide the work
Consideration 1: Tokens are a separate artifact that rules only read.
Radix Themes: it doesn't use any styling libraries internally; under the hood it's built with vanilla CSS. Its single stylesheet is built on separate tokens.css, components.css, and utilities.css files, and you also get access to the same CSS variables that power the Radix Themes components.
Panda and Chakra: Panda gives tokens their own layer, where the tokens layer contains css variables for tokens and semantic tokens. Chakra v3 appends @layer reset, base, tokens, recipes to the top of the generated emotion stylesheet.
shadcn: all components reference variables like --primary, --background, --radius; change them under :root / .dark and every component updates.
The rule, in every case: a theme is a set of values, and rules never contain a theme's literals.
Consideration 2: Component rules and system-wide rules live in named strata, and precedence between them is decided by the architecture, not by accident.
GOV.UK Frontend: follows a layered architecture inspired by ITCSS. The strata run helpers (mixins for things like focus states and visually hidden content), components, utilities, and overrides, where overrides are high-specificity classes typically using !important.
MUI: its modular layer mode splits styles into mui.global, mui.components, mui.theme, mui.custom, and mui.sx.
For you: the pd-/pa- sheet corresponds to Radix's components.css or MUI's mui.global, a named stratum, rather than an unstructured global sheet.
Consideration 3: What fails when the line is wrong.
Specificity wars. styled-components' own FAQ recommends the &&& trick for overrides, repeating the generated class to bump specificity high enough to override source order. That advice exists because the two stylesheets had no declared order.
Two authors of one property on one element. A GOV.UK user found that adding govuk-visually-hidden to a custom component did nothing, because without !important the component's own CSS overwrote it. MUI documents the same thing appearing when layers are turned on: the theme margin suddenly takes precedence because the theme layer comes after the components layer. The winner was never designed; it fell out of injection order.
A theme coupled into rules. MUI warns that to prevent SSR flicker there must be no usage of theme.palette.mode === 'dark' in the code base, because a rule that branches on the theme has to be regenerated when the theme changes.
For you: each (element, property) pair should have exactly one author. A Table that replaces a section's element with its grid should own every layout property of that element. The theme sheet should supply only skin properties there, through tokens.
2. ThemeProvider interpolation or CSS custom properties
Consideration 1: Hydration parity and first paint.
Class generation. In styled-components' own dynamic-styles guidance, prop interpolation generates new classes per unique value, while CSS custom properties generate none.
The v6.4 path. createTheme() converts a plain theme object into one where every leaf value is a CSS custom property reference. Passing that object to ThemeProvider gives stable class name hashes across themes, which prevents hydration mismatches when switching between light and dark.
MUI's measured trade-off. HTML is bigger because variables are generated for both modes, but time to interactive is shorter because stylesheets are not regenerated between modes.
Consideration 2: Switching themes without regenerating classes.
styled-components. The dark-mode recipe is CSS-first, and the prefers-color-scheme rule applies before any JavaScript runs, so there's no flash.
MUI. ThemeProvider does not re-render when switching between light and dark modes when cssVariables: true is set.
A theme switch then means rewriting eight custom properties on one selector. No component re-renders, and no class hash changes.
Consideration 3: Where styled-components and the ecosystem are heading.
styled-components' status. A March 2025 "Thank You" post moved the project into maintenance mode. Releases continued anyway: 6.3.0 added React Server Components support, and a v7 alpha replaced stylis with an in-house CSS parser.
ThemeProvider under RSC. ThemeProvider is a pass-through in RSC (no React context); use createTheme() or CSS custom properties for theming instead.
MUI's Pigment CSS. It remains in alpha and is on hold; it is not being developed at the moment.
Everyone else (Panda, Chakra, Tailwind v4/shadcn, MUI's cssVariables) is built on custom properties.
One practical constraint: since tokens become var() strings, they must be interpolated directly rather than combined with JavaScript arithmetic; compose in CSS via calc(), or use theme.raw when a real number is needed. For you: the Theme component's single sheet writes the eight properties once. ThemeProvider can remain, carrying only the stable var() references.
3. Where rules that carry meaning belong
Consideration 1: The platform puts meaning in markup, and the markup alone can be overridden.
Why 0 is fragile. The hidden state can be easily overridden with a CSS display property set to anything other than none, so any component that sets display: grid can accidentally un-hide something.
Tailwind's response. Tailwind v4 reinforces it in its base layer with !important: elements with a hidden attribute stay invisible unless using hidden="until-found"; remove the attribute if you want the element visible.
The cost. Existing patterns that overrode hidden with utilities or JavaScript-set display stopped working. In other words, the semantics were deliberately placed out of reach of skin.
Consideration 2: The recognised home is a system-level helper that cannot be overridden, independent of both theme and component.
GOV.UK visually hidden. GOV.UK's visually-hidden helper lives in the helpers stratum. After the collision described above, its mixins gained an optional important parameter defaulting to true.
GOV.UK display none. For hiding from everyone, GOV.UK also offers .govuk-!-display-none as an override class for users who don't want to use [hidden].
The pattern is: the component states the meaning as an attribute or state class, and an invariant rule outside the theme enforces it.
Consideration 3: Distinguish the kinds of "unseen", because they are different CSS.
Hidden from everyone: hidden means display none, removed from layout and from the accessibility tree.
A parenthetical still read aloud: use a visually-hidden helper.
A blank that keeps its space: use visibility: hidden.
A closed page that should still be searchable: hidden="until-found" behaves very differently than hidden and doesn't actually use display: none.
For you: each of your three cases maps to one of these, set by the Format that means it and enforced by an invariant layer the Theme never writes.
4. How the semantic-class sheet and component styles coexist
Consideration 1: Cascade layers are what the mixed systems actually use.
MUI on Emotion: enableCssLayer wraps Material UI styles in @layer mui, which anonymous-layer styles from CSS Modules, Tailwind, or plain CSS then override.
Chakra: does the same on top of Emotion, as above.
Radix: users assign the Radix import to a named layer with @import ... layer(radix_ui).
The deciding rules. Normal declarations in unlayered styles override layered ones, but important declarations reverse the order: important declarations in the first layer win, and all layered important declarations beat unlayered ones.
Consideration 2: For styled-components, the least fragile arrangement is to layer the global sheet and leave component output unlayered.
Stylis in v5 and v6. In v5, an @layer block inside a component template didn't wrap the generated class. v6 bumped stylis to 4.2.0 to enable @layer rule support. I haven't verified that nested-layer wrapping works in v6 or the v7 parser, so test it before relying on it.
Not depending on it. Put the Theme sheet in @layer pd.reset, pd.theme and leave styled-components output unlayered. Component rules then beat semantic-class rules regardless of specificity, which is exactly the "overridden by anonymous layer styles" relation MUI documents.
Where the invariants go. Put them !important in the earliest layer, where they beat both. This is the same mechanism a real bug report shows cutting the other way: a (0,5,1) unlayered selector lost to Tailwind's (0,1,0) layered !important purely because Tailwind's was layered.
Consideration 3: Order statement first; naming prevents clashes but not precedence.
The order statement. Panda notes that adding the layer line to the top of your CSS determines the order in which layers are applied. In your prerendered HTML, emit @layer ...; in a static <style> ahead of the styled-components tag, so injection order stops mattering.
Prefixes. Prefixes like govuk-, rt-, and your pd-/pa- stop names from colliding, and hashed classes do the same for components. Neither decides who wins. Only layers (or the &&& workaround) do.
