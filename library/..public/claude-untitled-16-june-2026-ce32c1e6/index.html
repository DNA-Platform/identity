Before the axis-by-axis comparison, one upfront question that changes everything: do you control the Electron app, or is it third-party? It determines the whole architecture, so I'll flag where it matters.
Recommended stack (short version)
Persistent .NET 10 (LTS) worker process running FlaUI 5.0 (UIA3), talking to your Node/TS process over a length-prefixed named-pipe protocol (MessagePack or JSON frames). Do not embed .NET in-process via edge-js, and do not spawn PowerShell per call. Keep UFO2's hybrid-detection idea but not UFO2 itself. Reserve the Anthropic computer-use API for a rarely-fired Tier-3 fallback, if at all.
Now the details.
(1) FlaUI via edge-js vs PowerShell-mediated UIA
Neither of the two framings you gave is the right target. Both PowerShell-subprocess and edge-js are flawed for opposite reasons, and the better answer is "FlaUI, but out-of-process over IPC."
PowerShell-mediated UIA is the worst of the options you're currently on: every call pays process-spawn cost (100s of ms), you're marshaling through System.Windows.Automation (the older UIA2 managed wrapper) or COM via reflection, and you have no persistent element handles — you re-resolve the tree every invocation. That's almost certainly your current latency and flakiness source.
FlaUI is the right library. It's actively maintained — FlaUI.Core/FlaUI.UIA3 are at 5.0.0 (Feb 2025), with repo activity into 2026 — MIT-licensed, and it gives you a clean UIA2/UIA3 choice plus built-in retry/condition logic and pattern wrappers. Use UIA3 (the COM-based modern API); UIA2 is the legacy managed path and you only fall back to it for the rare control that misbehaves under UIA3.
But edge-js is the wrong transport for it. edge-js still works, but its focus shifted to .NET Core long ago and Mono is deprecated; more importantly it's a native node-gyp addon, which means ABI-fragile rebuilds on every Node major bump, and — the dealbreaker — it loads the CLR in-process with your Node/Electron process. UIA calls block, hang, and occasionally deadlock COM apartments. When (not if) that happens in-process, it takes your main process with it. You want crash isolation. So: FlaUI yes, edge-js no, run it in a separate process.
(2) Does UFO2's hybrid UIA+vision add value for a well-accessible Electron app?
For a deterministic automation system against an Electron app with good accessibility: no, not as a system, and the vision half adds little.
Two separate points:
UFO2 itself is the wrong abstraction layer. It's a Python 3.10+ multi-agent AgentOS — HostAgent/AppAgent hierarchy, LLM-in-the-loop, OmniParser for vision, RAG knowledge substrate, MCP-coordinated actions. It fuses Windows UIA with vision-based parsing to support diverse interface styles, and that's genuinely good engineering, but it's an autonomous task-executor, not an embeddable automation primitive. Bolting it under a Node/TS system means running a Python agent stack and accepting nondeterminism where you presumably want repeatable scripted actions.
The hybrid UIA+vision value proposition specifically: vision (OmniParser-style) earns its keep when the UIA tree is incomplete — canvas/WebGL-rendered controls, image-only buttons, custom-drawn widgets with no accessible role/name. An Electron app with good accessibility exposes the Chromium accessibility tree through UIA with proper roles, names, and values, so vision is mostly redundant cost, latency, and nondeterminism. Steal the pattern — "try UIA, fall back to vision only when UIA returns nothing" — and implement a thin version yourself; don't adopt the framework.
The real Electron gotcha that makes people wrongly reach for vision: Chromium's accessibility tree is lazy and opt-in. Until an AT/UIA client attaches (or you force it), the UIA tree under an Electron window can be empty or partial, and people conclude "UIA doesn't work on Electron" and switch to screenshots. Fix the root cause instead: launch with --force-renderer-accessibility, and/or app.setAccessibilitySupportEnabled(true) / the ELECTRON_ENABLE_ACCESSIBILITY path. Do that and UIA becomes reliable and fast, and the vision question mostly evaporates.
If you control the app, there's a much stronger move than UIA for the web content at all: drive the renderer over the Chrome DevTools Protocol (--remote-debugging-port) with Playwright/CDP, and use UIA/FlaUI only for the native shell — OS file dialogs, system menus, tray, native modals. Splitting "web content → CDP, native chrome → UIA" is dramatically more robust and selector-stable than treating the whole window as a UIA surface. This is probably the highest-leverage architectural decision available to you.
(3) Computer-use API as a UIA fallback
Defensible as a last-resort tier, not as load-bearing infrastructure.
The current models behind the tool are Claude Opus 4.8, Sonnet 4.6, and Haiku 4.5; computer use was introduced as a feature letting Claude interpret screen content and simulate keyboard/mouse input, and the tool itself is a date-versioned beta tool type (check the docs for the current computer_* version string before wiring it). Sonnet is the usual price/latency pick for computer-use loops.
Realistic constraints as a fallback: it's seconds per step, costs per action, nondeterministic, operates at raw screen coordinates (so Win11 per-monitor DPI scaling will bite you on coordinate mapping), and requires you to ship screenshots of the user's screen to an external API — a real privacy/security consideration if this is end-user software. So it's appropriate only for the genuine long tail: novel, unscripted, ambiguous states UIA can't reach and that you can't pre-program.
A cleaner tiering than "UIA then Claude":
Tier 1 — UIA via FlaUI. Deterministic, fast, handles the overwhelming majority.
Tier 2 — local element detection. Template matching or a local OmniParser-style detector for coordinates, when a control has no usable UIA node. Cheap, offline, no API round-trip.
Tier 3 — computer-use API. Only for genuinely novel states. Most production systems never fire this.
If you do add Tier 3, gate it behind explicit conditions and log every invocation; you don't want silent, expensive, nondeterministic actions in your hot path.
(4) Better IPC than PowerShell subprocess
Yes — the persistent out-of-process worker is the single biggest win. Two good transports depending on how large your automation surface is.
Named pipes (my default recommendation). Lowest friction, no extra runtime deps, native on both sides. Node connects with net.connect({ path: '\\\\.\\pipe\\yourpipe' }); .NET serves with NamedPipeServerStream. Frame messages with a 4-byte length prefix and serialize with MessagePack (msgpackr on Node, MessagePack-CSharp / MessagePack NuGet on .NET) — JSON is fine if you'd rather keep it inspectable. This gives you a long-lived worker, persistent UIA element caches keyed by an ID you hand back to Node, request/response correlation IDs, and full crash isolation. For most automation APIs this is all you need.
gRPC (if the surface is large or you want streaming/typed contracts). Grpc.AspNetCore on .NET, @grpc/grpc-js (+@grpc/proto-loader or ts-proto for types) on Node. .NET's Kestrel can listen on a named pipe (ListenNamedPipe, .NET 8+) so you keep loopback off the TCP stack entirely; loopback TCP on a random port is the fallback if pipe transport gives you trouble. Worth the heavier setup if your automation contract is broad and evolving, or if you want server-streamed events (e.g. UIA event subscriptions pushed to Node) rather than poll/request-response. A .proto contract also documents the surface for free.
edge-js / in-process .NET hosting — reject for the reason above: no isolation. A hung UIA call should kill a worker you can respawn, not your Electron main process. The marginal latency you'd save in-process is dwarfed by UIA call times anyway.
Design notes for whichever transport: keep the worker stateful (cache resolved AutomationElements behind integer handles, expose findElement/invoke/getText/waitFor over the wire rather than shipping trees back and forth); run UIA work on a dedicated STA thread inside the worker and put a hard timeout + watchdog on every call so a hang becomes a recoverable worker restart; and have Node supervise the worker (spawn, health-ping, auto-respawn). Target .NET 10 LTS for the worker (or .NET 8 LTS if you want the maximally conservative runtime), FlaUI 5.0 UIA3, and whatever Node your Electron build bundles.
The two things I'd nail before writing any IPC code: confirm the Electron accessibility tree is actually being activated (most "UIA is unreliable on Electron" reports trace to this), and decide whether you can use CDP for the web content. Get those right and the FlaUI-over-named-pipe worker becomes almost boring in a good way, with vision and computer-use relegated to fallbacks that rarely fire.
