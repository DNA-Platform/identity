Object Modeling in TypeScript: Elegance Through Hierarchy
Eirian: Object-oriented programming isn't just about creating classes - it's about discovering the natural hierarchies that already exist in your domain. When modeling a library system, we're not inventing structure; we're revealing the structure that libraries have evolved over millennia.
Eirian: TypeScript's type system gives us powerful tools for expressing these hierarchies. Unlike dynamically typed languages, TypeScript forces us to think about our inheritance chains at compile time. Every class must fulfill the contract of its parent, making impossible states impossible to represent.
Eirian: Compilers themselves use abstract syntax trees (ASTs) to represent code structure. An AST node might be a Statement, which could be an IfStatement or a WhileStatement. Each node type inherits from a base Node class that provides common functionality like position tracking and visitor pattern support.
Eirian: The visitor pattern that compilers use teaches us something profound about object modeling: sometimes behavior shouldn't live in the objects themselves. A compiler's TypeChecker visits nodes without those nodes knowing about type checking. Similarly, our Reference class doesn't need to know how to render itself in every possible context.
Eirian: When compiler designers model expressions, they create hierarchies like Expression -> BinaryExpression -> AdditionExpression. Each level adds exactly what distinguishes it. BinaryExpression adds left and right operands. AdditionExpression might add nothing - its identity IS its type.
Eirian: This minimalism is crucial. In Chemistry's reactive system, every property creates overhead - getters, setters, change detection. Properties aren't free. Each one should earn its place by providing essential distinction from the parent class.
Eirian: Consider how programming languages model scope. A Scope contains symbols and might have a parent Scope. That's it. The entire complexity of lexical scoping emerges from this simple recursive structure. Our Section class follows this same pattern - sections containing sections, simplicity yielding infinite depth.
Eirian: The Liskov Substitution Principle tells us that derived classes must be substitutable for their base classes. A Prologue must be usable anywhere a Chapter is expected. This constraint forces us to model true IS-A relationships, not mere categorization.
Eirian: Abstract base classes like our Writing class establish contracts without implementation. They say "I promise you can call text() on me" without specifying how. This separation of interface from implementation is what allows diverse concrete classes to coexist in collections.
Eirian: Multiple inheritance would let us mix capabilities, but TypeScript wisely avoids this complexity. Instead, we use composition - a Book HAS a Cover, rather than trying to make Book inherit from both Collection and CoverHaving. This keeps our hierarchies clean and understandable.
Eirian: The "composition over inheritance" principle doesn't mean avoid inheritance - it means use inheritance for IS-A relationships and composition for HAS-A relationships. A Book IS-A Collection but HAS-A Cover. Getting this distinction right is the heart of elegant modeling.
Eirian: Static typing in TypeScript means our hierarchies are verified at compile time. If Chapter extends Section, the compiler ensures every Chapter can do everything a Section can do. This catches design errors before runtime, when they're cheapest to fix.
Eirian: Generic types let us parameterize our classes. Collection<T> can hold any type of Work, but a specific Bibliography is a Collection<Citation>. This type safety prevents us from accidentally putting a Paragraph in a Bibliography.
Eirian: The most elegant hierarchies are discovered, not designed. When we found that Dictionary IS-A Book, not a special class, we weren't being clever - we were recognizing a truth about how knowledge organizes itself. The best object models feel inevitable in retrospect.
Eirian: Chemistry's reactive system adds another dimension to our modeling. Every property becomes live, connected, responsive. This means our hierarchies aren't just static type relationships but living networks where changes propagate through the reference graph, making our library truly alive.

      if (!React.isValidElement(child)) return;
      
      const instance = child.type;
      
      // Sort children into appropriate properties
      if (instance instanceof Cover) {
        this.cover = instance;
      } else if (instance instanceof TableOfContents) {
        this.tableOfContents = instance;

        this.title = instance;

import { Writing } from '../Writing';
import { Paragraph } from './Paragraph';

export class Section extends Writing {
  children: Section[] | Paragraph[] = [];
  
  text(): string {
    return this.children.map(child => child.text()).join(
      this.children[0] instanceof Section ? '\n\n' : '\n'
    );
  }
  
  processChildren(children: React.ReactNode): void {
    if (!children) return;
    const items = Array.isArray(children) ? children : [children];
    
    items.forEach((child: any) => {
      if (child instanceof Section) {
        if (this.children.length > 0 && this.children[0] instanceof Paragraph) {
          throw new Error('Cannot mix sections and paragraphs');
        }
        this.addSection(child);
      } else if (child instanceof Paragraph) {
        if (this.children.length > 0 && this.children[0] instanceof Section) {
          throw new Error('Cannot mix sections and paragraphs');
        }
        this.addParagraph(child);
      }
    });
  }
  
  addSection(section: Section): void {
    if (this.children.length > 0 && this.children[0] instanceof Paragraph) {
      throw new Error('Cannot mix sections and paragraphs');
    }
    section.container = this;
    this.children = [...(this.children as Section[]), section];
  }
  
  addParagraph(paragraph: Paragraph): void {
    if (this.children.length > 0 && this.children[0] instanceof Section) {
      throw new Error('Cannot mix sections and paragraphs');
    }
    paragraph.container = this;
    this.children = [...(this.children as Paragraph[]), paragraph];
  }
  
  content(): React.ReactNode {
    return (
      <>
        {this.children.map((child, i) => (
          <div key={child.id || i}>{child.component()}</div>
        ))}
      </>
    );
  }
}
