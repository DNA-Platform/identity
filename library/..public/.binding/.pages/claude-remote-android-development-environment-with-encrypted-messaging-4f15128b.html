This is a well-structured concept and technically viable in outline. Let me break down the architecture, the real attack surfaces, and where the approach works vs. where it has gaps.
Russia + Android: Yes
Android dominates Russia at roughly 70-75%+ market share. iOS users skew wealthier/urban. For broad reach, Android is the right target.
The App You're Describing: What It Actually Is
You're essentially building PGP-over-Max — a cryptographic shim that sits between the user and Max's servers, making Max a dumb ciphertext carrier. This has solid precedent (OTR over AIM, PGP over email). The novel part is the sandboxed remote environment.
Architecture Options (Ranked by Feasibility)
Option A: Accessibility API Interceptor (No Root, No Remote VM)
The simplest viable approach, no remote compute needed:
Your app registers as an Android Accessibility Service
Intercepts text before it enters Max's compose field → encrypts → injects ciphertext
Intercepts incoming messages displayed by Max → decrypts → overlays plaintext on screen
Public keys exchanged as plaintext Max messages (they're public — fine)
Pros: Works on unrooted phones, no network dependency, hard to detect Cons: Max UI changes can break it; accessibility API is somewhat fragile; doesn't sandbox Max's other surveillance (contact list, metadata, etc.)
Option B: Remote Android VM + VPN Tunnel (Your Described Approach)
User's physical phone connects via SDK/streaming to a remote Android instance (think: AWS/GCP running an Android emulator, or a service like Genymotion Cloud)
Max runs inside the remote VM — fully controlled environment
Your app intercepts at the network layer inside the VM (you're root there)
TLS interception of Max's traffic to its own servers is possible because you control the VM's certificate store
Physical phone just displays a screen stream + input relay
Pros: Total control of Max's environment; can strip telemetry, block analytics SDKs, intercept all trafficCons: Latency; cost of remote compute per user; if Russia blocks the relay IPs, the whole system fails; streaming a phone screen is bandwidth-heavy
Option C: Hybrid — Local Encrypted Overlay + Remote Key Server
Your app runs locally on the Android phone
Manages keypairs locally (never leaves device)
Intercepts via Accessibility API
A lightweight relay server (outside Russia) only handles public key distribution, not messages
Messages travel through Max's infrastructure as ciphertext
This is probably the sweet spot. Minimal attack surface on your infrastructure; most of the security is local.
What "Eliminating Max's Surveillance" Actually Means
Max (VK Messenger, rebranded) has several surveillance vectors. Your architecture addresses them differently:
Surveillance VectorOption AOption BOption C
Message content✅ Encrypted before Max sees it✅ Intercepted at network layer✅ Encrypted before Max sees it
Contact graph / metadata❌ Max still sees who talks to whom✅ Can anonymize or spoof❌ Max still sees contact graph
Device telemetry / app analytics❌ Max's SDK runs normally✅ Block at VM network layer❌
Typing patterns / timing analysis❌✅ Can add jitter/padding❌
Message length analysisPartial (add padding to ciphertext)✅Partial
The honest constraint: No approach hides that two people are talking — only what they're saying. Traffic analysis remains available to FSB regardless.
The Certificate Pinning Problem
Max almost certainly uses TLS certificate pinning, which is the main obstacle to network-layer interception (Options B/C). Inside a VM you control, you can:
Patch the APK before installing — strip pinning logic (APK repacking + apktool)
Use Frida (dynamic instrumentation) to hook pinning checks at runtime
Root the VM and install your CA as system-trusted
All three are standard in mobile security research. Option B makes this tractable since you own the VM environment.
Key Exchange via Max: Sound Design
Sending public keys over Max's plaintext channel is fine — that's what public keys are for. The workflow:
User A installs your app → generates keypair → posts public key as a Max message or profile field
User B fetches it → subsequent messages are encrypted to A's public key
Max's servers receive: [BASE64 CIPHERTEXT BLOB] — opaque to them
Your app on B's side decrypts and displays
The main UX friction: key verification (how does A know B's public key wasn't swapped by a MITM?). You'd want a short fingerprint users can verify out-of-band.
Operational Risks Worth Modeling
App distribution: Google Play won't carry this; you'd distribute as an APK sideload. This is normalized in Russia (many apps are sideloaded post-app store removals).
Detection by FSB/SORM: They can see Max traffic contains ciphertext. This flags users as using encrypted comms, which in the current environment carries its own risk. This is a real tradeoff.
Max account bans: VK may detect and ban accounts sending non-standard payloads. Ciphertext in messages is unusual.
App integrity: If someone gets your APK, they can reverse-engineer the encryption scheme. Use well-established algorithms (X25519 + ChaCha20-Poly1305), not homebrew crypto.
Honest Assessment
The concept is sound and has been done in analogous contexts (OTR, Signal Protocol). The remote VM approach is the most powerful but operationally complex and expensive. The accessibility API approach is the most deployable but narrower in what it neutralizes. A hybrid local-crypto + public key server architecture is probably where you'd want to land for something actually usable at scale.
