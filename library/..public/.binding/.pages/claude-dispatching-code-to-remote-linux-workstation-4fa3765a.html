Your instinct is sound, and pieces of it are very standard. Docker for reproducibility and GitHub for code are exactly what most people use. The one part that's less common is using git commits as the channel forresults, since git handles large or binary outputs poorly and the history bloats fast. There are a few well-trodden setups close to what you described.
1. GitHub Actions with a self-hosted runner (closest to your idea)
Your colleague installs GitHub's runner agent on the Linux box and registers it to your repo. You then push, or click "Run workflow," and the job executes on his machine inside your Docker image. Results come back as workflow artifacts you download, or get pushed to a results branch or to object storage (S3, Backblaze B2, etc.). This is a common pattern in labs and ML teams. It needs no inbound ports on his side, because the runner polls GitHub outbound, which makes it IT-friendly. One caveat: keep the repo private, because a self-hosted runner on a public repo lets anyone's pull request run code on his machine. Also, if the work uses a GPU, the runner needs the NVIDIA container toolkit so Docker can see it.
2. SSH plus Docker (the most common interactive setup)
RustDesk is a remote desktop tool, so it's awkward for dispatching jobs. The usual fix is to put both machines on Tailscale, a zero-config VPN that works through NATs and firewalls, and use plain SSH. From Windows you can then:
run docker context create linuxbox --docker "host=ssh://you@linuxbox", so docker run commands from your machine execute on his,
or use VS Code Remote-SSH to edit and run directly on the box,
and pull results back with rsync or scp, or mount a shared folder.
This gives you the tightest loop: build and test locally, then flip the Docker context and run remotely with the same commands.
3. A job queue (if you'll run many jobs)
For parameter sweeps or long queues, people add a light scheduler on top of option 2, for example Slurm (heavyweight), task-spooler/ts (tiny), or a Python tool like Ray or Prefect. That's probably overkill to start.
A practical hybrid
Keep code and the Dockerfile in GitHub, and build the image on the Linux box (or push it to GitHub Container Registry). Dispatch jobs over SSH through Tailscale, or through a self-hosted runner if you prefer push-to-run. Write results to a synced directory or a bucket. Commit only small summaries (metrics, CSVs, plots) to git so you still get a versioned record of which code produced which numbers.

On a job branch, two more things appear: job.sh (the command to run) and results/ (written by the job).
The workflow
.github/workflows/run-job.yml:
yaml
name: run-job
on:
  push:
    branches: ['jobs/**']

permissions:
  contents: write

concurrency:
  group: ${{ github.ref }}      # re-pushing a job branch cancels its old run
  cancel-in-progress: true

jobs:
  run:
    runs-on: [self-hosted, linux, compute]
    timeout-minutes: 7200        # self-hosted jobs can run up to 5 days
    steps:
      - uses: actions/checkout@v4

      - name: Build image
        run: docker build -t job:${{ github.sha }} .

      - name: Run job
        run: |
          mkdir -p results
          docker run --rm \
            --user $(id -u):$(id -g) \
            -v "$PWD":/work -w /work \
            job:${{ github.sha }} \
            bash job.sh 2>&1 | tee results/log.txt
          # add --gpus all above if needed

      - name: Commit results
        if: always()               # commit logs even when the job fails
        run: |
          git config user.name  "compute-runner"
          git config user.email "runner@localhost"
          echo "${{ job.status }}" > results/STATUS
          git add results/
          git commit -m "[results] ${{ github.ref_name }}" || exit 0
          git push
A few design notes:
Pushes made with the workflow's own token don't trigger new runs, so the results commit won't loop.
--user keeps output files owned by the runner user instead of root, which otherwise breaks the commit step.
if: always() means a crashed job still sends back its log and a STATUS file.
Dispatch script (what Claude Code calls)
This uses a git worktree, so dispatching never disturbs your current checkout, and you or Claude Code can fire off several jobs in a row.
scripts/dispatch.sh:
bash
#!/usr/bin/env bash
# usage: scripts/dispatch.sh <job-name> "<command>"
set -euo pipefail
name="$1"; cmd="$2"
branch="jobs/${name}"
wt=$(mktemp -d)

git worktree add -b "$branch" "$wt" HEAD
printf '#!/usr/bin/env bash\nset -euo pipefail\n%s\n' "$cmd" > "$wt/job.sh"
git -C "$wt" add job.sh
git -C "$wt" commit -m "job: ${name}"
git -C "$wt" push -u origin "$branch"
git worktree remove "$wt"
echo "dispatched ${branch}"
Because it branches from HEAD, it includes committed work only. Claude Code should commit first, and the CLAUDE.md below tells it to.
scripts/collect.sh:
bash
#!/usr/bin/env bash
# usage: scripts/collect.sh <job-name>
set -euo pipefail
name="$1"
git fetch origin "jobs/${name}"
mkdir -p "results/${name}"
git archive "origin/jobs/${name}" results | tar -x --strip-components=1 -C "results/${name}"
cat "results/${name}/STATUS" 2>/dev/null || echo "not finished"

Heavy jobs run on a Linux workstation via GitHub Actions.
- To run something remotely: commit your changes, then
  `scripts/dispatch.sh <short-name> "<command>"` (command runs inside the Docker image, repo root as cwd).

Each time

Without Docker, this gets simpler. Git becomes the whole control channel, and a small watcher script on the Linux box does the pulling, so GitHub Actions isn't needed either. That also avoids two Actions limits that would hit multi-day training: its push token expires after 24 hours, and self-hosted jobs are capped at 5 days. In your terms, the branch is the teleporter. You write RUN into it here, and STATUS, run.log, and the results come back through it from there.
The loop
Launch (here). scripts/launch.sh lr-sweep "python train.py --config configs/big.yaml" creates runs/lr-sweep from your current commit, adds a one-line RUN file with the command, and pushes. You or Claude Code can do this.
Pick up (there). Every minute the watcher fetches and looks for runs/* branches that don't have a STATUS file yet. For each one it makes a fresh checkout and claims it by pushing STATUS: running.
Run (there). It runs the RUN command in the project environment for as long as it takes. Checkpoints go to $RUN_DIR, which is on the machine but outside the repo.
Commit (there). It runs git add -A, which respects .gitignore, and skips anything over 50 MB. Then it writes STATUS: done or failed, commits along with run.log, and pushes.
Collect (here). git fetch, then promote what you want to main with a cherry-pick or git checkout origin/runs/lr-sweep -- figures/.
To test locally, run the same command on your machine with a small config. The box runs exactly the committed code, so nothing else differs.

#!/usr/bin/env bash
# Watches for runs/* branches and executes them.
set -uo pipefail
MIRROR=/data/runner/mirror      # clone made with the deploy key
WORK=/data/runner/work          # fresh worktree per run
DATA=/data/runs                 # checkpoints etc., outside git

cd "$MIRROR"
while true; do
  git fetch -q --prune origin
  for ref in $(git for-each-ref --format='%(refname:short)' refs/remotes/origin/runs/); do
    git cat-file -e "$ref:STATUS" 2>/dev/null && continue   # claimed or finished
    git cat-file -e "$ref:RUN"    2>/dev/null || continue   # nothing to run
    branch=${ref#origin/}; name=${branch#runs/}; wt="$WORK/$name"

    rm -rf "$wt"; git worktree prune
    git worktree add -q -B "$branch" "$wt" "$ref" && cd "$wt" || { cd "$MIRROR"; continue; }

    # claim: if another watcher got there first, this push is rejected and we skip
    echo "running on $(hostname) since $(date -Is)" > STATUS
    git add STATUS && git commit -qm "claim $name"
    git push -q origin "$branch" || { cd "$MIRROR"; continue; }

    # run in the project env (swap uv for conda run, etc.)
    export RUN_NAME="$name" RUN_DIR="$DATA/$name"; mkdir -p "$RUN_DIR"
    uv run --frozen bash RUN > run.log 2>&1
    rc=$?

    # commit everything committable
    [ $rc -eq 0 ] && s="done" || s="failed (exit $rc)"
    echo "$s at $(date -Is)" > STATUS
    git add -A
    find . -path ./.git -prune -o -type f -size +50M -print0 | xargs -0 -r git reset -q --
    git commit -qm "results $name: $s"
    git push -q origin "$branch"
    cd "$MIRROR"
  done
  sleep 60
done

1. What GitHub allows
Plain git. GitHub warns on files above 50 MiB and hard-blocks files above 100 MiB. It recommends keeping repositories under 1 GB, and strongly under 5 GB. A single push is capped at 2 GiB, but files stored in LFS don't count toward that cap. So plain git can't carry this data. A 53 MB trace gets through with a warning, but one file over 100 MiB fails the whole push, and every version of every binary stays in history permanently, making every clone heavier.
Git LFS is the route. With LFS, git history stores a small pointer (a hash and a size) and the content goes to GitHub's LFS store. On git add, the LFS filter converts files matching tracked patterns into pointers. On git push, a pre-push hook uploads the new objects. On checkout, the content is downloaded. The git repository stays small no matter how much data goes in, so the repo-size guidance stops mattering. What matters instead:
Per-file cap. The LFS maximum file size is 2 GB on Free and Pro, 4 GB on Team, and 5 GB on Enterprise Cloud. This is the only hard wall.
Included quota. Free, Pro, and Free-for-organizations accounts get 10 GiB of storage and 10 GiB of bandwidth per month. Team and Enterprise Cloud get 250 GiB of each.
Overage prices. Beyond the quota, bandwidth costs $0.0875 per GiB and storage $0.07 per GiB per month. For scale, 100 GiB over the free amount is about $7 a month, and a full TiB is about $72.
What's metered. Downloads count against the repository owner's bandwidth. Uploads count toward storage, but their bandwidth isn't measured. For us, the box pushing results costs only storage, and Doug's machine pulling results costs bandwidth. All of it is billed to DNA-Platform as the repo owner, not to whoever pushes.
Budget behavior. With the budget at $0, there are no overage charges, but LFS is blocked for the rest of the calendar month once the quota runs out. Accounts without a payment method default to a $0 budget. In practice, if DNA-Platform is on Free with no payment method, pushes carrying LFS objects start failing once total storage passes 10 GiB. A job would then leave its results committed on the box but unpushed.
Storage is append-only. Storage is computed over every LFS object associated with the repository, whenever it was uploaded, so deleting a branch doesn't give storage back. Treat every push as permanent. That suits a scientific record, but budget for it.
Releases. GitHub doesn't limit the total size or bandwidth of release files, but each file must be under the plan's LFS cap. This could suit big immutable artifacts later (final checkpoints, dataset snapshots). It needs gh with Doug's credentials, since the deploy key can't create releases. Not needed now.

#!/usr/bin/env bash
# Run one job in this worktree, record provenance, commit everything, push.
# Usage (on the box, from the branch folder): bash tools/run_job.sh <command> [args...]
# Optional env: DATA_ROOT (dataset root to list), PYTHON (interpreter to snapshot),
#               LFS_MAX_BYTES (per-file LFS cap: 2 GB Free/Pro, 4 GB Team)
set -uo pipefail
export PATH="$HOME/doug/altered-states/.bin:$PATH"
cd "$(git rev-parse --show-toplevel)" || exit 1
branch=$(git rev-parse --abbrev-ref HEAD)
dirty=no; [ -n "$(git status --porcelain)" ] && dirty=yes
P=provenance; mkdir -p "$P"
LFS_MAX=${LFS_MAX_BYTES:-2000000000}
BIG=$((10*1024*1024))    # anything larger that isn't already LFS gets routed to LFS

# Provenance before the run
{ echo "branch:  $branch"; echo "commit:  $(git rev-parse HEAD)"; echo "dirty:   $dirty"
  echo "host:    $(hostname)"; echo "command: $*"; echo "start:   $(date -Is)"; } > "$P/meta.txt"
{ "${PYTHON:-python3}" -V; "${PYTHON:-python3}" -m pip freeze; nvidia-smi; uname -a; } > "$P/env.txt" 2>&1
[ -n "${DATA_ROOT:-}" ] && find "$DATA_ROOT" -type f -printf '%P\t%s\t%TY-%Tm-%Td %TH:%TM\n' | sort > "$P/data-listing.tsv"

# The run
"$@" > "$P/log.txt" 2>&1
rc=$?
{ echo "end:     $(date -Is)"; echo "exit:    $rc"; } >> "$P/meta.txt"

# Stage everything; route stray big files to LFS; record what GitHub can't take
git add -A
: > "$P/not-uploaded.tsv"
git diff --cached --name-only --diff-filter=AMR -z | while IFS= read -r -d '' f; do
  size=$(stat -c %s -- "$f")
  if [ "$size" -gt "$LFS_MAX" ]; then
    git reset -q -- "$f"
    printf '%s\t%s\t%s\n' "$(sha256sum -- "$f" | cut -d' ' -f1)" "$size" "$f" >> "$P/not-uploaded.tsv"
  elif [ "$size" -gt "$BIG" ] && ! git check-attr filter -- "$f" | grep -q ': lfs$'; then
    git reset -q -- "$f"
    git lfs track --filename "$f" > /dev/null
    git add -- .gitattributes "$f"
  fi
done
git add -- "$P/not-uploaded.tsv"
git commit -qm "run $branch: exit $rc"

# Push with retries (LFS uploads happen here)
for i in 1 2 3 4 5; do git push -q -u origin HEAD && exit 0; sleep $((i * 120)); done
echo "PUSH FAILED $(date -Is)" >&2; exit 1
What it guarantees:
Provenance. Every run's commit carries a provenance/ folder: the exact commit it ran from and whether the tree was dirty, the command, start and end times, the exit code, the Python packages, the GPU state, the log, and optionally the dataset listing.
Failures are recorded too. Failed runs are committed and pushed as well.
Stray big files go to LFS. A big file with an extension nobody anticipated is routed to LFS automatically instead of bloating plain history or blocking the push.
Nothing disappears. A file over the LFS cap stays on the box, and its sha256, size, and path are committed in not-uploaded.tsv, so the record still identifies it exactly. Checkpoints that big should be sharded below the cap, for example with sharded safetensors.
Push resilience. The push retries with backoff. A final failure is written to the job's .job.out file next to the branch folder.

Integrity. Compare sha256sum output on both ends for anything that matters scientifically.
Speed. tailscale ping lipshutzlab-01 shows whether traffic goes directly between the machines or through a Tailscale relay. Relays are much slower, which matters for bulk data.

6. The bridge: tools/bridge.sh
bash
#!/usr/bin/env bash
# Move a folder between this machine and the lab box over SSH, verified by sha256.
# usage: bash tools/bridge.sh up   <local-dir> <box-dir>      (box-dir relative to ~/doug/altered-states)
#        bash tools/bridge.sh down <box-dir>   <local-dir>
# Writes a manifest to bridge/manifests/ and a line to bridge/ledger.tsv; commit both.
set -euo pipefail
HOST=${BRIDGE_HOST:-lipshutzlab-01@lipshutzlab-01}
dir=$1 src=$2 dst=$3
root=$(git rev-parse --show-toplevel)
mkdir -p "$root/bridge/manifests"
name=$(echo "$dir-$(basename "$src")-$(date +%Y%m%d-%H%M%S)" | tr -c 'A-Za-z0-9._\n-' '_')
man="$root/bridge/manifests/$name.sha256"
hashcmd='find . -type f -print0 | sort -z | xargs -0 sha256sum'

if [ "$dir" = up ]; then
  (cd "$src" && eval "$hashcmd") > "$man"
  tar -cf - -C "$src" . | ssh "$HOST" "mkdir -p ~/doug/altered-states/$dst && tar -xf - -C ~/doug/altered-states/$dst"
  ssh "$HOST" "cd ~/doug/altered-states/$dst && sha256sum -c --quiet -" < "$man"
elif [ "$dir" = down ]; then
  ssh "$HOST" "cd ~/doug/altered-states/$src && $hashcmd" > "$man"
  mkdir -p "$dst"
  ssh "$HOST" "tar -cf - -C ~/doug/altered-states/$src ." | tar -xf - -C "$dst"
  (cd "$dst" && sha256sum -c --quiet -) < "$man"
else
  echo "usage: bridge.sh up|down <src> <dst>" >&2; exit 2
fi
files=$(wc -l < "$man")
printf '%s\t%s\t%s\t%s\t%s\t%s\n' "$(date -Is)" "$dir" "$src" "$dst" "$files" \
  "bridge/manifests/$name.sha256" >> "$root/bridge/ledger.tsv"
echo "verified $files files; manifest bridge/manifests/$name.sha256"
Each transfer does four things: hash on the sending side, stream the folder, verify on the receiving side, and record. A mismatch stops the script before anything is written to the ledger. A few practical notes:
Hashing time. Hashing big data takes a while on both ends, roughly half an hour per TB on each side at disk speed.
Paths. Use Git Bash-style local paths (/c/...) and folder names without spaces.
Huge single files. tar transfers can't resume, so for a huge single file on a shaky link, use sftp reput, or rsync where both ends have it, then run the same manifest check.

#!/usr/bin/env bash
# Run one job in this worktree, record provenance, commit everything, push.
# Usage (on the box, from the branch folder): bash tools/run_job.sh <command> [args...]
# Optional env: DATA_ROOT (bridged data folder to list), DATA_MANIFEST (its committed manifest),
#               PYTHON (interpreter to snapshot), LFS_MAX_BYTES (per-file LFS cap)
set -uo pipefail
export PATH="$HOME/doug/altered-states/.bin:$PATH"
cd "$(git rev-parse --show-toplevel)" || exit 1
branch=$(git rev-parse --abbrev-ref HEAD)
dirty=no; [ -n "$(git status --porcelain)" ] && dirty=yes
P=provenance; mkdir -p "$P"
LFS_MAX=${LFS_MAX_BYTES:-2000000000}
BIG=$((10*1024*1024))    # anything larger that isn't already LFS gets routed to LFS

# Provenance before the run
{ echo "branch:  $branch"; echo "commit:  $(git rev-parse HEAD)"; echo "dirty:   $dirty"
  echo "host:    $(hostname)"; echo "command: $*"; echo "start:   $(date -Is)"
  [ -n "${DATA_MANIFEST:-}" ] && echo "data:    $DATA_MANIFEST sha256=$(sha256sum < "$DATA_MANIFEST" | cut -d' ' -f1)"
} > "$P/meta.txt"
{ "${PYTHON:-python3}" -V; "${PYTHON:-python3}" -m pip freeze; nvidia-smi; uname -a; } > "$P/env.txt" 2>&1
[ -n "${DATA_ROOT:-}" ] && find "$DATA_ROOT" -type f -printf '%P\t%s\t%TY-%Tm-%Td %TH:%TM\n' | sort > "$P/data-listing.tsv"

# The run
"$@" > "$P/log.txt" 2>&1
rc=$?
{ echo "end:     $(date -Is)"; echo "exit:    $rc"; } >> "$P/meta.txt"

# Stage everything; route stray big files to LFS; record what GitHub can't take
git add -A
: > "$P/not-uploaded.tsv"
git diff --cached --name-only --diff-filter=AMR -z | while IFS= read -r -d '' f; do
  size=$(stat -c %s -- "$f")
  if [ "$size" -gt "$LFS_MAX" ]; then
    git reset -q -- "$f"
    printf '%s\t%s\t%s\n' "$(sha256sum -- "$f" | cut -d' ' -f1)" "$size" "$f" >> "$P/not-uploaded.tsv"
  elif [ "$size" -gt "$BIG" ] && ! git check-attr filter -- "$f" | grep -q ': lfs$'; then
    git reset -q -- "$f"
    git lfs track --filename "$f" > /dev/null
    git add -- .gitattributes "$f"
  fi
done
git add -- "$P/not-uploaded.tsv"
git commit -qm "run $branch: exit $rc"

# Push with retries (LFS uploads happen here)
for i in 1 2 3 4 5; do git push -q -u origin HEAD && exit 0; sleep $((i * 120)); done
echo "PUSH FAILED $(date -Is)" >&2; exit 1
What each run's commit records:
Provenance. It carries a provenance/ folder with the commit it ran from and whether the tree was dirty, the command, the times, the exit code, the packages, the GPU state, the log, and, when a bridged dataset is used, the hash of the manifest that pins it.
Failures. Failed runs are committed and pushed too.
Stray big files. Big files with unanticipated extensions go to LFS automatically.
Files over the LFS cap. These stay on the box. Their hashes, sizes, and paths are committed in not-uploaded.tsv, which makes them bridge-down items, verifiable against those hashes.
8. The loop
Sync: git -C main fetch -q && git -C main worktree add ../<branch> <branch> (or pull if the folder exists).
Launch: ``bash ssh lipshutzlab-01@lipshutzlab-01 'cd ~/doug/altered-states/<branch> && DATA_ROOT=~/doug/altered-states/shared/<item> DATA_MANIFEST=bridge/manifests/<name>.sha256 setsid nohup bash tools/run_job.sh python3 train.py --config configs/x.yaml > ../<branch>.job.out 2>&1 < /dev/null &'`` Keep branch names flat (no slashes).
Status: provenance/log.txt, nvidia-smi, and <branch>.job.out. git -C <branch> status -sb shows "ahead" if a push hasn't landed.
Harvest: git fetch, then read git show origin/<branch>:provenance/meta.txt. Promote to main with git checkout origin/<branch> -- <paths> and commit; this moves pointers, not bytes. Bring LFS bytes down over the bridge rather than from GitHub, and bridge down anything listed in not-uploaded.tsv. On Doug's clone, set lfs.fetchinclude or clone with GIT_LFS_SKIP_SMUDGE=1, so routine pulls don't download every trace from GitHub.
