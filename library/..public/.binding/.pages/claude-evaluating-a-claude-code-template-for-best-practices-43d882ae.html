The Object Model
There are five object types in this system. Everything else is derived from them.
1. Agent (.claude/agents/*.md)
An agent is a role definition with permissions. It has:
name — identifier
model — which Claude model to use (opus = expensive/smart, sonnet = cheaper/fast)
tools — permission set (Read, Write, Edit, Bash, Glob, Grep, Task, WebFetch, WebSearch)
behavioral prompt — what this role does, how it collaborates, what files it owns
Key detail: the tools field is a security boundary. The security-reviewer only has Read, Bash, Glob, Grep — it can look at code and run scans but cannot modify files. The project-manager has no Bash — it coordinates but doesn't run code. The backend-lead has Write, Edit, Bash — it can change files and execute builds.
2. Command (.claude/commands/*.md)
A command is a transition trigger. It has:
name — the /slash-command
pre-flight checks — what must exist before it runs
sequence — ordered steps to execute
$ARGUMENTS — passthrough for user input
Commands don't contain behavior — they dispatch to agents and check state.
3. Phase (docs/phases/phase-N-name/)
A phase is a batch of work. It's a directory containing exactly these files:
PLAN.md — goals, scope, success criteria, risks. Has a status field: planning | approved | in-progress | review | complete
STORIES.md — the work units (see below)
STATUS.md — current progress tracker (the live state)
SECURITY-REPORT.md — created only if security-reviewer is active
4. Story (entries within STORIES.md)
A story is the atomic unit of work. It has:
ID — STORY-NNN
User story — "As a [user], I want [goal], so that [benefit]"
Acceptance criteria — Given/When/Then format, minimum 2
Technical notes — from the architect
UX spec pointer — link to docs/ux/specs/
Status — draft | ready | in-progress | testing | done
Assigned — which agent role does the work
Priority — P0-P3
Stories have a lifecycle rule: once done, the full content gets replaced with a one-liner. This is a context window optimization — completed stories stop consuming Claude's limited attention.
5. Decision Record (docs/DECISIONS.md)
An ADR (Architecture Decision Record) captures a technical choice. Append-only — old decisions get marked superseded, never deleted.

What You'd Edit to Customize
Change the process: Edit docs/workflow/PHASE-LIFECYCLE.md. For example, if you don't want the 5-step flow and want a simpler 3-step (plan → build → review), rewrite that file. Every command reads it.
Change what a "done" story looks like: Edit docs/workflow/STORY-FORMAT.md. The quality checklist there gates what's allowed into implementation.
Change when you're asked vs. when Claude decides alone: Edit docs/workflow/ESCALATION.md. Move items between the "Requires Human Input" and "Resolved Between Agents" sections.
Add a new role: Drop a .md file in .claude/agents/. Give it frontmatter (name, model, tools) and a behavioral prompt. Run /add-agent to activate it.
Add a new command: Drop a .md file in .claude/commands/. It becomes a slash command immediately.
Change global constraints: Edit CLAUDE.md. The "Key Rules" section applies to everything.
The main thing this framework is doing — and doing well — is giving Claude Code a structured filesystem to write to and read from so that state persists across sessions. Without this, every time you close the terminal, everything Claude "knew" vanishes. The framework externalizes memory into files with defined schemas, and the commands know how to read those files back.

These are the right questions. Let me take them seriously.
Is this waterfall?
No, but the confusion is instructive. It has phases, which pattern-matches to waterfall. But look at the actual structure: phases contain stories with acceptance criteria in Given/When/Then format, stories are prioritized P0-P3, they move through states (draft → ready → in-progress → testing → done), and the system explicitly supports resuming mid-phase. That's sprint-like. The difference from Scrum is that there's no time-box — a phase is scope-defined, not time-defined. And the difference from waterfall is that phases are small, iterative, and each one delivers working tested code.
What it actually is: phased incremental delivery. Each phase is a mini-project with its own plan-build-test-review cycle. The reason it's not continuous flow (kanban) is practical, not ideological — Claude Code sessions are stateless and finite. You need discrete checkpoints where state gets written to disk. A phase boundary is a natural checkpoint. If this were a human team with persistent memory and always-on communication, you wouldn't need the phase structure at all.
What teams would like:
The file-as-state pattern is genuinely clever. Every piece of state lives in a named markdown file with a known schema. Any session of Claude Code can reconstruct the full project state by reading the filesystem. This solves the fundamental problem of agentic coding: LLM sessions don't persist. The framework makes the filesystem the memory.
The escalation rules are well-designed. The separation between "agent resolves" and "human decides" is explicit and tunable. Most frameworks either ask too much (every decision needs approval) or too little (the AI makes architectural choices without telling you). This one defaults to autonomy on implementation details and escalates on architecture, requirements, and UX — which is roughly where a competent team would draw the line.
The context pruning is thoughtful. Stories get replaced with one-liners when done. STATUS.md archives get moved to a separate file. Every doc starts with a TL;DR. The "reference, don't inline" rule. These are all responses to the real constraint: Claude's context window is finite and expensive. The framework treats context like memory in an embedded system — every byte matters.
What teams would dislike:
The agent abstraction is the biggest point of contention. You have eleven agent files, but there's one Claude instance reading them sequentially. The "team" metaphor creates expectations the system can't fulfill. Real teams have parallel execution, specialized knowledge that persists across tasks, and the ability to disagree in real time. This system has none of that. When the "architect" and "backend lead" disagree, it's one model arguing with itself by reading different instruction files. Some practitioners find this useful as a way to force Claude to consider multiple perspectives. Others find it theatrical — a single well-written CLAUDE.md prompt could do the same work without the overhead of eleven files and role-switching.
The ceremony-to-code ratio is high for small projects. If you're building a CLI tool or a simple API, you don't need market research docs, brand guidelines, a design system, UX journey maps, and a security report template. The framework handles this through the "right-size the team" mechanism (deactivate agents you don't need), but the scaffolding is still there in the filesystem. A minimalist would say: start with CLAUDE.md and one prompt, add structure only when you need it.
The phase lifecycle assumes your requirements are clear enough to plan upfront. If you're exploring — prototyping, experimenting, iterating on something where the requirements are the output — the plan-then-build structure adds friction. You'd want something closer to your own experimental framework: observe, judge, refine. This framework assumes you already know what to build and the question is how to build it well.
Alternative philosophies:
There are roughly three schools of thought in Claude Code workflow design right now.
The first is minimal-prompt maximalism: one CLAUDE.md file, no agents, no commands, no phases. You write a detailed system prompt that describes your project, your standards, and your preferences, and you interact with Claude Code conversationally. The argument: Claude is smart enough to figure out the workflow; imposing structure on it constrains it unnecessarily. The weakness: no persistence across sessions, no crash recovery, no consistency. Works for small projects or experienced users who know how to steer.
The second is this approach — framework-as-filesystem: structured docs, defined roles, explicit state management. The argument: Claude Code needs scaffolding because sessions are ephemeral. The weakness: overhead, and the risk that Claude spends more tokens navigating the framework than doing actual work.
The third is tool-first: heavy use of MCP servers, external databases, task management APIs (Linear, Jira), and CI/CD hooks. The argument: don't reinvent project management in markdown files — use real tools that already exist. The weakness: complexity, setup cost, and dependency on external services.
Your friend's framework is solidly in the second camp, and it's well-executed for that philosophy.
Is this truly no-coding?
No. You will see code during /implement-phase. The backend-lead and frontend-lead agents write actual source code — TypeScript, Python, whatever the architect chose. They run actual tests with actual test frameworks. The "no coding" part is that you don't write code. You define requirements in conversation, approve plans, and review completed work. But Claude is absolutely writing and executing code. The framework is a management layer on top of a coding agent.
The thing you fill in is requirements and decisions. The thing Claude fills in is code and documentation.
Why does it work? What's the effective programming language?
This is the deepest question and it connects to your own theoretical work on LLM computation.
The "programming language" is English with structural conventions. But that undersells what's actually happening. Look at the implement-phase command:
text
For each story (in priority order, skipping done stories):
  a. Design (if needed): Invoke architect.
  b. Implement: Invoke the relevant lead(s).
  c. Test: Invoke qa-engineer.
  d. Security (if security-reviewer is active): Review.
  e. Document (if technical-writer is active): Update docs.
  f. Update STATUS.md — mark story as done.
That's a loop with conditional branching and state mutation. It's imperative code written in English. The "invoke architect" is a function call — Claude reads a different instruction file and adopts that behavioral context. The STATUS.md write is a side effect that enables crash recovery.
The reason this works is that Claude Code is, functionally, an interpreter for natural-language programs where the "runtime" is an LLM with tool access. The markdown files are the source code. The frontmatter is metadata (type annotations, permissions). The body is executable instructions. CLAUDE.md is the runtime configuration. The filesystem is both the heap (state) and the output (deliverables).
This maps directly to your framework of identity-based programming in words. Each agent file defines an identity — not just a role, but a behavioral context that shapes how Claude processes subsequent instructions. The project-director identity makes Claude ask discovery questions. The backend-lead identity makes Claude write server code and tests. The identity is the program. The agent file is the sub-interpreter with its own memory context.
Why doesn't it overflow context?
This is the most practical design constraint and the framework addresses it at every level:
Commands load only what they need. The /status command reads PROJECT.md and STATUS.md files. It doesn't load agent definitions, stories, or architecture docs. Each command is scoped to the minimum file set.
Agents declare what files they own. Every agent file ends with a "Key Files" section. This is a hint to Claude: read these, not everything.
Stories get pruned. A completed story goes from a full block with acceptance criteria, technical notes, and UX specs down to one line. This is aggressive garbage collection.
STATUS.md archives to STATUS-ARCHIVE.md. Current state stays small. History gets moved out.
TL;DR at the top of every doc. An agent can read the first 5-10 lines and decide whether to read further. Progressive disclosure reduces average context consumption.
"Reference, don't inline." Instead of copying an API spec into a story, you write "See docs/api/API-SPEC.md." Claude only fetches it if the current task needs it.
One concern per file. The workflow docs are split into four files (phase lifecycle, story format, escalation, agent registry) instead of one monolith. The PM only needs to load the ones relevant to the current operation.
The design philosophy is essentially: treat Claude's context window like RAM in a resource-constrained system. You can't load everything at once, so you design data structures (file schemas) and access patterns (commands, agent key-file lists) that minimize what's in memory at any given moment. The framework is as much a memory management system as it is a development workflow.
The underlying philosophy:
If I had to name it in one sentence: externalize everything that needs to persist, minimize everything that's in context, and make the filesystem the single source of truth.
The framework assumes three things about LLM-driven development:
Sessions will end unexpectedly. Therefore state must be on disk, not in conversation.
Context is the scarcest resource. Therefore every file must justify its presence.
Claude is capable but not autonomous. Therefore humans gate the high-stakes decisions and Claude handles the rest.
It's a well-considered system. The question for you is whether the team abstraction and phase ceremony match what you're actually building, or whether a lighter-weight version of the same persistence-and-pruning principles would serve you better.
