We currently have a Windows desktop automation system for Claude Desktop built in TypeScript/Node.js. It uses:
A persistent PowerShell subprocess that calls .NET's System.Windows.Automation (UIA) for element discovery by name/role
Win32 P/Invoke through PowerShell for window management (FindWindow, SetForegroundWindow, ShowWindow)
Clipboard-based text input (pasting into the composer)
URL reading from the accessibility tree for navigation state detection
A tapering-poll gateway pattern (50ms doubling to 1000ms) for all async operations
This works but has limitations: PowerShell subprocess adds latency per call (~12ms), UIA through PowerShell is indirect, and we're limited to what the accessibility tree exposes. If we were rebuilding this from scratch today, what specific technology stack would you recommend? Consider:
Should we use FlaUI (.NET) directly instead of PowerShell-mediated UIA? What would the integration look like from Node.js?
Would UFO2's hybrid UIA+vision approach add value, or is pure UIA sufficient for an Electron app with good accessibility?
Is there a way to use Anthropic's computer-use API as a fallback for when UIA fails, while keeping UIA as the primary path?
For the persistent shell — is there a better IPC mechanism than spawning PowerShell? Named pipes, gRPC, direct .NET hosting in Node.js via edge-js?
Be specific about libraries, versions, and integration patterns. We're on Windows 11, Node.js, TypeScript.

Good—several of these had moved since my baseline, and the IPC question in particular has a much better answer now than it did a couple of years ago. Here's what I'd build.
Bottom line first
Collapse the Node → PowerShell → .NET UIA chain into Node → .NET, and stop re-discovering elements from the root on every call. Your ~12ms isn't mostly the IPC transport — it's PowerShell process scheduling plus re-serializing scripts plus re-walking the UIA tree each time. A persistent typed .NET host fixes all three, the biggest single win being that it can hold live 2 references across calls instead of re-finding them.
My recommended stack:
.NET 8 (LTS) sidecar process hosting FlaUI.UIA3 5.0.0 (the current release; it targets net6.0 / .NET Framework 4.8, so .NET 8 consumes it fine, and the repo is actively maintained into 2026).
StreamJsonRpc (Microsoft's JSON-RPC lib, the same one behind VS / LSP tooling) over a 0, with a thin TypeScript client on the Node side (vscode-jsonrpc, or raw net.connect('\\\\.\\pipe\\...') with length-prefix framing).
0 with the 1 tool + 2 beta header as the bounded fallback path.
If — and this is the lever that actually raises your ceiling — Claude Desktop can be launched with a remote-debugging port, Chrome DevTools Protocol (CDP) as the content layer, with UIA as the window/OS layer.
Now to your four questions.
1. FlaUI directly, yes — but the integration is the sidecar, not PowerShell
FlaUI is the right call. It's a clean managed wrapper over the COM IUIAutomation (UIA3) interface, current at 5.0.0, and it gives you typed patterns (ValuePattern, InvokePattern, ScrollPattern) and Retry helpers instead of you hand-rolling them through System.Windows.Automation script strings.
The integration shape that matters: run FlaUI inside a long-lived .NET sidecar, not via PowerShell and not (primarily) in-process. A persistent host lets you do the thing PowerShell structurally can't —
csharp
// Sidecar holds live references; Node calls by handle, not by re-search
private readonly UIA3Automation _automation = new();
private readonly Dictionary<string, AutomationElement> _cache = new();

public ElementInfo FindComposer(string windowHandle) {
    var window = _automation.FromHandle(new IntPtr(long.Parse(windowHandle)));
    var composer = window.FindFirstDescendant(cf => cf.ByControlType(ControlType.Edit));
    var id = Guid.NewGuid().ToString();
    _cache[id] = composer;            // keep it alive; reuse across calls
    return new ElementInfo(id, composer.BoundingRectangle, composer.Name);
}

public void SetText(string elementId, string text) {
    var el = _cache[elementId];
    if (el.Patterns.Value.IsSupported)
        el.Patterns.Value.Pattern.SetValue(text);   // no clipboard
    else { el.Focus(); Keyboard.Type(text); }        // SendInput fallback
}
Two threading details that bite people: run all UIA work on a dedicated MTA thread inside the sidecar (Microsoft's UIA client guidance is to avoid driving it from a UI/STA thread to dodge deadlocks), and mark the sidecar PerMonitorV2 DPI-aware in its app.manifest. On Windows 11 with mixed-DPI monitors, if you skip that, BoundingRectangle and your SendInput coordinates will silently disagree — and that same mismatch is what later corrupts the computer-use fallback's coordinate mapping.
2. Don't adopt UFO² — borrow two of its ideas; for Electron, CDP beats vision
UFO² is real and good, but it's the wrong shape for you. It's a Python "AgentOS" — a HostAgent that decomposes goals and coordinates per-application AppAgents, the current public release being v2.0.0 from April 2025 (there's a UFO³ now in their docs). It's a full agent framework, not a library you embed in a TS/Node tool. Lifting it in wholesale would mean adopting a Python multi-agent runtime to drive one Electron app you already control.
But two of its design choices are worth stealing. First, its core perception trick: a fusion pipeline that combines UIA metadata with vision-based detection to ground controls even in non-standard interfaces. Second, speculative multi-action planning to cut per-step LLM overhead.
The key reframe for your target: for a well-behaved Electron app, the right second half of that "hybrid" is not vision — it's CDP. Claude Desktop is Electron, so its composer, message list, and navigation state are a DOM. If you can expose the DevTools protocol, you get deterministic, sub-millisecond, LLM-free access to exactly the content the accessibility tree under-exposes today (your stated pain). CDP gives you real Page.navigatedWithinDocument / mutation events to await instead of polling the a11y tree for URL changes. So: pure UIA is mostly sufficient for an Electron app with good a11y, and where it isn't, CDP is a far better partner than vision — cheaper, deterministic, no model round-trip. Reserve vision for the genuinely-blind case in question 3.
(Caveat I can't verify for you: whether the shipped Claude Desktop build will accept a --remote-debugging-port flag, or whether that's locked down. Worth a five-minute test before committing — launch it with the flag and hit http://localhost:<port>/json. If it's closed, the UIA + computer-use combo below stands on its own.)
3. Computer-use as a bounded fallback — yes, and the wiring is clean
This is exactly the right role for it: UIA/CDP primary, computer-use as last resort when an element isn't found after your taper or the window is in an unrecognized state. Current spec — the tool type is computer_20251124 with the computer-use-2025-11-24 beta header, supported on Opus 4.8, 4.7, 4.6, Sonnet 4.6, and Opus 4.5 (the older computer_20250124 / computer-use-2025-01-24 is for Sonnet 4.5, Haiku 4.5, etc.). Companion tools are text_editor_20250728 and bash_20250124.
The loop: on primary-path failure, screenshot the window → send to Claude with the computer tool → it returns coordinate-based actions → you execute them through FlaUI's Mouse/Keyboard (which use SendInput) rather than letting anything else drive the cursor. Critical constraints:
Bound it hard. Max iterations and a cost ceiling per fallback episode; a vision agent in a loop on a misread screen is how you get a surprise bill.
Coordinate mapping is the failure mode. The model reasons in the pixel space of the screenshot you sent; if you downscaled the screenshot or your DPI awareness is off, clicks land wrong. Keep one source of truth for the coordinate transform between captured-image space and physical screen space, and reuse the PerMonitorV2 setup from question 1.
Model choice: Sonnet 4.6 for the routine fallback loop (latency/cost), escalate to Opus 4.8 only for the cases Sonnet can't resolve.
Treat the frequency of fallback as a regression signal — if computer-use starts firing often, a UIA selector or a CDP hook broke, and you want telemetry that surfaces that rather than silently papering over it with vision.
4. IPC: named pipes + StreamJsonRpc. Not edge-js. node-api-dotnet only if you go in-process.
Ranking for your case:
Named pipe + StreamJsonRpc (recommended). Replaces PowerShell with a purpose-built persistent host, gives you JSON-RPC 2.0 with typed request/response and async, transport latency well under a millisecond, and — the reason I lead with it —process isolation. UIA hangs are not hypothetical; when a target app stops pumping messages, a UIA call can block. Out-of-process, that stalls one sidecar call you can time out and recycle. In-process, it stalls your Node event loop. gRPC would also work but it's heavier than you need for localhost same-machine IPC; named pipes are the lower-ceremony, lower-latency choice on Windows.
node-api-dotnet (in-process) — the alternative if you want a single process. This is Microsoft's modern bridge (Microsoft.JavaScript.NodeApi), and it's the honest successor to edge-js: JS-to-.NET calls benchmark more than twice as fast as edge-js, and because it's built on Node-API it's compatible with any Node.js version without recompiling. It's still labeled Public Preview — most functionality works well, with some known limitations and possible minor breaking changes. Lowest possible latency (no marshalling hop), but you inherit the COM-apartment-versus-Node-event-loop management yourself, and a crash in the UIA layer takes the whole process down. Pick this only if you've measured the pipe hop as a real bottleneck — and given that UIA query time dominates either way, I doubt you will.
edge-js — I'd skip it. The maintained fork (agracio/edge-js) works, but it needs native rebuilds tied to your Node version and node-api-dotnet supersedes it on both performance and Node-version resilience.
A pragmatic note on whether to go in- or out-of-process: the latency difference between them is small because the UIA tree walk dominates both. The order-of-magnitude win over your current setup comes from killing PowerShell and caching live element references — not from choosing in-process over a pipe. So take the pipe and keep the isolation.
One thing orthogonal to your four
Replace polling where you can with UIA event subscriptions (StructureChangedEvent, AutomationPropertyChangedEvent, focus-changed) inside the sidecar, and keep the taper-poll only as fallback. UIA events are uneven in quality, so a hybrid is right — but for the specific case of navigation/URL-state detection, if CDP is available, awaiting a DOM navigation event is dramatically cleaner and more reliable than polling the accessibility tree for a URL string, which is the most brittle part of your current design.
