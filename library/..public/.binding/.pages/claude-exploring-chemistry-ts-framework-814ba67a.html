1. Mapped Types and Key Remapping Fundamentals
The TypeScript type system distinguishes between key filtering and value transformation in mapped types. Your $Properties type uses the as clause for key remapping, which was introduced in TypeScript 4.1. The critical insight is that[K in keyof T as TransformKey<K>]: TransformValue<T[K]> operates in two phases: first, it iterates over keys and decides which to keep (via the as clause), then it transforms the value type for each kept key. The as clause can return never to filter out keys entirely, creating a narrowed object type.
In your $Properties type, the pattern K extends \$inferFirst{infer First}inferFirst{infer Rest}\`extracts the character after the$, then checks ifFirst extends Lowercase<First>to ensure it's lowercase. Theinfer` keyword captures parts of the string literal type, allowing pattern matching on property names at the type level. This works because TypeScript's template literal types (introduced in 4.1) enable sophisticated string manipulation in the type system.
2. Method Signatures vs Function Property Types
Here's where things get subtle: TypeScript distinguishes between method signatures and function-typed properties. When you write async $method() { } in a class, TypeScript treats this as a method signature on the class prototype. However, when you write $method = async () => {} or $method: () => Promise<number>, this is a property whose value happens to be a function. The difference matters for variance,this binding, and crucially, for how mapped types handle them.
Method signatures have special handling in TypeScript. When you do T[K] where K is a method name, TypeScript returns the method's type, but this includes subtle metadata about being a method. The extends (...args: any[]) => any check works on both, but the way generics and contextual typing flow through them differs. This is why your $Properties type splits methods and non-methods into separate sections with different optionality—they're fundamentally different kinds of members.
3. The Promise Unwrapping Challenge
When you write T[K] extends (...args: infer Args) => Promise<infer R>, you're using conditional type inference. The infer keyword creates a type variable that TypeScript tries to infer from the structure. For Promise<infer R>, TypeScript looks at the return type and tries to match it against Promise<X>, then binds R to X. This works beautifully for simple cases like Promise<number> → R = number.
However, there's a catch with Promise<void>. TypeScript has special handling for void in Promise contexts because of async function semantics. An async function that doesn't explicitly return anything has return type Promise<void>, and when you unwrap it with infer R, you get R = void. Then void | undefined is actually distinct from just undefined—void means "ignore the return value" while undefined is an actual value. Your type should produce void | undefined, which is correct but feels redundant.
4. Generic Method Preservation Problem

TypeScript's mapped type system doesn't have a built-in way to say "keep the generic parameters but transform the return type."
The problem is that infer works at the type application level, not the declaration level. When you write T[K] extends (...args: infer Args) => Promise<infer R>, TypeScript is trying to match against an already-instantiated function type. Generic type parameters on methods are part of the function's schema, not its type, and mapped types operate on types. This is a fundamental limitation—you can't easily preserve generic parameters through a mapped type transformation.
Some libraries work around this by using overloads or by accepting that generic methods need manual type annotations at the call site.
