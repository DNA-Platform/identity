Right — this is axiom-search, not proof, and your sense that the craft is undocumented is fair. Published theories present a finished axiom set with the scaffolding kicked away, so the search that produced it is invisible. But there are two bodies of work that are exactly about what you're describing, and they map onto your process almost one-to-one.
The first is reverse mathematics (Friedman, Simpson). Ordinary math proves theorems from axioms; reverse math proves the axiom back from the theorem, over a deliberately weak base, to show the two are equivalent — that the theorem needs exactly that much strength, no more. That's your "fix a set of assumptions and see which desiderata fall out," but run as a measuring instrument: it doesn't just ask can I prove D from A, it pins down the precise logical content of D. And it's the rigorous form of your point that what each axiom says matters — reverse math is essentially the theory of how much a statement is actually claiming. Its famous finding is that almost all classical math collapses onto a handful of equivalence classes. For you that's encouraging: the space of honest assumption sets is usually far smaller than the space of possible ones.
The second is Lakatos's Proofs and Refutations — the craft side, the dialectic where definitions, conjectures, and proofs co-evolve and you bend the concepts to save or kill a claim. It's the one book that actually shows the sausage being made. You'll recognize your own moves in it.
Now the procedure. Take a desideratum D against a fixed assumption set A. There are exactly four cells:
A ⊢ D — won.
A ⊢ ¬D — A is incompatible with what you want; back up.
A ⊬ D and A ⊬ ¬D — independent: D is a legitimate candidate new axiom. This is the interesting cell, where your whole search lives.
A ⊢ ⊥ — A has overcommitted.
Your forward/backward dance is navigation of this lattice. Forward (toward complexity) = strengthening A until a wanted D crosses into "won." Backward (toward elegance) = pulling axioms out while keeping every won D still won — i.e. the smallest A whose provable-cone still contains all your won desiderata, and among ties, the one whose individual axioms read cleanly. That last clause is yours, and it isn't reducible to logic; it's the editorial layer reverse math deliberately leaves open.
Here's the hard truth, then the way through. There is no single decision procedure for "does A prove D?" — first-order validity is only semi-decidable (Church, Turing). If A ⊢ D a search eventually finds the proof; if not, it needn't ever halt, so you never get a clean "no."
But the question splits into two searches that together do the job:
Prove it — hunt a derivation of D (or of ⊥). Semi-decidable, and exactly what an iterative prove-then-check loop is built for.
Refute it / show independence — build a model of A ∧ ¬D: a concrete structure where your assumptions hold but D fails. And here a decision you already made pays off hugely. You kept specifications strictly finite and stayed first-order precisely to dodge second-order trouble. Finite model-finding is decidable. So the refutation half of your procedure is mechanizable in a way it simply would not be with second-order quantification or infinite specs. That early "specifications are strictly finite, avoid second-order" instinct was — whether you framed it this way or not — the move that makes the no answers tractable.
So the procedure is a dual loop: a prover hunting a derivation of D, a finite-model-finder hunting a countermodel, run together; whichever fires classifies (A, D) into one of the four cells. Independence results are the payoff — each hands you a vetted candidate axiom.
And this is exactly why your Claude Code instinct is right and the raw-horsepower gap stops mattering. The requirement quietly shifts: the tool doesn't need to be a great mathematician, it needs to be a great lab technician for a verifier. The dual loop is iteration against a checker — the one regime where "proof by intimidation" is structurally impossible, because nothing counts until the checker accepts it. It's also not novel: it's the architecture of Isabelle/HOL, where Sledgehammer throws your goal at external provers while Nitpick simultaneously hunts finite countermodels. Claude Code's job isn't to out-reason GPT-5.5 Pro one-shot; it's to drive that loop — hold the ledger, decide what to send the prover vs. the model-finder next, record the graph.

What an issue actually is. An issue is a standalone thread in the repo's issue tracker — a number, a title, a description, a conversation, labels, an assignee, open/closed state. Mentions. A commit message, PR, or another issue that writes #42 becomes a clickable cross-link to issue 42, and GitHub auto-records the backreference in the issue's timeline. That's the main way an issue gets tied to actual changes.
Closing keywords. A PR description saying Fixes #42 or Closes #42 will auto-close issue 42 when the PR merges. That's the tightest native coupling — and notice it's PR-to-issue, still not issue-to-file.

Labels are the only real categorization primitive — free-form tags you define (bug, reflection, axiom-edit). There's no built-in "this issue concerns these files" field.

Yes — and there are three routes, which matter because you'll pick based on how much setup you want versus how much autonomy.
1. The 0 CLI inside Claude Code (lightest). Claude Code runs shell commands, and GitHub's official CLI does the whole issue surface — gh issue create, gh issue list, gh issue comment, gh issue edit, gh issue close. You authenticate once with gh auth login and from then on Claude Code can just shell out. No server, no token plumbing in config, nothing to maintain. For a solo start this is the path of least resistance — you tell Claude Code "draft issues for each family that has no parser," it reads the library/ files and runs gh issue create for each.
2. GitHub's official MCP server (more structured). GitHub's own MCP server does issue and PR automation — create, update, and manage issues and pull requests, triage, and project boards. With Claude Code it's a one-liner because Claude Code supports HTTP transport, so you add it with a personal access token via the Authorization header — no Docker needed. This gives the agent structured tools (create_issue, etc.) rather than raw shell, which some people prefer for reliability and for letting subagents call them cleanly. The Claude Code docs explicitly pitch this pattern — "add the feature described in [issue] and create a PR on GitHub" — so reading-issues-and-acting-on-them is a first-class use case.
3. The hosted GitHub connector for claude.ai / Cowork (if you're not in the CLI). The remote connector also handles issues and PRs, but it needs a paid plan plus OAuth setup, and there's a live limitation worth knowing if you ever go multi-person: the connector's repo-scoped tools (issues, PRs, code) all work, but org-team membership tools return empty because the app only requests repository-level permissions, not organization ones. So issue-writing is fine; "list my org's teams" is not, yet.
My steer for where you are: start with the 0 CLI in Claude Code. It's the one with essentially zero standing infrastructure, it covers everything you described (drafting and triaging issues), and it keeps the whole loop — read the repo, notice a gap, file the issue — inside the same Claude Code session that's also writing the code. Graduate to the official MCP server only if you want subagents calling structured issue-tools rather than shelling out.
