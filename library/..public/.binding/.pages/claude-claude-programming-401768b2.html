Good — I've got enough to give you the real picture, including the part that complicates the "just set one up" instinct.
The honest headline first
The thing worth knowing before you build anything: Claude Code's own team deliberately removed vector search. Early versions used RAG with a local vector DB, and Boris Cherny (its creator) explained on Hacker News that they found plain agentic search — grep, find, read, and reasoning — consistently outperformed it. Their reasons were simplicity, security, privacy, staleness, and reliability. So the default tool you're using is vectorless by design, not by omission.
But that verdict is specifically about code exploration, and your case is a flat-file knowledge library (prose, notes, reference material). That distinction is the whole ballgame, so let me separate the two before getting to setup.
Why grep wins for code but the case shifts for prose
For code, identifiers are literal strings. If you want authenticateUser, grep finds it exactly, instantly, with no index to build or keep fresh. Structure matters too — following imports, call chains, and type hierarchies (AST navigation) often beats flattening code into embedding space. And an index built at session start is stale the moment the first file changes; embeddings of proprietary content also leak information, since research on embedding inversion has shown partial text recovery in some settings.
Prose is different. Knowledge gets expressed in varied vocabulary, so the failure mode of grep is real here: it can't understand that "user authentication" and "verify login credentials" are conceptually related. When the words you'd search for aren't the words the document used, exact-match search misses and the agent burns tokens reading files to compensate. That's exactly the gap embeddings fill. The vendor-driven (Milvus) claim is around ~40% token reduction at equivalent retrieval quality — discount it for commercial interest, but the direction is sound for a corpus where queries are conceptual rather than keyword-shaped.
The 2026 consensus that's emerged from this debate isn't "vectors" or "grep" — it's hybrid: keyword/BM25 plus dense vectors, with vector search no longer the default, but retrieved just-in-time as one tool among several.
The integration paths (concretely)
Three real mechanisms, in rough order of how people actually do it:
1. MCP server — the dominant path. You register a server with one command (claude mcp add ...) and Claude Code discovers its tools at runtime — typically something like index, search, store, find. The agent then calls them like any other tool. Named, working options:
zilliztech/claude-context — purpose-built for this, does hybrid (BM25 + dense), AST-aware chunking, pluggable embeddings (OpenAI, VoyageAI, Ollama, Gemini), backed by Milvus/Zilliz. The most "batteries-included" choice.
danielbowne/claude-context — a fork that swaps in LanceDB as a local, embedded, zero-config store. This is the one to look at if you want everything on-machine with no external service.
qdrant/mcp-server-qdrant — official Qdrant server; explicitly framed as a "semantic memory layer" with store/find tools. Good if you also want agent memory, not just document search.
Chroma, Pinecone, Weaviate, Milvus all have MCP servers too, but those are the database back-ends; the claude-context projects are the indexing layer on top.
2. Hooks-based indexing — for memory, not library search. Projects like isthatamullet/claude-vector-db hook into Claude Code's lifecycle to index your conversation history in real time, so the agent can semantically recall past sessions. Different problem from yours, but worth knowing it's the standard pattern for "agent memory."
3. Custom tool / skill — the DIY route. You write a local CLI that chunks, embeds, and queries, and let Claude call it via bash or wrap it as a Skill. Several people have built this with entirely local pieces (sentence-transformers or Ollama for embeddings, ChromaDB/LanceDB/sqlite-vec for storage) — no API fees, nothing leaving the machine, and some report it's faster than Claude's default search on their corpus.
Whichever path, the underlying pipeline is the same four steps and the operational cost lives here: chunk → embed → store → query, plus keeping the index fresh as files change. That re-chunk/re-embed-on-change loop is the "operational debt" that made the Claude Code team walk away for code.
So: whether to build one
A decision test rather than a recommendation, since it genuinely depends on your corpus:
How big is the library, and does it fit in context? If it's small enough that the agent can grep + read its way through in a couple of tool calls, a vector DB is mostly ceremony. The payoff scales with corpus size.
Are your queries conceptual or keyword-shaped? If you mostly know the terms ("find the note where I mention X"), grep already wins. If you're asking "what did I write about this idea" and the wording varies, embeddings earn their keep.
Does it change constantly? A library that's appended-to occasionally indexes cleanly. One churning every hour fights staleness.
Privacy posture? Local embeddings (Ollama/sentence-transformers) sidestep both the API cost and the inversion-leak concern.
If you do build, my read for your specific case — a flat-file knowledge library, not code — is: start with the local LanceDB claude-context fork or a small custom CLI with local embeddings, run it alongside (not instead of) grep, and treat it as hybrid. That gets you the conceptual-recall upside without a cloud dependency, a monthly bill, or the failure modes that pushed Claude Code itself back to plain search. Then measure: if semantic retrieval isn't surfacing things grep misses on your actual queries, you've learned cheaply that your corpus doesn't need it.
