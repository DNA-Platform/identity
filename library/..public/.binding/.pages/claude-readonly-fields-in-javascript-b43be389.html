Readonly Fields in JavaScript
Yes, you're correct that a readonly field is typically represented as a property with only a getter and no setter. Here are the main ways to implement readonly fields in JavaScript:
1. Property Descriptor with writable: false
javascript
Object.defineProperty(obj, 'readonlyProp', {
    value: 42,
    writable: false,  // Makes it readonly
    enumerable: true,
    configurable: false
});
2. Getter-Only Property (Most Common Pattern)
javascript
class MyClass {
    #privateValue = 42;  // Private field
    
    get readonlyProp() {
        return this.#privateValue;
    }
    // No setter defined - attempts to set will be ignored in non-strict mode
    // or throw an error in strict mode
}
3. Object.freeze() for Immutability
javascript
const obj = Object.freeze({
    readonlyProp: 42
});
// obj.readonlyProp = 100; // This will fail silently or throw in strict mode
4. TypeScript readonly Modifier (Compile-time only)
typescript
class MyClass {
    readonly readonlyProp: number = 42;  // TypeScript compile-time check
    // At runtime, this is just a regular property
}

You've discovered an important distinction between TypeScript's compile-time privacy and JavaScript's runtime behavior!
TypeScript private is Compile-Time Only
TypeScript's private keyword is only a compile-time check. Once your TypeScript is compiled to JavaScript, those private fields become regular properties that are fully accessible at runtime:
typescript
// TypeScript
class MyClass {
    private secret = "hidden";
}

// Compiles to JavaScript as:
class MyClass {
    constructor() {
        this.secret = "hidden";  // Just a regular property!
    }
}
Your Test is Bypassing TypeScript
When you write (child as any), you're telling TypeScript "ignore type checking here." This allows you to access private members at runtime:
typescript
const child = parent.$new();
(child as any).literature  // TypeScript allows this due to 'any'
                           // JavaScript happily returns the value
What Your Test Actually Shows
Your test is checking if child.literature is undefined, which it should be because:
parent.$new() creates a new instance of $Catalogue
Each instance has its own private members
The child doesn't inherit or share the parent's Map/Set instances
The test passes because each $Catalogue instance has its own private members, not because they're inaccessible.
True Runtime Privacy in JavaScript
For actual runtime privacy, you have three options:
1. Private Fields with # (ES2022)
typescript
class $Catalogue {
    #literature = new Map();  // True private field
    #references = new Map();
    
    someMethod() {
        this.#literature.get(key);  // Only accessible within class
    }
}

// Runtime test:
(child as any).#literature  // SyntaxError! Cannot access at all
(child as any)['#literature']  // undefined - doesn't exist as property
2. Closures
typescript
class $Catalogue {
    private literature: Map<any, any>;
    
    constructor() {
        const literature = new Map();  // Truly private via closure
        
        // Only expose through methods
        this.$find = (ref) => {
            return literature.get(ref);
        };
    }
}
3. WeakMaps for Private State
typescript
const privateLiterature = new WeakMap<$Catalogue, Map<any, any>>();

class $Catalogue {
    constructor() {
        privateLiterature.set(this, new Map());
    }
    
    $find(ref: any) {
        const literature = privateLiterature.get(this);
        return literature?.get(ref);
    }
}
Your Test Should Actually Be
If you want to test that private members aren't accessible, you'd need to:
Use # private fields and test that they throw errors
Or accept that TypeScript private is compile-time only
Your current test is actually correct for what it's testing: that child instances don't share the parent's data structures. Each $Catalogue gets its own Maps and Sets.
For Your $Chemistry Framework
Given your framework's philosophy of "elegant code assumes correct usage," TypeScript's compile-time privacy is probably sufficient. You're not trying to prevent malicious access, just guide developers toward correct usage patterns. The compile-time checks accomplish that goal.
If you truly need runtime privacy for the framework internals, consider using symbols or private fields for the most sensitive parts:
typescript
const LITERATURE = Symbol('literature');

class $Catalogue {
    private [LITERATURE] = new Map();  // Harder to access accidentally
    
    $find(ref: any) {
        return this[LITERATURE].get(ref);
    }
}

I know, it's frustrating! This is one of the most surprising things for developers coming from C#/Java. Here's why TypeScript made this choice:
Historical Reasons
1. TypeScript Predates JavaScript Private Fields
TypeScript was created in 2012. JavaScript didn't get real private fields (#) until ES2022! For a decade, TypeScript had to work with what JavaScript had.
typescript
// 2012-2021: TypeScript had NO runtime privacy option
class MyClass {
    private field = 42;  // Best we could do
}

// 2022: JavaScript finally gets real private fields
class MyClass {
    #field = 42;  // Actual runtime privacy!
}
2. TypeScript's Philosophy: "Erasable Types"
TypeScript's core design principle is that type annotations can be completely erased to produce valid JavaScript:
typescript
// TypeScript
class Foo {
    private x: number = 5;
    public y: string = "hi";
}

// After type erasure → Clean JavaScript
class Foo {
    constructor() {
        this.x = 5;
        this.y = "hi";
    }
}
If private changed runtime behavior, it wouldn't be "erasable" anymore.
Technical Reasons
3. Compatibility with Existing JavaScript
TypeScript needed to work with JavaScript libraries and patterns that rely on dynamic property access:
javascript
// Common JavaScript patterns that would break with true privacy
for (let key in obj) { /* iterate all properties */ }
Object.keys(obj)
JSON.stringify(obj)
Object.assign({}, obj)
4. Performance
Before # fields, implementing true privacy meant using WeakMaps or closures, which had performance costs:
typescript
// Closure-based privacy (slow, memory-heavy)
class MyClass {
    constructor() {
        let privateField = 42;
        this.getField = () => privateField;  // New function per instance!
    }
}
The "It's a Feature" Argument
5. Debugging & Testing
Being able to access "private" fields with as any is actually useful:
typescript
// In tests or debugging
console.log((complexObject as any).privateState);  // Thank god we can do this!

// With true private fields
console.log(complexObject.#privateField);  // SyntaxError - no way to debug!
6. Gradual Migration
TypeScript's approach allows JavaScript projects to gradually adopt types without changing behavior:
javascript
// Existing JavaScript class
class User {
    constructor() {
        this._id = generateId();  // "private by convention"
    }
}

// Add TypeScript types without breaking anything
class User {
    private _id: string;  // Just adds compile-time checks
    constructor() {
        this._id = generateId();
    }
}
Modern TypeScript Has Real Privacy Now!
Since ES2022 support, TypeScript now offers both:
typescript
class Modern {
    private softPrivate = "compile-time only";  // TypeScript private
    #hardPrivate = "runtime private";           // JavaScript private
    
    constructor() {
        // You can use both!
    }
}

// At runtime:
(modern as any).softPrivate   // ✅ Works - "compile-time only"
(modern as any).hardPrivate   // ✅ Works - undefined (doesn't exist)
(modern as any).#hardPrivate  // ❌ SyntaxError!
For Your $Chemistry Framework
Given your philosophy of "elegant code assumes correct usage," TypeScript's compile-time privacy is probably fine. But if you want true runtime encapsulation for critical internals:
typescript
class $Catalogue {
    // Use # for truly private runtime state
    #literature = new Map<$Representation, any>();
    #references = new Map<string, $Representation>();
    
    // Or use symbols for "harder to access accidentally"
    private [Symbol.for('$literature')] = new Map();
    
    // Keep TypeScript private for "please don't touch"
    private dereferenced = false;
}
The fact that TypeScript chose compile-time-only privacy was controversial, but it was the pragmatic choice given JavaScript's limitations at the time. Now we have options, but the default behavior remains for backward compatibility.

You're absolutely right to be frustrated by this! It's a perfect example of TypeScript's awkward position as a "superset of JavaScript."
The Current Weird Situation
typescript
class MyClass {
    private field = 1;        // ✅ Allowed (fake privacy)
    #privateField = 2;        // ✅ Allowed (real privacy)
    private #bothField = 3;   // ❌ ERROR! Can't combine them!
}
This is bizarre! You'd think private #field would be the MOST private - explicitly marked AND runtime enforced!
Why TypeScript Forbids private #field
1. "Valid JavaScript Must Be Valid TypeScript"
This is TypeScript's golden rule. Since this is valid JavaScript:
javascript
class MyClass {
    #field = 42;  // Valid JS
}
TypeScript MUST accept it without modification. If TypeScript required private #field, then valid JavaScript wouldn't compile.
2. Different Semantics
They actually mean different things:
typescript
class Parent {
    private tsPrivate = 1;    // Accessible in THIS CLASS
    protected tsProtected = 2; // Accessible in SUBCLASSES
    #jsPrivate = 3;           // Accessible in THIS CLASS ONLY
}

class Child extends Parent {
    method() {
        this.tsPrivate;    // ❌ TypeScript error
        this.tsProtected;  // ✅ Works
        this.#jsPrivate;   // ❌ SyntaxError - # doesn't support protected!
    }
}
TypeScript's private is part of a private/protected/public system. JavaScript's # is just "absolutely private."
The Community Debate
Many developers, like you, have argued TypeScript should allow private #field as optional syntax for clarity:
typescript
class MyClass {
    #field = 1;           // Fine, valid JS
    private #field2 = 2;  // Should be allowed for explicitness!
    
    // Makes intent crystal clear:
    private #internalState = {};      // Runtime + compile-time private
    protected legacyField = {};        // Compile-time only (no # equivalent)
    public apiField = {};              // Explicitly public
}
Why TypeScript Team Resists
They argue it would create confusion:
typescript
class Confusing {
    private a = 1;         // Fake private
    #b = 2;               // Real private
    private #c = 3;        // Real private... but looks special?
    
    // Would developers think these are different?
    #field1 = "real";
    private #field2 = "extra real??";
}
The Real Problem: protected Has No # Equivalent
This is the deeper issue:
typescript
class Parent {
    private field = 1;      // TS compile-time
    protected field2 = 2;   // TS compile-time
    #field3 = 3;           // JS runtime - but no protected version!
    
    // What would this even mean?
    protected #field4 = 4;  // ??? Can't exist - # is always private!
}
JavaScript's # fields can't do protected, so TypeScript's visibility modifiers and # fields are fundamentally incompatible systems.
Your Point Is Completely Valid Though!
TypeScript SHOULD allow redundant annotations for clarity:
typescript
class Ideal {
    // Let developers be explicit!
    private #truePrivate = 1;      // Yes, redundant, but CLEAR
    public normalField = 2;         // Already allowed redundancy
    readonly #constant = 3;         // Should be allowed!
    private readonly #both = 4;     // Maximum clarity!
}
Just like TypeScript allows redundant public:
typescript
class Example {
    public field = 1;  // 'public' is redundant but allowed
    field2 = 2;        // Same as above
}
For Your $Chemistry Framework
Given your philosophy, you might want to establish a pattern:
typescript
class $Catalogue {
    // True runtime privacy for critical internals
    #literature = new Map();
    #references = new Map();
    
    // TypeScript privacy for "protected" patterns
    protected topics: $Subject[] = [];
    
    // Explicit public for API surface
    public readonly $subject: $Subject;
    
    // Document the choice in comments
    private dereferenced = false;  // TS-only: for subclass access
}
The TypeScript team's reluctance to allow private #field is frustrating and feels like prioritizing dogma ("JS must be valid TS") over developer experience. Your instinct that it should at least be ALLOWED is spot-on - it would make code more self-documenting without breaking anything!
