Here's the full picture, synthesized from research across tools, the ESP API, and what professional contributors actually do at scale.
The Landscape
Three paths exist for bulk iStock upload:
Path 1: Raw ESP web portal (what you're doing now)
Manual drag-and-drop through esp.gettyimages.com. Fine for 5 files. Painful for 262. No scripting hooks. Dead end for scale.
Path 2: The ESP API directly
A real contributor REST API exists at https://api.gettyimages.com/esp with a sandbox at https://esp-sandbox.api.gettyimages.com/esp. There's even an open-source Go SDK (dysolution/espsdk) and CLI (dysolution/gettyup) that wrap it. To use it, you need a username/password for sandbox.espaws.com plus an API Key and Secret from developer.gettyimages.com/apps/mykeys.
The catch: the Getty Images API requires you to contact a Getty account rep to discuss access and licensing options. This API is gated — it's primarily for enterprise partners, not individual contributors. Getting keys as a solo contributor is not a reliable path in 2025.
Path 3: DeepMeta or qHero (what pros actually use)
This is the answer. Both tools wrap the ESP API using Getty-approved credentials under the hood.
DeepMeta is the longest-standing tool. The DeepMeta software uses the Getty Images API and is endorsed by iStockphoto LP / Getty Images. You can fully manage and upload batches to Getty Images/iStockphoto with DeepMeta 4. The upload process starts with creating a submission batch. Once files are selected, upload to the Getty ESP server starts immediately, and you can close the Upload panel and re-open it at any time to check progress.
Critically for Ana's situation: DeepMeta 4 supports importing CSV files with metadata to be applied to uploaded files — add the .csv file at the same time as the JPG/EPS files you're uploading, and the CSV metadata will be applied. The format is compatible with Getty ESP import formats.
Also: the date created and country fields will auto-populate if present in the IPTC/XMP data of the JPG thumbnail file for EPS vectors. Since the JPEGs already have IPTC injected, this means title, keywords, and country should auto-fill on import.
qHero is the newer competitor. It's praised for semi-automatic disambiguation and makes it much more convenient and significantly faster to choose the meanings of terms and synonyms of keywords for large groups of similar files. Several contributors report it's faster than DeepMeta for keywording.
The Critical Constraint: 100 Files Per Batch
A batch can hold a maximum of 100 files. iStock automatically closes batches after 3 months of inactivity.
With 131 pairs, that means 2 batches minimum:
Batch A: world-options first 100 pairs
Batch B: remaining 29 world-options + 3 singles from other folders
Recommendation
Use DeepMeta for this upload. It's free-tier sufficient for 131 files, endorsed by Getty, reads the IPTC from the JPEGs automatically, and handles the keyword disambiguation UI far better than raw ESP. No coding needed for this phase.

I found the key signal in DeepMeta's changelog. This is almost certainly a metadata namespace mismatch, not an ESP UI change. Let me explain what's happening.
What ESP Actually Reads
The DeepMeta changelog records two directly relevant bugs they had to fix: "Upload: If an illustration is added for upload and neither the EPS nor the JPG has a date in the exif, the last modified date of the EPS will be used as the creation date" and "Upload: Fix: upon adding files, if creation date was provided as string in exif, it was not read."
That's the tell. ESP reads date from EXIF, not from IPTC IIM. And it's picky about the format.
The likely problem with the build pipeline is that exiftool was told to write -DateCreated which writes to IPTC:DateCreated in IIM format (YYYYMMDD — a bare integer string). ESP is looking for EXIF:DateTimeOriginal or XMP:DateCreated in ISO 8601 format (YYYY:MM:DD HH:MM:SS for EXIF, or YYYY-MM-DD for XMP).
Similarly for keywords — if they were written as a single semicolon-delimited string to one field rather than as individual repeated -Keywords tags across both IPTC and XMP namespaces, ESP may not parse them.
The Fix
Run this on one of the JPEGs to see exactly what's in it right now:
bash
exiftool -DateCreated -XMP:DateCreated -EXIF:DateTimeOriginal -Keywords -XMP:Subject repo/serens-squares/dist/serens-squares.jpg
Then the corrected exiftool write command for the build pipeline should write to all three namespaces simultaneously:
bash
exiftool \
  -IPTC:DateCreated="20250101" \
  -XMP:DateCreated="2025-01-01" \
  -EXIF:DateTimeOriginal="2025:01:01 00:00:00" \
  -IPTC:Keywords="geometric pattern" \
  -IPTC:Keywords="seamless" \
  -XMP:Subject="geometric pattern" \
  -XMP:Subject="seamless" \
  output.jpg
Note the repeated -IPTC:Keywords and -XMP:Subject flags — each one is a separate keyword entry, not a delimited string in one field.
