You're right, those are one question. Let me answer it as one.
Yes, Cocoon is open for third-party developers today. The repo is at github.com/TelegramMessenger/cocoon. There are two participant roles: Workers (run a TEE-equipped GPU rig, earn TON per inference) and Developers (call the network via SDK/API, pay TON per inference). The Cocoon docs are explicit that "the client library is designed to run on servers (backend infrastructure). For example, the Telegram backend would run multiple client instances to handle user requests." So the canonical pattern for a third-party Telegram bot is:
User DMs your bot → your bot's webhook server receives the message → your server calls the Cocoon SDK to submit a confidential inference request → Cocoon's proxy routes to a TEE worker (Intel TDX) running an open-weight model (currently DeepSeek, Qwen, and growing) → encrypted result returns to your server → your bot replies in chat. Settlement happens on-chain in TON via Cocoon's smart contracts. Your business pays TON for compute. GPU operators earn TON. Validators capture fees on every transaction. This is the loop where TONX participates without owning hardware.
Now the businesses. The defensible category is anything where cryptographic privacy is the paid feature, not a nice-to-have. Building these on OpenAI's API gives you a "we promise" privacy story; building them on Cocoon gives you TEE attestation — a verifiable claim that the prompt and output were processed in a sealed enclave the operator cannot see. That difference is what justifies premium pricing and is the wedge against ChatGPT-wrapper competitors.

You're right. Let me actually answer them.
1. What's new, given bots could always call AI APIs?
A bot could call OpenAI on day one of the Bot API in 2015. Nothing about that changed on May 7. So the "AI Bot revolution" framing isn't about giving bots AI access — they already had it. What changed is bot platform mechanics, and the primitives happen to be shaped for AI use cases. Specifically:
Guest Bots — previously a bot had to be a member of a chat to be invoked. Now any user @-mentions any bot from any chat without adding it. Distribution collapses from "convince every group to install you" to "have a memorable username." Pure platform mechanics.
Bot-to-Bot — the Bot API previously filtered out messages originating from other bots, full stop. Bots literally could not talk to each other. That restriction is gone. New primitive entirely.
Streaming — bots used to fake streaming by editing a message repeatedly, hitting rate limits. Now there's first-class streaming. Mechanical change, big UX implication for LLM bots.
Chat Automation in Profiles — your user account (not a separate bot identity) can now have a bot answer on your behalf. Bot identity merges with user identity at the protocol level. This is the most architecturally significant change in the post.
Custom AI Styles — prompts become user-shareable artifacts that propagate through the social graph like sticker packs.
Cocoon is not in this announcement set as a bot platform feature. It appears exactly once, as the backend Telegram itself chose for sticker search. From a third-party bot developer's perspective, Cocoon is just one of the things your backend can call — same as it was before May 7. The Bot API doesn't know or care whether your bot's inference runs on OpenAI, Anthropic, Cocoon, or a Raspberry Pi in your closet. Cocoon and this update are orthogonal: the announcement is about how bots interact in chats, Cocoon is about where some bots run their compute.
Durov frames it as an "AI revolution" because the new primitives are mostly useless without AI driving them — streaming text doesn't matter for command bots, bot-to-bot only matters for agentic workflows, Profile Automation only matters if the auto-replier can plausibly imitate you. So the platform change is an AI play in motivation, but the change itself is structural, not a new AI capability.
That's the thing I missed: I treated "AI revolution" as if the news were AI access. The news is that bots stopped being second-class citizens you install per-chat and became a callable layer summonable from anywhere, composable with each other, and capable of acting as your account.
2. Bot businesses that make money — AI optional, the actual picture.
The Telegram bot economy already prints money and predates AI by years. The biggest existing categories:
Execution venues (largest by revenue today). Memecoin trading bots — Maestro, Banana Gun, BonkBot, Trojan, Photon, GMGN — charge 0.5–1% on every trade and route through Solana/EVM DEXs. Multiple of these have done eight to nine figures annually in fees. The product is speed: faster than any web wallet for a sniper trying to be the first buyer of a new launch. Almost all are Solana/EVM-focused. TON-native trading bots are a wide-open wedge — Storm Trade exists as a venue, but the bot-execution UX layer on top of TON DEXs is underbuilt relative to the Solana stack. This is a category where being first with a good TON sniper bot is a real opportunity.
Consumer games / tap-to-earn. Notcoin (35M users), Hamster Kombat (300M peak), Catizen, Dogs, Yescoin. Monetize via Stars purchases, ad networks (Hamster Kombat allegedly took ~$40M+ in pre-launch ad revenue), and token airdrops that recapture user attention. This category produced TON's first viral consumer wave and remains a working playbook for new entrants who can manufacture viral mechanics.
Casino / gambling. TON-denominated stakes, regulatory-arbitrage friendly because the front-end is just a chat. Significant unreported revenue.
Content paywalls. Bot takes Stars or TON, auto-adds buyer to a private channel. Used by trading-alpha groups, course creators, fitness coaches, NSFW creators. Most of the OnlyFans-replacement economy on Telegram runs through this pattern. Telegram takes a cut on Stars; the operator keeps the rest.
Utility SaaS. Price/wallet/sports/weather alerts (freemium with paid tiers), customer-support routing for businesses, lightweight productivity (polls, scheduling, task tracking for groups), affiliate funnels capturing commissions on off-platform purchases. Lower ARPU than trading or games but extremely long-tail.
Identity and marketplace infrastructure. Username sniping/auction bots adjacent to Fragment, sticker/NFT marketplaces, OTC escrow desks with KYC handled in chat.
Now layer the May 7 primitives on top, and these new shapes become viable:
Summonable specialist services sold as Stars subscriptions — translation, contract review, fact-check, sticker generation, on-demand data lookup. Guest Bots removes the "must be installed in this chat" friction, so the unit economics shift toward subscription rather than per-group install.
Profile-Automation-as-a-service for high-value inboxes — executives, founders, creators with thousands of incoming DMs. A bot that pre-screens, drafts replies, and surfaces urgent messages, sold as monthly SaaS at $50–500/mo. The willingness to pay is real because the alternative is a human EA at 20× the cost.
Multi-bot orchestration services — a "research desk" front-end that subcontracts to specialist bots (translation, citations, market data, legal precedent) via the bot-to-bot protocol and charges a margin on the orchestration. Marketplace-of-agents shape rather than monolithic product.
Style packs — branded voice templates, comedian writing styles, marketing copy systems, sold like sticker packs. Low ARPU per pack, near-zero marginal cost, viral distribution.
Hybrid AI + execution bots — the trading bot category extended with AI-driven position summaries, hedge suggestions, narrative explanations. The execution take rate is where the money is; the AI is the retention and conversion lever.
The pattern across both sets: the May 7 changes are not themselves new revenue streams. They're distribution and composability primitives that lower the cost of building bot-shaped businesses and expand the addressable surface for ones that already work. Trading bots alone have shown bots in Telegram can capture a percentage of transaction flow that on web is taken by Robinhood, Coinbase, and Binance. The interesting question is what other product categories can extract similar take rates once the primitives let them be summoned, composed, and embedded in the social graph rather than installed.

You're right, that was sloppy. Notcoin and Hamster Kombat aren't bots — they're Mini Apps (full webviews) launched from a bot. The bot is just the entry point and identity broker; the gameplay surface isn't bot-shaped. Let me actually answer at the level you're asking.
What a bot is, mechanically. A bot is a server you run, addressed by a Telegram username, that receives events from Telegram (incoming messages, button taps, file uploads, payment confirmations, group joins) via webhook, and sends things back (messages, inline keyboards, invoices, file attachments, Mini App launch links) via Telegram's HTTP API. Your server runs anywhere. Telegram is the transport, the identity layer, and the renderer.
What being a bot gives you for free, that a web or mobile app would otherwise have to build. This is the database-level answer to "why is this useful":
Identity. Every event arrives with a Telegram user ID. You never build signup, password reset, OAuth, sessions, or 2FA. Auth is solved on arrival.
Distribution. Any Telegram user reaches your service by knowing your @username. No App Store, no install, no marketing landing page. The user types your name.
Push. You can send a message to any user who has ever talked to you, anytime. No APNs, no FCM, no email deliverability problem. This is the most underpriced primitive in the platform.
UI. Buttons, inline keyboards, forms, file uploads, payment invoices, share sheets all render natively across every Telegram client on every OS. You don't write a frontend.
Payments. Stars and TON are first-class — one API call generates an invoice the user pays in two taps. No Stripe integration, no app-store cut.
Group context. A bot can be added to a group and receive events from many users at once, so any service involving multi-user coordination, mediation, or matching gets a native multi-user surface.
So a bot is useful any time you'd build a server-side service whose interaction shape is one of these:
Command in → server response. Stateful back-and-forth: support, intake, Q&A, surveys, ordering, booking, KYC, scheduling.
External event → push to user. "Tell me when X happens": price alerts, wallet monitors, on-chain events, server uptime, news, sports, package tracking. Largest underbuilt category, cheapest to build, because the bot replaces the entire push-notification stack.
Payment gate → access grant. Subscription channels, paywalled content, course access, premium support. The bot is the cashier and the access list.
User → external API → user. A keystroke-to-execution bridge: trading bots, swap bots, DNS lookups, domain registration, anything that invokes an external service on the user's behalf.
Multi-user mediation in groups. Polls, role assignment, marketplace matching, escrow between strangers, moderation, scheduling for teams.
Concrete shape, with the bot's actual mechanical role:
Memecoin trading bot (Maestro, BonkBot, Trojan). User types /buy CONTRACT 1 SOL. The bot's server signs and submits a swap to a DEX using a wallet keyed to the user's Telegram ID, monitors the transaction, sends the fill back as a chat message. The bot is a keystroke-to-blockchain bridge that uses Telegram for identity, UI, and notification. Charges 1% per swap. Eight-figure business.
On-chain wallet alerter. User gives the bot a wallet address. The server subscribes to chain events; on activity, it sends a Telegram message. The bot is a notification dispatcher with free identity and free push. Freemium subscription.
Paywalled channel. User clicks "subscribe," bot sends a Stars invoice, on payment confirmation the bot calls Telegram's API to add the user to a private channel and tracks renewals. The bot is a subscription register and access gate using Telegram's payment rails. Operator keeps roughly 70% of Stars revenue net of Telegram's cut.
B2B customer support. User DMs the bot with a question; the server checks the company's CRM, pulls account state, auto-answers from a knowledge base or escalates to a human via the company's Slack. The bot is a CRM frontend embedded in the user's existing messenger.
Where Cocoon fits in this picture. Your bot's server can call anything from inside its handler — Postgres, OpenAI, a smart contract, Stripe, Cocoon. They're at totally different layers. Bot API = how your service talks to users. Cocoon = where some bots happen to physically run their LLM inference. Same relationship as Stripe and AWS in a normal SaaS: one is your payment rail, the other is your compute backend, they don't compete and they don't substitute. Cocoon becomes the right compute backend specifically when your bot's value proposition includes a verifiable privacy claim — i.e. when "trust us, we don't log your prompts" isn't a defensible product statement and you need TEE attestation as part of what you're selling.
What May 7 actually changed about the primitive. Bots used to be installed-per-chat and could only talk to humans. Now: Guest Bots means a bot is callable from any chat without being a member; Bot-to-Bot means a bot can subcontract to other bots over the same API; Profile Automation means a bot can act as your account in your DMs. These extend the surface where the bot primitive applies — they don't change what a bot fundamentally is.

Yes, you can put a frontend around your bot. Your bot's webhook handler is just a regular HTTP endpoint on your server. Every event it receives — messages, button taps, payments, file uploads — lands in your application's database the same way a form submission on a website would. From that point on, Telegram is one input/output channel for your application; you can build any number of additional surfaces against the same backing data. Concrete patterns:
Bot + admin web dashboard. User talks to bot. Conversations land in your DB. Support agents see them in a Zendesk-style web UI and reply from the web UI; your server posts the replies back through the Bot API. The user sees a Telegram chat; the team sees a normal SaaS console.
Bot + user web/mobile app. User executes commands via bot, server stores state, user can also log into a web dashboard or iOS app to see analytics, history, settings. Maestro, Banana Gun and most serious trading bots do this — the bot is the fast input path, the web dashboard is the deep configuration and reporting surface.
Bot + scheduler/composer. Marketing team writes broadcasts in a web tool, server sends them through the Bot API to subscribed users. The bot is just the delivery channel.
The pattern to internalize: Telegram is a channel, your bot is your server, and your server can have any number of other channels (web, iOS, Android, Slack, email) over the same database. Same shape as a customer service platform with multi-channel inboxes — Telegram is just one row.
How users get an identity if your app spans Telegram + outside. Telegram identity is the user's Telegram user ID (a 64-bit integer that arrives on every bot event, pre-authenticated). The bridging problem is connecting that ID to a user record on your non-Telegram surface. There are five established patterns:
Login with Telegram (the official OAuth-shaped widget). Your web app embeds Telegram's login button. User clicks, Telegram authenticates them, your server receives a signed payload (user ID, name, username, photo) and verifies the HMAC using your bot's token. You now have a verified Telegram identity tied to your web session. This is the cleanest answer for web/mobile apps that want Telegram users.
Mini App initData. If your "external" surface is a Mini App launched from your bot, Telegram injects signed initData into the webview containing the user's identity. You verify the signature with your bot token. No separate signup — the Telegram identity is the app identity. This is why Mini Apps onboard so frictionlessly and why most TON consumer apps use this pattern.
Deeplink with one-time token. Your web app generates a code, gives the user a https://t.me/YourBot?start=login_<TOKEN> link. User clicks, the bot receives /start login_<TOKEN>, the bot's server matches the token to the pending web session and links the Telegram ID to it. Older but still common.
Phone-number share. Bot asks user to share their phone via the requestContact button. User taps "Share." Bot receives the phone number. You match it against your existing user database (email/phone signup users get linked to their Telegram account).
Reverse linking from your web app. User signs up normally on your website with email/password. Your site shows them a code or "Connect Telegram" button. They send the code to your bot, bot ties the Telegram user ID to their existing web account. This is how Linear, Notion, Vercel, etc. add Telegram notifications to existing accounts.
The architectural point: identity is federated in this stack. Telegram authenticates a Telegram user ID for you for free on every bot event and on every Mini App launch. Your job is to maintain a mapping in your database — "app user record N is linked to Telegram user ID M" — and use whichever of the five patterns fits the user's entry point. For a Telegram-native consumer product like Give, you can skip external identity entirely and just use Telegram ID as the user key; for a hybrid product where some users come in via web, you pick pattern 1 or 5.

DM with the bot — fine for transactional flows, alerts, AI chat. Often a Mini App does the same job better.

The strongest defense of the bot primitive is in the group-chat context, so I'll pick an app that lives there.
App: Tally — a shared expense and settlement ledger that lives in group chats.
Target users: roommates, travel groups, beach-house shares, recurring dinner crews, parent groups handling kid logistics, small project teams splitting costs. Anywhere a group already exists as a Telegram chat and people are already paying for things on each other's behalf.
Mechanical role of the bot. Tally is added to an existing group once. From that point, members capture expenses inline by @-mentioning it:
@TallyBot $80 dinner, split with Ana, Mike → bot updates the running ledger, posts a one-line confirmation
@TallyBot $1200 rent, I paid, owed by everyone equally → same
@TallyBot balance → bot DMs the asker their personal balance privately
@TallyBot settle → bot generates a Stars or TON invoice for the user's net balance to each creditor; one tap clears it
The bot pushes a weekly digest to the group: "As of Sunday, Mike owes Ana $40, Doug owes Mike $25, everyone else is square."
Where the Mini App fits. Tapping the bot's name opens a Mini App with the full historical ledger, charts, search, CSV export, FX rate configuration. The split is sharp: bot is for capture and notification inside the group; Mini App is for browsing and configuration outside it.
Monetization.
Free: groups up to 5 members, 30 days of history.
Pro: $3/month per group, paid in Stars by anyone in the group. Adds unlimited members and history, multi-currency with FX, receipt-photo OCR, recurring expenses, exports.
Settlement fee: 15bps on TON-settled cross-border splits where members want crypto rails instead of Venmo/Wise/Revolut.
Corporate tier: per-seat SaaS for international teams using Telegram natively (LatAm, MENA, ex-Soviet, India) who don't have Expensify/Concur as a default.
Why this specifically requires the bot primitive (the four arguments I'd defend):
The expenses are already happening in the chat as plain text. "I just paid for dinner, you owe me $40" is a sentence people already type. Tally captures that same intent via @-mention. Splitwise requires every member to leave the conversation, open a separate app, navigate to the right group, type the expense, and return. The friction differential is the product.
Push closes the settlement loop. Weekly "Anna owes Mike $87" reminders are what actually get people to pay. Mini Apps cannot push. Email gets ignored. The bot's free push channel — to a chat people open ten times a day — is the only delivery primitive cheap enough to make passive groups settle.
Multi-user mediation in groups is native to bots and impossible for Mini Apps. Every group member shares context with the bot. The bot can address individuals privately while keeping the audit trail public. A Mini App is one user per session.
Onboarding is one 0. Splitwise requires every member to install an app and sign up. Tally requires one person to add the bot. Network effects compound: every new group exposes ~5 new users to the bot, and the bot's username spreads as people copy it into other groups.
The web dashboard only exists for the corporate tier; consumer users never see it. The Mini App handles every case where chat-as-UI is wrong (six months of expense history, CSV generation, FX configuration).
That's the app. Probe it.

Right, you're correct — without LLM parsing the @-mention syntax has to be rigid command-style, which kills the UX premise. The NLU layer is what makes the chat-as-capture-surface actually work. Let me lay out the components.
Architecture, by component:
1. Telegram Bot API integration. Webhook server that receives every event from Telegram (messages, button taps, payments, group joins). Authenticates the bot token, dispatches events by type to handlers, and writes outbound calls back through Telegram's HTTP API. Includes a rate limiter (Telegram enforces per-bot send limits) and an idempotency layer (Telegram retries on webhook timeouts). This is the I/O boundary.
2. NLU / extraction layer. Receives raw message text on @-mention. Composes a structured-output prompt that includes the message text, the last ~10 messages of group context, and the group's member roster. Calls an LLM expecting JSON of the shape {amount, currency, payer_id, payee_ids[], split_type, description, confidence}. Validates against schema. If confidence < threshold, sends a clarification reply with an inline keyboard ("Did you mean: $80 split between you, Ana, and Mike?"). On confirm, commits to the ledger; on edit, opens a structured form. This is the layer where Cocoon vs. OpenAI vs. Anthropic is a backend choice — and where Tally has a real privacy product claim, since the input is financial data plus social graph (who eats with whom, who pays for whom). TEE attestation lets Tally credibly say "your spending data never leaves a sealed enclave," which OpenAI-backed competitors cannot say.
3. Member resolution. When the LLM returns "split with Ana, Mike," names need to map to Telegram user IDs in the group. Component maintains the group roster (synced on every member-change event from Telegram), normalized display-name index, recent-message-author bias for disambiguation, and a confirmation loop when ambiguous (two people named Ana).
4. Ledger core. Append-only expense table keyed by (group_id, expense_id), with payer, amount, currency, payees[], split_method, source_message_id, created_at. Derived balance graph computed on read. Includes a min-cash-flow simplifier that turns N-by-N debts into the minimum number of settlements ("Mike pays Ana $87, Doug pays Ana $40, done"). Edits are new rows with a supersedes pointer; nothing is mutated. This is the database.
5. Settlement / payments. Two rails:
Stars rail: generate Telegram payment invoices via sendInvoice, handle the pre_checkout_query and successful_payment webhook events, update ledger atomically with payment confirmation.
TON rail: TON Connect for wallet linking, generate settlement transaction templates, listen for confirmations on the TON blockchain via a node or RPC provider, mark ledger settled on confirmation. Idempotency guarded by transaction hash.
6. Notification scheduler. Cron generates weekly digests per active group; an event-driven path sends real-time alerts ("Mike just added you to a $40 split"). All deliveries go through the same Bot API client. Per-user quiet hours and notification preferences stored as user settings.
7. Mini App. React-based webview hosted on Tally's domain. Authenticates via Telegram's WebApp initData (HMAC-verified with the bot token, no separate login). Reads from a thin REST API over the ledger core. Used for browsing history, charts, CSV export, FX configuration, settling complex multi-party balances. Not in the MVP.
8. OCR pipeline (Pro tier, post-MVP). Photo upload event → vision model call (again, Cocoon or OpenAI's vision endpoint) → structured extraction {vendor, line_items[], total, tax, tip} → inline keyboard for user to assign payees per line item → ledger commit. Same NLU confirmation pattern as text.
9. FX layer (Pro tier). External rate provider (openexchangerates or similar), cached with short TTL, used both for display normalization and for settlement amount calculation in cross-currency groups.
10. Identity / subscription state. Telegram user ID is the universal primary key. Subscription records map (telegram_user_id, group_id) to plan tier and Stars receipt history. TON wallet links from TON Connect map telegram_user_id to wallet address.
11. Observability. Per-event logging, NLU success/failure rates by prompt version, LLM cost per group per month, settlement volume, group DAU/retention, error monitoring. Tracks LLM cost as a unit-economic input — every group has a measurable inference cost and a measurable revenue contribution.
Data flow on a typical event:
User types "@TallyBot $80 dinner, split with Ana and Mike" in a group → Telegram POSTs the update to the webhook → router identifies it as a bot mention → NLU layer pulls last 10 messages and the roster, sends to LLM, gets JSON back → member resolution maps "Ana" and "Mike" to user IDs → bot replies in chat with an inline keyboard ("Confirm: $80 paid by Doug, owed equally by Doug, Ana, Mike. ✓ / Edit / Cancel") → user taps Confirm → callback_query webhook fires → ledger writes the expense and updates the balance graph → bot edits its own message to "Recorded ✓" → done. End-to-end latency target ~2 seconds, dominated by the LLM call.
MVP cut. Components 1, 2, 3, 4, partial 5 (Stars only), partial 6, partial 10 (just user IDs and Stars subscriptions), partial 11. Mini App, TON, OCR, FX, corporate tier are all post-launch. The MVP is a webhook server, a Postgres database, an LLM API client, and the Telegram payment integration. One backend developer can build the MVP in 4–6 weeks.
On Cocoon specifically: the LLM call in component 2 is the point where compute backend matters. A back-of-envelope: 100K active groups × ~10 mentions/week × ~600 tokens average = ~2.6B tokens/month inference traffic. On Cocoon's open-weight inference (Qwen/DeepSeek-class), per-token cost is materially lower than OpenAI/Anthropic, and every settled inference call routes through TON smart contracts as validator-fee throughput. This is exactly the loop where the bot business creates real on-chain economic activity that benefits TONX's staked position regardless of any other thesis component.
