Good — the volatile pieces check out, and one naming-collision is worth flagging up front: the npm package you'd use to host .NET in Node is agracio's 0 fork (still maintained — last publish May 2026, supports the recent even-numbered LTS lines plus one Current release, falling back to node-gyp compile when no prebuilt binary matches). Here's how I'd build it.
The one detail that dominates everything: Electron's lazy accessibility
Chromium (and therefore Electron) does not populate its full UIA tree by default. The renderer accessibility tree is built lazily and only when it detects an assistive-tech client or is forced on. If your automation sees a sparse tree (just the window frame, no inner controls), that's almost always this — not a tool problem. Two fixes:
Launch the app with --force-renderer-accessibility, or
Have your UIA client set the proper flags so Chromium activates accessibility on connection (a real UIA client connecting usually triggers it; a half-baked one may not).
Whatever stack you pick is downstream of getting this right. With it on, a well-behaved Electron app exposes a genuinely rich UIA3 tree (roles, names, value patterns, invoke patterns), which is exactly what makes vision largely unnecessary (see UFO² below).
(1) FlaUI via edge-js vs PowerShell-mediated UIA
This isn't close. PowerShell-mediated UIA has three structural problems: you pay 200–600ms of powershell.exe spawn per call (or wrestle with a persistent runspace), you're stuck on System.Windows.Automation (the managed UIA2 wrapper — older, slower, missing UIA3 patterns), and you cannot hold 2 references across calls, so every interaction re-walks the tree from root, and you're parsing stringified output back into structure.
FlaUI's FlaUI.UIA3 wraps the modern UIA3 COM interface (Interop.UIAutomationCore). In-process you keep live element handles, cache property values, register StructureChanged/PropertyChanged event handlers, and use FlaUI's Retry/ConditionFactory helpers instead of hand-rolled polling. Target FlaUI 4.x (verify the current release on NuGet — the 4.x line is the one to use; FlaUI.UIA3 specifically, not FlaUI.UIA2).
So: FlaUI yes. But the interesting question is whether the bridge to it should be edge-js, which is really question (4).
(2) Does UFO²'s hybrid UIA+vision add value here?
For a well-instrumented Electron app: mostly no, and it's the wrong shape of dependency. UFO² is a Microsoft Research Python AgentOS (arXiv 2504.14603, source at github.com/microsoft/UFO). Its hybrid control detection fuses UIA metadata with vision-based grounding specifically because real GUIs are heterogeneous — some apps expose clean UIA, while legacy or custom-toolkit apps render controls that bypass UIA entirely. The vision layer (OmniParser-style) earns its cost precisely on the UIA-poor apps. An Electron app with good accessibility is the opposite case — the UIA tree is the strength — so OmniParser inference (GPU, added latency, an LLM in the loop) buys you little.
What's worth stealing from UFO² rather than adopting wholesale: its GUI–API hybrid action layer idea (prefer a native/programmatic action when one exists, fall back to synthetic UI interaction otherwise) and the principle of treating vision strictly as a fallback for controls absent from the structured tree. Adopting the whole framework would drag a Python runtime and an agentic LLM loop into what should be a deterministic Node system — a bad trade for your case.
(3) Computer-use API as UIA fallback
Reasonable as a last-resort escape hatch, not a tier you hit often. Current surface is the computer-use-2025-11-24 beta header on the Claude 4.x family (the older computer-use-2025-01-24 header covers earlier models). It's self-hosted — you run the tool execution in your environment and feed results back through the loop — and Anthropic still frames it as experimental, with known weak spots in scrolling, dragging, and zooming.
Design constraints if you wire it in:
Invoke only on a UIA miss (control genuinely not in the tree, or a dynamic <canvas> region Chromium doesn't expose semantically). Never in a hot loop — it's seconds and tokens per step versus milliseconds for UIA.
Scope the screenshot to the app window, not the full desktop, and downscale: accuracy degrades above roughly WXGA-class resolutions, and you'll want to map model coordinates back through your scale factor.
Keep it behind a feature flag with a hard step/cost budget so a flaky run can't spiral.
For your Electron target specifically, the cases where you'd actually need this are narrow — mostly canvas/WebGL content with no a11y annotations.
(4) IPC: the real architectural decision
Ranked for your case:
Best: persistent out-of-process .NET worker + gRPC. Stand up a small .NET 10 (current LTS) host that owns FlaUI, runs its own STA thread with a proper COM message pump (UIA is STA-sensitive — this matters), and exposes a typed automation surface via gRPC. Node side uses @grpc/grpc-js + @grpc/proto-loader. On Windows 11 you can run gRPC over a Unix domain socket (supported since Windows 1803) or a localhost loopback to avoid exposing a TCP port. Why this wins: crash/hang isolation (a wedged UIA call or a COM deadlock kills the worker, not your Node process — you just respawn it), a versioned .proto contract instead of stringly-typed glue, and server-streaming RPCs map perfectly onto UIA event subscriptions (stream PropertyChanged/StructureChanged events to Node instead of polling).
Strong alternative: named pipes (\\.\pipe\...) to the same persistent .NET worker, with length-prefixed MessagePack or JSON framing. Lower overhead than gRPC and dead simple, but you hand-roll the contract, request/response correlation, and event multiplexing. Pick this only if the gRPC toolchain feels like overkill and your surface is small.
edge-js (in-process .NET hosting): lowest possible latency, zero IPC, shared-heap marshalling. But it couples you to edge-js's native ABI and Node version (recompiles via node-gyp when no prebuilt matches), and crucially a .NET/COM crash or hang takes down your Node process — no isolation. The STA threading also gets fiddly in-process. I'd reach for this only if you've measured the out-of-process hop as a real bottleneck, which for UI automation (human-timescale actions) it almost never is.
Worth knowing about: skip .NET entirely with napi-rs + windows-rs. Write the native addon in Rust (napi-rs for the Node binding, the windows crate for the UIAutomationCore COM interfaces). One native module, no .NET runtime, clean prebuild story across Node versions. The cost is that you reimplement what FlaUI gives you for free — patterns, condition builders, retry logic, the sane element abstractions. Good fit if you want a single lean dependency and your automation surface is narrow; bad fit if you lean on FlaUI's ergonomics.
Recommended stack
A persistent .NET 10 worker process hosting FlaUI 4.x (0) on a dedicated STA thread, exposed to your Node 22/24 + TypeScript app over gRPC (@grpc/grpc-js, transported on a Windows UDS or loopback). UIA3 is the deterministic primary path; you launch/attach the Electron target with renderer accessibility forced on. A thin vision fallback calls thecomputer-use-2025-11-24 tool only when a target control is absent from the UIA tree, window-scoped and budgeted. Borrow UFO²'s "prefer programmatic action, fall back to synthetic input" layering as a design principle, but don't pull in the framework.
That gives you crash isolation, a typed evolvable contract, event streaming instead of polling, and a clean separation between the fast deterministic 95% and the slow probabilistic fallback.
One thing I'd want to pin down before committing: how dynamic is the part of the Electron UI you're driving — is it standard DOM-backed widgets (UIA handles these beautifully) or heavy <canvas>/WebGL surfaces? That answer is what determines whether the vision fallback is a rare nicety or load-bearing, and it changes how much I'd invest in tier 3.
