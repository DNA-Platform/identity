How do I check the ram and memory on my windows computer
Claude
17:00 UTC, 25 January 2026
There are a few quick ways to check RAM on Windows:
Task Manager (fastest method): Press Ctrl + Shift + Esc, click the "Performance" tab, then select "Memory" on the left. This shows total RAM, how much is in use, speed, and slots used.
System Settings: Press Win + I to open Settings, go to System → About. Under "Device specifications" you'll see "Installed RAM."
Command line: Open Command Prompt or PowerShell and type systeminfo — look for "Total Physical Memory" in the output. Or for just RAM: wmic memorychip get capacity, speed, manufacturer
If you want detailed specs (like which slots are populated, timings, etc.), Task Manager's Performance tab or a tool like CPU-Z gives you more granular info.

Global C-States Explanation
What C-States Are: C-States are CPU idle power states. C0 is fully active, C1 is the first idle state, and they go deeper (C3, C6, C8, etc.) with progressively more power savings but longer wake-up times.
Why Disabling Fixes NVMe Warm Restart:
When Windows initiates a restart, it doesn't do a full power cycle - it's a "soft" reboot. The CPU transitions through power states during this process. Here's what goes wrong:
During restart, the CPU enters a deep C-state momentarily
This triggers the PCIe bus to also enter a low-power state (L1 or deeper)
The NVMe drive gets a signal to enter its own low-power state
When the system tries to come back up, it expects the NVMe to respond immediately
The NVMe is still "waking up" from its power state - it misses the initialization window
BIOS/UEFI sees no drive → "Boot Device Not Found 3F0"
Cold boot works because everything gets a full power cycle - capacitors drain, all devices reset to known state, clean initialization sequence.
Why Global C-States specifically:
Global C-States controls whether the entire platform can enter these deep idle states, not just the CPU cores. When disabled:
PCIe links stay more active
NVMe maintains readier state
The restart sequence doesn't trigger the problematic power transition cascade
The Tradeoff: Slightly higher idle power consumption and heat. On a laptop this matters more than a desktop. For your issue, it's worth it.

Windows 11 + AMD Ryzen + NVMe Warm Restart Failure: A Technical Analysis
The Windows Restart Sequence and Its Distinction from Shutdown
When a user initiates a restart from Windows, the operating system follows a fundamentally different code path than shutdown. During restart, Windows sends IRP_MN_SET_POWER requests to all device drivers with the ShutdownType parameter set to PowerActionShutdownReset, signaling that the system is resetting rather than powering off indefinitely. This distinction matters because drivers can determine whether to fully power down devices or merely prepare them for rapid reinitialization. The Windows kernel power manager sequences these IRPs so that devices farther from the root power down before devices nearer the root, creating an orderly transition. However, unlike a cold boot where all hardware starts from a completely de-energized state, a warm restart maintains power to the system throughout the transition, meaning PCIe devices like NVMe drives never fully lose power and must handle the reinitialization sequence while potentially still in an intermediate power state.
StorNVMe Driver Power State Management
Microsoft's in-box NVMe driver, StorNVMe, manages NVMe device power states through a sophisticated algorithm that maps NVMe operational power states to Windows P-States (performance states) and non-operational states to F-States (idle power states). When the system is idle, StorNVMe traverses its internal table of power states and selects the deepest state where the sum of entry latency (ENLAT) and exit latency (EXLAT) falls within the current transition latency tolerance. The default idle timeout before transitioning to a low-power state varies based on system power state—during active use, StorNVMe prefers responsiveness, but on DC power the latency tolerance increases to 50ms, and during Modern Standby it extends to 500ms. Critically, Microsoft's documentation explicitly states that StorNVMe does not support devices with APST (Autonomous Power State Transition) enabled for Modern Standby support, indicating a known tension between NVMe-level and Windows-level power management that can create race conditions during power transitions.
The Critical Role of Device Power States During Restart
Windows defines device power states D0 through D3, with D3 subdivided into D3hot and D3cold starting with Windows 8. The transition from D3hot to D3cold is the only direct transition between low-power states that doesn't require returning to D0 first—all other transitions must pass through D0, allowing drivers to configure hardware as needed. During a warm restart, the device may be in any of these states when Windows initiates the shutdown sequence. If an NVMe device is in a deep F-state or has entered D3hot, and the restart sequence doesn't provide adequate time for the device to return to D0 and properly prepare for reinitialization, the device may miss the narrow window during which the BIOS/UEFI enumerates PCIe devices. Microsoft's documentation notes that devices should support RTD3 (Runtime D3) with resume latency of 100ms or less to meet the 1-second system resume requirement—but this assumes the device receives proper notification and timing during the transition.
PCIe Reset Types and Their Implications for Warm Restart
The PCIe specification defines several reset types with different characteristics. A cold reset (fundamental reset) occurs when power is removed and reapplied—this fully reinitializes all device state. A warm reset is triggered without disconnecting power, meaning the device must handle reinitialization while potentially retaining some internal state. A hot reset is triggered across the PCIe link when the link is forced into electrical idle or by sending TS1/TS2 ordered sets with the hot reset bit set. During a Windows warm restart, the system performs a warm reset rather than a cold reset—power is maintained to PCIe devices throughout. Microsoft's documentation for Modern Standby systems states that the parent PCIe Root Port must apply fundamental device reset for all children downstream upon D0→D3 transition and deassert reset upon D3→D0 transition. However, during a warm restart, this clean D3→D0 transition may not occur in the expected sequence, leaving the NVMe device in an ambiguous state when the BIOS begins PCIe enumeration.
Windows Power IRPs and the Restart Notification Chain
When Windows initiates a restart, the kernel power manager sends IRP_MN_SET_POWER requests down the device stack for each PnP device node. The system power IRP is explicitly a notification, not a direct request to change power state—drivers must not change their device's power state as a direct response to the system power IRP but should wait for a corresponding device power IRP. This two-stage notification process creates timing dependencies. If the StorNVMe driver receives the system power IRP indicating PowerSystemShutdown with ShutdownType PowerActionShutdownReset, it prepares for restart but waits for the device power IRP before actually transitioning the NVMe device. However, Microsoft's documentation notes that "a driver cannot fail an IRP_MN_SET_POWER request to set the system power state"—the power manager ignores any failure status. This means even if StorNVMe encounters issues preparing the NVMe device for restart, the restart proceeds regardless, potentially leaving the device in an inconsistent state.
Fast Startup's Absence During Restart and Why It Matters
Windows Fast Startup, enabled by default since Windows 8, performs a hybrid shutdown where the kernel session is hibernated to disk, allowing faster boot times by reloading the saved state rather than fully reinitializing. Critically, Fast Startup only applies to shutdown operations—restart always performs a full kernel reinitialization. This creates an asymmetry that explains why some users report NVMe detection issues on cold boot (shutdown + power on with Fast Startup) but not restart, while your case shows the opposite pattern. When Fast Startup is involved, the kernel and loaded drivers are written to the hibernation file, meaning drivers don't go through their normal unload/reload cycle. During restart, all drivers fully unload and reload, but the hardware itself doesn't experience a full power cycle. This mismatch between software state (fully reinitialized) and hardware state (warm, never fully powered down) is precisely where NVMe detection failures can occur.
