Great question! Purity and idempotency are related but distinct concepts:
Purity
A pure function:
Same input → Same output (deterministic)
No side effects (doesn't mutate external state)
typescript
// Pure
const pure = (x: number) => x * 2;
pure(5) === pure(5) === pure(5);  // Always 10

let counter = 0;
const impure = (x: number) => x + counter++;
impure(5);  // 5
impure(5);  // 6 (different output!)
Idempotency
An idempotent operation:
Repeated application has same effect as single application
f(f(x)) = f(x)
typescript
// Idempotent
const setToTen = (obj: any) => { obj.value = 10; return obj; };

// Not idempotent
const increment = (obj: any) => { obj.value++; return obj; };
increment(increment(obj)) !== increment(obj);  // Different effects!

typescript
// Pure function
const double = (x: number) => x * 2;
double(5) === double(5);  // Idempotent with respect to output

Testing Philosophy: Building Durable Unit Tests
The Purpose of Unit Testing Unit tests exist to verify that a piece of code fulfills its contract - the promises it makes about its behavior. A unit test should document what the code is supposed to do, not how it does it. When a developer reads a test, they should understand the intended behavior of the system without needing to examine the implementation. Tests serve as living documentation that executes, providing both specification and verification. The best unit tests outlive multiple refactorings of the underlying code because they test the stable contract, not the volatile implementation.
Testing Features vs Implementation Details The cardinal sin of unit testing is coupling tests to implementation details. An implementation detail is anything that could change without breaking the public contract. Testing that a private method was called, that a specific internal data structure was used, or that operations happened in a specific order (when order doesn't matter to the outcome) creates brittle tests that break during valid refactoring. Feature testing focuses on observable behavior: given this input, expect this output; given this state change, expect this new state. When you test features, you can completely rewrite the internals and the tests still pass if the behavior remains correct.
The Relationship Principle Good tests verify relationships and invariants, not absolute values. Testing that "ID equals 1" is brittle; testing that "ID1 differs from ID2" is durable. Testing that "the first instance has template status" is fragile; testing that "exactly one instance has template status" is robust. This principle extends to all aspects of testing: verify that sorting produces correct ordering, not specific positions; verify that transformations maintain properties, not specific outputs; verify that relationships hold, not that specific values appear.
Isolation Without Mocking Madness Unit tests should isolate the unit under test, but excessive mocking creates tests that verify mocking configuration rather than actual behavior. The best tests use real objects where possible, creating minimal test doubles only for external dependencies, expensive resources, or non-deterministic behavior. When you mock everything, you're testing that your mocks work, not that your code works. When a test requires extensive setup and mocking, it often signals that the code has poor separation of concerns.
State Independence Each test should start from a known state and leave no traces that affect other tests. Global state, static variables, and singletons are the enemies of test independence. When tests can run in any order and still pass, you have achieved true test isolation. This means resetting counters, clearing caches, and ensuring each test constructs its own test subjects. The temptation to share setup between tests for performance should be resisted unless the setup is truly immutable.
Semantic Test Structure Tests should follow the Arrange-Act-Assert pattern with clear semantic boundaries. Arrange sets up the test context, Act performs the operation being tested, and Assert verifies the outcome. When a test has multiple acts and asserts interleaved, it's really multiple tests masquerading as one. Each test should verify one logical concept, even if that concept requires multiple assertions. The test name should complete the sentence "It should..." with a clear, specific behavior.
Testing Error Paths Good tests verify both success and failure modes. Testing only the happy path leaves half the code unverified. Error conditions, edge cases, and boundary values often harbor the most bugs. When code can fail in multiple ways, each failure mode deserves its own test. This includes not just exceptions, but also graceful degradation, fallback behaviors, and error recovery. The error path tests often reveal missing error handling or unclear error contracts.
Performance Characteristics as Features While unit tests shouldn't be performance tests, algorithmic complexity is a feature. If a function promises O(1) lookup or O(n log n) sorting, tests can verify this contract without measuring exact timings. This might mean testing that doubling input size doesn't quadruple execution iterations, or that accessing any element takes constant operations. These tests document performance contracts without being sensitive to hardware or environmental variations.
Refactoring Confidence The ultimate measure of test quality is refactoring confidence. Good tests let you refactor fearlessly because they verify behavior, not structure. If changing an implementation detail breaks tests, those tests are too coupled. If changing behavior doesn't break tests, those tests are too loose. The sweet spot is tests that break only when actual behavior changes, providing a safety net that catches real regressions while allowing implementation evolution.
Test as Design Tool Writing tests first, or at least thinking about testability during design, produces better architecture. Code that's hard to test is often hard to use. If setting up a test requires extensive boilerplate, the API is probably too complex. If testing requires accessing private members, the abstraction is probably wrong. If tests are deeply nested with complex conditions, the code probably has too many responsibilities. Tests are the first client of your code - if they struggle, so will human clients.
