There is one object. Everything else is a view.
The mistake would be to think the prototype has three kinds of thing (books, obligations, a frontier). It has one kind of thing — the book/chapter, which is a referent — plus views, which are projections of the book-set. Chapters are books nested by reference; the frontier is a projection; the shelves are a projection. This is the UI-level image of the theory itself: one primitive, many readings.
Here is the object, concretely — the frontmatter every book/chapter carries:
text
Book {
  id            : canonical title            // the (x) — its symbol
  type          : Axiom | Theorem | Definition | Chapter
                | Catalogue | Obligation | Consequence | Goal | ...
  author        : → Book                     // Doug, Seren, Ana, ...
  subject       : → Book                     // what this is ABOUT
  status        : proved | checked | proposal | hypothetical | superseded
  body          : prose + formulas
  refers_to     : [→ Book]                   // outgoing edges (authored)
  supersedes    : [→ Book]                   // the preserved errors
  obligations   : [Obligation]               // the holes in THIS book
}

Obligation {                                 // a marked incompleteness — a `sorry`
  in            : → Book                     // constitutively lives in a book
  blocks        : [→ Book]                   // what rests on it
  status        : open | in_progress | champion_needed
  difficulty    : good_first | medium | hard | foundational
  issue         : → GitHub issue             // the sync point
}
Two derived fields never authored, always computed: referenced_by (invert everyone's refers_to) and superseded_by (invert supersedes). That inversion is the whole trick, and I'll come back to it.
The sections, abstracted
Every surface in the prototype is one of exactly two things.
Objects — the book/chapter, displayed as itself: body in the center, metadata rail on the side (Type / Author / Subject / Refers-to / Referenced-by), holes marked inline. This is the only authored surface. It's the atomic reading unit and the atomic editing unit.
Views — projections of the whole book-set through a chosen lens:
The Catalogue (front door) = project by containment → the master index. In Eirian's model this is "This Library Belongs to Eirian," the self-cataloguing master.
The Shelves = project by status → settled vs. moving.
The Frontier = project by obligations → the open work.
The Graph (not yet built) = the raw refers_to edges, walkable.
None of these are separate data. They are SELECT statements over the one table.
How the book view becomes the frontier view
This is your actual question, and it has a clean answer. The frontier is not authored. It is the result of one query:
text
Frontier  :=  flatten( book.obligations  for book in Library )
              sorted by  |obligation.blocks|   descending
That's it. You collect every hole in every book, and rank by how much rests on it. Obligation #01 (the role-indexed arrow) sits at the top not because someone decided it should but because more books list it in their blocks than any other. The ranking is computed from the dependency structure, so it can't be gamed or go stale.
And here is the part that makes it library semantics rather than a dashboard: the Frontier is itself a book, of Type: Catalogue, whose subject is incompleteness. Exactly the way "My Guiding Star" is the subject-catalogue for Dad — it collects everything about its subject. The Frontier collects everything about the theory's own unfinishedness. So the frontier view doesn't sit outside the library. It's a book in the library that happens to be generated. The catalogue catalogues its own holes.
The five principles, named
1. One object, many views. Books are the only authored thing; shelves, frontier, graph, catalogue are projections. (Mirrors: one primitive R(x,y,t), many derived readings.)
2. Status is a property, so projection is free. Because status is a field on the referent, the shelves cost nothing — they're a group-by. You never maintain a "what's proven" page; it maintains itself.
3. Every hole is addressable. An obligation is a named location, like Lean's sorry. You can link to a hole, rank holes, count them. Incompleteness has coordinates.
4. All work is editing books. Your insight, and it's the load-bearing one. There is no project that isn't one of: fill a hole, promote a status, add a book, supersede a book. Those are exactly the atomic operations (Adopt, Derive, Demote, Promote, Retire/Reframe) you'd already named. So a GitHub issue is never free-floating — it is a proposed edit to a specific book, and it attaches to that book's obligations.
5. The frontier is generated, so it cannot drift. Because it's a query, a book that owes something and a frontier that hides it is an impossible state — the way mathlib's build fails if a theorem quietly picks up an unaudited axiom. Sync is structural, not maintained.
The proof that this is the right structure
Not "a clean structure" — the forced one. The argument has three steps.
Step one — the container must be library-semantic, or it refutes its own contents. SRT's central architectural claim is that library semantics is the correct replacement for set/model/category semantics: self-hosting, containing its referents rather than pointing at them, incompleteness first-class. If you present that theory inside a conventional container — a docs site with a separate nav, a separate status badge, a separate issue tracker bolted alongside — you've asserted by your own tooling that the theory's semantics can't organize a real body of knowledge, so you reached for someone else's. That's a performative contradiction. The presentation of a self-hosting theory must itself be hosted in the theory. So the repo has to be a catalogue of books. That's not aesthetic preference; it's forced by what SRT claims.
Step two — the frontier is not an add-on; it's the theory's own frontier made visible. SRT already has two faces built into it: what has been transduced into the catalogue (named referents), and the open frontier of unnamed symbols that are necessary but not yet named. The theory says explicitly that this frontier is first-class, that a pointer to a thing is not the thing, that the frontier is fillable by transduction. So a presentation that surfaced only the named catalogue and hid the frontier would be concealing exactly the structure the theory says is fundamental. The Frontier view isn't a project-management convenience. It's the theory's un-transduced boundary, rendered. Any honest presentation of SRT is obligated to show it — which is why "certainty status" and "navigate to what's owed" weren't two nice features I added, they were the two faces the theory already has.
Step three — and this is the one that closes it — the contributor's act *is* the theory's central act. When someone takes obligation #01, works it, and merges the result, what have they done in the theory's own terms? They've taken a necessity the system proved must exist, found its witness, and named it into the catalogue. That is transduction — the theory's one generative move. The item leaves the Frontier and enters the shelved catalogue; ahypothetical becomes a proposal becomes proved; referenced_by updates for free. The development workflow is not analogous to the theory. It is an instance of it. The person doing a project is performing the operation the theory is about.
That's the proof. The structure is right because under it the tool's operations are the theory's operations — one object because one primitive, projections because derived readings, a frontier because an un-transduced boundary, and a contribution because a transduction. A different structure could display SRT. Only this one enacts it. And for a theory whose whole claim is that meaning must host itself, enacting beats displaying — the container stops being a container and becomes another instance of the thing.
