Good timing on this question — 2026 is the year agent memory stopped being "stuff history into the context window" and became a dedicated architectural component separate from the model's context window. For coding agents specifically, here are the approaches that have shaken out, roughly in order of increasing weight:
File-based notes (0 / 1 / 2). A curated markdown file in the project root that the agent reads at session start. It works, but requires manual upkeep and doesn't scale across sessions — you can't inject fifty prior sessions into a context window this way. Right choice when context is small, stable, and worth curating by hand: project conventions, architectural decisions, behavioral constraints. This is your procedural/semantic layer and it's still the backbone of most setups. The practical distinction that's emerged: a hand-written AGENTS.md for rules and persona, an agent-curated MEMORY.md for distilled learnings — with a human or the agent deciding what's worth keeping, because without it, semantic memory becomes a junk drawer.
Vector store / managed memory layer (Mem0, Zep, Hindsight). Facts get extracted from sessions, embedded, and retrieved by semantic similarity at the next session start. Right choice when you have ongoing work where decisions and context accumulate over days or weeks and there's too much to hand-curate. For coding agents the integration story matters: tools like Hindsight plug into OpenCode/Claude Code via hooks that recall relevant memories when a session starts and retain the conversation when the session goes idle, surviving context compaction. Mem0 is the lightweight default; Zep leads on temporal reasoning.
Knowledge graph / graph-vector hybrid (Cognee, Graphiti, Zep's Graphiti engine). Stores facts and the relationships between them, so the agent can reason across connected entities rather than retrieving isolated chunks. The motivation is that most basic vector stores retrieve semantically similar chunks but have no awareness of how facts relate to each other. Right choice when your agent works across many interrelated persistent entities — repos, vendors, modules, decisions that reference each other — or in multi-agent setups needing a shared memory substrate. Heaviest to operate; overkill for a solo agent on one codebase. Worth noting the benchmark spread is real: independent benchmarks show up to 15-point accuracy gaps between architectures on temporal queries, so the choice isn't cosmetic.
The actual consensus, though, is layered rather than pick-one. The dominant pattern is a fast session cache layered on top of a deeper semantic and relational memory system — Redis (or in-memory) for sub-millisecond working memory, plus a vector or graph store for durable cross-session knowledge. Two design rules show up repeatedly and are worth stealing regardless of backend: treat memory writes as first-class operations — don't rely on the LLM to decide what to remember, using explicit triggers at task completion or fact confirmation; and keep session-scoped memory strictly separate from permanent memory.
For your situation — a TypeScript agent driving Claude Desktop on a single evolving project — I'd start with the curated file layer and bolt on a managed vector layer (Mem0 or the Hindsight-style hook approach) only once you're feeling the pain of re-explaining context. Jump to a graph store only if the entity relationships in the automation system start to matter for retrieval.
Two failure modes to budget for from day one: staleness — a highly-retrieved memory about a user's employer is accurate until they change jobs, at which point it becomes confidently wrong, and high-relevance staleness is still an open problem decay doesn't solve — and memory poisoning (OWASP ASI06), the persistent-attack analogue to prompt injection that session-level controls miss. Both argue for keeping memory writes explicit and auditable, which the file-first approach gives you for free.
