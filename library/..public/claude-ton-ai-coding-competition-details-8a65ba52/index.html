Am I Familiar with the Tech?
Very much so — this is a sweet spot. The stack involves:
TON blockchain — I know it well. Smart contracts are written in FunC (low-level) or Tact (higher-level, TypeScript-like). TON has a very unique sharded architecture and async messaging model that trips people up compared to EVM chains.

AI Agents — autonomous systems that take actions, often using LLMs as their reasoning core

Good instinct to be skeptical there — TON's architecture is genuinely unusual compared to EVM chains. It's async, everything is message-passing between contracts, and even the testnet has gotchas that can eat days. So the smartest strategy is to minimize or eliminate custom smart contract deployment entirely and lean on existing TON infrastructure via APIs.
Here's one realistic idea per track:
Track 2: User-Facing Agent
"TON Wallet Copilot" — a Telegram bot that is your personal on-chain analyst
What it does: A user messages the bot their TON wallet address (or connects via TON Connect). The AI agent then answers natural language questions about their wallet — "what did I spend last week?", "which tokens am I holding that are losing value?", "summarize my last 10 transactions" — pulling live data and reasoning over it with an LLM.
Why it's deployable in days:
Zero smart contract deployment. You're just reading the chain via TONapi or toncenter.com REST APIs — they're excellent and well-documented
The bot itself is a standard Telegram Bot (Node.js + grammy or telegraf)
The AI reasoning layer is just Claude or GPT via API
Deploy the bot server to Railway or Fly.io — straightforward
The "agent" angle is that it's not just a lookup tool — it can autonomously fetch multiple data sources, reason across them, and give you synthesized insights, which fits the track criteria.
Track 1: Agent Infrastructure
TON MCP Server — a bridge letting any AI agent interact with TON
What it does: An MCP server that exposes TON blockchain capabilities as tools — get_wallet_balance, get_transaction_history, estimate_gas, get_jetton_price, send_transaction_payload (building the unsigned tx, not signing). Any AI agent (Claude, GPT, anything MCP-compatible) can then natively "speak TON" without knowing anything about the chain.
Why it's deployable in days:
Again, no custom smart contracts — you're wrapping existing APIs (TONapi, TON Center) into MCP tool definitions
An MCP server is just a Node.js/TypeScript process that speaks a well-defined JSON protocol
The post specifically linked MCP Docs, which signals the judges are actively looking for this
Deploy as a simple HTTPS endpoint — Vercel serverless functions even work
Why this is strategically interesting: It's genuinely useful infrastructure. Right now there's no good TON MCP server publicly available, so you'd be filling a real gap, which judges reward.
The honest hierarchy of difficulty: Track 2 bot < Track 1 MCP server < anything involving deploying your own smart contracts. Both of these ideas deliberately stay in the first two tiers.
