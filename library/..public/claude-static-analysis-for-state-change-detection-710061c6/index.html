Bottom line
The approach is valid but the novelty claim is substantially overstated. The techniques they want to use (HIR, SSA, backward slicing, reactive-scope inference) are all real, well-understood, and already deployed in production by other frameworks. The one architectural choice that's narrowly novel — emitting a separate pure 0 used only as a change-detection oracle, leaving the React render pipeline intact — is a design choice with real trade-offs, not a breakthrough.
More importantly, the teammates severely under-read the prior art. Meta has been writing this exact compiler, at much greater scope, for years. Starting without studying what they've published would be a mistake.
Is this unique? Short answer: no. Long answer:
React Compiler is the closest comp, and its architecture is almost identical. The pipeline lowers Babel AST to an HIR organized as a control-flow graph of basic blocks, converts to SSA, runs type inference, then does "reactive scope inference" — determining groups of values that mutate together — followed by scope-dependency propagation and codegen. That's the exact pipeline Cathy sketched. The Meta team explicitly describes inferReactiveScopeVariables, propagateScopeDependencies, pruneNonReactiveDependencies, pruneUnusedScopes as named passes — every phase Cathy proposed corresponds to a named pass already running in production inside React 19+.
The only architectural difference is the output shape. React Compiler memoizes each JSX element independently rather than memoizing the component as a whole, with cache slots and conditional equality checks inlined into the transformed component. So where Cathy proposes a separate compute(chemical), React Compiler inlines if ($[0] !== product.name) checks into the original function body. Same dependency analysis; different emission strategy.
So "nothing else computes a standalone characteristic function purely for change detection" is technically true as a micro-claim, but misleading. The underlying analysis is not novel. Framing this as a breakthrough to the expert will be embarrassing.
Million.js / BlockDOM is the second closest and arguably closer in spirit. It runs static analysis at compile time to produce an "Edit Map" that represents the dynamic parts of the virtual DOM, then at runtime does a shallow-equality dirty-check on state values and uses the Edit Map to directly update the DOM. The "extract the dynamic parts as a small data structure and dirty-check against that instead of rerunning everything" pattern — that's exactly Cathy's idea. Million produces the Edit Map as data (closer to the "dependency set" artifact Cathy describes) then both dirty-checks and patches from it. Cathy would stop at the dirty-check and let React do the patch.
Fict (published Dec 2025 — a month ago) is even closer. Its pipeline is: Build HIR (basic blocks + CFG), convert to SSA with versioned assignments for explicit dependency edges, analyze reactive scopes, detect control-flow reads, and generate fine-grained DOM. Still in experimental development, but this is a solo-developer project that has independently landed on essentially the same pipeline Cathy is proposing, with the same output semantics. If a single person has built this in a few months, the engineering estimate of "300-500 lines for SSA, 300-500 for slicing, 200-300 for codegen" is the right order of magnitude for a toy but probably off by 3-5× for production.
Solid, Svelte 5, Vue 3, Qwik, Preact Signals are all runtime proxy/signal tracking, not compile-time slicing. Cathy correctly excluded these from the comp list. Worth noting: Svelte 5 actually moved away from pure compile-time reactivity toward runtime proxies — reactivity in Svelte 5 is determined at runtime rather than compile time. That's a data point. The compile-time-only path is a road the community explored and partially retreated from.
SwiftUI is a different axis worth noting. It uses a reflection-based diffing algorithm that compares the view struct's stored properties — Equatable values via their conformance, others recursively. This short-circuits body evaluation entirely when props haven't changed. Doug's proposal is the inverse: don't look at inputs, analyze what body reads, compare only those reads. SwiftUI's approach is simpler but requires the framework to own the struct allocation. Doug's inverts the question at the cost of needing a compiler.
Prior art on the analysis itself
This is where the teammates are really naive — the academic literature on this is 40 years deep.
Program slicing (Weiser, 1981) is what they're proposing. Arthur's concern about soundness is the right concern. The literature is blunt: static program slicing lacks adequate precision because it relies on conservative program analysis to maintain soundness. Sound slicers over-approximate (more false positives, benign for Doug's case — spurious re-renders). Precise slicers require dynamic information. JSSlicer (2012) exists as a prototype JS slicer, and JSAI is a formally-sound abstract interpreter for JS. Both surface the same trade-off: for Turing-complete languages with dynamic dispatch, sound slicing is undecidable in the general case; the restriction set must be precisely specified and enforced.
Self-adjusting computation (Acar et al., 2002 onward) is the most directly relevant academic work and isn't mentioned by the teammates. Self-adjusting computation tracks control and data dependencies so that changes to data can be propagated through the computation by identifying the affected pieces and re-doing those pieces. Jane Street's Incremental library is the production OCaml implementation. This is a runtime system rather than a compile-time one, but the semantic model — a dependency graph derived from execution, used to decide what to recompute — is exactly the problem Cathy is solving, with 20+ years of formal backing.
Adapton (Hammer et al., PLDI 2014) extends SAC with demand-driven change propagation via a "demanded computation graph" — thunks that cache their observations and results. Also runtime, also directly relevant. The word "characteristic" that Cathy uses maps cleanly onto Adapton's "observations of a thunk."
If Doug brings an expert in and they haven't read Acar or Hammer, wrong expert.

What they missed that actually matters
One: $Chemistry is not vanilla React. The view method is on a class, reads happen via this.$prop, children are constructed by the bond constructor not inline JSX, and methods can call other methods on the prototype chain. This means the slicer must be inter-procedural from the start — it must follow this.someMethod() calls and union their reads into the slice. Intra-procedural slicing (which is what 300-500 lines buys you) won't work for your framework. React Compiler gets to be mostly intra-procedural because components are plain functions.
Two: the existing 0 in 1 is already doing structural change detection over JSX trees. That function, plus the symbol-based identity system, plus the fact that inline closures are compared by toString(), already constitutes a cheap-ish diff. Before building a compiler, Doug should measure: how expensive is the current post-commit re-render-and-diff actually? The proposal replaces a re-run of view() in the post-commit effect with a compute() call. If view() isn't the bottleneck, the compiler is premature.
Three: the "is it the same value?" question is underspecified. Cathy's { sources: [...], outputs: [...] } example has outputs that include expressions like s.$count * s.$price. What's the equality check on the output? If the output is a JSX element reference, you're back to structural comparison of trees. If it's a primitive, === works. For objects and closures, you need a decision that matches the decisions in reconcile.ts/walk.ts. The characteristic isn't free from the structural-equivalence problem; it just scopes it down.
Four: tooling choice. Use the TypeScript Compiler API, not Acorn + eslint-scope. Doug writes TypeScript. tsc has scope resolution, type info, and will let the slicer reason about this types, method signatures, and $Chemical subclassing. Acorn throws away the types that would make slicing sound. React Compiler pays the cost of doing all this analysis from raw JS because it has to support vanilla React; Doug doesn't.
Five: the "is this actually cheaper?" claim needs testing. The 10-100× cheaper number Cathy cites is speculation. The characteristic function has to evaluate every source on every check. Proxy-based tracking only fires when a source is written. For a view with many sources and infrequent writes, proxies are asymptotically cheaper. For few sources and frequent re-renders under lifecycle mutations, compute() wins. Cathy hasn't identified which regime $Chemistry is actually in.

Member reads off this: this.$count, this.children, this.totalPrice
Method calls on this: this.format(...), this.totals()

Ternaries, &&, ||, optional chaining — all plain ES expressions

That's almost everything real views do. It's plain ES with two load-bearing patterns — this.x member access and call expressions — and the JSX factory is just a regular call. No special casing needed for <Foo> vs _jsx(Foo, ...); it's all CallExpression nodes in the AST.
The important property: all reactive reads route through 0. That's not accidental — it's the framework's convention. $prop is reactive external state, bare prop is internal reactive, _prop is non-reactive, $$prop is framework internals. So the entire analysis reduces to: find every this.<path> read, decide which are reactive from the name.
That's a dramatically smaller problem than general JS slicing.
Library: acorn + acorn-walk
Small, battle-tested, runs at runtime in the browser without a build step. Used by webpack, Rollup, ESLint, Browserify. Acorn is ~17KB gzipped, zero dependencies, ESTree-compatible AST. acorn-walk is a companion visitor. If we ever need faster, meriyah is acorn-compatible and drop-in.
We don't need TypeScript parsing at runtime (view source is already compiled JS). We don't need JSX parsing (already transpiled to _jsx/createElement calls). We don't need anything fancy. parse(fn.toString(), { ecmaVersion: 'latest' }) and walk.

// $characteristic.ts
import { parse, Node } from 'acorn';
import { simple } from 'acorn-walk';

export interface Characteristic {
    reads: Path[];           // e.g., [['$count'], ['$price'], ['children']]
    bailout?: string;        // set if we couldn't fully analyze
}

type Path = string[];

const cache = new WeakMap<Function, Characteristic>();

export function characteristic(fn: Function, proto: any): Characteristic {
    let c = cache.get(fn);
    if (c) return c;
    c = analyze(fn, proto, new Set());
    cache.set(fn, c);
    return c;
}

function analyze(fn: Function, proto: any, visiting: Set<Function>): Characteristic {
    if (visiting.has(fn)) return { reads: [] };  // recursion guard
    visiting.add(fn);

    const source = normalize(fn.toString());
    let ast: Node;
    try { ast = parse(source, { ecmaVersion: 'latest' }); }
    catch (e) { return { reads: [], bailout: `parse: ${e.message}` }; }

    const reads = new Map<string, Path>();   // dedup by joined path
    const methodCalls = new Set<string>();
    const getterReads = new Set<string>();
    let bailout: string | undefined;

    simple(ast, {
        MemberExpression(node: any) {
            const path = thisPath(node);
            if (!path) return;
            // Dynamic access: bail
            if (path.some(p => p === null)) { bailout = 'dynamic member'; return; }
            // Is this read going to be called as a method?
            if (node._calledAsMethod) {
                methodCalls.add(path[0]);
                return;
            }
            // Non-call read of `this.x` — could be field OR getter
            const desc = descriptorOf(proto, path[0]);
            if (desc?.get) getterReads.add(path[0]);
            else reads.set(path.join('.'), path);
        },
        CallExpression(node: any) {
            // Mark its callee so MemberExpression knows
            if (node.callee?.type === 'MemberExpression') {
                node.callee._calledAsMethod = true;
            }
        },
    });

    // Recurse into methods and getters on this class
    for (const name of [...methodCalls, ...getterReads]) {
        const desc = descriptorOf(proto, name);
        const innerFn = desc?.value ?? desc?.get;
        if (typeof innerFn !== 'function') continue;
        const inner = analyze(innerFn, proto, visiting);
        if (inner.bailout) bailout ??= `via ${name}: ${inner.bailout}`;
        for (const p of inner.reads) reads.set(p.join('.'), p);
    }

    visiting.delete(fn);
    return { reads: [...reads.values()], bailout };
}

// Walk proto chain to find descriptor
function descriptorOf(proto: any, key: string): PropertyDescriptor | undefined {
    let p = proto;
    while (p && p !== Object.prototype) {
        const d = Object.getOwnPropertyDescriptor(p, key);
        if (d) return d;
        p = Object.getPrototypeOf(p);
    }
}

// Extract [head, ...tail] from a MemberExpression rooted at `this`.
// Returns null entries for dynamic (computed) access.
function thisPath(node: any): Path | undefined {
    const parts: (string | null)[] = [];
    let n = node;
    while (n?.type === 'MemberExpression') {
        if (n.computed) parts.unshift(null);
        else parts.unshift(n.property.name);
        n = n.object;
    }
    if (n?.type !== 'ThisExpression') return undefined;
    return parts as Path;
}

// Handles method shorthand: "view() { ... }" isn't a valid top-level statement.
function normalize(src: string): string {
    src = src.trim();
    if (src.startsWith('function') || src.startsWith('(')) return src;
    // method shorthand or class method
    return `(function ${src})`;
}

Category 3 is what makes this work. It's the category that says "this differs between renders but that's fine, we're not responsible for it."
And there's a fourth category that has to be surfaced honestly:
Mixed — position depends on both tracked and untracked sources. <span>{{this.name} at ${Date.now()}}</span>. We can't separate them; the output is contaminated. What to do?
Corner cases, worked through
C1. Mixed tracked + untracked in one position
{{this.name}-${Math.random()}} — the template literal combines a tracked read and an untracked call into one string. At the tree level this is one position. Value differs every render. If we mark it tracked, infinite loop. If we mark it untracked, changes to $name don't trigger re-render.
The honest answer: this is a programmer bug. Mixing tracked and untracked in one output position means you've tied reactivity to a nondeterministic source. The analyzer should reject this at parse time with a clear error, not silently pick a side. The A convention — non-chemical reads are outside the system — means you cannot have a position where tracked state's effect is gated by untracked state. Throw.
Rule: a position is tracked if and only if every expression feeding it is either literal or 0-rooted, and none of its expression tree evaluates an untracked call or reference.
C2. Untracked call whose argument is tracked
{formatMoney(this.$price)} — call is untracked (formatMoney isn't a particle), but the argument is this.$price. What category?
This is the one your earlier message already answered: tracked. The position's observable differences are determined by whether this.$price changed, because formatMoney is declared pure by convention. So the rule is:
A call expression 0 where 1 is untracked contributes "tracked" to its containing position *if and only if* every argument is tracked-or-static, and produces no sibling untracked reads. The arguments' this.* reads become the position's tracked reads.
formatMoney(this.$price) → tracked position, reads = {$price}. formatMoney(this.$price, Date.now()) → mixed → throw (per C1). formatMoney(5) → static (no reactive flow in).
C3. Method call on a non-particle held in state
{this.widget.create().value} — this.widget is reachable from this, but widget is not a particle. create() returns something, .value reads from it.
By the A convention: widget is opaque. We don't analyze create. But this.widget itself is a tracked read — if the widget reference changes, we care. And .create().value is a chain on top of that tracked read.
Two sub-cases:
C3a. widget reference is stable (programmer holds the same widget instance across renders). Then this.widget.create().value is effectively a tracked-read-followed-by-opaque-computation. The analyzer's honest answer: it doesn't know whether create() returns the same value two calls in a row. The safest thing is to mark the position tracked with read {widget}, meaning "re-check when widget reference changes." If create() is deterministic given widget, that's sufficient. If create() is Math.random, you get the same contamination as C1 and should throw — but we can't detect that statically because widget is opaque.
C3b. widget is a particle-typed property (programmer used a chemical class). Then we do analyze widget.create, recurse, and get its reads prefixed with this.widget..
The distinguishing signal: does widget's type extend $Particle? If the framework can answer that statically (via type info or a runtime instanceof check done once and cached), we branch on it.
Rule: for a call chain rooted in this.<path>, if <path>'s value is a particle, recurse through its methods. Otherwise, treat the entire chain as one tracked read keyed on the reference of the nearest particle-typed ancestor in the path, plus whatever this.* arguments appear in the chain.
The runtime check: first time the view is invoked, walk this.<path> and test instanceof $Particle at each segment. Cache where the particle boundary lies. Subsequent checks are just reference comparisons at that boundary.
C4. Destructuring tracked state into a local
js
view() {
    const { $name, $age } = this;
    return <div>{$name} is {$age}</div>;
}
Locals, not this reads at the usage site. But the analyzer's walker should follow the destructuring: $name and $age are aliases for this.$name and this.$age. This is routine scope analysis — track local bindings, resolve them back to their origin expressions.
acorn-walk gives you scope on request, or you roll a tiny scope tracker yourself (it's one map per function). Handle this case because it's idiomatic.
C5. Local computed from tracked state
js
view() {
    const total = this.$price * this.$qty;
    const label = `Total: ${total}`;
    return <span>{label}</span>;
}
label is tracked (depends on total, which depends on $price and $qty). Analyzer needs transitive scope resolution: for each local binding, record its dependency set by walking its initializer. When label is used in a JSX position, the position's reads are the union of all locals it transitively depends on — {$price, $qty}.
Straightforward SSA-lite: for each const / let in the function, map it to its expression's tracked reads. Resolve uses by lookup.
C6. Local computed from untracked source
js
view() {
    const now = Date.now();
    return <span>{now}</span>;
}
now is an untracked binding. The position {now} resolves to untracked. Category 3 — ignore. Same rule as if Date.now() appeared inline.
C7. Conditional position
js
view() {
    return <div>{this.$showDetail ? this.$detail : 'summary'}</div>;
}
Position's value depends on $showDetail (which branch) and $detail (the value if true). Reads = {$showDetail, $detail}. The analyzer unions reads across both branches of a ternary — conservative and correct.
C8. Array mapping with inline component
js
return <ul>{this.$items.map(item => <li>{item.name}</li>)}</ul>;
The outer position's reads are {$items}. The inline arrow's body reads item.name, which is destructuring-from-the-iteration-variable — not a this read at all. Each <li> inside the map is a child position, and its content depends on item, which depends on the outer $items. So the whole mapped list's dependency is {$items}.
Unless item is itself a particle and has reactive children: this.$items.map(item => <li>{item.$qty}</li>). Now the inner item.$qty is a reactive read on a particle, but relative to item, not to this. If items are bonded children, each <li> is really a child-chemical-rendered-in-place, and the child's re-render is handled by its render cycle, not the parent's. The parent's characteristic just needs to detect "did the set of items change" — which {$items} captures.
C9. The programmer stashes something in a local object
js
view() {
    const cache = { x: this.$a, y: this.$b };
    return <Component data={cache} />;
}
Each render creates a fresh cache object. Reference differs. If the comparator checks reference equality on the prop data, it always differs and triggers re-render. But the contents depend only on $a and $b.
This is where equivalent() from reconcile.ts already does the right thing — it walks plain objects structurally. So the position data={cache} is tracked, reads {$a, $b}, and the comparator at render time uses structural comparison.
Actually wait — we said we compare outputs, not inputs. So the question is: is cache in T₁ structurally equal to cache in T₂? equivalent() handles that already. Good. No special analyzer work needed for this case; it's just standard structural comparison at the position.
C10. Inline arrow function in a prop
js
<button onClick={() => this.$count++}>Click</button>
New arrow each render. Different reference. equivalent() already handles this via a.toString() === b.toString() for functions. If the arrow's source text hasn't changed (same file, same line, same expression), it'll be the same string. Still works.
But: the arrow captures this. It doesn't execute during render. So the analyzer should not descend into FunctionExpression or ArrowFunctionExpression bodies when collecting reads for a position. The position's reads are the captures of the arrow that are live at render time — basically, none of them, because the arrow only reads them when called. Treat the arrow as a static-ish value for the purposes of characterization (compared via toString()).
This is important. Without this rule, onClick={() => this.$count++} would falsely mark the position as reading $count, and every render where $count changed would diff — which it already does legitimately via other positions, so not wrong, just noisy. But consider onClick={() => this.$lastClickAt = Date.now()} — the arrow body has an untracked call. If we descended, we'd contaminate the position. Don't descend.
C11. Calling a particle method that returns an opaque value
js
totals() { return new Calculator(this.$items).sum(); }
view() { return <span>{this.totals()}</span>; }
Method is on the particle, so A says we recurse. Inside totals, we see new Calculator(this.$items) — constructor of a non-particle — and .sum(). Opaque computation, but tracked input {$items}.
Same rule as C2 extended to constructors: new Foo(tracked_args) is tracked-propagation if Foo is opaque and arguments are all tracked, with the reads being the union of argument reads. .sum() on the result is an opaque-method-on-opaque-result, further extension of the same rule — still tracked, still reads {$items}.
The rule generalizes: any chain of opaque calls/constructions whose inputs are all tracked-or-static is itself tracked, with reads = union of input reads.
C12. Method that mutates this
js
increment() { this.$count++; return this.$count; }
view() { return <span>{this.increment()}</span>; }
This is a sin. view should be pure; calling a mutating method from it breaks the world. The analyzer should detect this.$<prop> = or this.$<prop>++ assignments inside any method transitively called from view and throw.
Easy to detect: AssignmentExpression or UpdateExpression whose target is a this.<path> MemberExpression, anywhere in the recursion. Bail with a clear error pointing at the line.
Note: internal reactive props (bare names, not $ prefix) can legitimately be assigned — they're the internal mutable state pattern. So the rule is: assigning to this.$<externally-reactive> in a view-reachable method is forbidden. Assigning to this.<internal> is allowed for bookkeeping but makes the containing method untracked-in-its-reads (because the read will see the mutation). Easier rule: view-reachable methods can't assign to any reactive property.
C13. View calls itself or mutual recursion
js
render() { return this.view(); }
view() { return this.something ? this.render() : <div/>; }
Infinite parse recursion if the analyzer isn't careful. The visiting: Set<Function> guard in the earlier sketch handles this — when we hit a function already being analyzed, we return a sentinel "recursive, assume empty reads from this path." The reads we missed through the recursive edge will be picked up on the first non-recursive encounter.
This is sound because recursion doesn't introduce new reads relative to the set already being computed — any path the recursion could reach is already being walked.
C14. Calls on super or through prototype explicitly
super.view() in a subclass calling the parent's view. Analyzer must resolve super to the prototype chain's next view and recurse into that. Same cache mechanism — every function is analyzed once.
Object.getPrototypeOf(this).method.call(this) — dynamic, opaque. Bail.
C15. Getters on the particle
js
get fullName() { return `${this.$first} ${this.$last}`; }
view() { return <span>{this.fullName}</span>; }
Access to this.fullName looks like a property read but is really a function call. Analyzer needs to distinguish. At parse time, when we see this.<name> not followed by a call, check the descriptor on the prototype. If it's a getter, treat the read as equivalent to invoking the getter — recurse. If it's a data field, treat as a direct read.
The particle system has this convention: $-prefixed properties are typically getters/setters. Existing $Reflection code does exactly this check (descriptor.get, descriptor.set).
C16. Bonded child that gets re-bonded during lifecycle
Bond constructor runs every render. It might reassign this.$child to a different chemical instance based on some condition. If view reads this.$child.$something, the path crosses from parent to child. Between pre-effect and post-effect snapshots, the parent's bond might not have re-run (bond only runs during render), so this.$child hasn't changed references. But inside the child, its own lifecycle might have mutated $something.
Wait — the child has its own render cycle, its own characteristic, its own post-effect check. If $something changed inside the child, the child re-renders itself. The parent doesn't need to know. The parent's characteristic includes $child.$something only if the parent's view reads it directly. In which case, yes, the parent needs to re-render too, because the parent's output has {this.$child.$something} embedded.
This is actually the important case for crossing chemical boundaries. When a parent's view reads through to a child's state, the parent is legitimately coupled to the child's state. Comparison at the path this.$child.$something picks up whether the final value changed — whether the change came from $child being reassigned or from the child mutating $something internally. Both get caught by the same comparison.
C17. View that returns a non-JSX value
A $Chemical view that returns this.children directly, or a primitive, or a string. No JSX tree. No positions to classify.
Degenerate case: one top-level position, classified by the return expression itself. Returns a this.* path? Tracked with that path's reads. Returns a constant? Static. Returns a call? Apply the call rules.
Manifest becomes { positions: [{ path: [], kind: ..., reads: [...] }] } — one entry at the root.
C18. View that early-returns
js
view() {
    if (!this.$ready) return null;
    return <div>{this.$data}</div>;
}
Multiple return statements, each producing different tree shapes. The analyzer has to produce a manifest that covers both. Two options:
Option 1 — conservative: union all reads across all return paths, mark the whole output tracked if any return path is tracked. Manifest has no position structure because the shape differs between renders. Comparator falls back to equivalent() on the whole tree. Cheap analysis, less-precise comparison.
Option 2 — precise: emit a manifest per return path, plus the branch condition's reads. At comparison time, evaluate which return path each of T₁ and T₂ took, then use the appropriate manifest. More analysis, more precise comparison.
I'd start with option 1 and only implement option 2 if profiling shows it matters. Structurally-different outputs already force a top-level re-render via React's type-based diff (different root types always diff); the precision gain is only on "same branch both times."
C19. Destructuring a particle
js
view() {
    const { $name, $age } = this.$user;  // $user is a particle
    return <div>{$name}: {$age}</div>;
}
Alias analysis plus boundary crossing. $name is locally bound to this.$user.$name, $age to this.$user.$age. Positions using them resolve to those paths. Same machinery as C4, just with a particle-to-particle path at the root.
C20. Conditional property existence
js
view() {
    return <div>{this.$optional?.name}</div>;
}
Optional chaining. Tracked read of $optional, and if present, .name. If $optional is opaque (non-particle), this is a chained access on a tracked root — treat as tracked with read{$optional}, same as C3a. If it's a particle, recurse.
Things I don't think we've considered
D1. The bond constructor as a first-class concern
You mentioned bond constructor assignments are part of state. The bond constructor runs at render time and writes to chemical state. View runs after bond. So by the time view runs, whatever bond assigned is visible as this.<prop>.
But — between pre-effect and post-effect — the bond has not re-run (unless something triggered a re-render). So this.<bond-assigned-prop> might hold its pre-effect value still. If an effect mutates a reactive property that the bond would have consumed to set another property, the derived property is stale until next render.
This is fine semantically: the characteristic detects the reactive mutation, triggers re-render, next render re-runs bond, derived property updates. The staleness between effect and next render is exactly what $update$() resolves.
But it means we should not try to re-run bond in the post-effect check. Only re-run view. The bond graph is consistent because view reads whatever state is current, which includes any effect-time mutations directly but not their downstream bond-computed consequences. That's correct — the re-render pass will reconcile.
D2. Characteristic changes that don't affect the view
js
view() {
    return <div>{this.$a > 0 ? 'positive' : 'non-positive'}</div>;
}
$a changes from 5 to 7. The branch output is the same ('positive'). If we check at the value level (this.$a), we diff and re-render unnecessarily. If we check at the output level (the string 'positive'), we don't.
This is the argument for Strategy C (check outputs, not inputs) — it automatically collapses value-equivalent states. At the output level, T₁ and T₂ are equal, no re-render. Win for Strategy C.
D3. Referential identity vs structural equivalence in output comparison
For tracked positions, equivalent() does structural comparison — inline objects are walked, inline functions compared by toString(). That handles most cases.
But what about <Child data={this.$complexObject} /> where $complexObject is a large reactive plain object? equivalent() walks it. That's O(size) per render. For small objects fine. For large objects, expensive.
Optimization-in-the-future: allow programmers to mark specific properties as "compare by reference." Or detect reference stability heuristically (same reference as last time → equal). Don't need this yet; start with structural.
D4. Timing: when is the analysis done?
Lazy, on first render of a chemical class. The particle's view function is stable (on the prototype). First time we render it, analyze, cache the manifest on the class. Subsequent instances of the same class reuse the manifest.
This means the first render of each class pays the analysis cost. For a typical app with a few dozen chemical classes, that's a few dozen ~1ms analyses, done once. Acceptable.
D5. Manifest invalidation
When would a manifest become stale? If the programmer hot-reloads and changes the view source. HMR rebuilds the class, new function reference, new WeakMap entry. Old manifest garbage-collected with the old class. Handled for free.
If the programmer monkey-patches the prototype at runtime, same story — new function, new manifest.
D6. Debug / dev-mode assertion
In dev mode, we could compute the manifest's answer and fall back to full structural diff, and assert they agree. If the manifest says "equal" but structural diff says "differ," the analyzer has a bug. This is the property-test oracle Arthur mentioned, and it's cheap to run in dev mode.
D7. What happens when view throws
T₁ computed successfully, effects run, T₂ throws. Now we can't compare. Currently, a view throw propagates up and React unmounts/error-boundaries. Our code path should let the throw propagate; no characteristic check needed — the component is already broken.
Conversely, T₁ throws — React caught it already. We never get to the post-effect compare. Handled.
D8. React's own memoization interacting
If a parent re-renders and passes the same props to a chemical child, the child's synthesized component still gets called (React doesn't memoize by default). Our characteristic machinery runs. If nothing changed, we skip $update$(). But React already rendered this pass. So the skip doesn't help this render — it prevents spurious future renders triggered by effect-time mutations.
If the parent wraps our component in React.memo, we get an extra gate. Doesn't break anything.
Summary of rules, consolidated
A position is static if no expression flows into it.
A position is tracked if every expression flowing into it is either literal, this.*-rooted, or an opaque call/construction whose inputs are all tracked-or-static.
A position is untracked if it contains any opaque call with no tracked input (e.g., Date.now()) and no tracked input anywhere in its expression tree.
A position is mixed if it combines tracked state with untracked calls in the same expression — throw at parse time.
Locals are resolved transitively; their category is the category of their initializer.
Nested functions' bodies are not descended into for read collection (they're values compared by toString).
Method calls on this that hit particle methods are recursed; on non-particles, treated as opaque.
Getters are recursed as if called.
Assignments to reactive properties in view-reachable methods are forbidden — throw.
Self-recursion in analysis is guarded; recursive edges contribute nothing to reads.
Early returns / multiple return paths start conservative (union + tree fallback); precision is a future optimization.
Comparison at tracked positions uses equivalent() from reconcile.ts.
Untracked positions are skipped in comparison.
Analysis is lazy, per-class, cached on the function reference.
